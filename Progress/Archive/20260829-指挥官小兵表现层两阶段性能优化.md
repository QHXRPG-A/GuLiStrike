# 指挥官小兵表现层两阶段性能优化

- 需求：[指挥官小兵表现层两阶段性能优化](../RequirementDocument/20260829-指挥官小兵表现层两阶段性能优化.md)
- 开发：[指挥官小兵表现层两阶段性能优化](../DevelopmentDocumentation/20260829-指挥官小兵表现层两阶段性能优化.md)
- 结论：第一阶段远距硬切与本地调参、第二阶段 Crowd 资产替换均已接通；客户端性能 Gate 通过。

## 完成内容

### 第一阶段：稳定 ISM 的远距止血

- `AGuLiCommanderPresentationActor` 的 Unit ISM 默认使用 `SetCullDistances(100000, 100000)`；Ring ISM 使用 `SetCullDistances(0, 0)`。
- 不按距离增删实例，不迁移 HISM，继续维持 Unit/Ring 各 500 个实例与稳定的 `SoldierId → InstanceIndex`。
- Unit 默认关闭 CastShadow、DistanceFieldLighting、DynamicIndirectLighting 与 RayTracing；Ring 固定关闭同一组重型功能。
- 所有 Soldier 使用同一裁切规则，选中状态在远距只通过金色脚环表达；Transform、预测、小地图与网络合同不受影响。
- 新增非 Shipping、本地 World 会话级命令：
  - `gs.Commander.Presentation.List [prefix]`
  - `gs.Commander.Presentation.Get <key>`
  - `gs.Commander.Presentation.Set <key> <value>`
  - `gs.Commander.Presentation.Reset <key|all>`
- 六个白名单 key 支持严格解析；缺参、多参、NaN/Inf、非法整数/布尔和越界值均拒绝，不静默 Clamp。
- Config 采用 raw/presence-aware 读取：缺项来源为 `cpp_default`，显式合法项为 `config`，malformed 项逐键报错并回退编译默认值。

### 第二阶段：独立 Crowd 网格

- 保留 Marketplace 源资产与旧 `SM_CommanderFourFRobot`，新建五个最终资产：
  - `/Game/Commander/Units/SM_CommanderFourFRobot_Crowd`
  - `/Game/Commander/Units/M_CommanderFourFRobot_Crowd`
  - `/Game/Commander/Units/T_CommanderFourFRobot_Crowd_BaseColor`
  - `/Game/Commander/Units/T_CommanderFourFRobot_Crowd_Normal`
  - `/Game/Commander/Units/T_CommanderFourFRobot_Crowd_ORM`
- 原 16 Section/材质被烘焙为一个 UV Atlas、一个 Section、一个轻量材质。
- 实际 LOD tris 为 `18999 / 964 / 238`，ScreenSize 为 `1 / 0.056 / 0.028`；每级一个 Section。
- 三张贴图均为 2048²；ORM 明确转换为 `R=AO / G=Roughness / B=Metallic`。
- 最终材质为 Opaque、Default Lit、单面、三个 Texture Sample，无 WPO、透明、双面或 glTF 通用分支。
- Crowd Mesh 关闭 Nanite、Ray Tracing、Distance Field、Collision、CPU Access 和 Nav Data。
- Mesh Section 保留投影能力，使本地 `unit.cast_shadow=true` 调试开关真实有效；正常运行时仍由组件默认关闭阴影。

### 数据接线

- `GuLiStrikeCommander.xlsx`、导出 JSON、保存后的 `DT_GuLiStrikeCommander_Soldiers` 与 C++ resolver fallback 均切换到 Crowd Mesh。
- DataTable 回读确认 `DefaultSoldier` 的 3600cm/s、100 Health、战斗数值与新模型引用全部一致。
- SoldierId、RPC、PoseChunk、Health wire contract 与复制字段没有变化。

## 关键问题与修复

首次通过 MCP 的 GameThread TaskGraph 回调同步执行 Material Merge 时，MaterialBaking 为等待纹理流送再次泵 GameThread TaskGraph，触发 TaskGraph recursion guard；改用 CoreTicker 仍存在 MaterialBaking 内部 nested CoreTicker 的重入风险。最终命令通过 `GEditor->GetTimerManager()->SetTimerForNextTick` 延迟到编辑器下一 Tick，实际烘焙成功且不再崩溃。
