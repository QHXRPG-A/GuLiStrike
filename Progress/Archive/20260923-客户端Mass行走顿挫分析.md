# 2026-09-23：客户端Mass行走顿挫分析

## 场景与观测范围

用户报告客户端Mass行走“一卡一卡”。期望连续行进；现象需区分整体低帧率、客户端位置校正和服务器位置跳变。用户自行重开源码UE编辑器PID24508（12:11:43），地图`/Game/Maps/LVL_CommanderMassPrototype`，同一进程内专服加双客户端，已加载上一阶段编译的新导航诊断。当前存活600、活动472；抽查1和170为Normal/moving=1、有效NodeRef、无沿面失败。当前没有已完成的玩家手动移动规划，本轮自动推进不能替代旧红方手动移动复测。

采集使用原生只读查询、已有`InputSnapshot`、`PredictionTrace.Start baseline`和18秒Slate回调观察。没有改变玩家输入、相机、游戏参数、画质、预测开关或对局。选择Soldier 1比较两个客户端，采样时属于320m外的远距姿态档；上下文截图数据没有视口内单位，因此这些轨迹证明表现管线的问题，不是玩家当前可见单位的逐像素录屏。CPU/GPU热点没有在本轮分解。

## 已确认：硬校正时间基准错误

`GuLiCommanderPresentationActor.cpp:1625`直接计算最新服务器样本与`PresentedTransform`的距离。显示位置本来就按插值缓冲延后，而这里没有消除时间差。超过200cm后清空Samples、立即写入新位置并重置播放时钟；`EvaluateAuthoritativeTransform`在只有一份样本时固定显示该点，直到后续样本到来。

| 指标 | 客户端1 | 客户端2 |
|---|---:|---:|
| 采样时长 | 12.059秒 | 16.016秒 |
| 显示帧 / 接收样本 | 193 / 45 | 259 / 59 |
| 单兵样本实际频率 | 3.670Hz | 3.637Hz |
| 强制校正次数 | 14 | 19 |
| 相邻显示帧位移小于0.1cm | 84/192（43.75%） | 105/258（40.70%） |
| 最大单显示帧位移 | 263.824cm | 280.721cm |
| 本地命令预测 | 无 | 无 |

两份采样开头各有8份零速度样本，不能把表内全部零位移帧都算成异常停顿。14次及19次硬校正则全部发生于非零速度样本；下方分析以这些可分辨的事件为依据。

例如样本3517与前一样本只相隔0.200秒，位置前进160cm；它与延后约0.304秒的显示位置却相差210cm，触发强制校正。后续多次纠错在220至264cm量级，显示时间落后约0.30至0.36秒。观察窗口12:20:21至12:20:37没有任何`Authority pose discontinuity`，整局也没有Soldier 1的此类日志，因此这批规律性停顿无需服务器瞬移就能发生。

置信度高：第一处偏差发生在客户端新样本进入缓冲时；正常时间差被当成位置错误，继而造成清空、跳到最新点和单样本停留。上一轮失效NodeRef修复不覆盖此逻辑。

## 放大因素：同进程低帧率与发送调度

18秒被动观察，剔除首个跨窗口帧后295个样本：平均60.928ms（16.413FPS）、P50 61.153ms、P95 81.724ms、P99 85.874ms、最大88.151ms。三世界共享这一编辑器帧节拍；这是当前场景的整体帧耗时，不能写成客户端渲染或服务器Mass独占耗时。

当前配置为10Hz捕获、3相发送，320m内移动全频、远距移动和静止各除2。`GuLiCommanderWorldReplicationComponent.cpp:221`要求旧帧三相发完后才捕获新帧，旧帧在该函数末尾清空，下一份只能等后续世界帧。低帧率时额外等待降低实际捕获/发送频率；本次远距单位约3.6Hz，样本到达间隔P50约260ms、P95约360ms、最大418ms。客户端自适应缓冲升高，又更容易碰到2米硬校正条件。

代码机制和实测降频吻合；没有收集逐阶段调度计时或CPU/GPU分析，因此不将全部掉帧与降频归于某一个函数，也不声称存在或排除了网络丢包。

## 另一个独立问题：权威位置跳变

本局12:14:11至12:19:25的日志共19次，涉及19个单位，单次位移649.4至1375.0cm；大部分集中在(约25000,-17000)到(约26201,-17404)cm附近。该诊断发生在姿态量化和发送之前，不能归因于客户端插值。Soldier 272曾在0.1秒样本间跳1306.4cm，允许值200cm。

当前`GuLiCommanderNavigationPolicy::IsSurfaceMoveResultAcceptable`只检查调用成功、有限数值及50cm的Z差，没有检查XY位移是否超出本步速度预算。沿面移动结果随后直接写入Soldier.Location；这是高优先级核查点。但本次没有记录位置写入来源或沿面函数输入/输出，尚不能证明19次都来自该分支；动态导航修复、到位写入等路径也需保持可区分。

## 后续修复与验证范围

1. 首先使用一致的时间基准判断真实位置纠错，将正常插值滞后与异常偏移分开；保留明确传送、位移事件及严重异常的处理，不只调大200cm阈值。
2. 核查三相发送完成与新姿态捕获顺序，保持现有10Hz目标和查询/带宽预算，避免低帧率下额外空等。
3. 给服务器异常位移定位具体写入路径，验证实际沿面结果与本步XY预算，再制定修复；不能用客户端平滑掩盖13米权威跳变。
4. 修复后在原地图近距/远距移动、稳定帧率/低帧率、开始/停止/转向、动态建筑和明确传送下回读同类指标：正常匀速段无误触发硬校正、无非预期零位移帧串、无超预算未标记权威跳变，位置样本频率与调度一致。新运行验证按用户授权执行。
