# 2026-09-23：红方移动超时诊断与导航引用修复

## 现场与首个异常

地图`/Game/Maps/LVL_CommanderMassPrototype`，源码UE5.7，玩家编辑器PID39864自行启动专服及双客户端。另一空闲交付编辑器PID39884占用常用MCP端口；因此通过Windows电脑操作工具定位实际玩家窗口，使用UE自身Python控制台执行有限的只读查询。没有绕过VibeUE的API Key要求，没有启动新游戏、移动单位、保存运行世界或修改选择。

日志03:31:23 UTC确认500个Mass生成，随后两个客户端同步就绪。用户截图红方15个选择，之后抓取时为13个：29、30、34、35、40、44、45、130、134、140、170、175、191。它们全部`Idle / moving=0 / order=0 / final=none`，没有战斗目标。原截图另有169和174，同样Idle。

命令4、10、21、24、25失败为`PlanningResult:2/Ack:11`：前者是Completed轮询结果，后者是TimedOut。规划5秒超时导致任务清理，尚无新命令成功提交证据。命令1的Ack10表示被取消，不能混算为不可达。

在服务器运行世界按15个原始位置只读查询最后目标`(-13760,60814,-1778)`：CommanderSoldier与Default各15/15有效且非局部路径，起点XY原位投影成功。基地附近R2C4中心为`(-20000,60000,-1778.599)`；运行时有`GuLiPlacedBuilding_4/_5`及`GuLiResourceFactoryActor_4`。03:45快照全场600存活（含运行中增援），544处于PersonalPathRecovery；这不是初始生成数量变更。

## 假设与源码核对

1. 导航引用过期：高度吻合。`HandleNavigationGenerationFinished`只失效流场，未刷新单位缓存多边形引用；Route用`LastValidNavLocation`覆盖刚投影的CommandStart。Recast的沿面移动直接使用NodeRef，动态瓦片重建后引用即可能失效；重新按坐标寻路成功不代表旧引用有效。**旧构建没有输出NodeRef，尚未直接测得这批单位旧引用无效，也尚未验证修复效果。**
2. 路径恢复耗尽规划预算：不据现有计数成立；PersonalPathRecovery使用独立固定步预算，不能等同于TickNavigationRepairs的共享预算。
3. 选择/同步/GameMode缺失：现场选择、服务器命令与500生成/同步日志排除此轮入口缺失。
4. 完全没有导航通路：15个现场路径查询全部完整，排除该组位置到已采集目标的全局不可达；不代表所有编队落点或整个战场均有效。
