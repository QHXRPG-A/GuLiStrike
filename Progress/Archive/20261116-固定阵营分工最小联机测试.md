# 固定阵营分工最小联机测试

## 结果

在 `/Game/Maps/LVL_CommanderMassPrototype` 上使用源码版 `UnrealEditor-Cmd.exe -game -NullRHI`，复用正式网络与玩法代码，使用 `RuntimeManifest-200.json`。进程帧率上限为 30，采用现有 Review IPC 读状态与提交一次实际开牌请求；没有新增正式自动化测试框架，没有伪造业务成功或绕过权威校验。

| 最小场景 | 实测结果 |
|---|---|
| 两端各自承担本队 | 两端 ready/world_ready/state_ready 为真，持续推进；各核对 226 个存活初始单位，归属不匹配为 0。观察到实际伤害请求，两端抽样受伤对象血量一致。 |
| 四端固定分工 | 四端均进入模拟；各核对 228 个存活初始对象，归属不匹配为 0。指挥官本地模拟 Mass，无双本地模拟游骑兵、巡天、建筑、账户及肉鸽根对象。 |
| 指挥官请求无双执行公共系统 | 红方指挥官提交 `rogue_open`，实际动作完成；红方无双记录 `capability/army/mutate` 请求执行。仅开牌，未验证完整选卡流程。 |
| 同队备份 | 双方指挥官持有无双公共组的完整备份；双方无双持有 Mass 组备份，观察到最近 2 份完整版本。 |
| 无双突然掉线 | 仅终止身份核实过的红方无双测试进程。3 个存活端均确认其离线，19 个权威组完成恢复，原由无双模拟的 160 个仍存活对象全部转给红方指挥官。包含游骑兵、巡天、建筑和阵营系统。恢复后 ready=true、paused=false、failure 为空，逻辑帧继续推进。 |

对象数量是各次状态采样时的存活样本数，不等于完整玩法覆盖率。接管结果在断开后约 35 秒的最终采样中确认；未作精确暂停／恢复耗时测量。最小范围通过，整个功能仍待玩家及其他专项场景验证。

## 本轮发现与修复

1. 200 兵清单仍携带 Army v1、旧 Mass 状态版本等内容，当前编译代码已使用 v2／新版状态。用当前正式编辑器导出器重新生成 200／600 兵运行清单，并由原生读取器验证后发布；未修改 DataTable 或地图。600 兵清单仅更新协议／哈希并移除 5 个失效调度参数；200 兵清单同时补齐当前已存在的兵种参数与矿车表现描述。完整差异及原始字节保存在 `TestResults/NetworkMinimal/20261116-manifest-refresh`。
2. `GuLiHybridManifest.cpp` 的解析阶段不再重复初始化能力；统一由已验证加载路径执行，并保留实际错误原因。
3. `GuLiNetControlPoint.cpp` 修复旧的“据点始终中立”状态校验。已分配运行权威组的据点阵营必须与能力中的 Owner 一致；尚未分配权威组的原始清单仍允许中立表示。
4. `GuLiNetOwnerTransactions.cpp` 补齐初始化失败原因，定位到阶段及对象，避免只出现空的 `Runtime configuration failed:`。
