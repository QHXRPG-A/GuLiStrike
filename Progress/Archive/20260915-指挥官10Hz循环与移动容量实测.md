# 2026-09-15：指挥官10Hz循环与移动容量实测

## 行为与实现

权威固定步由30Hz降为10Hz，单兵从三步一次改为每步一次，实际移动积分继续为0.1秒。共享时钟定义在[GuLiCommanderSimulationTiming.h](../../Source/GuLiStrike/Commander/GuLiCommanderSimulationTiming.h)，由权威、捕获和客户端Tick时间解释共同使用；导航扩宽门槛15→5步维持0.5秒，索敌6→2步维持0.2秒，攻击冷却仍按秒累计。独立CPA处理器的30Hz三相调度保持原状，每兵仍10Hz。

[世界复制组件](../../Source/GuLiStrike/Commander/Framework/GuLiCommanderWorldReplicationComponent.cpp)按10Hz捕获，使用独立世界时间约0/33/67ms三相发送，保留远距离与静止降频。降频开发过程中的单相发送曾使800人两客只有约460人持续呈现移动；恢复独立三相后，同档三端均有800人实际位移。新增CSV只观测发送尝试和连接饱和，不改变连接预算或增加重发队列。

[显式压测驱动](../../Source/GuLiStrike/Development/GuLiCommanderMoveStress.cpp)仅非Shipping编译，在独立Game进程内调用正式生成和移动规划接口，按100人批次下令；采样全体存活单位真实位移、规划延迟、固定步与网络计数。启动前关闭本场景已有生产组件的Tick并冻结占领增长，防止原兵营占用压测名额。入口没有自动运行，不保存地图或人口配置。

[启动脚本](../../Scripts/run_commander_move_stress.ps1)提供纯服务端、真实无渲染客户端和完整渲染一客/两客，以及晚加入/在线增兵两种时序；拒绝覆盖结果，结束时只停止本轮进程。[分析脚本](../../Scripts/analyze_commander_move_stress.py)按P95帧成本和实际移动人数P05判定负载，NullRHI客户端不作FPS验收。

独立专服启动还暴露了部署点可选编辑器箭头为空，已修正其构造使用入口。两处既有Teleport实现的首包含头顺序作最小调整，解决Game构建阻塞。

## 实测结论

完整条件、逐运行原始数据与失败记录见[容量报告](../../TestResults/CommanderMove10Hz/REPORT.md)。硬件为i9-14900KF、RTX4090、32GB内存；源码Editor二进制以`-game`运行，客户端1920×1080/Epic，固定视野、正式剔除，未全选显示全军路径线。人数为双方合计。

| 场景 | 结果 |
|---|---|
| 最终4000人纯服务端，40秒 | 9.997Hz、无丢步，实际移动P05=3976；固定步P95=22.715ms，世界帧P95=50.544ms，符合本轮预算 |
| 800人一客完整渲染，40秒 | 实际移动P05=800，帧P95=10.979ms，满足60FPS判据 |
| 800人两客完整渲染，各40秒 | 两客实际移动P05=800，帧P95=18.649/19.084ms，满足30FPS，未达到60FPS |
| 1200人先加入再增兵，两客完整渲染，各40秒 | 两客实际移动P05=1200，帧P95=18.348/19.801ms，满足30FPS；服务端约10Hz、无丢步 |
| 2000人先加入再增兵，两客无渲染 | 服务端2000人全部移动；两客实际移动P05仅1401/1399，同步未通过，发送尝试遇到饱和的比例38.6% |
| 1000/4000人晚加入 | 初始名册构造消息超过65536字节；4000档还超过FastArray单次2048项变更限制，没有有效容量窗口 |

6000档因提前到达和Blocked使实际移动不足95%，8000档在落点规划阶段失败，均不能称为CPU极限。无客户端、无渲染客户端和完整渲染对照将模拟、复制与共享显卡影响分别记录。服务端有客户端时采50秒，包含客户端退出尾段，不宣称完整50秒始终两客在线。
