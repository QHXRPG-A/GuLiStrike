# 2v2席位运行验证

在 `/Game/Maps/LVL_CommanderMassPrototype` 使用正式 `RuntimeManifest-600.json`、本机 LocalUdp、一个 Coordinator 与四个逻辑客户端做实测。房间使用 Coordinator 默认人数，蓝方无双最后启动。载具输入通过已有玩法验收入口提交，比较各客户端的原生运行状态。普通 Local PIE 单独以配置角色启动。使用[已编译产物](20261114-2v2席位授权编译.md)。

| 实测项 | 结果 |
|---|---|
| 红蓝无双为 Ground/Ground、Ground/Air、Air/Ground、Air/Air | 四种组合均在三人就绪时等待，第四人就绪后开局，四人取得对应角色的 Pawn |
| 同队第二名指挥官与第二种无双载具 | Coordinator 拒绝，理由为 `Role seat occupied` |
| 游骑兵和巡天移动 | 单一权威模拟，其他三端应用移动，验收同时观察到游骑兵燃料消耗与巡天加速 |
| 600 个开局兵种与资源组 | 兵种在本队分摊，开局约150个每人。采样时一个兵种已阵亡。385 个资源组对象由同一端持有 |
| 蓝方巡天正常离队 | 原巡天休眠，剩余三人继续对局。两次快照间有146个存活兵种的权威归属转给蓝方指挥官 |
| 普通 Local PIE | 红方游骑兵与蓝方指挥官进入600兵对局，回读四席及正式游骑兵 Pawn，Editor和子进程均正常关闭 |

## 重连与验收失败

同一身份离队后改为 Ground 返回被 `Role is locked for this match` 拒绝。使用原 Air 角色返回时，Coordinator 接受并将席位版本从1升为2。刚开局和完成载具移动后各复测一次，均因15秒内未交齐状态而退出加入流程。红方指挥官在两个样本中停在 `capture/application-ack`，采集偏移188。重连端随后分别记录 `installed=1412 expected=4152` 和 `installed=1275 expected=7789`。根因仍需定位，状态回填错误出现前已观察到成员超时。[首轮失败状态](../../TestResults/2v2-ground-air-84518e79/failure-states.json) · [刚开局重连采样](../../TestResults/2v2-ground-air-8c48695e/reconnect-transition.json)

现有 `RoomSeats2v2`、`RoomMetadata`、`IndivisibleGroupsAndFixedRoles` 独立执行通过。完整 `GuLiNetCoreAcceptance` 退出码1，首条失败为 `blocked application lane does not block independent delivery`。单独执行 `BoundedReliableApplicationAdmission` 得到相同失败。该用例仅建立消息通道，复现不依赖房间席位或重连流程。[专项结果](../Evidence/20261114-2v2Runtime/focused-core-result.json) · [完整测试日志](../Evidence/20261114-2v2Runtime/core-acceptance.log)

首次四端探针错误要求采样时600个兵种全部存活。检查到600个开局对象都已登记、各端一致观察到其中1个阵亡后，探针改为按正式清单核对开局身份，再校验存活兵种的模拟权。两次 PIE 预检分别遇到配置类型和 Pawn 方法未暴露到 Python 的问题，最终使用受支持的接口回读 Pawn 与四席占用。原始结果与修正后的复测均保留。[PIE最终回读](../Evidence/20261114-2v2Runtime/local-pie-verified-result.json)

全部测试进程均已正常退出。运行记录覆盖本机同步和配置角色启动，交互选席与跨机延迟留待对应场景核验。[结构化汇总](../Evidence/20261114-2v2Runtime/runtime-summary.json)
