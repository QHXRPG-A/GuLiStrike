# 指挥官小兵表现层两阶段性能优化

- 说明补充：2026-08-30。补齐术语、问题起因与验证边界；不改变原需求，不修改代码、资产或归档。

## 背景

指挥官模式需要同时表现 500 名小兵。最初为快速验证玩法，将商城 FourFRobot 骨骼模型转换成静态代理，再批量显示 500 份。这样省去了为每名小兵创建完整场景对象和组件的成本，但静态代理仍保留了适合近景角色的高精度几何和材质，并没有自动变成适合群体显示的轻量资源。

用户随后在着色器复杂度视图中看到密集编队呈现大片红色、褐色与粉色；同时提出远处兵模可以隐藏，但脚下圆环必须继续表达队伍和选中信息。本需求因此分成两步：先停止远距离无效渲染，再降低近中距离仍需显示的每台机器人的成本。

### 术语说明

正文优先使用中文全称；保留英文仅为对照引擎界面、命令和资源名称，不要求读者先认识缩写。

| 名称 | 在本项目中的含义 | 不能误解成什么 |
|---|---|---|
| 群体专用轻量静态网格（Crowd Mesh） | 给数百个小兵同屏使用的模型版本；这里是 `SM_CommanderFourFRobot_Crowd`，仍是普通 `UStaticMesh` | 不是群体寻路、Mass 群体模拟、动画或新的网络实体 |
| 实例化静态网格（Instanced Static Mesh） | 用一个 `UInstancedStaticMeshComponent` 管理同一个模型的许多副本；每份副本保存位置、旋转、缩放和少量自定义数据，渲染时可以合批 | 不是自动减面，也不是把 500 个可见模型的几何成本变成 1 个 |
| 网格分段（Section） | 一个细节等级中，使用某个材质槽绘制的一组三角形；身体、武器等不同材质区域常被分成不同段 | 分段数不等于三角形数；合成一段也不等于减面 |
| 细节等级（Level of Detail） | 同一模型的几种精度版本，屏幕上越小越适合使用低精度版本；资源字段中的 `LOD0/1/2` 分别指三档 | `ScreenSize` 是屏幕投影大小阈值，不是固定米数 |
| 贴图图集（Texture Atlas） | 把原来分散在多个材质区域的表面信息烘焙进统一贴图；网格用二维纹理坐标（U、V）找到对应区域 | 不是简单把材质槽名称合并，必须处理坐标、纹理和材质引用 |
| 绘制调用（Draw Call）与渲染阶段（Render Pass） | 前者是一次绘制提交，后者是深度、基础颜色、阴影等处理阶段；同一物体可能参与多个阶段 | 单阶段三角形数量不等于一帧总三角形数量 |
| 着色器复杂度（Shader Complexity）与重复覆盖（Overdraw） | 前者帮助观察着色指令成本及重叠负担，后者指同一屏幕像素被多层表面反复覆盖 | 红色不是面数计数器，也不能直接换算成显卡耗时 |
| 第 95 百分位帧耗时（p95） | 将样本耗时排序，约 95% 样本不超过该值；用来观察较慢帧 | 不是平均值，也不是最慢的一帧 |

### 旧资源的已知基线

以下为本轮优化前的资产审计，不是今天重新捕获的性能数据。来源：[FourFRobot 原资源审计](../FourFRobotRenderAudit.json)。

| 项目 | 优化前事实 | 为什么会形成负担 |
|---|---|---|
| 来源 | `/Game/Assets/Arma/FourFRobot`，静态代理为 `/Game/Commander/Units/SM_CommanderFourFRobot` | 将近景角色直接复制到群体场景 |
| 几何 | 单台 112,008 个三角形、87,277 个顶点，仅一个细节等级 | 远处也没有低精度版本可切换 |
| 网格分段与材质 | 16 个分段、16 个材质槽 | 即使使用实例化静态网格，仍需按材质分段组织绘制 |
| 贴图 | 16 组材质共引用 48 张 4096×4096 贴图 | 增加纹理驻留、流送和资源绑定压力 |
| 材质来源 | 图形库传输格式（Graphics Library Transmission Format）导入器的通用材质体系 | 比专门为群体制作的材质更复杂，但未启用的静态分支可能被编译器移除 |
| 组件开关 | 阴影、距离场照明、动态间接光、光追可见性均开启 | 可见实例还可能参与额外渲染工作 |
| 裁切 | 开始距离 150,000cm，结束距离 500,000cm | 不应假定开始距离就是完全隐藏；原配置最远到约 5 公里才结束 |

### 根因与必须避免的误读

- 几何量：若 500 人都可见且都用原唯一精度，单个渲染阶段理论上是 `112,008 × 500 = 56,004,000` 个三角形。实例化只减少对象和提交开销，不会消除每份可见实例的三角形。
- 分段：原资源每个细节等级有 16 组材质分段；实例可合批，不能直接算成 `500 × 16 = 8000` 次固定绘制调用。实际调用数还受渲染阶段、可见性和细节等级分布影响。
- 纹理：每个材质区主要使用自己的基础颜色、法线、金属度/粗糙度贴图，不是每个像素采样全部 48 张。48 张 4K 贴图的顶层纹素总量是 805,306,368；纹素规模不能直接代替压缩后显存或实际驻留量。
- 重叠与着色：大量机器人在俯视镜头下互相遮挡，会重复覆盖屏幕像素；复杂度截图说明风险，不能仅凭截图认定面数是唯一瓶颈，或认定某个材质分支占用了多少毫秒。
- 距离与额外功能：看不清细节的远处兵模仍可能被绘制，阴影等功能又增加额外成本。因此仅减面或仅裁切都不能独自覆盖本次问题。

## 需求描述

### 第一阶段：远处只保留战术信息

- 保留现有实例化静态网格组件与稳定索引。机器人模型组件 `UnitInstances`、脚环组件 `RingInstances` 各管理 500 个实例，不为裁切新增、删除或重新编号实例。
- 机器人模型默认在距摄像机 `100000cm`（1000 米）时硬切；所有小兵同规则，选中单位也不例外。
- 脚环默认不做距离裁切，保持当前世界尺寸、队伍颜色、选中金色和死亡后暗红残留 5 秒的逻辑。仍遵守正常视锥和遮挡规则，不要求屏幕外的脚环强制显示。
- 机器人和脚环均默认关闭阴影、距离场照明、动态间接光、光追可见性；脚环继续进行普通光栅化绘制。不改变全场景的光照或画质设置。
- 裁切只影响显示：小兵位置更新、客户端预测、选择、移动、小地图和命令线继续工作。回到范围内时应在最新位置显示，不闪回旧位置。
- 距离按摄像机与实例实际位置判断，不能把相机臂长直接当成模型距镜头的距离。

### 本地表现调参

命令只存在于非发布版本（非 Shipping），只影响命令所属的客户端世界（`UWorld`，即本次运行的世界实例），不接入服务器的 `gs.GM` 玩法调参。

```text
gs.Commander.Presentation.List [prefix]
gs.Commander.Presentation.Get <key>
gs.Commander.Presentation.Set <key> <value>
gs.Commander.Presentation.Reset <key|all>
```

| 键名 | 含义 | 默认值 | 合法输入 |
|---|---|---:|---|
| `unit_cull_distance_cm` | 机器人模型硬切距离，单位厘米 | 100000 | 整数 1–10000000 |
| `ring_cull_distance_cm` | 脚环裁切距离，单位厘米 | 0 | 整数 0–10000000；0 为禁用距离裁切 |
| `unit.cast_shadow` | 模型组件是否投射阴影 | false | true、false、1、0 |
| `unit.affect_distance_field_lighting` | 模型组件是否参与距离场照明 | false | true、false、1、0 |
| `unit.affect_dynamic_indirect_lighting` | 模型组件是否参与动态间接光 | false | true、false、1、0 |
| `unit.visible_in_ray_tracing` | 模型组件是否对光线追踪可见 | false | true、false、1、0 |

- 优先级为：代码默认值 < 配置文件基线 < 当前世界本地覆盖值。
- 缺参、多参、未知键、非数值（NaN）、无穷大（Inf）、非法整数、非法布尔值和越界值必须拒绝，不自动钳制到边界。
- 配置文件缺项保留代码默认值；显式非法项逐键记录错误并回退，不拖累其他合法项。恢复命令撤销本地覆盖，回到基线。
- 查询和修改需回显基线、旧/新有效值、来源和应用对象数量；覆盖不复制、不写磁盘，世界销毁后不应残留。
- 开关控制组件属性，不负责重新生成资产级已禁用的光追或距离场数据；属性回读成功不等于相应画面效果已恢复。

### 第二阶段：制作群体专用轻量模型

- 保留商城源资产与旧静态代理，另建 `/Game/Commander/Units/SM_CommanderFourFRobot_Crowd` 和专用材质。
- 原 16 个网格分段烘焙为统一贴图图集；整个网格只有一个材质槽，每个细节等级只有一个网格分段并引用该槽。
- 细节等级固定为三档：最高精度不超过 20,000 个三角形；中精度不超过 6,000，屏幕阈值 `0.056`；低精度不超过 1,500，屏幕阈值 `0.028`。
- 材质是不透明（Opaque）、默认受光（Default Lit）、单面材质，只保留三张 2048×2048 贴图：基础颜色（BaseColor）、法线（Normal）、遮蔽/粗糙度/金属度合图（Occlusion–Roughness–Metallic）。合图红通道存环境遮蔽，绿通道存粗糙度，蓝通道存金属度。
- 基础颜色按颜色空间读取（`sRGB=true`）；法线线性读取并使用法线图压缩（`TC_Normalmap`）；合图线性读取并使用遮罩压缩（`TC_Masks`）。
- 不使用透明、双面、世界位置偏移（World Position Offset）、渐隐或通用导入材质分支。
- 网格关闭虚拟化几何系统 Nanite、光线追踪支持、距离场、碰撞、中央处理器端网格数据访问和导航数据。
- `DefaultSoldier` 在 Excel、导出数据、引擎数据表与代码默认回退中均指向轻量网格；正常运行不再依赖英雄级 FourFRobot 及其 48 张源贴图。旧资产保留作烘焙源和人工回退，不作为正常代码兜底。

## 边界

- 不改为层级实例化静态网格（Hierarchical Instanced Static Mesh）；不按距离增删实例，不改变“小兵编号 `SoldierId` → 实例序号 `InstanceIndex`”。
- 不新增服务器模拟、网络字段或复制负担。性能优化不修改小兵寻路、速度、生命、战斗逻辑；这里的“不修改网络合同”仅指本次性能优化，不评价其他功能迭代。
- 不新增骨骼动画、远景替身图像（Impostor）、屏幕空间图标、多兵种混编或运行时模型热切换。
- 原资产允许暂留打包内容；不在本轮承诺包体清理或完整发布包验收。
- 1000 米硬切是已确认取舍；减面和图集可能降低近景纹理、轮廓及细零件精度，仍须视觉对照。结构测试通过不等于用户已接受美术降质，也不等于美术保真度已经验收。
- 不承诺距离裁切减少服务器寻路或客户端位置重建成本；它主要减少不可见兵模的渲染工作。

## 验收标准

下面的已勾选项依据 2026-08-29 留存证据，不代表 2026-08-30 重跑测试。目标未降低，缺少证据的完整矩阵单独保留为待验收。

原性能目标保持不变：500 名小兵场景总帧第 95 百分位不超过 16.67ms，本轮小兵表现层游戏线程开销第 95 百分位不超过 1ms。已有表现计时只覆盖 `RebuildLocalInstances`（本地实例位置重建），应与完整表现层计时范围区分，不能靠改名缩小验收范围。

### 已有实现与证据

- [x] 机器人组件默认 `SetCullDistances(100000, 100000)`，脚环组件默认 `SetCullDistances(0, 0)`；命令修改/拒绝/恢复后各保留 500 个实例。
- [x] 六键本地命令、非法配置处理、参数个数校验与两真实世界的命令/组件设置隔离有自动化证据；发布版本不注册命令。
- [x] 三档网格分别实测为 18,999 / 964 / 238 个三角形，每档一个分段引用网格唯一的材质槽；三张 2K 贴图与禁用项通过验证。
- [x] Excel、导出数据、引擎数据表与代码回退均指向轻量网格；本次未新增复制字段。
- [x] 编辑器内运行（Play In Editor）在相机臂长 20000 / 80000 / 111392 / 180000cm 下留存距离报告与画面；111392 / 180000cm 记录支持远距只保留脚环，20000cm 画面不构成 500 台近景可见的最坏用例。
- [x] 已记录单机测试场景的三轮总帧第 95 百分位耗时不超过 16.67ms，表现位置重建不超过 1ms；最差分别为 9.1613ms 和 0.6033ms。

### 完整验收仍需补齐

- [ ] 在每个实例到摄像机实际距离 `100000cm ± 1cm` 附近验证硬切、持续移动时的再显示位置，以及远距选择/移动/预测/小地图/命令线的完整交互。
- [ ] 两个实际客户端使用不同镜头，验证各自独立裁切；补拍死亡暗红脚环保留 5 秒。两世界的命令隔离测试不能代替这些画面验证。
- [ ] 带本地覆盖值直接销毁世界，再开新世界，验证覆盖不泄漏；现有测试先恢复再销毁，不完整覆盖此生命周期场景。
- [ ] 用显卡逐阶段分析（`ProfileGPU`）确认相机臂长 180000cm 时机器人网格绘制为零，脚环仍按画面范围显示；实例计数和距离报告不是逐阶段绘制计数。
- [ ] 在 80000cm 中心编队和 20000cm 最坏视图下分别确认机器人几何贡献不超过 800,000 / 10,000,000 个三角形/渲染阶段；资产理论上界不代替实际精度分布和绘制捕获。
- [ ] 补充同条件优化前后的客户端/服务器捕获；服务器游戏线程第 95 百分位耗时回退不得超过 5%。没有改前数据时不宣称准确提速百分比。
- [ ] 在独立 Win64 Development 游戏构建中复验性能门槛；现有数字来自 `UnrealEditor Development -game` 的未烘焙单机游戏模式，不是打包后的游戏性能。
- [ ] 核对本轮小兵表现层游戏线程的完整计时范围，必要时补充计时，按不超过 1ms 的原目标验收；不以单个函数的样本代替未计入的工作。
- [ ] 对照原资源审核近景外观、各档精度轮廓、法线与细零件，确认美术保真度；三角形与材质合同通过不能代替此项。

### 性能测试必须记录的条件

- 地图 `/Game/Maps/LVL_CommanderMassPrototype`，500 名小兵，1920×1080、100% 渲染比例、固定画质、关闭垂直同步。
- 原目标为预热 10 秒、有效采样约 30 秒、重复三次；已留存实现为每轮 4800 帧，丢弃前 1200 帧，统计后 3600 帧，帧率上限 120。
- 对比必须固定相机位置/朝向、相机臂长、单位分布、运行模式、画质与机器条件；不能把不同视角的单帧数字作为优化前后对比。
- 保存中位数与第 95 百分位、单位毫秒，并区分总帧、游戏线程、显卡与表现位置重建。具体结果、证据和限制见同名开发文档。
