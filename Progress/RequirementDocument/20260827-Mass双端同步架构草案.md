# GuLiStrike：Mass 双端同步架构草案

- 版本：v0.3
- 适用范围：[5v5 大战场玩法](./20260826-5v5大战场玩法草案.md) 的指挥、移动与多人同步层

## 0. 文档约定与版本结论

- **已确认**：已经由项目讨论锁定，实施不得静默改回旧模型。
- **建议初值**：必须经过原型或压力测试后才能固化的参数。
- **未验证**：已有实现方向或代码基础，但尚无满足本版验收标准的证据。

v0.3 完整取代 v0.2 的“永久 25 人 CommandGroup”控制模型。25 人仍是指挥官一次可以控制的最小目标规模，但不是永久编制：即使圆内只命中一名 Soldier，服务端也会尝试把该 Soldier 与附近友军动态组成一个最多 25 人的临时控制组；下一次选择可以重新分组。

v0.2 中固定 `GroupId + SlotIndex + AliveMask`、固定 20/400 个玩家控制组、禁止拆分/合并等结论不再作为实施依据。已验证的表现层频闪修复和场景亮度修复仍然有效。

## 1. 背景与目标

当前首个可玩原型生成 500 名 Soldier。v0.2 基线虽由服务端以 30Hz 模拟，却只以 5Hz 发布组摘要，客户端又以 10Hz 直接套用摘要位置且没有插值，因此曾出现约 200ms 一次的阶梯式移动；v0.3 已迁移到 10Hz 逐兵成员帧与逐渲染帧插值，完整受损网络视觉 Gate 仍按本文验收。

本版需要同时解决控制语义、权威边界和移动观感：

1. 每名 Soldier 在服务端都是独立且持久可识别的权威实体。
2. 玩家只提交圆选和移动意图，服务端根据权威位置动态组成最多 25 人的控制组。
3. Soldier 的位置、旋转、生命、碰撞、订单和导航结果均由服务端裁决。
4. 客户端通过 10Hz 精确成员帧、逐帧插值和短时表现预测消除阶梯移动，不获得玩法写权限。
5. 先完成 500 人正确性与性能基线，再验证局部流场；本轮不实施万人 Backend。

## 2. 身份、控制组与订单

### 2.1 四种互不混用的概念

| 概念 | 生命周期 | 玩家可见/可控 | 约束 |
|---|---|---|---|
| `SoldierId` | 整局 | 可见；不能通过 RPC 直接提交控制 | 本局唯一且不复用；与本机 Mass EntityHandle 解耦。 |
| `ControlCohortId` | 一次有效选择 | 可见且作为底部 UI 卡片 | 服务端动态创建，最多 25 人；允许欠编；成员在该 SelectionRevision 内冻结。 |
| `OrderId / OrderFormation` | 一次已接受命令 | 可见订单状态 | 从下令时的 Cohort 成员复制而来；后续选择不会停止它。 |
| `ReplicationCluster` | 单个复制帧或未来模拟分区 | 不可见、不可控 | 仅用于压缩、空间分包或万人扩展，不具有编制和玩法身份。 |

- `FMassEntityHandle` 只在当前进程内部使用，永远不上网。
- `ControlCohortId`、`OrderId` 和复制分块编号不得替代 `SoldierId`。
- Soldier 死亡后身份和可靠状态仍存在到残骸/比赛状态要求的生命周期结束；网络丢包不能令其复活。

### 2.2 25 人的准确含义

- 25 是一个动态 ControlCohort 的**目标人数和硬上限**，不是永久编制。
- 玩家圆选只命中一名 Soldier 时，该 Soldier 必须作为种子保留，并尝试吸纳附近合资格友军直至 25 人。
- 圆内超过 25 人时拆成多个 ControlCohort；例如圆内 26 名有效 Soldier 会至少生成两个组，第二组可以继续从附近补员。
- 周边没有足够合资格友军或超过补员距离时允许欠编，剩余 Soldier 仍然可控。
- 选中以后不会因为成员死亡自动补员；只有后续选择才能重新编组。

## 3. 圆形选择规则

### 3.1 输入与权威

- 指挥官使用 80m、200m、450m 三档半透明圆形选取框。
- 客户端只发送圆心、半径档、Replace/Shift、ClientRequestId 和预期 SelectionRevision；不得发送希望选中的 SoldierId 列表。
- 服务端只允许同队、存活、可控且位于当前权威世界中的 Soldier 参与选择，并负责幂等、版本和频率校验。
- 圆内没有任何有效种子时结果为空，不得从圆外凭空组成一组。

### 3.2 确定性动态分组

服务端使用 100m 空间哈希查询候选人，并按以下顺序执行：

1. 以权威位置找出圆内有效 Soldier，按到圆心的二维距离升序排列，距离相同按 SoldierId 升序。
2. 取第一名未分配 Soldier 作为新 Cohort 种子。
3. 以当前 Cohort 动态质心为基准，优先从剩余圆内候选中加入最近成员；每次加入后重新计算质心，直到 25 人或圆内候选耗尽。
4. 若该 Cohort 仍不足 25 人，再从圆外未分配的有效友军中按距动态质心由近到远补员；候选距当次质心超过 300m 时停止补员。
5. 对仍未分配的圆内种子重复以上步骤。任何 Soldier 在一次选择结果中最多属于一个 Cohort。

相同权威快照、输入和既有选择状态必须产生完全相同的 Cohort 成员与顺序。

### 3.3 Replace、Shift 与清空

- Replace 丢弃当前选择，按本次圆选结果创建全新的 ControlCohort。
- Shift 命中现有 Cohort 任一存活成员时，切换移除整个 Cohort；其成员在同一次 Shift 请求中不得立刻被重新组成新组。
- Shift 圆中不属于被切换组的新 Soldier 继续按动态算法形成附加 Cohort；保留的既有 Cohort 不重组，且其成员不重复加入新组。
- Esc 只清空当前选择，不停止已经生效的订单。
- Cohort 全员死亡时从当前选择移除；死亡成员不触发自动补员。

## 4. 移动命令与服务端模拟

### 4.1 订单语义

- 移动 RPC 继续只提交世界目标、SelectionRevision 和 ClientCommandId。
- 服务端验证选择版本和目标后，为每个当前 ControlCohort 创建独立 OrderFormation，并把下令瞬间仍可控的成员复制进订单。
- 重新选择本身不改变 Soldier 的移动；只有服务端接受的新命令才写入 `ActiveOrderId`。
- 同一 Soldier 同时只有一个 ActiveOrderId。最新被服务端接受的命令覆盖旧命令；旧 OrderFormation 的其余成员继续移动并重排空缺槽位。
- 部分 Cohort 无法到达目标时允许逐组拒绝；已接受组不因其他组失败而回滚。

### 4.2 第一阶段：共享路径、弹性编队与避障

- Dedicated Server 固定以 30Hz 模拟全部 500 个独立 Soldier Mass Entity。
- Commander Soldier 使用命名 `CommanderSoldier` 的独立 NavData；当前原型参数为 `AgentRadius=750cm`，与普通角色的 `Default AgentRadius=34cm` 分离。共享路径、出生投射、地面投射和编队可走性探测不得静默回退 Default NavData。
- 一个 OrderFormation 只计算一条共享 NavMesh 路径，不对 25 名成员分别寻路；路径必须来自 Commander 专用 NavData、有效且非 Partial，失败时不得退化为穿越 Landscape 的直线移动。
- 目标区域和组内槽位按最小移动代价分配，减少交叉穿插；成员变化时才重新分配。
- 途中根据共享路径附近的可走宽度，把弹性阵形动态压缩为 1–5 列；槽位修正最多占转向需求的 30%，个体可以为绕障暂时偏离。
- 到达后收紧为 1800cm 间距的 5×5 阵形；服务端在接受订单前必须验证完整终点足迹，终点放不下时拒绝对应 Cohort，而不是让外排 Soldier 永久冻结。
- 静态障碍和不可行走地形由 NavMesh 约束；Soldier 之间由服务端 Mass Avoidance 和 AgentRadius 软分离，不为 500 人创建独立 Chaos 刚体。
- Soldier 暂不制作动画，但权威位置、Yaw、速度、地面贴合与碰撞必须持续更新。

### 4.3 第二阶段：走廊局部流场

流场在第一阶段通过后以配置开关接入，不替代服务端权威：

- 以共享 NavMesh 路径为中心，只在半宽 150m 的局部走廊生成方向场，而不是覆盖整张 8km 级 Landscape。
- 建议初值为 500cm 网格、64×64 单瓦片；从目的地反向积分生成方向。
- 流场提供主行进方向，弹性槽位修正编队，Mass Avoidance 负责最终个体分离。
- Walkability 在游戏线程采样，积分可异步计算；仅当 OrderId、NavMesh Generation、PathRevision、PathPointIndex 和 TileCoordinate 均仍匹配时安装结果。
- 流场缺失、过期、构建失败或 Soldier 走出有效区时，自动退回共享 NavMesh 路径。
- 流场只运行在服务端；客户端不以本地流场结果写入玩法 Transform。

## 5. 双端同步与平滑

### 5.1 权威状态与运动帧

- Soldier 队伍、生命状态、状态 Revision 和 ActiveOrderId 使用可靠的 FastArray 当前状态复制；快照同时携带 SnapshotMatchEpoch 与 SnapshotRevision，死亡等事实不能依赖不可靠运动包。
- 服务端每 3 个 30Hz 模拟 Tick 捕获一次精确成员帧，即 10Hz。
- 运动通过每连接的 Owner Channel 以 Unreliable pose chunks 发送：每块最多 32 人、目标载荷不超过约 1000B。
- 每块包含 FrameSequence、ServerSimTick、服务器时间、空间锚点，以及 SoldierId、10cm 相对位置、量化速度、Yaw、ActiveOrderId 和 Teleport/状态标记。
- Soldier 先按 Team、空间单元和 SoldierId 确定性排序，再以当前块动态锚点检查 signed-int16/10cm 相对编码范围；任一候选或既有成员会饱和时必须提前拆出新块，禁止跨队或超范围坐标被静默截断。复制块与 ControlCohort 无关，成员可以跨帧换块。
- 当前 500 人帧形成 16 个块，服务端把一帧的块错峰到 3 个模拟 Tick 发送，并轮换起始块；没有 Ready 客户端时仍推进并按期丢弃不可靠 Pose 快照，不能把空服期间的旧帧留给下一次登录。
- 客户端待处理 Pose 队列与协议块上限统一为 512；32 样本块必须对 SoldierId、位置、速度、Yaw、ActiveOrderId、状态和 Flags 全字段往返一致。
- 客户端在可靠 Soldier 名册建立前不得用未知 SoldierId 的运动样本创建权威事实。
- 初次加入/重连时，服务端以 ProtocolVersion、MatchEpoch、SyncGeneration、ExpectedRosterCount 和 SnapshotRevision 建立 Bootstrap 门控；客户端完整应用匹配快照并 ACK 后，服务端才允许 PoseChunk。PoseChunk 的 AuthorityEpoch 必须等于当前 MatchEpoch。
- Selection 与 Move ACK 的 Fast 路径使用 Owner Unreliable Client RPC，150ms fallback 使用 Owner Reliable Client RPC；两者以 `CommandKind + ClientCommandId` 进入同一去重 FIFO，最终可靠 ACK 不依赖“最近一条属性”合并结果。

### 5.2 客户端插值

- 客户端镜像 Mass Archetype 只包含身份、Transform、插值和 Representation，不包含 Movement、Force 或 Avoidance Fragment。
- 表现层每渲染帧更新，不再以 0.1 秒轮询直接套用服务端位置。
- 默认渲染时间落后服务器 100ms；位置使用带速度的 Hermite 插值，Yaw 使用最短弧插值。
- 缺少后一帧时最多外推 100ms，之后保持；Teleport 或误差大于 1000cm 时才直接纠正，普通误差平滑收敛。
- 乱序或旧 FrameSequence 必须丢弃；单块丢失不能阻塞其他 Soldier。
- 表现时钟优先使用当前 NetConnection 的 RTT 统计，在连接统计未就绪时回退 PlayerState Ping；测试与诊断必须按 Soldier 记录移动步长、累计行程、Pose 间隔和未标记硬跳，任何未标记硬跳均不得被良好的 p95 掩盖。

### 5.3 立即视觉预测

- 玩家点击地面后一帧内立即显示目标脉冲和流水命令线，并让已确认选择中的 Soldier 沿目标方向做纯表现预测。
- 预测最长 250ms、单次最大偏移 450cm；它不参与选择、碰撞、伤害、占点或服务端目标验证。
- 收到拒绝 ACK 时，在 150ms 内融回权威轨迹。
- 收到接受 ACK 以及带匹配 ActiveOrderId 的成员帧后，使用阻尼方式消除预测误差，再回到普通插值。
- 部分 Cohort 被拒绝时只回滚对应 Soldier，其他已接受 Cohort 继续。

### 5.4 低延迟且最终可靠的命令交付

- Selection/Move 在 `t0` 先发送 Fast RPC，`15ms` 未收到同 ID ACK 时只重试一次 Fast；`150ms` 仍无 ACK 时以相同 ID 和相同 payload 发送 Reliable fallback。
- 服务端以 `CommandKind + ClientCommandId + canonical payload` 做幂等：同 ID、同 payload 只执行一次并回放缓存 ACK；同 ID、不同 payload 返回 InvalidRequest，不得覆盖已接受命令。
- Reliable ACK 回放不受 Fast replay cap 限制；每个 ID 的 Fast 尝试/缓存 ACK 回放最多 2 次，避免丢包重试绕过速率边界。
- Selection 采用单 in-flight 加有界 FIFO；Move 若依赖尚未确认的 Selection，必须等待其 ACK 并使用服务器返回的 SelectionRevision。多个待发 Move 采用 latest-wins，避免执行已经被玩家后续点击取代的目标。

## 6. 表现与指挥官 UI

- FourFRobot 继续使用 `/Game/Assets/Arma/FourFRobot` 的静态代理，不制作 Soldier 动画。
- `SoldierId -> ISM InstanceIndex` 必须稳定；逐帧批量原位更新位置和旋转，禁止恢复周期性 `ClearInstances()` 或动态 HISM 树全量重建。
- 脚环状态至少包含：未选为队伍色、选中为高亮金色、摧毁为暗灰/红色；摧毁圈按残骸生命周期移除。
- 底部 UI 改为当前临时 ControlCohort 卡片，显示 `存活数/25`、欠编、等待确认、移动和拒绝状态；Replace/Shift 后事件驱动增删。
- 小地图已使用 Landscape 高度缓存生成地形背景，以插值后的 Soldier 位置绘点，并显示镜头视野框、当前选择与目标；点击小地图可聚焦相机。预测目标和选择高亮只作为反馈，不参与命令权威。
- 移动命令线已实现 Pending、Accepted、Rejected 三种本地表现状态及流水效果，从选中军团指向目的地；ACK 不携带修正终点，因此当前线终点仍使用客户端请求目标，不能据此推导新的权威目标。
- 底部命令区与右上战术地图均属于受保护 UI 区域，LMB/RMB 命中后不得继续发送世界选择或移动 RPC。
- 指挥视角使用 RTS 透视相机、地形跟随、分段缩放、边界回弹和小地图点击聚焦，不能只把普通摄像机垂直抬高。Final 截图已完成小地图地形、相机框和命令线的视觉核对；小地图点击跳转的交互手感仍需人工复核。

## 7. 地图、规模与边界

- 原型默认生成 500 名 Soldier，红蓝各 250；所有 Soldier 在服务器逐兵精确模拟。
- 原型地图使用从 `/Game/Maps/LVL_Main` 取得的 Landscape，在独立关卡补齐并烘焙 NavMeshBounds 和指挥玩法对象；不得修改原始 `LVL_Main`。
- 同一 NavMeshBounds 为 `Default` 与 `CommanderSoldier` 生成两套 NavData；权威 Soldier 只查询后者。当前原型保留 34cm Default Agent，并配置 750cm Commander Agent，不能用全局参数破坏旧玩法地图。
- 当前每队只允许一名 Commander，其余角色为 Observer；本版不处理同队多指挥官的控制权冲突。
- 本版不制作 Soldier 动画、攻击 AI、战争迷雾、在线匹配、万人动态聚合 Backend 或客户端权威战斗。
- 万人阶段只保留动态 ReplicationCluster/Backend 接口方向；不得重新引入永久 25 人玩家编制。
- 首版继续使用 Legacy Replication；是否引入 Iris/Replication Graph 必须由实测瓶颈另立需求。

## 8. 验收标准
