# GuLiStrike：Mass 双端同步架构草案

- 类型：技术架构
- 日期：2026-08-27
- 版本：v0.2
- 状态：草案（25 人最小控制粒度与服务端分层权威已确认）
- 适用范围：[5v5 大战场玩法](./20260826-5v5大战场玩法草案.md) 的多人联机同步层

## 0. 文档约定

- **已确认**：已经由项目讨论锁定，后续实现不得静默放宽。
- **建议初值**：必须通过原型或压力测试验证的可调参数。
- **待验证**：方向明确，但只有实测通过后才能升级为正式架构。

v0.2 取代 v0.1 中“服务端完全不维护 Tier-2 空间状态”“GameState FastArray 直接作为事件日志”和“客户端宽松 Claim 直接产生战果”的方案。原讨论结论保留在本文决策记录中，不再作为实施依据。

## 1. 背景与核心目标

主 GDD 将单局小型单位峰值定为约 10000，并把实体模拟、导航和网络列为高优先级技术风险。当前首个可玩原型只生成 500 名 Soldier，但同步协议必须保留向万人扩展的路径。

本架构同时保证：

1. 玩法事实由 Dedicated Server 唯一裁决。
2. 当前 500 人原型能够精确选择、移动、受伤和死亡。
3. 万人阶段不要求向所有客户端逐帧复制 10000 个 Transform。
4. 客户端局部表现可以存在误差，但队伍、编制、存活、订单、占点、资源、比分和胜负必须一致。

## 2. 已确认的 25 人基本单位

> **CommandGroup（基本指挥单位）是玩家能够控制的最小精度；每个 CommandGroup 固定拥有 25 个成员槽。**

- Soldier 不是独立可控对象；玩家不能选择、下令或持久追踪少于一个完整 CommandGroup 的成员集合。
- 当前 500 人由 20 个 CommandGroup 组成，红蓝各 10 组。
- 最终 10000 人对应总计 400 个 CommandGroup；具体双方配额由玩法配置决定。
- GroupId 表示永久编制，在本局全灭、补员和模拟精度切换时保持不变，并且整局不复用。
- 每个成员由 `{GroupId, SlotIndex 0..24, Generation}` 标识；同一槽位补入新成员时 Generation 递增，旧世代事件不得作用于新成员。
- v1 不允许拆分或合并 CommandGroup。可通过 ParentFormationId 把多个组组织成更高层编队，但不会产生更小的玩家控制单位。

### 2.1 选择与命令行为

- 三档圆形选择最终得到 GroupId 集合，而不是 SoldierId 集合。
- 服务端使用 CommandGroup 的权威锚点和选择包络与圆形范围求交；一旦命中就整组选择。
- Shift 只能整组增加/移除，Esc 清空全部组；敌方组、全灭组和不可控组不能进入选择集。
- 点击任一成员或底部卡片时，反馈必须明确表示“将控制整个 25 人组”。
- 移动命令以组为单位产生共享路径和 5×5 槽位；成员死亡不取消订单，最后一名成员死亡时才取消并将组置为 Depleted。

## 3. 技术路线决策

| 路线 | 结论 | 说明 |
|---|---|---|
| Lockstep 全确定模拟 | 放弃 | Mass 避障、异步导航和浮点顺序无法保证跨端位级确定；也不适合 FPS 交互和晚加入。 |
| 服务端逐兵权威 | **500 人原型采用** | 为选择、移动、生命和网络预算提供正确性基线；“服务端模拟”与“逐帧复制所有 Transform”分开评估。 |
| 服务端仅记账、客户端完全自治 | 放弃为正式方案 | 服务端没有空间模型时无法验证选择、射程、占点和 DensitySnapshot，也会形成多客户端重复裁判。 |
| **服务端 CommandGroup 分层权威 + 客户端 Mass 表现** | **万人目标方案，待阶梯压测** | 服务端始终维护 20～400 个组；热区整组展开成员级权威，冷区只维护组锚点、存活、订单和聚合战斗。 |

核心思想不是“服务端不知道小兵”，而是把权威精度按玩法相关性分层：远区以 25 人组为事实边界，操作者和据点附近再恢复成员级空间代理。

## 4. 四层权威模型

| 层 | 内容 | 服务端职责 | 客户端职责 | 同步方式 |
|---|---|---|---|---|
| Tier-0 权威 Actor | 操作者载具、建筑、据点、投射物、边界 | 精确模拟与裁决 | UE Actor 镜像、预测与表现 | 标准属性复制/RPC |
| Tier-1 权威事实 | 比分、占领、出生/补员、存活、订单结果、胜负 | 唯一写入、版本化并提供快照 | 消费当前状态与事实、刷新 UI/FX | FastArray 当前状态 + 有序事实批次 |
| Tier-1.5 CommandGroup | 组锚点、路径、包络、25 槽生命、军令、占点贡献 | 固定维护 20～400 个权威组 | 围绕权威组状态展开阵形 | 全局 2～5Hz，变化立即 |
| Tier-2 Soldier | 组内成员移动、避障、实例化表现 | 500 模式或热区内精确模拟；冷区聚合结算 | Mass 插值或本地自治表现 | 热区 5～10Hz；冷区由组状态重建 |

设计红线：

- Tier-2 不能直接写入 Tier-0/Tier-1/Tier-1.5 数值。
- 客户端不能直接决定伤害、死亡、占点、资源或胜负。
- 服务端可以不维护远区逐兵 Transform，但必须维护足以产生可信密度、路径、占点和战果的 CommandGroup 空间模型。
- 热区只改变服务端模拟精度，不转移权威；同一 CommandGroup 必须整体进入或退出精细模式。

## 5. 同步信息分类

| 类型 | 示例 | 传输纪律 |
|---|---|---|
| 当前权威状态 | GroupAnchor、AliveMask、OrderRevision、据点、比分、角色槽 | FastArray/RepNotify；允许跳过中间值，但最终必须收敛。 |
| 客户端意图 | 选择圆、SelectionRevision、移动目标、FireIntent | PlayerController 的 Server RPC；必须鉴权、幂等、限流并由服务器重新验证。 |
| 不可丢事实 | 出生/补员、死亡入账、占领易手、结算 | 显式 MatchEpoch、GlobalFactId、按连接 StreamSeq、累计 ACK 和快照高水位。 |
| 纯视觉事件 | 死亡 FX、命令线、目标脉冲、声音 | 可不可靠发送；丢失不得改变玩法状态，必须能由当前状态修复。 |

`FFastArraySerializer` 不是永久事件日志。业务事件号不得复用 FastArray 的 ReplicationID；事实保留窗口、ACK、缺口和重连快照均由项目协议显式定义。

## 6. 服务端行为要求

### 6.1 500 人正确性基线

- Dedicated Server 创建并模拟全部 500 个 Mass Entity。
- 服务端精确负责位置、Yaw、NavMesh、Mass Avoidance、选择、订单、生命和死亡。
- 客户端只接收按 25 人组压缩的约 10Hz 成员帧并插值，不运行会修改镜像 Transform 的自主移动处理器。
- 当前全 20 组均视为精细权威组；不存在客户端战斗 Claim。

### 6.2 万人分层方案

- Dedicated Server 固定模拟最多 400 个 CommandGroup 的锚点、路径、包络、AliveMask、成员生命、订单和占点贡献。
- 热区由操作者、活跃据点和服务器战斗判定触发；一个组整体展开 25 个成员级权威代理。
- 热区外 Soldier 由客户端在组路径走廊和阵形包络内表现自治；Soldier 对 Soldier 的伤亡由服务端以 2～5Hz 按组聚合结算。
- 操作者只提交 FireIntent。服务器依据 Tier-0 武器状态与热区成员代理或组包络决定命中、伤害和受伤槽。
- DensitySnapshot 从服务端组锚点和 AliveMask 生成，不接受客户端密度作为玩法事实；100m 稀疏网格和 5～10 秒关键帧为建议初值。

### 6.3 死亡与补员

- CommandGroup 使用 25 位 AliveMask 表达当前成员存活；客户端丢失死亡表现后必须能由下一份 AliveMask 自动修复。
- 成员死亡后保留 5 秒红圈残骸表现，然后移除 Soldier 实体；组累计死亡数据继续存在。
- 全组归零后保留 GroupId 和 UI 卡片，不接受新命令。
- 新编制只能一次创建完整 25 槽组；不足 25 的新增兵力只能补入既有组或进入服务器补员池。
- 补员 Ticket 必须携带 ExpectedRosterRevision 和新 Generation，并保证重复应用不产生重复成员。

## 7. 晚加入、重连与时间

- 使用 UE GameState 的服务器世界时间和显式 ServerSimTick；校时只对齐时间，不能被视为跨端状态一致性的来源。
- 晚加入和重连使用原子快照高水位：在 GlobalFactId=S 捕获快照，分块传输并校验，客户端完成后再消费 S+1 之后的事实。
- Bootstrap 完成前不开放世界输入；快照 Hash 错误、超时或事件窗口溢出时重新生成快照。
- 直接 IP 原型由服务器签发 OwnerOnly ReconnectToken；重连恢复玩家队伍、角色、槽位和有效组订单，不信任客户端本地存档。

## 8. 性能与容量假设

以下均为建议初值，尚未由项目 Dedicated Server 实测：

- 20 组控制摘要 5Hz：目标单客户端不高于 100kbps、整局不高于 1Mbps。
- 500 个成员精确同步 10Hz：目标单客户端平均不高于 1.5Mbps、p95 不高于 2Mbps。
- 400 组常态采用全局 2Hz、20% 热点补到 5Hz：目标单客户端不高于 0.75Mbps、整局不高于 7.5Mbps。
- 不允许向十个客户端全局复制 10000 个 10Hz Transform；估算会达到约 192～307Mbps/局服务端上行。
- 服务器目标 TickRate 为 30Hz，对应 33.3ms 帧预算；性能标准不得再混用 60Hz 客户端的 16.7ms 预算。

扩容必须按 `500 → 1000 → 2500 → 5000 → 10000` 阶梯验证。只有服务端逐兵基线和 CommandGroup Hybrid 均有实测数据，才能确定正式万人 Backend。

## 9. 边界

- 不做 Lockstep，不承诺跨平台浮点位级一致。
- 首版不引入 Iris、Replication Graph、在线匹配或客户端权威存档。
- 本文不定义占点公式、Buff 数值、武器平衡或具体补员经济。
- 500 原型不制作 Soldier 动画、攻击 AI、载具操作者玩法或战争迷雾。
- 客户端可在 Tier-2 层产生视觉差异，但不允许以“娱乐 PvP”为理由放宽服务器的角色、队伍、订单、伤害和事实校验。

## 10. 验收标准

- [ ] 当前 500 人严格生成 20 个 CommandGroup，红蓝各 10 组，每组固定 25 个成员槽。
- [ ] 圆形选择、卡片选择、Shift 和移动命令只产生整组结果；代码与网络数据中不存在玩家可控的 SlotIndex/SoldierId。
- [ ] 服务端可在不信任客户端成员位置的前提下重新验证组选择、队伍、目标和命令版本。
- [ ] 阵营、GroupId、AliveMask、Generation、订单、占点、资源、比分和胜负全量 Hash 100% 一致。
- [ ] 延迟到达的旧 Generation/AuthorityEpoch 伤害不能影响新成员或新权威代理。
- [ ] 5% 丢包、100ms RTT、重复/乱序 RPC 下不出现重复命令、重复补员、重复死亡或永久状态漂移。
- [ ] 十客户端 Dedicated Server 中，500 人命令确认 p95≤150ms，断线重连后 5 秒内恢复可操作状态。
- [ ] 400 组常态控制面达到本文带宽和服务器 p95 预算后，万人 Hybrid 才能从“待验证”升级为正式架构。
