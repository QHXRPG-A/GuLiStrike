# 导航内存优化与对局容量预算

## 背景与目标

2026-09-22，新版本工程车在 `/Game/Maps/LVL_CommanderMassPrototype` 的 Standalone PIE 跑测期间，系统物理内存占用曾达到约 92%。用户要求分析内存来源、判断客户端与服务端归属、评估地图缩减和跨对局共享，并将内存优化登记为需求。

目标是降低每局服务端的常驻导航内存及重建峰值，支持合理的同机并发对局数量，同时保留地形行走、动态建筑、矿簇采空和工程车作业能力。容量结论必须来自独立进程实测，不能用编辑器整体占用替代。

## 已有证据与测量口径

当前证据来自源码版 UE 5.7、`GuLiStrikeEditor Win64 Development`，编辑器进程 PID 24572。实际模式为 Standalone PIE，包含权威玩法逻辑、玩家渲染及编辑器开销，并非专用服务器测试。

| 实测项目 | 数据及边界 |
|---|---|
| 监控时间 | 16:09:44 至 16:31:50，基线后 15 次有效读取；调度延迟使实际跨度为 22 分 6 秒，并非严格 15 分钟 |
| UE 私有提交 | 监控首尾约 21.313 → 21.382 GiB，增加约 70.9 MiB；此窗口未显示持续单调增长 |
| UE 工作集 | 多数样本约 15 GiB，末次约 11.3 GiB；后续下降没有伴随相同幅度的私有提交释放，不能据此宣称优化成功 |
| 导航总统计 | 6650.249 MiB，约 6.49 GiB，包含编辑器世界与 PIE 世界 |
| 其中：导航碰撞树 | 6129.902 MiB，约 5.99 GiB，是最大已识别导航项 |
| Recast / Tile cache | 分别约 519.587 / 214.685 MiB；不同统计存在包含关系，不能与导航总项直接相加 |
| 地形 | 每个世界 1024 个组件，覆盖约 8.16 km × 8.16 km，碰撞 Mip 为 0 |
| 导航范围与配置 | 覆盖约 5.6 km × 5.6 km；两个世界均为 Instant 收集，各有 Default 与 CommanderSoldier 两种动态 NavMesh |

内存分类诊断在监控完成后执行；其中 `obj list` 本身耗时约 4.4 秒，不得混入正常玩法停顿统计。诊断使用 `Mem FROMREPORT` 跳过强制垃圾回收，未修改场景或导航配置。

以上 6.49 GiB 既不是单局专用服务器实测值，也不是一台机器所有对局共享的固定值。当前导航实例归各自 World 所有；同局玩家使用该局服务端导航，不同对局各维护动态状态。项目目前关闭客户端导航，客户端仍有自身地形、碰撞和渲染开销。

## 需求描述

### 1. 优先减少单局不必要的常驻数据

- 对地形导航采用按需收集、按瓦片切片等候选方式，避免为整个已加载地形长期保留完整展开几何。优先验证 Landscape 的 Lazy 收集能力。
- 优化前后保持相同地图、单位规格、导航精度和玩法负载；不得以关闭必要碰撞、取消动态导航或降低功能正确性换取内存下降。
- 审核两种导航代理的实际使用者及覆盖范围，确认无使用者后才可移除对应导航数据。
- 建筑放置、拆除及矿簇采空仍只更新受影响的导航和工作点位；保留工程车共享查询预算、失败缓存和路径复用。

### 2. 将正式地图尺寸纳入预算

2026-09-23最新目标为1.8km内部战场、2.3km完整地形，每侧保留250m外围地形带。此前[4.2km阶段](../Archive/20260922-4.2km地图与7x7据点重布局交付.md)和[3.2km阶段](../Archive/20260923-3.2km地形与9x9据点及Mass出生修复.md)保留为历史；以本节当前尺寸为准。

| 项目 | 原场景实读 | 已确认目标 |
|---|---:|---:|
| 完整Landscape | 8.16×8.16km，8161×8161采样 | 2.3×2.3km，4081×4081采样，中心世界原点 |
| 地形组件 | 32×32＝1024 | 保持16×16＝256，单节255四边形，XY Scale＝230000/4080 |
| 内部战场 | 5.6×5.6km | 1.8×1.8km，XY边界±90000cm |
| 据点 | 5×5，单格1120m | 9×9，共81格，单格200m |
| 初始据点 | 红R1C3、蓝R5C3 | 红R1C5、蓝R9C5 |
| 出生锚点 | 工厂Y＝±252000、集合Y＝±196000cm | 工厂Y＝±87500、集合Y＝±72500cm，重新贴地 |
| 矿藏预算 | 200蓝簇、40红簇、6240节点 | 总量及每簇26节点不变，重新采样与烘焙 |

从已备份的原始高度和权重重新生成地形，避免叠加旧道路；保留陨石坑、中央高台和四向坡道，起伏按2300/8160缩放并重做平台、道路及出生区域。全部81个Marker和Region保留身份，中心为`((列−5)×20000,(5−行)×20000)`cm。物体尺寸和现有美术保持。

资源布局版本4→5，旧烘焙失效。密度按1.8/2.7重采样，继续schema v1、25m格、180°对称和55m簇间距。每个密度格按两轴¼、½、¾位置确定性采样；据点中心避让65m、格边界留12.5m，50m道路净空另计矿簇实际占地。中央6蓝/4红镜像成对，中央及高预算格优先，统一检查跨格间距。固定逐格预算沿用[开发文档](../DevelopmentDocumentation/20260922-导航内存优化与对局容量预算.md)。

地图已绑定GuLiCommanderGameMode/Controller。旧图曾因矿簇阻挡出生位而整批Mass生成失败，工程车独立生成不代表部队就绪。本轮继续共用运行时/编辑器出生计算，编队增加向战场内4000cm偏移，保留双方各250个Mass、单位半径、间距、整批校验及150cm投影修正上限。完整编队、工厂、初始工程车及固定建筑实际占地同时参与整地、矿区避让和烘焙检查，失败需报告阵营/编队/槽位和冲突对象。

地面导航XY半尺寸90000cm，保留Default、CommanderSoldier、原精度和Dynamic模式。FlightNav按地形加现有52300cm水平余量，XY半尺寸167300cm、全宽3.346km；Z根据地形下界和现有飞行高度余量校核。按地形/固定障碍→初始地面导航→资源烘焙及出生检查→最终地空导航保存并核对签名。

本次同时实施建造车自主接单：取消距离排序，保留车辆当前所在据点优先，同级按建筑创建顺序；没有可用本据点工单时接其他据点。外据点工单途中若当前据点出现可用工单，允许退单并重新优先接本地单。已占位施工的车暂停自动接单和换单，指定目标的手动命令不被自动抢占。途中只记录意向，每0.2秒检查；抵达100cm内才原子占位，抢位失败短暂排除该位置1秒并退单。每栋最多四个有效施工位，S停止、手动队列、路径预算与失败缓存保留；成本、速度及其他经济数值不变。

本次不修改碰撞规则。工程车与地形/建筑碰撞、工程车相互忽略；Mass表现模型无实体碰撞，工程车Crowd单向避让Mass，反向工程车动态避让尚未接入，不能承诺两者不穿插。

组件减少75%是几何数量变化，不能直接视为内存下降75%。历史估算不作为本阶段收益承诺；编辑器、客户端和专服必须分别实测。地图缩减与Lazy收集可能作用于相同数据，收益不能相加。

### 3. 评估静态底图与动态变化分离

- 固定地形及固定障碍可作为预烘焙基础数据；建筑阻挡、矿簇消失和其他变化由每局独立维护。
- 矿簇采空必须能够恢复原有地面的通行能力，基础数据不能永久烘焙不可恢复的矿簇空洞。
- `Dynamic Modifiers Only` 不支持生成新的可行走表面。矿厂坡道等若需要新增表面，必须保留相应的动态生成能力；不能只修改模式后默认功能等价。

### 4. 按收益决定是否做跨对局共享

跨对局共享是单局优化后的评估项，不是本需求已选定的实施方案。共享候选限于相同地图内容版本、引擎数据格式和导航规格下的只读地形或基础导航数据。

- 每局的建筑与矿簇阻挡、修改后的瓦片及连接、据点通道、矿位和建造位占用、路径结果、失败缓存均保持隔离。
- 并发寻路的查询工作区独立，不共享可变搜索状态。
- UE/Detour 挂接瓦片时会修改内部数据，不能直接把运行中的 NavMesh 或原始可变瓦片交给多个 World 使用。
- 多进程部署若需真正降低物理内存，须评估只读文件映射或共享内存、数据版本、生命周期及失效策略；各进程分别加载同一个资产不等于共享解码后的内存。
- 必须说明底层改造及维护成本、共享失败时的私有加载回退，以及跨局数据隔离验证成本。不得为共享而默认改变“一局一个进程”等部署方案。
- 容量估算采用“共享静态数据 + 各局私有数据 + 管理开销”；共享主要节省内存，不替代每局寻路计算预算。

## 验收标准

- [x] 明确正式地图面积、实际加载的地形组件数、导航范围、精度、代理类型及内容版本；保存回读证据见开发记录。
- [ ] 建造车优先本据点、同级最早工单；外据点途中遇本地新单换单，施工中的车不接新单；验证抵达抢位、满员转单、销毁、不可达、S停止和手动队列。
- [ ] 新图真实生成双方各250个Mass单位、同步就绪，框选结果及移动/停止命令正确；500槽编辑器预检不能替代此项。
- [ ] 区分 Editor PIE、独立客户端和专用服务器；记录服务器目标平台、构建配置、每局单位数及同时运行局数。
- [ ] 在相同场景及配置下记录优化前后工作集、私有提交、系统可用内存、导航碰撞树、Recast 和重建峰值；明确统计的包含关系。
- [ ] 单局常驻内存及重建峰值实际下降；具体预算由正式地图与独服基线确定，不以本文估算充当达标证据。
- [ ] 持续运行至少 30 分钟，覆盖集中采空、同时施工、拥堵和据点易主；内存不因过期瓦片、请求、占用或世界残留而持续增长。
- [ ] 矿车持续采矿和交矿，建造车持续施工；坡道入口、负坐标、不同导航代理、动态阻挡及矿簇采空后的通行正确。
- [ ] 内存优化不破坏工程车原有功能和性能验收：共享路径预算、稳定等位零寻路、导航就绪时的响应及主线程停顿均需验证。
- [ ] 若采用跨局共享，验证一局建造、采空、结束或重启不会改变其他局导航；检查并发读写、版本切换、释放和回退。
- [ ] 多局容量基于整机实测，正确区分共享驻留页与私有内存，避免将各进程工作集简单相加造成重复计数。
