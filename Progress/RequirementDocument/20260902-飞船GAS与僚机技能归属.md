# 飞船 GAS 与僚机技能归属 — 需求补充

- 日期：2026-09-02
- 状态：已确认，待完整验收
- 主需求：[僚机体系与空中三维导航](20260902-僚机体系与空中三维导航.md)
- 配对开发文档：[飞船 GAS 与僚机技能归属](../DevelopmentDocumentation/20260902-飞船GAS与僚机技能归属.md)

## 1. 不可变产品决策

1. 飞船必须拥有独立的 Gameplay Ability System Component。
2. Ship ASC 随 Ship Pawn 创建和销毁，`OwnerActor=AvatarActor=Ship`；不得复用或替换 PlayerState 上已有的 Army ASC。
3. Ship 与单架 Wingman 均不得新增 `AttributeSet`。生命、速度、伤害等数值不由 GameplayEffect 改写。
4. 飞船数值继续由基础表、部件贡献与稳定技能修饰源合成，并只通过现有 `RecomputeStats` 与 Ship CMC 配置屏障提交。
5. 单架 Mass Wingman 不拥有 ASC。Ship GameplayAbility 只负责组级授权、激活、互斥、取消和冷却；Mass Processor 负责逐架编队、三维导航、避障、索敌及开火意图。
6. 首版只交付双环编队、初始自动武器、主动导弹齐射三项 Ship Ability。
7. 现有飞船物理武器组件与开火链本轮保留，不迁移为 GameplayAbility；它只接入统一目标与伤害账本。

## 2. 生命周期与载荷

- Ship BeginPlay、首次占有和重占有可以重复初始化 ActorInfo，但同一能力不得重复授予。
- 普通 UnPossess 只关闭本地玩家主动技能输入。双环编队与初始武器被动授权继续有效，避免短暂控制器切换销毁整个僚机组。
- Ship 死亡或 EndPlay 取消全部 Ship Ability，使旧 GroupAbilityConfig 失效，并可靠结束旧 Wingman Group。
- PlayerState 保存会话级 `FGuLiShipAbilityLoadoutState`，只保存稳定 AbilityId；不得保存 AbilitySpecHandle、活动实例、临时 GameplayEffect 或冷却。
- 新 Ship 创建新 ASC、新 GroupGeneration 与新实体身份；按 PlayerState 载荷重新授予三项能力并满编生成。
- 本功能不增加跨局 SaveGame。进入新对局后能力活动状态与冷却全部重新开始。

## 3. 首版能力语义

### 3.1 双环编队

- 双环编队是默认授予并由服务器自动激活的长驻被动能力。
- 它发布组级 FormationDefinition；实际 Guidance、固定翼积分、避障和恢复仍仅在当前 Lease Owner 客户端执行。
- 任意活动 Wingman Group 必须恰有一个有效编队能力。
- 将来的编队切换必须经历“服务器准备新配置、Lease Owner ACK、指定 ClientSimTick 原子生效”；提交前继续使用旧编队，切换只改变 Guidance，禁止传送吸附。

### 3.2 初始自动武器

- 初始武器是默认授予并自动激活的全编队被动能力。
- 每架存活 Wingman 独立索敌，保存独立冷却、`DomainFireSequence`、Emitter 身份和 SourceAcceptedStateRef。
- 每发基础武器不是一次 GameplayAbility 激活；Ship Ability 只提供当前武器授权和定义版本。

### 3.3 主动导弹齐射

- 导弹使用输入 GameplayTag 激活。拥有客户端只预测准星锁定反馈，不能预测伤害、弹体真相或冷却提交。
- 服务器验证 Ship、Group、目标、敌我、距离、LOS、AbilitySetRevision、WeaponDefinitionRevision 与共享冷却。
- 服务器从具有新鲜 Accepted 状态的 Flight 中确定一个稳定 Flight；该 Flight 每个存活且合法的成员各发射一枚。
- 没有合法发射者时整次失败且不进入冷却。导弹只有 Ship 级共享冷却，不使用充能、弹药或通用能量。
- 导弹采用服务器 30Hz 轻量逻辑弹体及 Segment/Sphere Sweep；不得生成逐弹复制 Actor。
- 导弹发射后不得重新选敌。目标死亡、超时或路径失效时自毁；已被服务器接纳的弹体不因 Emitter 随后死亡或 Group 进入 Stale 而取消其一次既定结算。

## 4. 网络与权威要求

- ClientValidatedRelay 的既定原则保持不变：服务器不得运行 Wingman StateTree、A*、Steering、Flight Integration 或生成替代 Transform。
- Ship GAS 权威状态必须投影为可靠的 `FGuLiGroupAbilityConfigSnapshot`，供当前及备份 Lease Owner 使用；备份方无须也不得访问原 Ship ASC 或 AbilitySpec。
- Bootstrap 由五个 Scope 扩展为六个：Roster、AuthorityMap、Health、Dead、AcceptedSnapshot、GroupAbilityConfig。六者必须共享同一 Cut、Revision 和确认哈希。
- TransferCommit、Resume 与 Takeover Baseline 必须冻结 AbilityConfig Revision/Hash。
- Candidate 必须携带 AbilitySetRevision、FormationCommandRevision 与 FormationDefinitionChecksum。
- FireIntent 必须携带 WeaponAbilityId、WeaponDefinitionRevision、AbilitySetRevision 与实际 Emitter WingmanHandle。
- 服务端必须在推进序列、冷却、Accepted Snapshot 或 Damage Ledger 之前拒绝能力版本不一致的数据。
- CarrierSourceRef 引用 Ship CMC 服务器重演后的 CanonicalEpoch 与 MoveRevision。跨 Channel 尚未到达时最多 Pending 0.25 秒，之后明确 Reject；不得使用客户端声明的 Ship Transform 填补。

## 5. 目标、生命与伤害

- Ship、Commander Soldier 与 Wingman 通过统一 TargetHandle 和窄 Adapter 接入目标查询。
- Ship 生命继续使用自定义服务器 Health Component；Wingman 生命继续属于服务器生命周期数据。
- 基础武器、导弹及现有 Ship Projectile 必须进入同一幂等 Damage Ledger。
- 相同 Shot/Impact/Damage ID 重复到达时最多提交一次伤害、一次死亡和一次奖励。

## 6. 验收条件

- 每艘 Ship 恰有一个 Ship ASC；PlayerState Army ASC 仍为另一独立组件；每架 Wingman 的 ASC 数量为零。
- BeginPlay、占有与重占有不重复授予；重生保留稳定 AbilityId，但旧活动实例和冷却均不存在。
- 任意 Group 最多一个编队能力生效；缺少有效编队或未确认 GroupAbilityConfig 时不得进入 Active。
- 旧能力版本 Candidate/FireIntent 不推进任何序列、冷却、快照或伤害。
- Backup Owner 仅凭可靠投影即可恢复模拟，但不能释放主动导弹或发起技能切换。
- 导弹齐射的逻辑弹体上限等于选定 Flight 当前合法成员数；复制 Missile Actor 数始终为零。
- 六 Scope Bootstrap、LateJoin、Resume 与 Takeover 的 Cut/Revision/Hash 一致。
- 原主需求中的服务器零 Wingman 运动、弱网、带宽、100 单位和拆分 4000 Harness 硬 Gate 继续成立。

## 7. 明确不在首版范围

- Ship 或 Wingman `AttributeSet`。
- 把现有 Ship 自身物理武器完整迁移为 GameplayAbility。
- 为每发基础弹或导弹激活一次 GA。
- 为每架 Wingman 创建 ASC、Actor 或复制弹体。
- 导弹中途换目标、弹药/能量经济、跨局能力存档，以及逐架 Wingman 微操。
