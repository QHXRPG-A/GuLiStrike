# 客户端性能优化与压测问题记录

## 1. 背景与目标

2026-09-15 的压测已经证明，指挥官客户端可以接收并表现约1,200个持续移动单位，但同机双客户端的帧时间、真实鼠标操作中的移动跳动，以及拉远镜头后的单位识别仍有问题。网络协议9显著减少了数据量，客户端整体CPU和帧率并未出现相应幅度的改善。

本需求同时关注三项结果：**帧时间稳定、移动显示连续、交互信息可读**。不能以平均帧率正常代替同步验收，也不能以减少网络字节数代替客户端性能改善。

本文记录实测现象、高消耗项、原因判断及验收要求。函数名用于定位现有证据，不规定类拆分、接口签名或具体算法；初始阶段只记录需求。用户后续已授权[本轮 CPU 优化实施与复测](../DevelopmentDocumentation/20260915-客户端CPU增量维护与10Hz刷新.md)。

### 2.2 统计解释

- P95表示95%的样本不超过该值；人数另看P05和逐帧最低值。P05不是最低值，P95的倒数不是平均FPS。
- A组整帧来自去掉首秒的 `frames.csv`，线程/GPU来自引擎CSV，采集边界略有差别。B组共同30秒另行对齐，不能与A组直接计算优化百分比。
- 函数“包含子调用”与“自身”必须区分；自身时间仍可能包括未单独打点的内部函数。线程包含等待，不能把CPU、渲染线程、GPU时间相加。
- 1核心当量表示每秒消耗1秒CPU时间；不是整机CPU百分比。KB/s采用1,000字节，MiB采用1,048,576字节。工作集是驻留量，私有提交不等于物理内存占用。
- 所有结论均限于对应源码快照和采集条件；同机双客共享GPU及内存，不能将双客FPS乘二推算分机性能。

按当轮P95门槛，一客满足60FPS预算16.67ms；双客满足30FPS预算33.33ms，未满足60FPS预算。双客存在约33.8ms的个别帧，不能把“P95通过30FPS”解释为没有任何长帧。

三台客户端实际移动人数P05均为1,200；服务端约10Hz、无丢步。旧的“合法捕获帧接收约9.997Hz”只证明不断收到对应帧的合法分块，不能证明每个单位都以10Hz更新。B组才补齐逐单位有效样本统计。

相同镜头下，双客GPU P95由单客6.802ms增至16.691／17.055ms，渲染线程时间同步增加，GameThread增长相对较小。**证据支持同机共享渲染资源影响明显；尚不能把全部等待都归因于GPU，也不能称为所有场景均为纯GPU瓶颈。**

### 3.2 项目及引擎CPU高消耗项

下表以A组双客客户端1为准。预算占比 = 平均包含子调用耗时 ÷ 16.6667ms，仅用于衡量单项对60FPS预算的压力，**不是整进程CPU占比，各行也不能累加**。

| 已测函数／范围 | 平均包含子调用 ms/帧 | 平均自身 ms/帧 | P95 | 单项预算占比 |
|---|---:|---:|---:|---:|
| `AGuLiCommanderPresentationActor::RebuildLocalInstances` | 1.360 | 1.201 | 1.907ms/次 | 8.16% |
| `UGuLiCommanderMiniMapWidget::NativePaint`绘制路径 | 0.426 | 0.426 | 0.559ms/次 | 2.56% |
| `UInstancedStaticMeshComponent::CalcBoundsImpl` | 0.225 | 0.225 | 未单独导出 | 1.35% |
| `UInstancedStaticMeshComponent::BatchUpdateInstancesTransforms` | 0.159 | 0.159 | 0.242ms/帧 | 0.95% |
| `AGuLiCommanderHealthBarRenderer::Tick`中的UpdateInstances范围 | 0.111 | 0.111 | 0.151ms/次 | 0.67% |

ISM批量写入已包含在1.360ms内。实例更新、小地图、血条约每帧一次；边界计算和ISM批量写入约每帧两次。前三个项目事件的P95按调用统计，ISM的P95按帧聚合，两者口径不同。客户端2实例更新平均1.347ms、P95 1.877ms；小地图平均0.427ms、P95 0.558ms，与客户端1相近。

其他范围：UI整体平均1.700ms、P95 2.189ms，包含Slate及Viewport多个入口；`WorldTickMisc`平均1.698ms、P95 2.277ms，与项目事件重叠。`UpdateCoreCsvStats_BeginFrame`自身约0.256ms/帧是采样环境成本，不作为玩法逻辑优化收益承诺。

### 3.3 高消耗项的原因与证据强度

| 项目 | 已确认的工作方式／原因 | 仍未证实的部分 |
|---|---|---|
| 单位表现更新 | 现有函数承担姿态消费、时钟与插值、完整名册遍历、选中态整理、生命状态反馈、Mass镜像和实例提交；逐帧复制多组Transform数组并先隐藏再填回。稳定实例池检查也遍历名册和集合 | 调用树只单独测到0.159ms的ISM子项；其余约1.201ms不能直接分配给数组、插值或Mass，必须补充分段归因 |
| Mass客户端镜像 | 当前每单位通过延迟命令提交身份、队伍、血量及Transform；部分不变字段也随逐帧更新提交 | 缺少独立耗时和分配统计，不能称其为已确认的最大CPU瓶颈，也不能将它等同于客户端重新运行服务器模拟 |
| ISM与边界／场景更新 | 当前已经使用批量实例；移动后调用 `MarkRenderStateDirty()`；采样中存在 `CalcBoundsImpl`、`AddPrimitive (GT)`及场景更新成本 | 尚未证明这些成本全部来自同一个失效调用，不能直接声称“删一行便节省全部成本” |
| 小地图 | 数据快照已经每0.1秒刷新；绘制路径仍按画面帧执行，包含20×20地形格的采样、变换和绘制，以及逐单位点投影。数据10Hz不等于绘制10Hz | 静态地形、单位点和其他Slate入口尚未分别计时，不能把0.426ms全部算成士兵点 |
| 血条 | 即使本次可见数为0，Tick仍维护实例池、复制工作数组并遍历名册；显示条件筛选在更新过程中完成 | 没有大量血条同时显示的有效性能数据；0.111ms不能用于推算1,200条血条和受击效果的总成本 |

源码定位：[单位表现](../../Source/GuLiStrike/Commander/Presentation/GuLiCommanderPresentationActor.cpp)、[小地图](../../Source/GuLiStrike/Commander/UI/GuLiCommanderMiniMapWidget.cpp)、[血条](../../Source/GuLiStrike/Commander/UI/GuLiCommanderHealthBarRenderer.cpp)。表中源码工作方式也核对了2026-09-15当前工作区；历史耗时只属于A组采样快照，并非这些路径修改后的重新测量。

## 4. 渲染线程等待与GPU高消耗项（A组）

### 4.1 必须区分等待与计算

| 范围 | 客户端1平均／P95 | 已知含义 |
|---|---:|---|
| RenderThread `EventWait/Visibility` | 8.373／10.192ms | `FVisibilityTaskData::ProcessRenderThreadTasks()`处动态网格任务管线的等待；不是“可见性计算独占执行10ms” |
| `Game thread idle time` | 平均8.741ms/游戏帧 | 帧同步等待；不能再加到GameThread逻辑成本上 |
| `FRDGBuilder::CollectResources`对应范围 | 0.883／1.111ms | 包含子操作及任务等待，尚未细分 |

单客的 `EventWait/Visibility` 为平均1.834ms、P95 3.006ms，双客明显增加。等待对象所在流程已定位，最终耗时来源尚需关联生产任务、资源提交和GPU队列；不能把该范围的全部耗时标成显卡执行时间。

### 5.4 负载有效性与后续源码边界

六轮存活数均为1,200。除优化后第3轮三端移动人数P05为1199／1200／1199外，其余均为1200；但基线第3轮客户端1逐帧最低为1160，其余客户端最低1198–1199。不得把P05差1人表述为“所有帧最多差1人”。

共同30秒内服务器10Hz、0丢步，客户端0解码失败；单兵有效姿态约7.46–7.51Hz，平均样本间隔约133–134ms，P95 200ms，符合混合10Hz／5Hz下发。0解码失败只覆盖编解码结果，不能证明插值显示没有跳动。

旧协议清理后另有一轮1,200单位双客联调：客户端实际移动P05为1199／1200、最低均1198，有效姿态7.501／7.498Hz，服务端10Hz、0丢步，客户端0解码失败。该轮没有重做六轮CPU／内存／流量对比，不能并入上表。完整证据见[协议对比报告](../../TestResults/CommanderPoseCompression/REPORT.md)与[清理后联调记录](../../TestResults/CommanderPoseCompression/protocol-cleanup/README.md)。

## 6. 真实鼠标操作发现的问题（C组）

### 6.1 操作与观测

实际用系统鼠标完成单选、框选约24名单位、右键移动、多次换向、缩放镜头，并在另一客户端观察同一支部队。未用压测器合成命令替代这些操作。120秒跟踪只针对313号单位，日志中包含5次真实鼠标移动指令。

| 原始轨迹指标 | 结果 | 解释 |
|---|---:|---|
| 时长／总记录 | 120.004秒／7804条 | 含开始、结束及不同事件 |
| 画面帧／姿态到达／鼠标指令 | 7197／600／5 | 单兵姿态约5Hz；画面帧间隔中位数16.667ms |
| 播放时间倒退 | 13次 | 相邻frame的 `render_server_seconds` 差小于0 |
| 最大倒退／最大向前跳进 | 100.053／127.893ms | 正常约16.667ms的显示帧中出现时间突变 |
| 最严重一帧显示位移 | 539.680cm | 帧间隔约16.666ms，显示速度约323.82m/s；该单位基础速度36m/s |
| 该最严重帧的播放时间跳进 | 122.922ms | 与显示突然窜动对应；不是服务器修改了单位基础速度 |
| 从静止指令到首次显示位移 | 约150／150／250／166.668ms | 四次起步，首次位移阈值>1cm；第五次已在移动，不计算“起步延迟0ms” |
| 显式hard_snap／network_reset事件 | 0／0 | 说明没有走这两条诊断分支，不等于没有视觉跳动或网络问题 |

计算方法：只取连续frame记录；帧间位移为两次 `presented_xyz` 的欧氏距离；显示速度为该距离÷本地时间差。原始证据：[移动CSV](../../TestResults/CommanderPoseCompression/mouse-repro-20260915-173032/before-mouse-movement.csv)、[启动参数](../../TestResults/CommanderPoseCompression/mouse-repro-20260915-173032/launch.json)。

上述响应值是鼠标到首次可见位移，不是RTT，也不是服务端站位规划耗时。现有轨迹中的ACK诊断依赖旧预测上下文，没有完整的确认事件链，本轮不能分解“输入→确认→规划→显示”的各段延迟。

### 6.2 跳动的已定位原因与修复状态

修复前，待命／移动切换会清零收包间隔和抖动统计，使自适应插值延迟从约220–230ms突然降到120ms，后续样本又抬高延迟。显示时间直接由估计服务器时间减去该延迟得到，因此既可能突然跳进，也可能回退。轨迹中的时间突变与源码路径一致，属于显示时间推进问题。

当前工作区已修改为跨状态保留收包统计，并让播放时间平滑向前推进；另修复打开控制台时鼠标贴边仍推动镜头的问题。修复前源码保存在[表现代码快照](../../TestResults/CommanderPoseCompression/mouse-repro-20260915-173032/before-source/GuLiCommanderPresentationActor.cpp)。

该修复已通过源码版[Editor构建](../../TestResults/CommanderPoseCompression/mouse-repro-20260915-173032/editor-build.log)和[Game构建](../../TestResults/CommanderPoseCompression/mouse-repro-20260915-173032/game-build.log)，引擎、项目与涉及插件BuildId核对一致。**修复后的双客户端鼠标复测、相关回归与性能复测尚未运行；不能标记为玩法已验证。**

## 7. 客户端优化需求与优先级

| 编号／优先级 | 必须达到的结果 | 验收关注点 |
|---|---|---|
| CP-01／先完成 | 起步、停止、连续改向及姿态频率变化时，单位移动显示连续，普通状态切换不造成播放时间倒退 | 先复验已有修复；显式传送、重连及战局切换独立记录，不混入正常移动平滑度 |
| CP-02／高 | 减少单位表现中与实际变化无关的重复整理、分配和提交，同时保持可见移动单位逐帧插值 | 对名册维护、姿态消费、插值、Mass镜像、实例提交分别给出耗时；移动、静止、屏幕外单位的成本应可区分 |
| CP-03／高 | 降低渲染提交、场景更新及实际GPU高消耗项，维持兵种、阵营和选中信息可辨认 | 补齐具体资源级归因；画质或剔除策略的调整须明示并进行同视角视觉核对，不把等待时间当成可直接删除的计算 |
| CP-04／中 | 小地图静态内容和单位标记减少无变化重绘；血条仅为需要显示的单位承担相应工作 | 保留小地图定位／点击准确性、选择反馈和受击提示；动态信息更新不能因缓存变得过时 |
| CP-05／中 | 模型、圆环、血条在镜头缩放和远近切换时形成一致、可解释的显示规则 | 地面选择和命令身份不受表现剔除影响；不能出现镜头拉远后误以为单位丢失的状态 |
| CP-06／后续按证据推进 | 内存分配与驻留有归因；后续优化同时报告工作集、提交量、缓存和资源代价 | 区分短时分配、持久缓存和资源驻留；不将2.06MiB协议缓存当作整个进程内存来源 |

保持服务端10Hz模拟及当前协议精度。客户端渲染频率、界面内容刷新和网络姿态频率分别管理，不将整个客户端统一降为10Hz。网络消费、移动显示和UI读取的职责应可独立观察；本需求不引入新的模块或通用容错框架。

优化顺序以实测成本、风险和用户可见问题共同决定。当前协议处理仅约4ms/s，继续压缩网络不是已证实的客户端帧率首要收益来源；本轮不要求新增压缩算法。不得为了降低客户端成本改变服务端站位、寻路、战斗或所有权规则。

### 8.1 首轮验收口径

- [ ] 明确每组源码版本、构建、地图、人数、实际移动人数、分辨率、画质、镜头、前后台、帧率上限与采集开关；正式对比在同一设置下进行。

- [ ] 先确认存活数、真实移动人数分布、服务器约10Hz且无丢步，再比较CPU、GPU、内存和网络；不得通过减少有效负载获得改善。

- [ ] 每项改动给出对应成本的前后测量及整体影响，收益和回退同时保留；不同嵌套范围不重复相加，采集开销与等待单列。
- [ ] 同一视角核对模型、圆环、血条、路径线和小地图信息；降低画质、距离或显示数量时须列明实际差异。
- [ ] 内存报告包含平均、P95、峰值及实际缓存分配；尚无资源／调用栈归因的项目明确写待验证。

### 8.2 后续待评审补测范围

全军同屏、全选路径线、大量血条及交火特效、数分钟持续操作、打包客户端、分机和真实公网延迟／丢包均未在上述有效性能对比中覆盖。它们是后续容量结论需要补齐的范围，**本次没有执行或扩充这些测试，也没有新增自动化测试代码**。

分机结果应用相同版本和画质，分别报告客户端资源；同机结果只用于相对比较。尚未有依据承诺“客户端最多支持多少单位”。旧协议阶段2,000在线单位曾受复制带宽限制，1,000／4,000单位晚加入曾受初始名册消息限制；这些历史失败见[容量报告](../../TestResults/CommanderMove10Hz/REPORT.md)，不能直接当成协议9当前的渲染上限或已修复结论。
