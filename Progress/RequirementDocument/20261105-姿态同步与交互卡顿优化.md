# 姿态同步与交互卡顿优化

## 背景与目标

采集目录为 `D:/UE5.7/PerformanceCaptures/GuLiStrike/20261105-101855-DB6FBE62/`。5.04 秒网络样本中姿态通道约 160,159 B/s，达到 160,000 B/s 预算；回执约占该通道 33.78%，消息与包头合计约占 60.77%。这说明应先减少重复传输开销，不能仅以增加预算掩盖排队。

CPU 窗口发现连续三个长帧约 73.63、119.58、80.70 ms，其中矿石重建两帧分别创建 6,179 个物理实例；另三个选择长帧各有三次完整对象目录复制，累计约 25.75–26.32 ms。网络排队年龄不是 RTT，现有证据也不能推导 GPU 瓶颈。

## 已确认范围

1. 同一接收端、同一发送时段的多个姿态合包，公共信息只写一次。
2. 确认回执批量发送并无损压缩，保留增量编码基线确认。
3. 保留现有 10 Hz 姿态/组件发送上限，抑制真正不变的状态；核对字段，不牺牲位置、转向或动画精度。
4. 领地归属改变不再清空和重建整图矿石碰撞、阻挡及导航。
5. 选择输入改为按需读取，不重复复制全部对象能力与历史数据。
6. 采集工具按姿态、姿态确认回执、组件状态统计窗口内入队、首发和被替换的数量，另列静止单位姿态实际发出与跳过次数，供玩家定位积压。
7. 同一士兵发往同一接收端的等价静止姿态只保留一份待发记录。真正发出后首次及后续未确认补发统一间隔 200 毫秒，已确认的稳定状态约每 0.5 秒校正一次。
8. 静止士兵的可预测循环待机动画由远端续播，首发、真实字段变化、动画纠偏、未确认补发和周期校正分别统计。移动、转身、炮管、死亡、切片和传送继续按真实样本更新。
9. 以 18:38 采集为基线，在原地图、单对端、约 300 名本地模拟士兵的同负载窗口，将姿态通道实际发送量从 160.43 KB/s 降至 ≤100 KB/s。范围包括传输协议、对象身份、士兵姿态块和车辆通行与作业分发。保留既有通道预算和位置精度，核对回执、队列、连接错误和其他通道流量。

- 身份、对象生命代次、权限代次、时序和基线校验保留；不增加正式默认关闭开关。
- 初次矿石目录安装、真实目录恢复及显式障碍重同步仍允许完整初始化。正常采空继续使用单节点移除与异步导航恢复。
- [x] 正式入口代码实现、静态检查、原地图验证入口保存及相关实体数据核对。
- [x] Editor 与协调器均构建为协议 35，四份清单由新版 Editor 导出并通过协调器离线校验。
- [x] 协议 36 同负载姿态通道实发量 ≤100 KB/s。三间独立房间测得 54.70、56.19、53.92 KB/s。[实测记录](../Evidence/20261105-PoseNetwork/20261105-motion-100/acceptance.json)
