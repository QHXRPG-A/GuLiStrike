# 指挥官兵种技能、Ship 武器通道与 Roguelike 升级归属 · 多武器执行与冷却

<!-- guli-progress:split-content -->
## 6. 多武器执行与冷却范围

### 6.1 冷却与资源归属

| 范围 | 示例 | 状态归属 |
|---|---|---|
| 单兵单槽 | 每名 WM01 的机枪独立射击、锁定不同目标 | `SoldierId + SlotId`；沿用固定步战斗 |
| 全队某兵种/槽位 | 指挥官命令所有 WM01 发动一次齐射 | 显式军队技能/冷却组状态；GA 可管理命令激活，但不能替代各士兵执行状态 |
| 指挥官自身 | 指挥官战术技能的费用或冷却 | 指挥官 ASC；若要求换任后保留，则另有 Team 状态作为权威依据 |
| 单僚机单槽 | 同一僚机基础武器和副武器各自射击 | `WingmanHandle + WeaponSlotId`；客户端预测，服务器权威 |
| 当前 Ship / 僚机组的共享指令 | 一个 Flight 导弹齐射 | 显式 `CooldownGroupId + 当前 Ship/Group 身份`；Flight 是执行者子集，不自动拥有独立齐射冷却 |
| 飞船单挂点 | 两门独立本体武器 | `Ship 实例/代际 + 挂点 SlotId`；共享开火输入不等于共享冷却 |

自动武器槽默认各自寻敌、各自冷却；主动齐射按其目标与共享组规则执行。共用弹药、炮塔转向、舰体朝向约束或互斥开火应显式配置，不能靠槽位名称或同一 GA 类隐式决定。技能数为 x+y 不表示所有槽每一帧都会开火。

同一共享冷却组只维护一份进度。首版不允许组内不同槽对同一冷却来源配置互相冲突的持续时间；相关修改须作用到组或由明确的组规则裁决。换武器、短暂卸下再装回均不能清掉既有共享冷却。

### 6.2 陆军执行改造（保留原有范围）

需要改造的执行边界：

1. 每兵从一套 Attack 改为已启用槽位的紧凑状态集合；同兵种共享只读 Profile 缓存，不复制升级账本，不保存跨提交失效的裸指针。
2. **目标实体集合与武器执行集合分离**：空间网格里每名士兵仍只有一个位置/身份。不能简单复制当前 CombatSample 为每槽一份，同时继续把它当目标网格输入，否则会重复登记目标并破坏索引假设。
3. 一次固定步读取一致的 Loadout 快照，确定性遍历士兵/槽位；攻击仍基于同一存活快照收集后统一结算，保留当前同拍互杀语义。寻敌调度可用稳定的 SoldierId 与 SlotId 分散，避免同兵多槽全挤在同一步。
4. 增删槽位要有独立 `LoadoutRevision`，不能仅用所有 Profile 的最大 Revision 判断变化。既有 Pending/Committed 合并路径还需明确移除或禁用处理，不能留下旧槽继续开火。
5. 攻击事件保留兵种、SlotId、SkillId、ProfileRevision 与事件身份。当前伤害事件只有来源兵、目标兵、SkillId、Damage，无法充分支持精确的兵种槽位归因和后续触发链。

规模上，共享配置和可选 Spec 约随 `Σ K_兵种` 增长，每兵武器状态及攻击遍历约随 `Σ(N_兵种 × K_兵种)` 增长；这只是结构分析，不是性能测量。优化重点是武器寻敌/执行和实际状态数量，不能用“一个 ASC 上多了几个 GA”代替成本分析。

### 6.3 僚机通道与网络改造

1. 把固定 BasicWeaponRuntime / MissileRuntime 扩展为按僚机类型和 WeaponSlotId 索引的已提交通道集合，包含启用状态、SkillId、ProfileRevision、行为和所需参数。Formation 独立保留；无已装备武器仍可以拥有合法编队，非法候选配置则整笔拒绝并保留旧配置。
2. 本地自动射击状态及服务器 `BasicNextFireTimeByEmitter` 扩展为成员/武器槽状态；成员仍只有一个位置、生命和 Roster 身份。各槽共享空间候选数据但按自身目标规则筛选，武器升级不改移动、避障和导航算法。
3. 开火请求增加通道身份、SkillId、通道/Loadout 版本，沿用 MatchEpoch、组/成员代际、LeaseEpoch 和 Accepted 状态引用。服务器从已提交 Profile 解析参数，校验发送者权限、成员存活、已装备、射程、视线和该槽冷却；客户端不提供最终伤害或任意成长倍率。
4. 保留当前域级 DomainFireSequence 的顺序/去重职责，不能让每个新武器槽各自从 1 开始而发生冲突。伤害/弹丸事件增加 BindingKey、发射者、ProfileRevision 和根事件身份；射击 ID 的生成与去重键必须包含足够的通道上下文。
5. 用完整通道清单及 LoadoutRevision 表达新增、禁用、移除和替换，扩展可靠快照、序列化/哈希、协议版本、Bootstrap 与备份执行者恢复。仅添加一份本地 TArray 不能视为联机多槽完成。
6. 各端按已声明生效版本切换参数；旧版本在新配置生效后提交的开火意图不补套新伤害，按版本拒绝并等待同步。短暂升级窗口允许等待配置，不能放松现有身份/版本校验来维持射击。
7. 武器更新可以推进组配置快照版本，但不得重置 FormationCommandRevision、编队种子、成员身份或未受影响通道的进度。备份客户端只恢复模拟和意图生成，不复制领取奖励的权限。

多槽会增加开火意图与结算数量。开发方案应结合已确认的最大通道数说明载荷/队列上限和合法射速预算；不删除既有节流或扩大整套网络验证范围，也不在未经测量时承诺额外性能容量。

### 6.4 飞船本体武器接入

本体武器为独立接入阶段：将逻辑挂点 SlotId 映射到现有 SocketName 和 InstalledPart；装配选择仍由现有服务器配装流程确认，武器专属基础值及局内修饰解析成该挂点 Profile。部件的 Fire 使用这份配置，LastFireTime/冷却迁移按通道管理，装卸组件不再成为免费刷新射速的途径。

保留当前炮口权威变换、装配版本/移动屏障和复制弹丸链；Projectile 创建时记录伤害及绑定来源。武器部件可能同时影响质量和飞行参数，涉及真实部件换装时必须沿用既有装配事务；纯伤害升级不触发移动配置重算。首轮不把自定义蓝图 Fire 自动视为兼容，需明确哪些部件执行器接受最终 Profile。
