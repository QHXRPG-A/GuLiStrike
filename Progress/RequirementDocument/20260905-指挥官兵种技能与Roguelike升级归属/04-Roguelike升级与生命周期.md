# 指挥官兵种技能、Ship 武器通道与 Roguelike 升级归属 · Roguelike 升级与生命周期

<!-- guli-progress:split-content -->
## 7. Roguelike 修改规则

### 7.1 奖励到底绑定什么

| 奖励目标语义 | 举例 | 同槽换武器后 |
|---|---|---|
| 槽位绑定 | WM01 / BasicAttack 伤害提升 | 继续作用于该槽当前装备，适合稳定的兵种成长 |
| 槽位 + 指定 SkillId | WM01 的该槽只有装备机枪时享受强化 | 改装其他技能后暂不生效，保留取得记录；换回时重新生效 |
| 兵种/范围 + 最终技能标签 | 本队符合范围的火焰武器强化 | 按替换后的最终定义标签匹配，不误按换装前标签计算 |

首版建议以“明确兵种 + 明确槽位”为主，技能专精和跨槽标签升级按内容需求增加。一个奖励若能选择多个目标，必须在选取时保存玩家实际选择，不能每次重算时重新随机选择。

相同规则适用于空中：奖励目标先限定 OwnerKey、Domain 和类型/配装，再选择槽位；“我的僚机 BasicWeapon 强化”不影响同队另一名 Air 玩家、WM01 或飞船本体主炮。一次针对僚机类型的奖励影响该配装全部该型成员，不随当前存活数量复制多份奖励。

| 空中奖励示例 | 操作 | 换装/补员语义 |
|---|---|---|
| 僚机 BasicWeapon 槽伤害提升 | 修改指定绑定 | 同槽换武器继续生效；补充的新僚机读取同一 Profile |
| 该槽机枪专精 | 绑定 + SkillId 限定 | 换成别的武器时暂不生效，换回恢复 |
| 解锁僚机 SecondaryWeapon | 解锁并按配置装备候选 | 新增并行通道；基础自动武器和导弹共享冷却不重置 |
| 僚机导弹齐射冷却缩短 | 修改明确的齐射冷却属性/共享组 | 不等价于每架基础武器攻速提升 |
| Ship 左挂点主炮强化 | 修改 ShipMounted 挂点绑定 | 只作用于允许挂载的本体武器；不自动影响僚机 |

机枪、激光、散射等名称用于说明装备与成长规则，不是本稿声称已存在的完整武器内容。多弹丸/分裂/燃烧仍需相应执行和表现支持。

当前 RequiredTags 来自最终 SkillDefinition，不代表已支持词条动态增删技能标签；若升级要改变标签，需明确解析阶段及循环约束，不能让目标筛选与加标签互相递归。

### 7.2 叠加不能由随机实例 ID 决定

现有解析公式（每个属性分别计算）：

`最终值 = (基础值 + 所有来源固定值之和) × ∏来源(1 + 该来源内百分比之和)`

因此两个 +20% 放在同一个 SkillSource 中是 ×1.40；放在两个不同 SourceInstanceId 中是 ×1.44。同 ID 的 Upsert 是更新来源，不是自动增加一层。这是现有行为，不是本稿建议的肉鸽平衡参数。

建议将“奖励取得身份”与“数学叠加分组”分开：

- 每次合法获得保留独立 UpgradeInstanceId；重发同一次选择不能再叠一层。
- 普通常规增伤建议同组相加；独立乘区必须由配置明确声明，不能因为创建了新 GUID 就变成新乘区。
- 升级层可把同组实例聚合成既有 SkillSource，再调用解析器；是否需要扩展显式组字段留给开发方案。不同来源的既有公式不在本稿中悄悄改变。
- 上限、同卡升阶、互斥组、冲突提示来自 UpgradeDefinition。等级是成长记录推导出的值，不直接把 AbilitySpec.Level 当作唯一账本。
- 同槽替换先决出 SkillId，再使用其兵种/槽位基础参数叠加修饰。沿用当前同优先级不同替换目标整笔拒绝规则，包括被更高优先级遮住的冲突，不依赖取得顺序“最后一张赢”。
- 数值范围和行为参数必须在候选阶段校验；不依靠 GM 覆盖或静默截断掩盖非法组合。

### 7.3 奖励选择需要联合事务

建议流程：`服务端生成有效选项 → 玩家提交选项及允许的目标 → 校验身份/对局/奖励状态 → 构建候选成长记录与全部受影响来源 → 解析校验 → 在执行域的提交边界整体提交 → 返回已生效版本`。陆军沿用固定步；僚机使用可靠配置投影及生效版本；Ship 本体使用装配/武器配置提交边界。

- 客户端不直接提交任意倍率、SkillId 或来源修改作为正式奖励结果；当前服务端命令桥不等于已有完整的奖励领取协议。
- 奖励消费、升级实例、解锁状态与所有受影响 Profile 必须一致提交。不能先扣奖励，再逐条 Upsert，失败时留半套升级。
- 同一次领取重发返回同一结果；另一份有效奖励才是新的取得实例。解析失败不消费奖励、不改变旧状态。
- 当前来源账本可早于固定步 Profile 提交更新；未来必须区分“已接受/待提交”和“已生效”。UI以提交回执和版本为准。
- 跨世界、旧 MatchEpoch、过期指挥官、无权控制该空中配装的玩家或重复选择请求不得产生新的成长修改。
- 首版一份奖励只作用于一个 OwnerKey、一个 Domain，可在该范围影响多个明确绑定。不加入同时修改多名玩家、陆军和空中域的跨域奖励事务；未来有这类奖励时再补协调提交合同，不能假设地面固定步与客户端僚机 tick 是同一条时间线。

## 8. 升级、换装与生命周期规则（建议默认值）

### 8.1 单通道运行变化

| 变化 | 建议处理 |
|---|---|
| 只改伤害/射程 | 保留该槽射击节奏；目标仍需按新范围验证。不重置其他槽 |
| 改攻速 | 沿用当前剩余冷却比例换算；0 攻速保留暂停比例，不通过升级赠送额外一发 |
| 同槽替换 SkillId/ExecutorId | 自动通道清目标、等待新技能完整射击间隔，只处理此槽；若旧剩余冷却更长则不缩短。共享齐射保留组剩余冷却；替换为新主动武器至少等待其配置的换装准备时间，首版建议为完整冷却 |
| 解锁新增槽 | 自动通道新建状态并等待完整间隔；主动槽按初次就绪策略处理，首版新解锁建议等待完整冷却。共享组若有更长剩余冷却则继续受其约束；不重置已有槽 |
| 撤销解锁来源 | 重算是否仍有其他来源维持解锁；确实锁回时移除可执行状态，但保留同生命必要的剩余冷却约束。再次解锁按新启用处理，并受未结束的旧冷却限制 |
| 指挥官换任/新对局 | 同队换任重建入口并保留本局成长；新 MatchEpoch 清除旧局记录与运行引用 |
| 僚机死亡/补充 | 只移除死去成员的执行状态；成长/Profile 保留。新身份成员读取当前通道集合，自动武器按新成员策略就绪；首版建议等待完整间隔 |
| Ship 重生 | 同一空中成长所有者恢复配装和成长，创建新 ASC/组/成员；当前生命的目标、预测请求和临时效果不迁移 |
| Ship 本体同挂点换部件 | 绑定保留，执行组件可重建；同生命的剩余冷却按上述换装规则迁移，其他挂点不重置 |

移除成长解锁与战斗中的临时沉默/缴械是不同操作，不共用一条“删槽再加回”逻辑。后者若需要，应另行定义暂停、禁用和恢复规则。

以上“完整间隔/准备时间”是新增或替换通道的建议。首轮迁移现有默认机枪、导弹时保持既有首次就绪行为；改变已有出生体验需要另列产品选择。换装期间已经服务端接受的攻击不因撤销 GA 被追溯删除。

### 8.2 空中成长与冷却的存续

空中成长存储在 Pawn 之外的本局记录，PlayerState 可持有配装恢复引用/视图；只有该玩家在有效 Air 身份下才挂接当前 Ship ASC。角色切换、零存活僚机、租约移交不会把成长转给执行模拟的客户端或新占位玩家。

建议首轮保留现有 Ship 重生时清理战斗冷却的行为，只新增配装/成长恢复；这是与同生命换装保留冷却不同的规则。若产品要求防止死亡/切角色刷新齐射，应将共享冷却截止时间另存至空中成长所有者的本局运行记录。这个选择在第 12 节确认，不能把“成长保留”自动解释成“所有冷却保留”。

### 8.3 已发出攻击与后续效果

各域接入已有或新增投射物、持续效果和触发词条时，需要遵守以下契约：

- 默认在发射/创建效果时保存必要参数和来源版本，后续升级不追溯改写已发出的攻击；需要命中时动态取值的属性必须明确标注。
- 命中触发需要来源槽位、根事件/链深度等上下文；默认派生触发不再次触发同类链，例外需显式规则和上限，避免分裂/命中相互递归。
- 附加效果配置与目标身上的持续运行状态分开；不能把数百个目标的燃烧计时器塞进共享 Profile 或指挥官 GA。
- 当前攻击可用性要求正伤害且按敌人选择目标。治疗、纯控制、光环等不只是换一个 Executor，还需要对应的触发、目标选择或状态处理路径；不列入首轮多武器改造。

僚机逻辑导弹和 Ship 本体弹丸已经存在；本次通道接入就要为它们记录发射时的 BindingKey、SkillId、ProfileRevision 和参数快照，不能把这项推迟到“以后有弹丸”时再做。组销毁/目标失效时是否结束既有弹丸沿用其生命周期合同，单纯升级或同生命换装不改写已发出伤害。

### 8.4 对局中的武器动态更换（用户明确要求）

玩家可以在对局运行中，把指定绑定切换为其已拥有/解锁且兼容的候选武器；自动和主动武器都通过同一配装请求入口校验。首版不附加“只能出生时换装”限制，候选获取、费用和特殊战斗限制若需要，由具体内容规则另行声明。

建议流程：`选择目标通道和候选 → 提交 RequestId / BindingKey / 目标 SkillId / ExpectedLoadoutRevision → 服务端校验权限、解锁、兼容和资源就绪 → 构建候选配装及最终 Profile → 在该域提交边界一次切换 → 返回新版本与已生效结果`。

- 普通换装不伪装成获取一份升级奖励，也不自动消耗奖励次数；若一次奖励同时解锁并装备武器，仍按第 7.3 节联合事务处理。
- 准备期间继续使用旧的完整有效配置；需要的运行定义和关键资源未准备好时等待或拒绝，不能先拆掉旧武器再尝试加载。资源预加载不进入逐兵/逐槽战斗循环。
- 同槽换装保持 BindingKey 与实体身份，只迁移该槽状态。服务器完成提交后，现存单位的后续攻击读取新配置，尚未生成/补充的单位读取最新局内配装；已发出攻击按 8.3 保留旧快照。
- UI 可先显示“请求中/准备中”，只有提交回执对应版本才显示“已生效”。客户端预测效果不得提前获得新武器权威伤害；尚未收到新配置的执行者按版本规则等待同步。
- 重复 RequestId 返回原结果；两个基于同一旧版本的冲突换装由服务端串行裁决，过期请求返回当前版本。迟到资源回调、旧角色、旧 Pawn、旧奖励选项不能覆盖后续已确认的配装。
- 卸装、再装备和撤销解锁要保留同生命必要的通道/共享组冷却约束；通过删除运行数组再新建，不能绕过 8.1 的等待与迁移规则。
- 同一僚机类型的换装默认影响该配装全部同型成员；逐架私人武器、只改指定 Flight 的配装不在首轮范围。未来若需要，增加明确的子编成身份，不能用临时选中集合替代稳定归属。

### 8.5 兵种的动态加入与更换

运行系统要支持局内启用新兵种/型号、建立其默认通道和成长记录、调整生成/补充编成，以及撤下当前编成；其 Profile 与通道集合通过版本提交进入执行和展示。重新启用本局已有类型时读取该类型已保存的配装/成长，不重新覆盖默认武器。

兵种切换会改变 SubjectId，因此切到另一兵种时读取另一套绑定。原兵种的专属升级保留，重新使用原兵种时恢复；不把 A 的成长复制给 B。明确声明作用于多个类型的奖励按选择器重新解析。

“让现存士兵或僚机立即变成另一型号”涉及生命值、成员身份、编队容量、碰撞/移动参数和模型迁移，不能作为普通武器换装的副作用。草案保留两种可选应用范围：仅影响随后生成/补充的单位，或通过专门的在场单位替换事务即时更换。后者需要单列保留/重建身份、生命迁移与旧请求失效规则；第 12 节确认之前不擅自选择。武器局内动态更换已是明确要求，不依赖这个选择。

## 9. 若采用 x+y 个 GAS 入口，必须遵守的约束

本节保留陆军方案 B 的约束；绑定、同类多 Spec、冷却隔离和事件路由原则同样适用于 Ship。Owner/Avatar 与换任流程按各自 ASC 的实际生命周期接入。

1. 用 `BindingKey → SpecHandle` 精确激活/撤销；同一个 GA 类可授予多个 Spec，不能用按类查找代替槽位身份。UE 5.7 的 `FindAbilitySpecFromClass` 只返回第一个匹配项。
2. GA 类默认对象是共享定义，不把某兵种本局倍率写进 CDO。可用有明确持有方的绑定对象作为 SourceObject 或使用独立映射；SourceObject 是弱引用，设置它不等于自动完成对象生命周期、网络复制或持久化。
3. 默认 GA 冷却依据 ASC 拥有的标签检查。同 ASC 上使用相同冷却标签会相互阻塞，不会因为 SpecHandle/SourceObject 不同而自动隔离。必须明确独立绑定冷却还是共享冷却组。
4. 同理，把 Damage 等属性放到指挥官 AttributeSet，不会自动产生按 UnitTypeId/SlotId 隔离的动态属性表。GE 标签和 SetByCaller 也不会自动替代兵种技能目标解析；军队最终数值仍以解析层为准。
5. 自动武器 GA 可以只处理启用/停用、事件或命令，不承担每兵每发射击；若复用 GameplayEvent，必须按绑定路由，避免多个 Spec 响应同一个泛化事件而全部误触发。
6. 指挥官离任/角色切换时清理入口，新任从 Team 记录重建映射；不会以 GA 对象或旧 SpecHandle 作为成长存续条件。共享军队冷却若要求继承，也从权威军队状态恢复。
7. 现有 Army AbilityActorInfo 的 Owner/Avatar 都是 PlayerState。引入需要 Pawn、动画、目标数据或客户端预测的主动能力时要专门接入，不能假设当前桥接 GA 已提供整套战术施法流程。
