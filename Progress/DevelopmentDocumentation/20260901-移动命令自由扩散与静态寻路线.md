# 移动命令自由扩散与静态寻路线 — 技术方案

- 对应需求：[移动命令自由扩散与静态寻路线](../RequirementDocument/20260901-移动命令自由扩散与静态寻路线.md)

## 技术选型

采用“确定性六角候选池 → scratch预约协调 → cohort软锚分配 → 共享路径/拆组/单兵降级 → 固定步原子提交”。固定5×5终点不再参与合法性裁决；`ControlCohort`只保留为最多25人的协议与路由单位。候选按距点击点由近到远生成，因此玩家点击语义优先；9000cm软锚和匈牙利匹配只减少同组离散与交叉，不向玩法层承诺阵型。

终点候选使用1800cm世界轴固定六角格和45000cm圆形上限。先做范围、空间哈希和已知预约等低成本过滤，再查询Landscape高度与`CommanderSoldier` NavMesh。单次请求内按量化格坐标和导航代次缓存投影/连通结果，避免重复查询；每帧限制64次投影和4次路径查询，保证规划工作能跨帧推进且仍保持确定性。固定候选总量代替墙钟超时，避免不同机器因帧耗时不同得到不同结果。

预约先在scratch状态求解。本次所有Eligible成员的旧预约暂时释放，未选友军保持硬预约，敌军忽略。失败成员恢复旧预约后如果压住暂定新槽，受影响单位继续向外重配，直到预约稳定或候选耗尽。准备完成前不改`ActiveOrderId`、Formation、选择和复制端点；Pending单位继续执行旧命令。

路径继续优先共享以控制大规模查询量。每组以实际起点和终点medoid构建共享长路径，并校验成员连接段；失败时沿终点包围盒最长轴稳定二分为内部Formation，最后降级为单兵完整路径。失败的“成员—候选”配对进入本任务黑名单，再尝试更外候选，不因为一条路径失败直接否定整个cohort。

协议升级到v6，回执在cohort内表达单兵Eligible和Accepted掩码。移动结果至少一人成功才分配非零批次；提交时一次性从选择中移除失败成员，并通过OwnerOnly终点FastArray复制实际起止点。终点线不塞进ACK或10Hz姿态流，客户端使用复制端点绘制1px静态绿线。

不使用固定5×5回退，因为它正是中心或单槽失败导致整组拒绝的来源；不为所有单位一开始就计算独立长路径，因为500兵会放大NavMesh查询尖峰；不引入DetourCrowd、ORCA或流场，因为本次问题可在现有导航、Mass避让和协议边界内闭环。

## 公共接口与状态约定

- `GULI_COMMANDER_PROTOCOL_VERSION`：`5 → 6`；v5与v6不能混接。
- `FGuLiCohortCommandAck`新增`MemberCount`、`EligibleMemberMask`、`AcceptedMemberMask`。位序绑定服务器受理移动时冻结的该cohort `MemberIds`，最多25位；反序列化与`Sanitize`清除`MemberCount`之外的高位，并保证`Accepted ⊆ Eligible`。
- cohort结果：`AcceptedMemberMask == EligibleMemberMask != 0`为`Accepted`；Accepted为非空真子集时为`PartiallyAccepted`；Eligible非空但Accepted为空为`PathFailed`；Eligible为空为`NoSelection`。
- 总体结果聚合全部cohort：至少一人成功才分配非零`BatchOrderId`；存在成功与失败为`PartiallyAccepted`；无人成功保持0。
- `ServerSelectionRevision`指向提交后选择。规划型失败成员从选择中移除；整单系统拒绝保持原选择和版本。
- `FGuLiMoveEndpointFastArray`为OwnerOnly可靠状态，每项包含`SoldierId`、`ActiveOrderId`、`AuthoritativeStart`、`FinalDestination`和`Revision`。同一Soldier只保留当前活动指令项；到达、Blocked、死亡、换局和改令负责移除或替换。
- `TryGetLastMovePlanningDebug`及`gs.GM.Commander.Nav.LastMove [CohortId]`只在服务器非Shipping环境提供；调试数据不进入游戏协议或持久化存档。

## 规划与提交状态机

1. **创建任务**：校验身份、战局、请求格式和选择版本，冻结cohort成员顺序、请求目标及NavMesh代次。重复的同ID同内容请求关联已有Pending任务。
2. **候选投影**：按距离/六角坐标消费最多2263个候选；每帧最多64次Nav投影。记录修正量、去重、半径、硬预约和失败原因统计。
3. **槽位分配**：按中心优先从合法池分配，cohort软锚保持局部集中，组内匈牙利匹配成员。所有本批旧预约在scratch中释放。
4. **路由验证**：每帧最多4次路径查询；共享路径失败后稳定二分，再降级单兵。失败配对黑名单后回到槽位分配，不复用过期结果。
5. **预约协调**：给失败成员恢复旧预约；若与暂定新槽冲突，稳定撤销受影响分配并继续外扩，直至状态不再变化或候选耗尽。
6. **提交前复核**：重新读取存活、阵营、权威位置、选择依赖与NavMesh代次。可恢复的起点变化重做连接/路由；权限、换局和连接代次失效直接取消。
7. **固定步提交**：下一次30Hz权威步一次写入成功成员的新批次、Formation、最终槽、选择和终点FastArray；生成可靠最终ACK。任何阶段都不得暴露半套scratch状态。

## UI与诊断规则

- Pending继续显示现有橙色反馈；整单无人成功时显示短暂红色反馈。
- 收到权威终点后，不再播放“选择中心→点击点”的Accepted流水动画。每名当前仍被选中、存活且`ActiveOrderId`匹配的成功单位绘制一条起点到最终槽的绿色1px静态直线。
- 绿线无流动、箭头、脉冲、标签、淡入或淡出。改选、改令、到达、Blocked、死亡和网络重置立即隐藏；视锥外、投影失败或屏幕长度不足2px时不提交绘制。
- 最终Warning按命令汇总：目标、cohort、Eligible/Accepted掩码、候选/投影/路径计数、最远搜索半径和首要失败阶段。单候选失败只累计计数，避免日志洪泛。
- `Nav.Stats`增加Pending任务、候选投影、路径查询、部分接受及按失败阶段计数；`Nav.LastMove`输出最近规划的成员/槽位/冲突/拆分/耗时明细。

## 风险与备忘

- 450m圆内候选、Nav投影与寻路查询量较大，必须保持硬预算、请求内缓存和低成本过滤顺序；不能把分帧规划重新变成单帧全量循环。
- 单兵部分接受会改变ACK和选择版本语义。服务端、客户端与序列化必须同批升级，任何v5混接都应在握手阶段拒绝。
- 失败单位恢复旧预约可能使先前暂定的新槽失效，预约协调必须迭代至稳定，且使用ID/候选序保证结果不依赖容器遍历顺序。
- 路径查询结果只能在对应战局、NavMesh代次、成员状态和起点仍有效时提交；异步准备不能绕过最终权威复核。
- 终点FastArray是可靠OwnerOnly状态，不保证先于ACK到达。客户端必须按`ActiveOrderId`和版本暂存/消费，不能用到达顺序推断因果。
- 默认Game/Editor地图已改为`/Game/Maps/LVL_CommanderMassPrototype`。`LVL_Main`和`LVL_ShipTest`仍配置旧Ship GameMode，其中`LVL_ShipTest`没有本需求所需Landscape和Commander导航数据；二者不能作为本轮默认冒烟地图。
- 默认地图无头冒烟只覆盖500兵生成及其中20兵的一次命令链，不等同于25/250/500交互PIE、双客户端或完整性能验收。
- NavMesh动态重建已实现分帧预算，但尚未以500个活动单位实测重建峰值；该项不能仅凭源码和自动化判定性能达标。
- Launcher版引擎不支持Server Target；Dedicated Server和双客户端尚未完成。静态绿线已通过源码与自动化检查，但500条线的运行绘制耗时尚未采样。
