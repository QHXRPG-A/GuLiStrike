# 交火优化正式版本交付

用户先要求采用16.22ms、P95 26.39ms版本，替换实验代码、清理会话临时文件并上传GitHub，然后再处理响应目标；随后明确让助手权衡16.23ms、P95 26.01ms候选。当前目标仅为指挥官点击到绿线与全部受令本机Mass单位实际起步、模型提交严格小于20ms。15ms整帧指标保留为历史背景，不再作为当前推进目标。

## 版本取舍

`pair-61-fast-compression`在同一build-41下关闭Trace和阶段日志，采用600初始单位、2359×1748视口、133.4米相机、固定3600逻辑步起点、30秒采样；两组逐帧确认游戏前台、编辑器最小化。

| 指标 | 标准压缩 | 快速小消息压缩 |
|---|---:|---:|
| 平均帧间隔 | 16.2188ms | 16.2310ms |
| P95 | 26.3908ms | 26.0135ms |
| 完整帧间隔数量 | 1849 | 1848 |
| 事务worker累计计时 | 20.052秒 | 18.596秒 |
| 发送数据 | 47,564,524字节 | 51,150,905字节 |
| 接纳逻辑步 | 1800 | 1800 |
| 完成位移的受测成员 | 48 | 48 |

平均差0.0122ms基本持平；P95约改善1.43%，仅一轮，不能据此承诺稳定收益。worker计时下降约7.26%，发送字节增加约7.54%（该窗口约120KB/s），编码失败、发送失败、接收队列溢出、控制连接中断均为0。另两次带Trace诊断中单次压缩75.85→51.61微秒，支持压缩工作减少；真实战斗历史不同，不把所有差值归因于压缩。worker计时含调度因素，不能当作纯CPU指令执行时间，也不能与主线程、GPU相加。

选择快速压缩是为降低事务线程的CPU工作及后续排队压力，保留`gs.Hybrid.FastSmallPayloadCompression=0`独立回退。默认1在客户端建立时锁定，同步到所属逻辑客户端。可靠消息正文≤64KiB使用zlib低压缩级别；更大正文仍使用标准级别。压缩无损，完整身份、解码尺寸、字典复位、校验、分片、队列字节预算、发送与应用顺序保持。
