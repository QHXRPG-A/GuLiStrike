# 《星际争霸 II》部队操作在 GuLiStrike 中的实现难度评估

评估日期：2026-09-20。关联读物：[星际争霸 II 部队操作拆解](星际争霸II部队操作拆解.md)。

**建议先做选兵减选、镜头定位、数字编队和基础停止，再做玩家攻击移动与混编施法。** 当前最难的部分是完整命令队列、指定目标追击、自由装卸部队，以及大量单位在拥堵、接敌和连续改令时仍然顺畅。难度主要来自这些行为之间的相互影响。

本评估以当前工作区的 C++、配置和资产生成脚本为依据，包含尚未提交的项目改动。它是静态代码审阅，未运行本轮游戏体验、联机或性能验收；“已有”表示找到了实现路径，不表示本次重新验证通过。原拆解中的 SC2 待验证细节继续保留，不能作为已确定的项目规则。

难度分级均为【评估】，不是工期承诺：**低**表示能在现有交互或表现层局部补齐；**中**表示需要贯通输入、服务器校验和反馈；**高**表示要补充持续任务、跨系统状态或失效处理；**很高**表示还要在大规模、联机和复杂地形下持续打磨体验。各项共享基础工作，不能把等级简单相加换算成天数。

## 一、哪些基础已经具备

以下为【代码事实】。代码入口列在文末，文件中的函数名可用于再次定位。

| 已有基础 | 代码证据 | 对难度的实际影响 |
|---|---|---|
| 点选、框选、范围选、同类选、追加选 | `FGuLiSelectionRequest`、`ResolveCandidates`、`CombineMembership`；[K1][k1]、[K2][k2]、[K3][k3] | 选兵无需整体重做。`Toggle` 已有内部实现，但玩家 Shift 当前传的是纯 `Add` |
| 稳定单位身份与服务器选择版本 | `SoldierId`、`ActorIds`、`SelectionRevision`；[K1][k1] | 可以作为数字编队的基础；当前请求只支持空间选取等意图，不能直接召回任意保存的成员集合 |
| 普通移动的规划、执行和反馈 | `BeginMovePlanning`、终点预约、逐兵到达/失败、命令 ACK；[K4][k4]、[K5][k5] | 移动和部分失败已有基础；停止、排队与连续改令必须接上现有生命周期 |
| 自动寻敌与射击 | `CollectChannelAttacks`、射程筛选、目标保留、冷却；[K6][k6] | 指定目标攻击可复用武器执行，但玩家指定目标、追击和目标丢失的处理仍需补充 |
| 自动出兵使用的攻击移动 | `RegisterBatch` → `IssueAttackMove`，以及 `bAttackMoveHolding`；[K4][k4]、[K7][k7] | 有遇敌停下射击的基础，但接口要求自动推进单位且有单组容量约束，不能直接当作玩家 A 移动 |
| 选中单位技能与逐兵结果 | `ActivateSelectedUnits` → `ExecuteSelectedUnitSkills`；[K8][k8]、[K4][k4] | 已有服务器施法与冷却；现有命令按每名已选士兵自身技能尝试执行，尚不是“当前子组施法”或“自动挑一个施法者” |
| 镜头跳转、选中圈、血条、命令反馈 | `JumpToWorldLocation`、HUD、Presentation；[K10][k10]、[K11][k11]、[K12][k12] | 镜头书签和已有状态的提示相对容易；完整队列路径要先有真实队列状态 |
| 群体路径与避让 | 弹性通行列、个人路径恢复、分离与避让、终点分配；[K4][k4]、[K13][k13] | 已有大量移动基础；进一步达到稳定接敌、让路和快速微操，属于系统打磨，不能视为从零，也不能视为已经完成 |
| 工程车据点运输、外部单位控制 | `UGuLiEngineeringTravelComponent`、外部控制和相位状态；[K14][k14]、[K4][k4] | 存在离场/恢复与落位的相关能力，但工程车沿据点网络运输，与运输机承载多个士兵是不同任务 |

当前的 `ControlCohort` 是最多 25 人的内部临时集合，不是玩家的数字编队。当前网络中的 `MovesAwaitingSelection` 是等待选兵确认的请求缓存，也不是按到达顺序执行的 Shift 任务队列。两者最容易被误判为“已经有了”。

## 二、逐项难度与最小可用范围

下表的“最小可用”是建议的 GuLiStrike 范围，不宣称完整复刻 SC2。全部结论为【评估】，已有实现的依据见第一节与代码入口。

| 操作 | 最小可用难度 | 可以先做到什么 | 做完整后增加的工作 |
|---|---|---|---|
| 点选减选、选择数量和状态提示 | **低** | 给点选提供明确的移除/切换入口，复用内部集合运算 | 同屏框选、头像操作与修饰键统一后为中；不能把 `Toggle` 当作任意场景下的“只删除”，也不能未经设计就改变现有 Shift 纯追加 |
| 双击同类、当前屏幕内同类选择 | **中** | 双击识别和明确的屏幕作用域 | 当前 `SameType` 按全图同类、距离和上限选取；屏幕范围要进入服务器规则，不能只在客户端显示筛选结果 |
| 一键全军选择 | **中** | 选取本阵营可指挥的存活战斗单位 | 需要新增对应选兵意图，明确工程车、相位单位和多线部队的边界；现有全图同类选择不能代替全军选择 |
| 点击兵种卡筛选、头像移除 | **中** | 先做按兵种聚合的可交互卡片 | 当前主要是单张汇总卡；逐兵头像还涉及排序、滚动、伤亡更新和大量单位下的刷新成本，完整形态为中至高 |
| 镜头跳到所选单位、镜头书签 | **低** | 复用本地镜头跳转，保存/恢复位置 | 分散选择的落点、空组、远近缩放需要明确。数字编队双击定位还依赖编队功能；无限远跟随与自动构图另外评估 |
| 数字编队创建、覆盖、召回 | **中** | 保存稳定单位身份，召回时由服务器过滤有效成员 | 要支持 Mass 士兵与 Actor 单位、选择确认时序、换局清理、死亡成员和现有按键冲突。仅保存当前 `CohortId` 不够 |
| 编队追加、从其他编队移出 | **中**，依赖数字编队 | 在编队成员集合上做并集、差集；增援手动追加 | 重叠组、空组、成员离场和恢复的规则。完成编队基础后，这部分新增算法负担较小 |
| 现有移动的光标、接令/拒绝提示 | **低** | 完善已存在的 Pending、Accepted、Rejected 状态展示 | 区分到达与接令、部分成功、逐兵原因后为中。声音反馈仍有素材和重复播放控制成本 |
| 普通停止 S | **中** | 所选单位停止当前移动，允许既有自动射击 | 必须处理尚未提交的规划、旧队形引用、目标预约和迟到结果。`StopAutomaticMove` 仅处理自动推进单位，不能直接充当通用 S |
| 坚守 H | **中至高** | 保持当前位置，允许射程内自动攻击 | 需要独立且可持续的坚守规则，说明是否接受友军推动、外部搬运和技能位移；未来有追击时，要保证不会自行追出位置 |
| 玩家攻击移动 A 地板 | **中至高** | 移向地面点，遇到可攻击敌人时暂停前进，目标不再可打后继续 | 自动出兵逻辑与手动命令的归属要分开；完整接敌追击、返回路径、不同射程、部分单位被阻塞时为高 |
| 指定目标攻击与集火 | **中**仅限射程内优先目标；完整功能**高** | 先允许合法、射程内目标成为优先攻击对象 | “走过去打”需要持续追踪、接近位置、路径更新、死亡/不可达回退和命令打断；点击目标不等于全队都有可开火位置 |
| 巡逻 | **中**，依赖移动完成事件 | 两个明确地面点间往返 | 接敌中断再恢复、普通命令替换和局部路径失败后为中至高。先有可靠的任务完成规则再做 |
| 跟随 | **中至高** | 跟随一个合法友军，保持约定间距 | 移动目标反复改路、集体挤占、目标死亡/离场与战斗行为；大量单位追随同一目标不能每帧各自完整寻路 |
| Shift 多段纯移动 | **中至高** | 每个接令单位按序走地面点，普通命令覆盖剩余路线 | 要定义逐兵还是整队到达后前进、失败怎么推进、选中子集如何改令，并改造当前会合并后续点击的接令缓存 |
| 移动→攻击→技能→装载的混合队列 | **高** | 在基础任务队列之后逐类接入 | 不同完成条件、无限持续任务、目标消失、重复请求、取消与恢复组合起来，远多于“存一个数组” |
| Tab 子组与按子组批量施法 | **中** | 保留整队选择，独立切换当前兵种子组，仅给该子组施法 | 当前技能请求没有子组条件；必须让服务器解析并校验执行范围，不能只改变按钮后仍对全体施法 |
| 智能单体施法、自动施法 | **中**仅限明确受限规则；通用版**高** | 在当前子组中选一个已就绪、在射程内的施法者；或为一个技能加开关与固定触发条件 | 自动走入射程、重复施法去重、忙碌与队列优先级、目标预留、资源分配；现有自动武器射击不能直接替代这些规则 |
| 形态切换 | **中**仅限属性/外观切换；完整功能**高** | 一个兵种在稳定身份下切换明确的属性和表现 | 体积、导航、可移动性、武器、技能、选择子组同时改变时，要处理切换期间受令、中断、死亡和落位 |
| 装载、运输、卸载 | **高** | 一个运输载体、明确容量与固定卸载规则 | 需要乘员身份、容量占用、装载接近、离地面状态、死亡结算、卸载合法落点与失败恢复；工程车据点运输不能直接等同于载兵 |
| 手动散兵、抽出残血兵撤退 | **低至中** | 借助精确子集选择和已有移动分开下令 | 效果受当前路径、终点分配与选择响应影响；一键自动散开或自动救兵已经增加了新的策略行为，难度为高 |
| 基础窄口通行 | **已有机制；具体规模待验证** | 复用共享路径、1–5 列收窄、局部避让和受阻恢复 | 先确认通道的导航连通性、单位体型和出口空间；没有证据表明需要整体重写，实际缺陷的增量难度按复现结果判断 |
| 密集混行、双向会车、接敌展开与主动让路 | **高至很高** | 在已有通行能力上，针对可重现的拥堵改善协调与效率 | 不同体型/速度、友敌阻挡、坚守、快速换向、多个部队交叉时要共同成立；这是复杂场景的稳定性与体验成本，不表示当前无法穿过窄口 |
| 接近 SC2 的拉扯与连续改令手感 | **很高** | 先定义本项目移动射击规则，再测输入到执行的各段延迟 | 攻击时序、移动起停、规划预算、服务器节拍、网络和客户端显示都参与。可先获得明确响应，但完整体验无法只靠快捷键或调高一个频率完成 |

## 三、最容易低估的六个问题

### 1. 数字编队的集合操作简单，可靠召回要贯通服务器

【代码事实】现在选兵请求表达点、框、范围或同类，最终成员由服务器解析；稳定 `SoldierId` 和 `ActorIds` 已经存在。服务器临时分组可能随着选择改变重新形成。[K1][k1]、[K2][k2]。

【评估】编队基础应保存稳定成员身份，不能保存一批会变化的临时组号。具体可以采用“本地保存、服务器校验召回”或“服务器保存、按组号召回”，后续按网络要求选一种即可；本次不指定新接口。难点是召回时成员已死亡、另一条选择尚未确认、同时发出移动等时序。

【代码事实】现有输入绑定和生成脚本使用数字键 1–6 执行动作/建造选择、7 切换选兵工具。直接照搬数字编队会发生冲突。[K3][k3]、[K15][k15]。这是先要解决的交互分配问题；脚本配置也不等于本次已检查所有生成资产的实际键位。

### 2. 当前攻击移动有可复用部分，但服务的是自动推进

【代码事实】`IssueAttackMove` 仅接受 `bAutomaticAdvance` 单位，单次数量受内部组容量限制，采用自己的目标投影和路径生成。普通手动移动提交会清除 `bAutomaticAdvance` 与 `bAttackMoveHolding`；自动推进子系统会剔除不再自动推进的成员。[K4][k4]、[K7][k7]。

【评估】玩家 A 移动要成为明确的手动任务，不能简单把选中士兵重新标为自动出兵，否则其后可能再次受自动目标决策影响。可复用的是寻敌、战斗暂停和移动执行等部分；需要补的是手动命令归属、规划接入、覆盖、中断和完成规则。

【代码事实】当前 `CollectChannelAttacks` 不使用 `bHasMoveOrder` 来禁止自动射击，射程检查主要围绕存活、阵营和距离。[K6][k6]。因此本轮静态代码不支持“普通移动必定停止攻击”的假设。

【评估】设计 M/A 时先决定：普通移动是否允许开火、A 是否停步、离开射程是否追击。若移动仍可自动射击，M 与 A 的主要差异可以是是否主动停步接敌，但必须在提示中说清楚。拉扯价值也要按这套规则重新判断。

### 3. 停止与坚守，需要表达不同的持续承诺

【代码事实】已有 `StopAutomaticMove` 仅停止自动推进者，手动移动规划、活动队形和终点状态分布在权威子系统中。当前普通射击循环也没有“为射程外敌人发起追击路径”的职责。[K4][k4]、[K6][k6]。

【评估】基础 S 应能取消当前动作和适用的待提交改令，之后进入项目定义的空闲行为；H 应持续约束离位。若尚无空闲追击、两者又同样不让路，那么 S/H 可能表现得几乎一样。先定义实际差异，再决定是否同时开放两个按钮。

最容易遗漏的情况是：玩家按 S 时移动仍在规划，随后旧规划提交，单位又走起来。只把当前速度设成零不足以完成停止功能。

### 4. 网络排队和单位任务排队，等待的是不同事件

【代码事实】`MovesAwaitingSelection` 按选择依赖保存移动请求；`DeferredMoveAfterCurrentAck` 保存等待上一条回执后的移动。相同依赖下的新点击可以替换缓存。它们等待的是 ACK/选择副本，不是“单位已经到达”。`FGuLiMassOrderFragment` 目前保存当前活动指令。[K5][k5]、[K16][k16]。

【评估】Shift 队列至少要补齐：

- 发令时冻结谁收到哪些后续任务，之后换选兵不会改变这些任务。
- 每一种任务如何成功、失败、取消，哪些任务必须由玩家改令才能结束。
- 普通命令覆盖哪些成员的余下任务；停止如何使迟到的规划与回执失效。
- 一部分单位先到达、阵亡或被阻挡时，其他单位是否继续。

建议先做纯地面移动队列，再接巡逻与其他任务。不能仅在客户端连续发送几个现有移动请求来模拟完整队列。

### 5. 智能施法的困难在“谁执行”和“执行前需要做什么”

【代码事实】单位技能请求携带选择版本和地面目标，空 `GlobalSkillId` 表示对确认选择中的士兵逐个使用其自身技能；没有当前子组、指定一个施法者或排队施法字段。[K8][k8]、[K9][k9]。

【评估】先实现 Tab 切换兵种子组和子组批量施法，成本相对可控。再做“从已经在射程内且冷却就绪者中，按稳定规则选一个”的单体施法。若要求某个施法者自动接近目标、等待资源、插入原队列并避免多个单位浪费技能，就已进入持续任务系统。

原 SC2 拆解里智能施法的精确排序仍有待验证项；GuLiStrike 应制定可解释的自身规则，不把未确认的排序当实现标准。

### 6. 群体移动与微操手感，需要按实际规模验证

**补充澄清：现有算法已经实现基础窄口通行机制。“高至很高”指密集混行和复杂干扰下的稳定表现，不是对当前算法作出“实现不了”的判断。**

【代码事实】`DetermineTransitFormationColumns` 根据导航探测在 5–1 列间选择通行宽度；`UpdateTransitColumnHysteresis` 立即收窄，扩宽则等待连续成功与重排间隔。逐兵无进展后可进入中心线恢复、个人路径恢复，最终失败者进入 `Blocked`。这些逻辑已经进入权威移动执行路径。[K4][k4]、[K13][k13]。探测全部失败时返回单列只是回退选择，不能使原本不连通或体型无法通过的通道变得可走。

【历史实测】[2026-09-16 避让修复归档](../../../Archive/20260916-据点矿厂落点与Detour避让卡顿修复.md)记录了 1200 单位、单客/双客各三轮持续移动，以及既定窗口内的移动人数与帧成本结果。这证明已有规模移动基础；该归档明确未覆盖所有地形和长时间拥堵，不能把它外推为 1200 单位同时通过同一窄口已经验收。

【评估】现有收窄解决“队形如何适应通道”，局部避让解决邻近冲突，终点预约解决落点争抢；这些能力还不足以直接保证多队抢同一入口、两端对向进入、出口停兵或接敌堵口都能自动协调顺畅。现有分离主要通过速度修正实现，也不能据此承诺单位绝不重叠。应先定位具体场景是路径不通、入口拥堵、出口占位，还是密集计算成本，再决定是否补通行次序、让路或约束；当前没有整体替换寻路算法的依据。

【代码事实】现有移动有共享路径、逐兵进展、收窄、恢复和预约等逻辑。模拟基准为 10 Hz；当前配置中的插值基础回看时间为 0.12 秒，最大自适应回看为 0.35 秒。这些是源码/配置值，不是本轮测得的输入延迟。生产 Controller 路径未找到 `BeginPredictedMove` 的调用；预测函数保留在表现类中。[K4][k4]、[K12][k12]、[K13][k13]、[K17][k17]、[K18][k18]。

【评估】小地图或镜头快捷键的改善，不能解决单位起步晚；本地立即亮一个目标标记，也不能证明服务器已经改令。需要分别观察：输入被识别、请求被接收、规划完成、单位实际移动、客户端显示移动。

接敌还会引入新的矛盾：最短路未必有开火位置，整齐队形未必能展开输出，刚停止射击的前排可能阻塞后排。提升频率、改变避让或恢复位置预测都有成本，应由测量决定。现有协议容量和历史场景记录，不能直接当作新功能在目标规模下已通过的证据。

## 四、建议分批顺序

以下为【建议】，尚未转为开发需求或承诺实现。各批以玩家能够完整使用的操作为边界。

| 顺序 | 建议内容 | 玩家获得的直接价值 | 进入下一批前应明确的边界 |
|---|---|---|---|
| 第一批：控制对象清楚 | 点选减选、镜头定位/书签、基础数字编队及增援追加、对应状态提示 | 可以稳定管理多支部队，减少重新框选和找部队的操作 | 数字键分配；编队召回的服务器校验；死亡/换局清理；保持现有移动不受换选影响 |
| 第二批：战术命令明确 | 通用停止；确定 M/A 与移动射击规则后开放玩家 A 移动；有实际差异时再开放 H | 能明确表达赶路、接敌、停止和守住位置 | 规划中的 S、新命令覆盖、自动出兵交接、部分接令失败；不先承诺完整追击 |
| 第三批：减少重复操作 | Tab 子组、子组批量施法、纯移动 Shift 队列 | 混编技能不误发，单位可按事先安排连续行进 | 技能实际执行范围与反馈一致；队列以到达/终止推进；子集改令不会取消其他单位任务 |
| 第四批：扩展持续任务 | 完整指定攻击与追击、巡逻、跟随、受限智能施法、按需扩大队列类型 | 部队能持续处理目标，降低反复点选负担 | 每类目标失效规则、回到原任务的规则、路径更新预算和混合类型兼容性 |
| 后续专项 | 通用运输装卸、改变导航的形态转换、复杂拥堵与高强度微操打磨 | 扩展战术深度与大规模体验 | 明确实际兵种、体型、地图、部队规模和联机条件；分别记录体验证据与性能证据 |

如果只选择一轮较小的实现，建议取第一批，加上第二批里的**通用停止**。数字编队虽不是最低成本，却能直接改善多线管理；群体寻路和完整混合队列不宜混在这一轮里。基础完成后，玩家 A 移动通常比运输系统更值得优先投入。

全军选择和可点击兵种卡可以在第一批基础上补充，但其优先级应低于可靠的编队召回，避免把所有操作都引向全军一起改令。

## 五、范围改变时，难度如何改变

| 范围选择 | 难度变化与原因 |
|---|---|
| 先只支持 Mass 战斗士兵 | 可减少工程车采矿、施工、据点运输任务与新命令的交互；混合选择中不适用者必须有明确反馈 |
| 先提供射程内优先攻击，不自动追击 | 可明显缩小指定攻击的工作量；产品名称与提示应准确表达“优先目标”，不能宣称完整点杀追击 |
| 单体施法只挑当前合法施法者，不自动走过去 | 可复用已有冷却与范围检查；没有合格施法者时反馈失败，不隐式生成未定义任务 |
| 形态变化保持碰撞体和移动方式 | 主要处理属性/表现与状态同步；如果改变可通过空间、导航类型或占位，升级为高难度 |
| 运输仅指既有工程车据点转运 | 可沿用已有运输模型；如果新增可移动载体及乘员列表，则是新的载兵系统 |
| 要求单位失去视野后停止获取精确目标位置 | 当前所审阅的士兵寻敌函数未包含视野过滤；需先确认项目视野/可见性合同并接入，不能只补一个“丢目标”分支 |
| 要求数千单位持续交叉改令仍有相同微操手感 | 需要在目标规模下重新测量接令、规划、路径、避让、网络和 UI；不能把协议选择容量当性能保证 |

【待验证】本轮未在运行中的关卡检查兵种速度/体型、生成后的所有输入资产、实际射击表现、网络延迟和拥堵复现。不同速度/体型的真实组合会改变最后两项群体体验的成本；现有源码只能确定涉及哪些系统，不能确定最终效果与工期。
