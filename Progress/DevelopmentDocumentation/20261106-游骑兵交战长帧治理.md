## 实现与不变条件

### 后台事务与主线程追赶

旧输入循环已有 2 ms 片段，但后续 `PollNetwork` 仍可一次连续计算百余笔事务；接收回调也可能直接进入事务计算。本轮将对端事务事实存入现有就绪队列，正式异步客户端统一调用 `PollNetwork(Now,4,.001)`。意图重试、待决请求、冻结的一轮重试、就绪对端事务、活动工作流重试和依赖已满足的结果分别按最多 4 项或约 1 ms 让出。每阶段保证至少尝试一项，单笔事务不可抢占，因此这不是整个维护函数的 1 ms 硬上限。

未处理身份保留在原队列/轮次中并继续唤醒；轮转游标避免持续新请求挤占旧请求，未访问请求不提前改写重试期限。保留原 2 ms 输入片段、业务权限和依赖校验、恢复路径、逻辑时钟、完整模拟步以及主线程输入/回执 FIFO。后台跨维护阶段的访问时机因让出而改变；不声称与旧版整批访问的墙钟顺序完全相同。没有限制每渲染帧可执行的模拟步，也没有丢步或丢事务。

涉及 `GuLiNetAsyncClient.h/.cpp`、`GuLiNetClient.h`、`GuLiNetPeerWork.cpp` 和 `GuLiHybridWorldSubsystem.cpp`。移除 `gs.Hybrid.NetworkRetryBatchLimit`、`gs.Hybrid.DeferPeerTransactions` 及异步配置旧字段；同步 Core 调用者仍可用零预算完整处理，其接口用于既有合同程序。`Scripts/Performance/diagnose_commander_response.py` 不再发送失效参数，旧入口说明同步更新。

### HUD 与首次命中特效

`GuLiGroundHUDWidget.cpp`、`GuLiGroundMapWidget.cpp` 新增 Tick、布局、插值、小地图、准星/射线、采样、阴影、轮廓、深度键、排序和写索引 Scope。热点是小地图地形缓存重建中的八方向画家排序。每个三角形原来的顶点和只计算一次，每个方向的点积深度只计算一次；排序比较器直接读取连续深度数据，结果写入已预留的索引空间。

保留原三角形精确求和、点积、比较符、排序算法和前一方向的输入排列，不改变相等深度的原有排序行为。64×64 网格、8 个方向、3000 cm 锚点、采样/阴影/轮廓公式、顶点/颜色/索引数量、准星射线及刷新时机不变；没有隔帧更新或异步展示旧地形。

中间版本重启后发现 `GuLiLinearFlight_Publish` 内首次命中的 `NS_Hit` 同步加载 48.746 ms。`GuLiGroundMechWeaponComponent.cpp::LoadConfiguration` 现在与原枪口资源一起预载配置中的 `BulletVfxId`、`ImpactVfxId`，沿用世界 VFX 注册表强引用缓存，仅可呈现端执行。资源、首次命中触发条件和效果保持；加载工作提前到武器准备期，不是删除该成本。最终重启后的首轮及后两轮计时窗均未再出现 `LoadObject`/`RequestCompile`。

### 渲染缓冲申请来源

源码引擎 `D3D12Buffer.cpp::CreateRHIBuffer` 增加 DebugName/OwnerName CPU Scope；`NiagaraRendererRibbons.cpp` 在普通网格和光追动态几何入口加入 SceneProxy 资源名。Development 默认的 Niagara Proxy 名称宏未开启，因此需单独补充此身份。没有更改 GPU 缓冲策略、特效资产、光追、材质或画质。

最终重启首轮最大缓冲申请为 **2.7168 ms**：`DynamicPrimitive → NS_MiningLaser_Optimized_GPU_All_ThreeTier → RibbonIndirectDrawBuffer → AllocatePoolResource → TryAllocateInternal → CreateNewPool`，其中新池创建 2.6386 ms。其余约 0.6–0.86 ms 的较大申请包括 `NiagaraRibbonIndexBuffer`、`RibbonSortedIndices`、`TangentsAndDistancesBuffer`、`MultiRibbonIndicesBuffer`、`RibbonLookupTableBuffer`、`SegmentsBuffer`，也落在该采矿激光的网格/光追收集链下。

业务资源为 VfxId=36，路径 `/Game/GuLiStrike/FX/Mining/NS_MiningLaser_Optimized_GPU_All_ThreeTier`；`GuLiMiningPresentationComponent::ApplyVisibleMining` 经模型的 `StartMiningAt/StopMining` 承担采矿束表现。另一个出生位置诊断窗观察到 `RayTracingDynamicVertexBuffer` 和 `DistanceFields.DFObjectDataUploadBuffer`，该窗不进入同场景性能对照。

原始用户采样的 24.6245 ms 上传阻塞属于 EditorPrimitives/PrePass 并行任务，但缺少资源身份，本轮没有复现。不能把本轮采矿激光直接认定为那次历史阻塞的资产，也不能声称已经修复全部 RHI 长帧。旧版对照还有一次 52.0056 ms 的 GameThread 同步等待，最终三轮没有出现；这个未复现事件同样不计为某项代码已证明消除的根因。

源码引擎两文件补丁为 `Scripts/Performance/engine-ground-buffer-tracing.patch`；已对当前引擎执行 `git apply --reverse --check`，成功。精确前后哈希在证据目录 `engine-source-before.json`、`niagara-source-before.json`、`engine-source-final.json`。
