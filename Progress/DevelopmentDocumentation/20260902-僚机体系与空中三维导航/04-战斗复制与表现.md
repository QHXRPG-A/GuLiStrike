# 僚机体系、空中三维导航与客户端校验转发 — 技术方案 · 战斗、复制与表现

<!-- guli-progress:split-content -->
## 7. 战斗、死亡与表现

### 7.1 本地索敌

- Client Owner使用已复制Commander Pose、Accepted Wingman/Ground Pose和Ship状态建立本地三维空间哈希。
- Acquire默认5Hz错峰；目标失效时立即运行。
- 排序：Enemy/Alive/Available/球形Range/本地LOS，然后DistanceSquared、TargetKind、StableId、Generation。
- 不运行服务器周期性TargetObservation生成器。
- 客户端候选只决定“想打谁”，不决定命中和伤害。

### 7.2 状态引用

`FGuLiSourceStateRef`为类型化Variant：

- Ship：`SourceGeneration + ShipCanonicalEpoch + ServerMoveRevision`
- Wingman/Ground：`GroupGeneration + FlightOrPartitionId + AuthorityEpoch + AcceptedSnapshotSequence`
- Commander：`SourceGeneration + ServerSimTick`

`FGuLiFireIntent`至少包含：

`SourceHandle, TargetHandle, SourceStateRef, OptionalClientSeenTargetRef, ClientFireTick, DomainFireSequence, WeaponAbilityId, WeaponDefinitionRevision, AbilitySetRevision, Aim, HitCandidate, ClientLOSPrediction`

`DomainFireSequence`在同一Source EntityGeneration内严格单调，跨Roster/Lease/重连不重置。Bootstrap/Transfer Baseline冻结LastConsumed高水位。

### 7.3 服务器事件驱动Fire验证

FireIntent到达时：

1. 以`MatchEpoch + SourceKind + StableId + EntityGeneration + DomainFireSequence`只读Find；若已有Reservation/终态，直接返回既有结果，不重复执行Gate或Damage。
2. 未命中时先做廉价Source身份、Generation和类型化状态存在检查；Wingman/Ground还必须匹配当前AuthorityEpoch/Lease且Availability=Active、Alive。旧Lease在此以StaleLease拒绝，不创建Reservation、不推进LastConsumed高水位。
3. 只有当前合法权威才原子FindOrReserve新的DomainFireSequence；并发重复只能共享同一Reservation。
4. 验证Source/Target类型化Ref和历史存在。
5. Source或Target属于ClientValidatedRelay时，其Accepted Snapshot Age均不超过Profile的CombatStateAge；Ship/Commander按各自类型化服务器状态Ref窗口校验。年龄在请求到达时即时计算，不等待下一次Watchdog。
6. Target必须Alive、Enemy、Available；Stale/Unavailable或状态过旧时不作为新目标。
7. 使用服务器持有的Ship/Commander/Accepted历史，在共同可验证时间附近检查球形距离和LOS；禁止向未来外推客户端状态。
8. 验证服务器冷却、武器配置、弹药和射速。
9. 通过后创建ShotId；Damage只由Damage Ledger提交一次。

同Lease历史窗口内较旧AcceptedSnapshot Ref可以合法，只要当前组仍Active且Ref未过期。旧Lease、Stale、Unavailable、Dead或历史过期全部拒绝。已接纳Shot/Projectile可以在Source随后Stale/换主后完成一次结算。

### 7.4 Damage Ledger

- 客户端不能提交Damage、HealthAfter、Death、Reward或Replenish。
- Ledger记录Source/Target、类型化StateRef、ShotId、DamageEventId、HealthBefore/After、CommitTime、幂等键和结果。
- 同一DamageEventId/DeathEventId/RewardEventId CommitCount必须为1。
- 致死DamageEvent稳定派生DeathEventId和RewardEventId，并分别进入有界幂等记录；`BeginServerEpoch`清理旧Epoch的Damage/Death/Reward域。
- Reward只通过可选窄Policy/Sink授予；未配置时明确记录`NotGranted/PolicyUnavailable`，不得回调旧ScoreUpdate或在Ledger中硬编码经济数值。
- Health<=0后服务器可靠提交Dead并更新Roster；迟到Candidate/Fire不得复活或继续伤害。
- Commander B↔B保持现有30HzCombat Phase。

### 7.5 Ship与Projectile

- `UGuLiCombatHealthComponent`为Ship提供服务器生命和OnRep。
- Ship移动继续CMC重演，不进入ClientValidatedRelay。
- `AGuLiStrikeProjectile`携带SourceHandle、SourceStateRef、Team、Damage、SweepRadius和ShotId。
- 服务器对已接纳Shot执行Segment/Sphere Sweep，命中Mass Wingman后进入统一Ledger；保留旧NPC分支。

### 7.6 权威表现

- Owner可立即播放可撤销Muzzle预测。
- Hit/Death/Reward只由服务器事件表现。
- 按连接维护有界、ACK/重试的Combat Presentation FastArray；EventId幂等，客户端只渲染一次。
- 预测被拒绝时淡出，不能残留命中或死亡表现。

## 8. 网络复制与远端重建

### 8.1 可靠流

`AGuLiWingmanStateReplicator` FastArray只承载：

- Group/Generation、RosterRevision和Required Masks；
- Member身份、Flight/Slot、Team；
- Health/MaxHealth、LifeState、StateRevision；
- Active/Pending Lease、AuthorityEpoch、Availability；
- ActiveLeaseState/Availability、PendingLeaseTransactionState、接管各Deadline和当前BaselineRevision/Hash；
- Bootstrap/Resume Baseline Revision和FireSequence高水位。
- TransferCommit冻结的Baseline Revision/Hash和FireSequence高水位。
- UploadRateGrant的RateClass、GrantRevision、EffectiveClientSimTick和ExpiryServerTime。
- GroupAbilityConfig的Ship/Group代次、AbilitySet/Definition/FormationCommand Revision、稳定AbilityId、Checksum和EffectiveClientSimTick。

Accepted Transform、Velocity、Quaternion、AcceptedSequence和FrameSequence不进入常规可靠FastArray，避免可靠队列承载连续运动。

### 8.2 不可靠流

- Client→Server：普通Flight Candidate、Atomic Batch Fragment、Heartbeat、FireIntent。
- Server→Owner：不可靠Acceptance/Reject/Rebase，以及可靠UploadRateGrant、Baseline/RevisedBaseline和Lease Transaction状态。
- Server→Observers：Accepted Pose Chunk。

`FGuLiAcceptedPoseChunk`按`GroupGeneration + FlightId + AuthorityEpoch + RosterRevision`同质分块，包含AcceptedSnapshotSequence、AcceptedServerTime、ClientSimTick、ValidatedPayloadHash、Anchor和成员样本。客户端只应用更新Sequence、已知Roster和当前GroupGeneration数据。

### 8.3 频率

| 对象/流 | 本地模拟 | 上行 | 服务端处理 | 下行 |
|---|---:|---:|---:|---:|
| Ship | 渲染/物理帧率 | SavedMove 20～30Hz | CMC重演15～30Hz | 沿用现有CMC |
| Wingman Cruise | Owner 30Hz | 每Flight 5Hz | 收包触发Validator/Store/Relay | 可见3D近5Hz、中/远≥2.5Hz；隐藏/图标1Hz |
| Wingman Combat/Hazard | Owner 30Hz | 每Flight 10Hz | 收包触发Validator/Store/Relay | 可见3D近10Hz、中5Hz、远≥2.5Hz；隐藏/图标1Hz |
| GroundMachine | Owner 30Hz | 5Hz/战斗10Hz | 收包触发 | 5～10Hz相关性 |
| Commander | 无客户端逻辑模拟 | 无 | 服务器30Hz | 现有10Hz Pose |
| Heartbeat | — | 1Hz | 1Hz Maintenance读取 | Lease离散事件可靠 |
| FireIntent | 客户端事件 | 按武器事件 | 收包触发Combat | Shot/Damage结果事件 |

### 8.4 远端表现

- Cruise使用约250ms插值缓冲，Combat/Hazard约150ms。
- 没有新Accepted Pose时，按最后Velocity/Rotation做最多500ms视觉外推。
- 外推只写Presentation Transform，不能进入目标、碰撞、FireIntent、Candidate或服务器状态。
- 500ms后记录`REMOTE_EXTRAPOLATION_ENDED`、停止外推并立即淡出；150ms内记录`REMOTE_HIDDEN_AFTER_EXTRAPOLATION`并完成隐藏。不得只冻结后继续显示；收到Stale/Unavailable可靠状态时立即隐藏。
- 只要三维模型仍可见，相关性调度的目标下行必须≥2.5Hz；1Hz仅用于已隐藏组或聚合图标。
- Resume后用首个新Accepted Pose重新建立缓冲，不从隐藏位置长期插值穿图。

### 8.5 Bootstrap与LateJoin

每个连接由服务器冻结同一`BootstrapRevision + BootstrapCutServerTime`：

1. Roster
2. AuthorityMap（Active/Pending Lease、AuthorityEpoch、Availability、Active/Pending TransactionState、Deadline和当前BaselineRevision/Hash）
3. Health
4. Dead
5. AcceptedSnapshot
6. GroupAbilityConfig

六Scope分别使用确定性序列化和Hash，共享同一Cut/Revision。客户端全部应用并ACK后才Ready，再消费更新Pose。不存在服务器生成的中间运动历史补播。

### 8.6 带宽目标

首版目标：

- 每个Air Owner Candidate平均上行≤0.12Mbps，Combat 1秒滚动峰值≤0.25Mbps。
- 每个相关观察者Accepted Pose平均下行≤0.25Mbps。
- Combat事件与可靠状态另计，但单客户端新增双向总平均≤0.50Mbps。
- GroundMachineIntegration必须提供独立实测预算。

Network Insights按connection/direction/stream_tag读取压缩/加密后的UE Packet/Bunch字节，包含UE头和重传，不包含IP/UDP/Ethernet；不能用应用Payload估算代替。
