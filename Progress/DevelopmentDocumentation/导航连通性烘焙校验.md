# 导航连通性烘焙校验 — 技术方案

## 技术选型与边界

实现放在 GuLiStrikeEditor，使用现有 NavigationSystem/Navmesh/UnrealEd/GuLiStrike 依赖，不增加运行时模块依赖。复用 `GuLiCommanderNavigationPolicy` 的代理名称与配置合同；从源世界唯一的 CommanderSoldier RecastNavMesh 获取数据，不回退至 Default 代理。

使用引擎 Detour 过滤器、特殊链接过滤器和 `GetPolyNeighbors` 获取导航图。邻接关系压缩保存，正向和反向图通过非递归 Kosaraju 分区；时间与空间复杂度 O(多边形数 + 链接数)，没有 A* 查询节点上限。只统计包含地面多边形的强连通分区，链接参与连通计算但不作为站立区域。最大面积分区仅作为诊断中的主区域标识；不会据此免除其他分区的失败判定。

两点投影受显式范围约束。共享分区内直接确认双向连接；不同分区则分别做有向可达遍历，区分断开与单向。分析结果仅证明所读取 NavMesh 的拓扑连接，不替代运行时 Mass 跟随、动态障碍、特殊动作执行或最终到达验收。

`GuLiNavigationConnectivitySettings.RequiredWorldPackages` 显式启用指挥官地图的完整连通合同，其他地图保留原有烘焙规则。`PrepareWorldNavigation` 在所有烘焙结束、提交成功元数据与保存之前检查；`ValidateWorldNavigation` 也检查，所以缓存、PIE 许可和 Cook 不会绕过。Prepare 保存后只复核缓存，避免同一调用重复构建完整图。引擎原生 Build Paths 可以生成断开的 NavMesh，但不会被 GuLi Prepare/Validate 认证为成功。
