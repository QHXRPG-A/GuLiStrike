# 指挥官单位体型与避障距离配置及接入分析

## 结论

两个字段的算术成本很小，现有空间哈希和预测避让可继续使用。完整落地是中等范围的跨模块修改，主要工作是让生成、编队、终点占位、移动分离和工程车读取同一套体型数据。
不能只把全局150厘米改为625厘米，否则所有扫荡者也会被当成战争机器；只增大推开力度仍无法保证最小净距。

本轮只改Excel和说明。后续生成头文件、DataTable与游戏逻辑未实施，现有游戏行为仍然保持。

## 统一数据合同

表内保存最终尺度的米数。初始化时一次转换：

```cpp
BodyRadiusCm = ModelWidthMeters * 50.0f;
MinGapCm = MinAvoidanceDistanceMeters * 100.0f;
MinCenterDistanceCm = RadiusA + RadiusB + FMath::Max(GapA, GapB);
```

战争机器625厘米半径、250厘米净距，两台最小中心距1500厘米。不要再乘0.2的PresentationScale。
宽度必须有限且>0，净距必须有限且>=0；缺失或非法配置应报出兵种和字段，避免静默沿用小半径。
`ModelWidthMeters`用于圆形占地近似，模型渲染继续走原有比例。当前宽度并非任意朝向下精确三角轮廓的保证，长条伸出物/转向需按可见结果校准。

## 必须同时处理的边界

1. **查询范围不能小于安全距离。** 当前预测检测距离1200厘米，而战争机器同类安全距离1500厘米；手动分离网格初始单元300厘米并只查相邻3×3格。需按单位半径、可能邻居最大半径和净距计算查询半径；预测范围还要留相对速度与提前避让的空间。单元尺寸和扫描格数一起修改，不能只加判断半径。
2. **软避让不保证硬距离。** 当前手动分离力度0.25，只是叠加速度；位移最后只验证NavMesh表面。静止/到达者不主动纠正位置，恢复路径状态也可能跳过通常避让。若要满足“不能近过”，需位置层约束；对当前真正冲突的邻居不能沿用预测阶段最多6个碰撞体的截断。候选移动还应考虑一个步长内的穿越，不能仅验末点。
3. **高密度布局要先合法。** 增大到15米槽距后，5×5战争机器方阵中心跨度达60米，旧30米方阵间距会令方阵互相重叠。旧90米终点搜索域也未必容得下大批战争机器，应按数量/体型扩大搜索或明确部分接收，不能压缩回旧槽距。
4. **工程车不是Mass实体。** 当前Crowd的MaxAgentRadius仅400厘米，低于战争机器625厘米本体半径，Config中也有覆盖；桥接时须同步检查上限。现有Mass只读障碍桥接是单向的，完整单位互避需补工程车参与快照。Detour的单个半径不能精确表达`max(GapA,GapB)`；把半个净距分别塞进半径得到的是平均值，会低估异类净距。项目层应统一做成对约束，Crowd作为路径和预判服务；若预判采用保守膨胀，必须记录它可能造成额外让距，不能说它与精确公式等价。
5. **导航身体半径和单位间留白分别维护。** 世界墙体/窄通道需适合真正的BodyRadius，不应把“单位之间2.5米净距”直接等同于墙边留白。当前CommanderSoldier的NavMesh AgentRadius是150厘米，不能仅改动态避让就宣称大模型对墙也安全；完整体型通行需要离散的小/大Agent规格或体型清空检查及对应烘焙评估。不要为每个单位动态重建NavMesh。

首版混编可按临时导航小组的最大体型布置候选，再以成对规则验证；这样实现简单，但混编会更松散。逐行按不同体型紧密排布可作为后续优化，不必首版引入装箱算法。

## 复杂度和计算量

| 项目 | 判断 |
|---|---|
| 数据/数学 | 每种兵种解析一次；每对多一次max和常数次加乘。若每实体缓存两个float，500个单位原始字段约4KB，不含容器对齐及工作快照 |
| 网格与邻居 | 常见分布为O(N+N×k)，k是实际查询邻居数；保持局部查询，不改成每帧全军两两比较。极端拥挤时k仍可能接近N，不能保证最坏O(N) |
| 较大查询范围 | 会访问更多桶/候选，是主要CPU增量。以300厘米格子直接扫1500厘米半径为例需要11×11格，远多于当前手动分离3×3格；这是桶访问示例，不是实测帧耗时倍率 |
| 局部硬约束 | 有额外成对检查；可限定少量求解迭代，未能满足时拒绝移动/等待，不能因预算耗尽就允许越界。大批初始重叠会放大成本，应由合法生成防止 |
| 规划/生成 | 增大占地会扩大分布和候选搜索；这些是生成/命令阶段工作，继续用现有分帧预算。地图容纳能力可能下降，这是体型语义的实际后果 |
| 导航/网络/GPU | 单位间净距无需新增网格绘制、物理刚体或每帧网络消息；若增加大Agent烘焙，会增加导航构建时间和内存，独立于两字段的算术成本 |

总体：方案复杂度适度增加，完整改动范围中等。运行时间增量可控但非零，不能在未实测前承诺百分比。首版只采用一种空间网格方案，根据现有计数再决定是否分大小体型网格，不预先叠加多套基础设施。

## 原生碰撞能否直接解决（2026-09-18补充）

结论：碰撞可以承担最后的阻挡，但当前Mass移动链没有接入原生阻挡；开启模型碰撞不会自动修正服务器位置。建议采用“提前避让＋二维圆形间距约束”，工程车继续使用已有CharacterMovement胶囊扫掠，世界几何按实际身体尺寸导航或做必要的简单形状扫掠。无需为全军开启Chaos刚体模拟。

| 路线 | 对本项目的作用 | 接入和成本判断 |
|---|---|---|
| 只打开实例模型的Block碰撞 | 能让其他查询看见碰撞体，但当前直接写Mass/ISM位置的逻辑不会自动停下 | 会增加实例物理形状的创建、位置更新和查询负担，却未接通权威阻挡，不采用 |
| 简单胶囊/球形Sweep，不开启SimulatePhysics | 移动前查询沿途障碍，配合滑移和去穿透；适合现有工程车及世界几何 | 可复用引擎查询；Mass相互阻挡仍须提供查询形体或自行检测其他Mass实体，不能只扫渲染实例 |
| 全部单位为Chaos动态刚体 | 接触求解可以产生推挤，但仍不负责提前绕行、合法出生和目标占位 | 需接管位置所有权，处理驱动力、旋转/翻倒限制和同步；持续活动群体预计比仅做局部二维约束更重，尚无同场实测 |
| Mass预测避让＋局部二维约束 | 提前转向，最后检查成对安全距离；难以通过时停车/让路 | 复用现有数据和空间索引，新增小型原生求解策略；推荐作为主路线 |

这里的“胶囊碰撞”与“物理模拟”是两回事。`SafeMoveUpdatedComponent(..., bSweep=true, ...)`会执行移动扫掠，并在初始穿透时尝试消除穿透；不要求角色开启动态刚体模拟。UE简单碰撞可以使用球、胶囊、盒或凸包，单位互避无需使用模型三角面。参见[Epic简单与复杂碰撞说明（5.7）](https://dev.epicgames.com/documentation/en-us/unreal-engine/simple-versus-complex-collision-in-unreal-engine?application_version=5.7)。

### 为什么碰撞半径不能随便加2.5米

普通本体碰撞只约束接触，不能自动留出2.5米空隙。若把每台战争机器半径增加2.5米，两台之间会空出5米；若各增加1.25米，同类正确，但异类不正确：

战争机器与扫荡者的本体半径之和为7.8米。各加半个自身净距时，碰撞中心距为`7.8 + 1.25 + 0.25 = 9.3米`，低于需求的`7.8 + max(2.5,0.5) = 10.3米`。

因此单个固定膨胀半径无法精确表达异类之间的max规则。保守地各加全部净距能满足“至少”的下限，却会让队伍比配置要求更松，挤窄通路。精确留距应使用成对函数；真实身体半径、单位净距、墙体导航半径保持各自语义。

## 推荐的最小实现路径

### 1. 先防止制造重叠

两列经既有导出器进入共享兵种定义；初始化时缓存米→厘米转换。先修初始部署、工厂出口和目的地槽位，所有入口用同一距离函数。生产空间不足时查找其他合法位置或等待，不能先堆在原点再依赖碰撞炸开。

对于当前配置，战争机器之间中心距15米；5×5方阵中心跨度60米。必须同步改变方阵锚点间距和出生搜索范围。这部分主要在生成/下命令时计算，修复初始高密度也能减轻后续分离负担。

### 2. 在Mass提交位置前增加一道几何约束

保留现有路径、目标速度、预测避让。把现有“逐单位立即提交位置”改为“生成本步候选→统一检查和修正→提交”，初始位置和候选位置分别缓存在连续数组，服务器仍拥有唯一最终位置。纯计算函数放在现有Commander/Mass/Navigation策略层，共享体型/成对距离定义放在两类单位都能使用的Gameplay层，无需新增UE模块。

建议的每步顺序：

1. 从同一时刻的单位状态建立/复用局部空间索引，包含移动、静止、到达及恢复状态。按体型与本步位移覆盖邻域，不硬编码相邻3×3格。
2. 从导航、预测避让得到移动候选。对可能相交的运动包围范围生成邻居对，同一对只处理一次；预测最多6个障碍的限制不能用于最后的安全检查。
3. 检查整段相对运动，不只检查候选终点。对初始相对位置`p`、相对位移`d`，取`u=clamp(-dot(p,d)/dot(d,d),0,1)`（位移近零时取0），检查`|p+u*d|² >= Dmin²`。这仅针对本步直线段；分段路径必须逐段处理。
4. 冲突时削减朝向对方的位移、允许安全切向移动，再作少量局部修正，例如2～4轮作为初始实现预算。静止/工作锁定单位优先不被推走，移动者让行；完全同点用稳定ID决定退让方向，不能对零向量归一化。
5. 修正位置重新验证NavMesh及所有受影响邻居。没有解时拒绝本步冲突移动，保留已合法位置并反馈受阻，交给现有恢复/重新找位逻辑；不能在循环结束后无条件接受剩余穿透。回退一个单位会改变其他单位的安全条件，需连同冲突集合重新校验，必要时冻结该集合。
6. 统一提交最终位置，并由实际位移更新速度、LastValidNavLocation和Mass片段。不要让碰撞修正与导航/动画速度持有不同位置。

当前权威模拟为10Hz（`Commander/GuLiCommanderSimulationTiming.h:10`）。按当前最高移动速度7.2米/秒，常规0.1秒步长可移动0.72米，对向相对位移1.44米，所以“每步末尾没有交叠”不能代替沿途检测；低频/累积移动步必须用实际DeltaSeconds。

有限迭代只改善候选。严格下限依赖合法初态、完整邻域、连续运动检查及最后拒绝不合法提交；并不保证任何密度都能前进，也不自动保证无死锁。旧存档/传送造成的非法初态须先合法化，不能套用“回退即安全”的前提。

### 3. 工程车必须双向接入

工程车继续由现有CharacterMovement移动和胶囊Sweep负责世界碰撞，Crowd提供提前避让。Mass/工程车共用体型与成对检查，但无需强行共用整套移动器。

目前只把Mass快照提供给Crowd，且物理胶囊半径130厘米也不是新增表中净距。需给Mass提供工程车状态，并在工程车实际移动入口消费相同安全检查。可利用已有`UGuLiExternalCharacterMovementComponent`以及可重写的`MoveUpdatedComponentImpl`接入，但必须保持原CMC移动/碰撞结果语义；不要在移动完成后随意SetActorLocation造成速度和网络校正分歧。

服务器要规定先后顺序/提交时点，并在每个工程车实际移动子步校验或预留运动范围。只读取上一次10Hz车辆快照，不能保证车辆在两次Mass更新之间始终满足距离。

已找到的额外入口：`GuLiMiningVehiclePawn.cpp:343`的工厂进出用`SetActorLocationAndRotation(..., false)`；`GuLiExternalCharacterMovementComponent.cpp`的外部位移也直接传送。正常工厂移动和需要遵守占位规则的落点必须经过相同约束，单改普通MoveTo不覆盖它们。既有穿越/特殊技能豁免须按玩法定义处理。

### 4. 显示预测不能把合法单位重新画进邻居

`GuLiCommanderPresentationActor.cpp:1754,2471`在权威插值结果上添加客户端预测位移，当前这段没有单位间距校验。因此服务器位置修复后仍须审查该偏移：优先对拥挤/受阻单位抑制位移预测，必要时使用同一体型规则限制显示偏移；不为客户端实例额外启动物理模拟。客户端各自插值时间与分段路径也需保持一致，否则两个合法权威端点不足以证明中间画面合法。

这属于显示一致性，不改变服务器裁决。先完成体型与Mass约束，再完成工程车和显示接入，之后才能宣称“所有正常单位都满足最小净距”；仅完成第一阶段只能称为减少穿模。

## 性能判断的依据和限制

轻量方案的主要运行增量是局部候选对和少量约束轮次，平均成本可写成`O(N + I×N×k)`，I为轮次、k为附近参与者数；极端密集时仍可能恶化。使用平方距离过滤、不逐帧取模型Bounds、复用数组和网格即可，无需先做多级树、新插件或逐单位Actor代理。扩大单位间距后密度本身会降低，实际候选数量不必按半径面积机械翻倍估算。

Chaos也有高效的空间筛选，不能说它必然全量两两比较；静止刚体可休眠，也不能笼统说“原生碰撞都很耗”。本项目若把所有持续移动的Mass单位改成动态刚体，会新增刚体状态维护、接触求解和姿态同步，若用子步提高稳定性还会继续增加CPU/内存工作。这里“更重”是基于工作内容的工程判断，并非测得的帧率结论。[Epic物理子步说明（5.7）](https://dev.epicgames.com/documentation/en-us/unreal-engine/physics-sub-stepping-in-unreal-engine?application_version=5.7)明确指出稳定性提高伴随CPU及维护成本。

两列配置和圆形距离公式本身很轻。真正增加开发复杂度的是生成、混合移动器、提交顺序、异常落点和显示预测要遵守同一规则；原生物理无法省掉这些接入工作。当前可推荐混合方案，但没有理由承诺“只多几个百分比”或指定帧耗时。本次只做源码与文档核对，未创建性能场景、未扩充测试矩阵，也未执行不同实现的性能对照。
