## 技术选型与数据流

纯数据匹配器位于现有 `Battle/Combat`，没有新增模块、第三方库或 Commander 内部依赖。每艘 Ship 以自己的组状态独立执行以下链路：

1. 服务器读取存活 roster、1秒内 Accepted Pose、当前自动分配和服务器目标目录。
2. 目标目录中的 `CommanderSoldier` 归为地面目标，`Ship/Wingman` 归为空中目标；同一目标按完整身份去重，地面落点每次扫描只投影一次。
3. 服务器依据成员攻击通道、获取/释放范围和状态生成合法边，并每0.2秒运行多轮矩形匈牙利求解。
4. 求解结果发布为最多25条逐成员自动目标；手动目标存在时清空对外自动表并跳过求解。
5. Relay可靠同步完整状态。拥有客户端按成员身份读取目标，继续运行原 `AirDogfight` 或 `GroundDive` 状态机。
6. 客户端提交开火记录，服务器以完整成员、目标和分配版本查询最近授权快照，再执行原时效、租约、配置、射程、射界、LOS及冷却校验。

Legacy基础自动武器也从第4步读取服务器分配，保留逐成员5Hz错峰和实际开火门，不再构建本地候选或调用 `SelectBestTarget`。Ship自身的手动导弹索敌继续使用原 `FGuLiWingmanTargetAcquisition`。

## 纯数据匈牙利分配器

新增 [GuLiWingmanTargetAssignment.h](../../Source/GuLiStrike/Battle/Combat/GuLiWingmanTargetAssignment.h) 与 [GuLiWingmanTargetAssignment.cpp](../../Source/GuLiStrike/Battle/Combat/GuLiWingmanTargetAssignment.cpp)。输入结构明确区分成员、目标和合法边；合法边携带完整成员与目标身份、四舍五入到最近整数厘米的三维距离，以及是否从仍可保留的旧目标切换。

`Solve` 先按完整成员与目标身份稳定排序。重复输入、非法身份、负代价、越界成员数或乘加溢出会返回失败并清空输出。零距离是合法代价，`Cmax=0` 时未分配惩罚正确取1。

每轮以剩余成员为行，以全部真实目标和与行数相同的未分配槽为列。设本轮成员数为 `N`、最大合法边代价为 `Cmax`，未分配槽代价为 `P = N × Cmax + 1`。这一代价使少一个未分配项优先于任何合法距离差异，因此先最大化合法匹配数量，再最小化总代价。非法边使用更高的受控代价，并在输出阶段再次拒绝。

保存一轮真实匹配后，求解器移除已分配成员、重新开放全部目标并继续运行，直到成员分完或没有新增合法配对。输出按完整成员身份排序并记录轮次。同一目标每轮最多分配一架，因此目标较少时形成均匀的多轮覆盖。换敌惩罚固定为 `10000cm`；它只在旧自动目标仍可合法保留而成员改配其他目标时加入。

## 服务器候选、版本与归队

[GuLiWingmanAttackCombat.cpp](../../Source/GuLiStrike/Battle/Combat/GuLiWingmanAttackCombat.cpp) 中的 `TickAttackTargeting` 负责统一候选和发布：

- `Recover`、`Stale`、死亡、无攻击能力或没有1秒内 Accepted Pose 的成员不参与。
- `AirDogfight` 提供空中能力，`GroundDive` 提供地面能力；Legacy保留通用直射兼容能力，但只能消费服务器分配。
- Ship获取范围内的目标向具备对应能力的全部成员开放；获取范围外、释放范围内的旧目标仅向原成员开放。
- 求解失败发布空自动表并拒绝新增授权。只有扫描开始时存在旧自动表，且全部旧目标都因超过释放范围而失效时，才进入原整组归队锁；目标死亡、成员不可用、普通无候选或混合失效不创建该锁。
- 每个完整成员身份维护非零递增分配版本。目标关系改变，或清空后重新获得目标时推进版本；仅权威位置、半径和服务器时间刷新时保持版本。
- `SynchronizeRosterState` 同步清理死亡成员、旧 `EntityGeneration` 的分配、版本和 Checkpoint。补充成员取得新姿态后，以新身份进入下一轮。

有效手动目标继续只存于 `FGuLiWingmanAttackAuthorityState::Target`。手动目标存在时自动表对外为空，`GetAttackTarget` 和 Ship共享属性也只反映这一手动目标；取消或失效后恢复自动求解。

### Candidate整数厘米边界一致性

PIE长测暴露了一个由攻击运动触发的既有边界问题：Mass Integration 曾用高精度 `FVector` 检查最终FlightNav位移，而 Candidate随后才把端点四舍五入为整数厘米。靠近导航边界时，高精度端点可以合法，但实际上线上发送的整数厘米端点会落到边界外；权威端首先返回 `EndpointOutsideNavigation`，该Flight保留的轨迹再连续触发 `TrailInvalid`，最终让Relay从 `Active` 进入 `Stale` 和 `Unavailable`。

`GuLiWingmanProtocol::QuantizePositionCentimeters` 与 `ExpandPositionCentimeters` 现在定义唯一的Candidate位置表示。普通与单Flight Candidate均通过该入口构建位置；Integration在提交本地高精度Transform前，使用相同整数厘米起终点完成FlightNav、物理障碍和Carrier包络最终门。这样客户端放行的位移一定能以相同端点发布给服务器，不再由后续舍入制造第一条非法轨迹。

### 对地全员参战修正与范围显示

后续PIE采样把“分配数量”和“实际执行数量”分开检查。修正前的 [38秒样本](../../TestResults/WORK-20260908-002/AttackSparseAt38s.json) 中，服务器已有23条逐成员自动分配，但25架里只有9架处于攻击引导，16架为Idle；[127秒样本](../../TestResults/WORK-20260908-002/AttackSparseLater.json) 仍有14架Idle。未开始成员反复尝试后 `StartTime/RunId` 仍为0，证明匈牙利结果已发布，失败发生在 `GroundDive` 执行入口。

执行器现在先从成员到目标的直接方向开始，再按成员稳定种子以 `±45°、±90°、±135°、180°` 的有限顺序寻找最多8条航线。QA进一步把失败拆为FlightNav、静态碰撞、找不到地面和净空不足；现场失败全部属于 `EndpointOutsideNavigation`。根因是旧几何把100米 `PullUpHeight` 当作有限半径转弯的起点，圆弧中段还会下沉约37.76米；地图地面约为 `Z=-73米` 时，弧底会落到FlightNav下边界之外。

`BuildGroundPath` 现把 `PullUpHeight` 解释为整段圆弧相对目标点的最低净空，并把转弯两端自动抬高圆弧下沉量。默认45米/秒、20°/秒配置下，进场点约位于目标上方185.49米，转弯起点约137.76米，弧底保持100米。客户端和服务器仍用同一函数重建路径，未增加协议字段或放宽FlightNav、静态碰撞、地面净空及开火授权门。

Ship新增 [GuLiShipTargetingRangeComponent](../../Source/GuLiStrike/Gameplay/Ship/GuLiShipTargetingRangeComponent.h)，以无碰撞、无复制的运行时线框渲染三个正交大圆。本地受控Ship每帧把同一份 `FGuLiWingmanTargetingTuning::AcquireRadiusCentimeters` 写入组件；远端Ship和服务器隐藏。默认显示青色1500米三维获取范围，可由 `bShowWingmanTargetingRange` 关闭。

## 逐架目标与攻击执行

协议层新增 `FGuLiWingmanAutoTargetAssignment`，包含完整 `Emitter` 与 `FGuLiWingmanAttackTarget Target`。`FGuLiWingmanAttackAuthorityState` 新增最多25条 `AutomaticTargets`，要求成员唯一、稳定排序、目标有效且属于同组，并把完整自动表纳入稳定哈希与有界 `NetSerialize`。

`ResolveTargetForEmitter(State, Emitter)` 优先返回有效手动目标，否则按完整成员身份查找自动分配。客户端在遍历 Mass 实体时调用该入口：空中目标进入原对空机枪/缠斗通道，地面目标进入原俯冲轰炸通道，同一组可同时运行两种方式；没有分配的成员继续原跟随行为。

实际目标身份改变时，对空机动按原规则重置；单纯位置或服务器时间刷新不会重置。进入 `Dive/PullUp/Climb` 后，当前目标、条带、路径和 Checkpoint保持冻结，即使自动表已发布下一目标也不覆盖该轮；冻结轮结束后才消费最新分配。

相关执行入口位于 [GuLiWingmanAttackSimulation.cpp](../../Source/GuLiStrike/Gameplay/Wingman/Combat/GuLiWingmanAttackSimulation.cpp)、[GuLiWingmanSimulationSubsystem.cpp](../../Source/GuLiStrike/Gameplay/Wingman/GuLiWingmanSimulationSubsystem.cpp) 和 [GuLiWingmanSimulationSubsystem.h](../../Source/GuLiStrike/Gameplay/Wingman/GuLiWingmanSimulationSubsystem.h)。

## v12同步与开火授权

[GuLiWingmanProtocolTypes.h](../../Source/GuLiStrike/Battle/Contracts/GuLiWingmanProtocolTypes.h) 与 [GuLiWingmanProtocolTypes.cpp](../../Source/GuLiStrike/Battle/Contracts/GuLiWingmanProtocolTypes.cpp) 将当前协议升至v12。可靠状态的合法性、序列化和稳定哈希覆盖逐成员自动表，bootstrap和租约交接据此恢复分配与冻结 Checkpoint；v11/v12不混用。

`FGuLiWingmanFireIntent` 新增非零 `TargetAssignmentRevision`。构建开火意图的主入口和兼容入口均接收完整 `FGuLiWingmanAttackTarget`，调用方无法只传目标句柄而遗漏版本、类型、指定标志、权威位置或时间。

服务器保留最近16个扫描或模式切换快照。自动模式复制逐成员表，手动模式按当时存活 roster 展开共享目标。Legacy开火必须命中同一完整成员、目标及分配版本；非Legacy新攻击轮还核对完整目标记录。合法迟到记录仍受原时间窗约束，已冻结地面轮继续按同一成员、武器配置、租约、RunId和Checkpoint处理，不能跨成员或跨代复用。

[GuLiWingmanRelayComponent.cpp](../../Source/GuLiStrike/Battle/Network/Relay/GuLiWingmanRelayComponent.cpp) 已删除Legacy本地候选收集、空间哈希和 `SelectBestTarget`；到期成员直接读取权威逐架目标，并以分配中的权威位置形成瞄准与开火意图。5Hz错峰、冷却、射程、射界和客户端LOS预判保持。
