# 僚机无规则护航盘旋技能重构 — 开发文档

- 配对需求：[僚机无规则护航盘旋技能重构](../RequirementDocument/20260904-僚机无规则护航盘旋技能重构.md)
- 继承架构：[飞船 GAS 与僚机技能归属](20260902-飞船GAS与僚机技能归属.md)
- 相关实现：[僚机体系与空中三维导航](20260902-僚机体系与空中三维导航.md)
- 当前协议：Wingman v8 已链接生效；V2 AbilitySet/SwarmOrbit DataAsset 已部署并通过跨编辑器进程审计

## 1. 技术结论

推荐实现 **Bounded Deterministic Swarm Flow（有界确定性群集流场）**：

`母舰运动前馈 + 三维切向旋流 + Curl Noise + 软壳层约束 + 局部分离/弱对齐 + 优先级安全解析 + 固定翼积分`

它不是在双环槽位公式上继续加随机偏移，而是把 Guidance 的抽象从“移动目标点”改成“preferred velocity/acceleration field”。现有 Mass、FlightNav、固定步积分、客户端 Lease Owner 和服务器 Candidate 校验边界继续保留。

真实 N-body 仅作为研究对照，不进入运行时依赖。即使 25 架的 `O(N²)` 算力可接受，它仍不满足本项目的控制、固定翼可达性和网络可复现需求。

## 2. 当前耦合点与重构原因

当前代码并非只有一个“圆形公式”，双环概念已穿过数据、投影、Mass 初始化和 Guidance：

| 层 | 当前事实 | 重构要求 |
|---|---|---|
| Ability | `UGuLiShipDoubleRingFormationAbility` 使用稳定 ID `Ship.Ability.Formation.DoubleRing` | 新增 `SwarmOrbit` Ability，不偷换旧 ID 语义 |
| Definition | `UGuLiWingmanFormationDefinition` 直接暴露双环槽数、半径、高度、角速度 | 引入 FormationModel 与独立 SwarmOrbit 调参组 |
| Runtime DTO | `FGuLiWingmanFormationRuntimeConfig` 复制双环字段 | 改为带版本的通用 POD 投影，哈希显式覆盖选中模型 |
| Mass Fragment | `FGuLiWingmanFormationSlotFragment` 保存 Radius/Height/Phase/AngularSpeed | 替换为稳定 AgentSeed、偏好域和噪声域参数；不再保存精确槽位 |
| Spawn/Apply | `GuLiWingmanSimulationSubsystem` 按成员序号分内外环并计算相位 | 按稳定身份生成个体参数；切换时保留 Transform/Velocity |
| Guidance | 每帧推进相位，计算圆周位置，再混合切线和 ToSlot | 直接生成 preferred velocity；位置只用于域约束和恢复 |
| Avoidance | 再次把 DesiredForward 与 ToGuidance 混合 | 只消费一个 preferred velocity，按安全优先级解析 |
| Integration | 第三次从 DesiredPosition 推方向 | 只消费 resolved velocity/direction，继续作为唯一 Transform Writer |
| Navigation | 以 Slot Offset 构造 Flight 路径目标 | 改为 Flight 宏观偏置/安全域目标，不恢复精确相位 |

原 V1 双环参数也存在动力学矛盾：内环 `600 m × 0.08 rad/s = 48 m/s`、外环 `900 m × 0.06 rad/s = 54 m/s`，而巡航速度为 `45 m/s`。在有限转向率下追逐不同速的精确旋转槽位，会自然出现内切、追赶和反复纠偏；继续调权重不能消除这个结构性矛盾。开发期曾出现的 `300/450 m`、`CatchUp/Recover=600/900 m` 是短暂误改，已恢复为精确 V1 几何 `600/900 m`、`±150 m`、`1200/2500 m`。

## 3. 为什么不用真实引力

### 3.1 单中心引力仍然规则

理想中心力为：

```text
a_g = -μ r / |r|³
```

稳定圆轨道满足 `v = sqrt(μ / |r|)`。给每架僚机不同的偏心率、轨道面和初相位，可以让群体短期看起来复杂，但每架仍沿规则 Kepler 轨道运动；母舰加速后，整个惯性系轨道也不会自动成为好用的跟随技能。

更关键的是，本项目对速度、转向和避障做了非保守限幅。任何数值耗散、速度钳制或阻尼都会改变轨道能量，最常见结果就是再次螺旋向内或向外漂移。专业 N-body 工具 REBOUND 为此提供 leapfrog、WHFast 等辛积分器和近距离处理；这恰好说明完整天体积分不是一个应塞进游戏跟随 Guidance 的小公式。

### 3.2 多体引力带来的“无规则”不可控

加入僚机之间的互相引力后会产生近距离强力、交换能量、碰撞和逃逸；混沌来自系统失控，而不是可导演的生命感。它还与舰体排斥、最小飞行速度、最大转率和 FlightNav 硬边界不断冲突。

### 3.3 可以保留的引力隐喻

如果需要更强的“被母舰吸引”观感，只允许使用软化、限幅的中心分量：

```text
a_soft = -μ r / (|r|² + ε²)^(3/2)
```

但首选仍是带死区的径向弹簧/阻尼，因为它能直接表达“在护航域内自由、越界才纠正”：

```text
a_band = -k * SignedDistanceToAllowedBand(r) * n
         -c * RadialVelocityNearBoundary * n
```

切向驱动独立补充轨道能量，避免中心吸引和阻尼造成半径单向衰减。

## 4. 核心运动模型

### 4.1 坐标与输入

对第 `i` 架僚机：

```text
r_i = WingmanPosition_i - CarrierPosition
u_i = WingmanVelocity_i - CarrierVelocity
t   = ClientSimTick * FixedStep
```

流场在“只随母舰平移、不随母舰姿态刚性旋转”的相对坐标中采样。母舰速度直接进入 preferred velocity；母舰加速度可由连续 Canonical Move 差分后限幅、低通，作为可选前馈。

### 4.2 每 Flight 宏观旋流

每个 Flight 由 `GroupSeed + FlightIndex` 得到稳定基础轴 `Axis0`、旋流方向和低频相位。轨道轴用低频连续噪声缓慢进动：

```text
Axis_f(t) = Normalize(Axis0_f + AxisNoise_f(t) * AxisPrecessionAmount)
Tangent_i = Normalize(Axis_f(t) × Normalize(r_i))
v_swirl   = Tangent_i * SwirlSpeed_i(t)
```

五个 Flight 的宏观趋势提供远景可读性；不能把它再解释为五个刚性槽位组。

### 4.3 每成员 Curl Noise

用三个互相错开的连续标量噪声构成向量势 `Ψ`，速度扰动为：

```text
q_i       = r_i / SpatialScale + SeededDomainOffset_i
v_curl_i  = Curl(Ψ(q_i, t / TemporalScale)) * CurlStrength
```

Curl 场无散度，不会像直接把三轴噪声当速度那样天然制造“汇点”，因此特别适合避免全体向某个噪声洼地聚集。最终仍需外部壳层约束；“无散度”不等于“不会离开护航域”。

首版建议在项目内实现小型稳定 gradient/value-noise 与中心差分 Curl，避免新增运行时库：25 架 × 30 Hz 的采样量很小。`FastNoiseLite` 可作为 MIT 许可的算法/性能参照；只有质量或成本证明需要时再评估 vendoring。

### 4.4 软壳层与个体偏好

护航域由硬内边界、软活动带和硬外恢复边界组成：

- `HullExclusion`：基于母舰实际 bounds/安全体积，最高优先级向外推出。
- `InnerSoftRadius .. OuterSoftRadius`：主要活动带，允许 Curl 引起的径向漂移。
- `PreferredRadius_i(t)`：每架稳定偏好半径，只提供弱回归，不形成固定环。
- `VerticalHalfExtent`：限制厚度但允许上下穿行；边界使用 smoothstep 增强，而非瞬时反弹。
- `RecoveryRadius`：越过后切入 CatchUp/Recover，逐步压低风格分量。

### 4.5 局部群集项

沿用空间哈希，只处理邻域：

- Separation：强，防止拥挤和近距离碰撞。
- Alignment：弱，只对同 Flight 或较近邻居生效，避免 25 架完全同向锁相。
- Cohesion：极弱或关闭；群体已经由母舰锚点和壳层约束，过强 Cohesion 会重现向中心收缩。
- Collision Prediction：仅在最近接近时间落入短窗口时提高优先级。

### 4.6 Preferred velocity

常态 Guidance 的概念输出为：

```text
v_preferred = CarrierVelocity
            + v_swirl
            + v_curl
            + v_band
            + v_separation
            + v_alignment
```

再用响应时间转成名义加速度：

```text
a_nominal = ClampMagnitude((v_preferred - WingmanVelocity) / ResponseTime, MaxAcceleration)
```

避免把 `DesiredPosition -> ToTarget -> DesiredForward` 在 Guidance、Avoidance、Integration 三层重复计算。

## 5. 优先级控制与固定翼可达性

采用 Reynolds 所述的 prioritized acceleration allocation 思路：从最高优先级开始消耗本固定步可用的转向/加速度预算。

| 优先级 | 分量 | 处理方式 |
|---:|---|---|
| 0 | 最终一步 WorldStatic/WorldDynamic/FlightNav sweep | 保留上一步已验证速度，按剩余净空和刹车距离逐步减速；必要时允许安全停至 0，不得瞬时跳到最低速度 |
| 1 | 舰体排斥、受控恢复 | 可覆盖所有风格方向 |
| 2 | 预测碰撞与 Separation | 消耗剩余横向控制量 |
| 3 | CatchUp、外边界回归、内边界推出 | 在安全余量内建立跟随 |
| 4 | Swirl、Curl、弱 Alignment | 只使用剩余预算 |

ORCA/RVO2-3D 的“输入 preferred velocity，输出无碰速度”接口值得借鉴，但它生成的速度对可瞬时换向的代理更友好。僚机是带最小速度和最大转率的非完整约束飞行体，因此首版保留现有 heading probe、FlightNav 和唯一积分器，不直接接入 RVO2-3D。

## 6. 确定性与种子

### 6.1 权威种子

服务器创建 Group 时产生或稳定派生 `FormationSeed`，随可靠 GroupAbilityConfig 投影并进入 SnapshotHash。派生输入只允许使用稳定值：ShipInstanceId、ShipGeneration、GroupGeneration、FormationAbilityId；禁止 UObject 地址、FName 比较索引和本地时间。

### 6.2 分层派生

```text
FlightSeed = Hash(FormationSeed, FlightIndex)
AgentSeed  = Hash(FlightSeed, MemberIndex, EntityGeneration)
```

FlightSeed 控制宏观轴、旋流方向和慢速脉动；AgentSeed 控制偏好半径、垂直偏置、噪声域偏移和小幅速度差。

### 6.3 时间源

所有噪声只采样 `ClientSimTick * FixedStep`。Resume/Takeover 从已确认 Cut 与 tick 继续，不从“收到包后的本地秒数”重新起相位。

### 6.4 数值边界

- 噪声输入在采样前量化或限制有效范围，避免长局时间精度损失。
- 所有向量在进入 Guidance DTO 前检查 finite/NaN，并对零长度叉乘提供稳定备用轴。
- 最终 Candidate 继续按协议量化；确定性目标是“相同平台/配置/输入 Cut 的量化结果一致”，不承诺任意 CPU 的浮点逐 bit 一致。

## 7. 数据与公共 API 设计

### 7.1 Formation 模型

建议新增：

```text
EGuLiWingmanFormationModel
  DoubleRingLegacy
  SwarmOrbit
```

`UGuLiWingmanFormationDefinition` 保留共同飞行/避障参数，并增加分组的 `FGuLiWingmanSwarmOrbitTuning`。旧双环字段放入明确的 legacy 分组和 `EditCondition`，新代码不读取它们。

不建议首轮使用 UObject 策略对象驱动 Mass：可靠快照和备份 Lease Owner 需要纯 POD 数值；枚举 + 版本化数值 payload 更容易显式序列化和稳定哈希。

### 7.2 新运行时字段

`FGuLiWingmanFormationRuntimeConfig` 至少需要：

| 组 | 字段 |
|---|---|
| 身份 | `Model`、`GuidanceAlgorithmVersion`、`FormationSeed` |
| 域 | 内/外软半径、硬恢复半径、垂直半高、舰体安全余量 |
| 旋流 | 速度范围、轴倾角范围、轴进动频率/幅度、反向流比例或 Flight 映射 |
| 噪声 | 空间尺度、时间尺度、强度、宏观/微观混合比例、octave 数 |
| 约束 | 径向回归强度、边界阻尼、ResponseTime、Alignment/Cohesion 权重 |
| 公共飞行 | 最低/巡航/追赶速度、加减速、最大转率、最大滚转 |
| 安全 | AgentRadius、SeparationRadius、LookAhead、CatchUp/Recovery 阈值 |

所有有效范围、单位和字段顺序必须进入 `IsWellFormed`、Definition checksum、SnapshotHash 和资产审计。

## 8. Processor 管线

建议顺序：

```text
Group State / Mode
  -> Neighborhood Snapshot & Spatial Hash
  -> Swarm Flow Guidance (preferred velocity)
  -> Safety Resolver (hull/world/FlightNav/separation)
  -> Fixed-Wing Integration (sole Transform writer)
  -> Candidate / Presentation
```

### 8.1 `UGuLiWingmanFormationGuidanceProcessor`

- 只读 Carrier、Identity、Tuning、Dynamics、Navigation。
- 只写 Guidance，不执行 trace、不写 Transform。
- 根据 Model 路由；`SwarmOrbit` 不调用双环位置公式。

### 8.2 Safety Resolver

- 复用现有确定性 3D spatial hash、heading probes、FlightNav segment 和受控恢复。
- 将重复的 `DesiredForward + ToTarget` 混合收敛为一次 preferred velocity 解析。
- Separation 与世界避障必须有独立调试计数，便于判断是风格场还是安全层在主导动作。

### 8.3 Integration

- 保留 30 Hz 固定步、最大转率、加减速、滚转和平移唯一写入权。
- 对 resolved velocity 执行可达性投影；风格算法不得直接设置朝向或位置。
- 保留最终一步物理/FlightNav fail-closed sweep。

## 9. Flight 状态与权重

StateTree/Group Behavior 只决定高层状态，不生成轨迹几何：

| 状态 | 跟随/回归 | Swirl/Curl | Navigation | Candidate |
|---|---:|---:|---|---|
| SpawnSettle | 中 | 低并渐入 | 否 | 满足现有 Gate 后才发 |
| Orbit/SwarmEscort | 低到中 | 高 | 否 | 正常 |
| CatchUp | 高 | 低 | 必要时 | 正常 |
| Recover | 最高 | 极低 | 是/安全锚 | 正常 |
| Stale | 私有模拟按既有规则保留或冻结 | 不影响 roster 可见性 | 不新发 | 抑制 |
| Dead | 无 | 无 | 无 | 无 |

常态 Orbit 与移动 Escort 可以使用同一流场；CarrierVelocity 前馈负责移动，不需要另建一套规则轨迹。

## 10. GAS、投影与协议

### 10.0 FlightNav 决策（已锁定）

- 保留当前八叉树、A*、portal clearance、路径平滑和逐段校验，不重做导航底座。
- 常态 `Orbit/Follow` 不请求 A*；`CatchUp/Recover` 才以 Flight 为单位请求路径。
- `SwarmOrbit` 的 A* 终点使用由 `FormationSeed + FlightIndex` 派生的稳定恢复锚点，不再追逐随相位旋转的成员槽位。
- A* 输出只影响安全走廊/恢复方向，不能直接覆盖成员 Transform；每架僚机的 heading probe 与 Integration 最终段校验仍是 fail-closed 安全门。
- 本轮不升级 FlightNav 烘焙格式，也不重烘导航资产；只有实测出现连通性或 clearance 失败时才单独立项增强。

### 10.1 新技能

- Tag：`Ship.Ability.Formation.SwarmOrbit`
- Class：`UGuLiShipSwarmOrbitFormationAbility`
- Slot：`EGuLiShipAbilitySlot::Formation`
- Activation：`WhileGranted`
- NetExecutionPolicy：`ServerOnly`
- Definition：独立 `DA_WingmanFormation_SwarmOrbit`

现有 `FGuLiShipAbilityGrant`、每槽唯一性和持久投影模型已经支持这个归属，不需要给 Wingman 新增 ASC。

### 10.2 快照

`BuildGroupAbilityConfigSnapshot` 已不再逐字段假定双环；Definition 通过显式 `BuildRuntimeConfig` 集中执行：

```text
Definition -> validate -> canonical runtime DTO -> stable hash
```

快照新增 Model、AlgorithmVersion、FormationSeed 与 SwarmOrbit 数值。备份 Owner 仍只消费 DTO，不加载 Ship ASC 或 DataAsset。

### 10.3 协议版本

因为 SnapshotHash 输入和可靠快照线结构改变，按当前项目契约升级 `GULI_WINGMAN_PROTOCOL_VERSION` 到 v8，并同步：

- GroupAbilityConfig NetSerialize / stable hash。
- Bootstrap 六 Scope 中 AbilityConfig 的 hash/cut。
- Candidate/Resume/Takeover 的版本与 checksum gate。
- Golden bytes、资产审计和部署 JSON。

不能让 v7 数据静默落入 v8 默认字段。

## 11. 表现层消失问题的独立修复口

新 Guidance 不应承担 Presentation 生命周期修复。实施时增加明确不变量：

```text
Visible = InRoster && Alive && !GroupExplicitlyEnded
```

`Stale/Unavailable` 只改变姿态来源策略：

- 在保留窗口内使用最后两帧做有限 Hermite/速度外推。
- 超过外推窗口后冻结最后合法姿态。
- Resume 到来后从当前显示姿态平滑接回新 Cut。
- 只有 Death、Roster removal、Revoked/Ended 才释放 ISM/Actor 表现实例。

同时保留日志/计数，禁止把算法越界伪装成表现回收。

## 12. 模块职责与依赖

现有单一 `GuLiStrike` 运行时模块已依赖 GameplayAbilities、StateTree、MassEntity、MassMovement、MassNavigation 等，无需新增模块或第三方插件。

| 责任 | 所有者 | 允许依赖 | 禁止反向依赖 |
|---|---|---|---|
| Ability 身份/Definition/DTO | `Gameplay/Ship/Abilities` | GAS、GameplayTags、Core | 不依赖 Mass Processor 或 Presentation |
| 本地群集 Guidance | `Gameplay/Wingman/Mass` | 纯 DTO、Mass、FlightNav 查询接口 | 不访问 Ship ASC/DataAsset |
| Group 高层状态 | `Gameplay/Wingman/Behavior` | 状态/调参 DTO | 不写单架 Transform |
| 网络校验/快照 | `Battle/Contracts`、`Battle/Relay` | 版本化 DTO | 不运行 Guidance/Noise/N-body |
| 表现保留 | `Gameplay/Wingman/Presentation` | Candidate/Accepted Cut | 不决定存活或权威运动 |

## 13. 迁移与回退策略

## 16. 风险与对策

| 风险 | 触发方式 | 对策 |
|---|---|---|
| 噪声过强变成乱飞 | Curl 占满转向预算 | 低优先级分配、强度上限、按状态衰减 |
| 仍然缩圈 | Cohesion/中心力过强或切向能量不足 | Cohesion 默认极弱；径向死区；切向速度闭环；记录平均半径趋势 |
| 全体同步摆动 | 共用相同噪声域/时间相位 | FlightSeed + AgentSeed 分层，宏观/微观混合 |
| 失去群体感 | 个体噪声完全独立 | 同 Flight 共享慢速轴和部分宏观流 |
| 避障后无法回归 | 安全层长期压制 Guidance | 沿用受控恢复与 FlightNav，恢复后渐入风格项 |
| ORCA 输出不可飞 | 速度解不满足固定翼约束 | 首版不接 ORCA；所有命令经转率/速度可达性投影 |
| Resume 后相位跳变 | 使用本地墙钟或重新随机 | 可靠 FormationSeed + ClientSimTick 采样 |
| 协议静默错读 | v7/v8 字段默认值混用 | 升协议并 fail-closed；同步 checksum/golden bytes |
| 新算法掩盖消失问题 | Presentation 仍按 Stale 回收 | 把可见性不变量独立验收 |

### 17.1 论文/原始资料

- [Curl-Noise for Procedural Fluid Flow — Bridson et al.](https://www.cs.ubc.ca/~rbridson/docs/bridson-siggraph2007-curlnoise.pdf)：采用无散度、可空间调制的连续速度场思想。
- [Real-Time Obstacle Avoidance for Manipulators and Mobile Robots — Khatib](https://doi.org/10.1177/027836498600500106)：参考人工势场作为边界/障碍约束，不把势场当完整行为。

### 17.2 GitHub

- [meshula/OpenSteer](https://github.com/meshula/OpenSteer)：MIT；展示用简单 steering behavior 组合复杂行为。适合作为结构参考，不直接移植旧式 vehicle 框架。

### 17.3 Celestis 源码审阅

用户提供的 [openfw-game/celestis](https://github.com/openfw-game/celestis) 与目标题材接近，但当前代码并没有实现 GDD 所写的“spaceships follow the planet orbit and protect it”。全仓库的 `spaceship` 只出现在 GDD/README，`scripts/` 下没有飞船、护卫、索敌或编队实现；现有代码处理的是玩家行星捕获小行星。

当前链路为：

1. `Player` 的 `Area2D` 检测物体进入，先将其加入 `GravityController.orbit_objects`，再调用 Orbit Controller。
2. `GravityController` 每物理帧施加 `gravity_strength / distance` 的向心加速度；这不是标准万有引力的反平方形式。
3. `OrbitController.enter_orbit` 记录捕获瞬间的半径与角度，并启动一个 1 秒 one-shot Timer。
4. Timer 到期后，控制器把列表内对象统一标记为 orbiting。
5. 后续不再积分轨道，而是执行 `angle += (orbit_speed / radius) * delta`，然后直接写 `center + radius * (cos, sin)`。因此半径严格锁定，`orbit_speed / radius` 实际保证各半径使用相同线速度。

历史 [PR #7](https://github.com/openfw-game/celestis/pull/7) 曾在 Asteroid 内使用 `1/r²` 引力靠近中心，再在延时后记录当前半径并切换到参数圆；[PR #8](https://github.com/openfw-game/celestis/pull/8) 删除了逐对象实现，[PR #9](https://github.com/openfw-game/celestis/pull/9) 改成当前 Gravity/Orbit 两控制器。这个演进说明项目最终依靠“引力吸入阶段 + 运动学圆轨道”获得稳定外观，而不是靠引力本身维持轨道。

可借鉴点：

- 捕获/模式切换时继承当前位置对应的半径与方向，避免第一次切换瞬移。
- 用 `angularSpeed = tangentialSpeed / radius` 从期望线速度推角速度，避免本项目当前环速度低于固定翼最低速度的矛盾。
- 将获取/吸引阶段与稳定护航阶段分开建模。

不可直接迁移点：

- 它是 2D 精确圆，直接覆盖对象 Position；会得到比当前双环更规则的轨迹，也绕过固定翼动力学、避障与唯一 Transform Writer。
- Gravity 和 Orbit 同时保留运动写入：Asteroid 自己按 velocity 积分，Orbit Controller 又直接写 position，职责存在冲突。
- 单个共享 Timer 在新对象进入时会重启，并在到期时激活列表中所有对象；不是逐对象状态机。
- `exit_orbit` 被注释，退出 Area 只从 Gravity 列表移除，没有从 Orbit 列表移除。
- `GravityController` 调用可选 `active_orbit`，但仓库没有该方法实现。
- 当前 `player.gd` 查找 `$OrbitController`，而 Player 场景实际子节点名是 `OrbitingObject`，存在 NodePath 接线不一致。
- `project.godot` 的当前启动场景仍是旧 `single_player.tscn`；该场景没有接入 Player prefab 的 Gravity/Orbit 控制器链，且把继承 `CharacterBody2D` 的 `player.gd` 挂在一个 `Node2D` 子节点上。静态源码不能证明当前 main 可运行这套捕获轨道。
- 源码注释已经承认 orbiting object 计数不准确；没有 Separation、障碍规避、确定性种子、网络快照或 Resume/Takeover 设计。

对 GuLiStrike 的结论：Celestis 可以作为“如何在视觉原型里强制得到稳定圆轨道”的反例/参考，但不能作为僚机无规则护航算法的实现基础。唯一值得吸收进 SwarmOrbit 主方案的是“继承切换状态”和“由可飞线速度反推局部旋流角速度”；仍坚持 Curl Flow + 软边界 + 局部分离 + 固定翼可达性解析。

## 20. 2026-09-05 PIE 停飞、坠落与消失二次修复

### 20.1 故障链

这次现象不是单一的“盘旋公式失效”，而是四层安全逻辑串成了放大链：

1. Integration 的最终 FlightNav 门拒绝一步运动后，会把约 `44 m/s` 的旧速度瞬时钳到 `30 m/s` 最低速度。服务器按有限加减速包络复算时把这个跳变判成 `SpeedDelta`；修复前首个证据为 `actual=1423.84 cm/s`、`permitted=170 cm/s`。
2. BehaviorPolicy 把任意一架的 Emergency 通过组级 OR 扩散给整个 Flight，StateTree 随后把五架全部切成 Recover，于是玩家看到“一组僚机一起往母舰掉”。
3. 旧安全探针只返回某个方向是否有效，没有返回沿该方向还剩多少可飞距离；起步又直接给巡航速度，飞到八叉树边界或 Portal 拐角前无法按刹车距离提前减速。
4. 客户端以 30Hz 沿可飞弧线积分，但普通 5Hz Candidate 过去只上传首尾点。服务器把这 0.2 秒运动当作直线弦段校验；弦可能切出弯曲安全走廊并得到 `MissingLink`，即使客户端每个 30Hz 小步都合法。Candidate 连续被拒后，Flight 的 accepted sequence 停住，租约最终 Stale/Unavailable；表现层旧逻辑再把断流误画成消失。

### 20.2 已实施修改

- Avoidance 同时发布“战略安全方向”和“下一固定步安全方向”；Integration 只消费经过当前固定步 FlightNav 检查的方向。
- FlightNav 射线净空用 7 次有界二分逼近实际可飞距离，并以 `速度² / 2a + 安全余量` 计算前视与动态限速。净空不足时按减速度逐步刹车，允许降到 0；最终门失败时恢复 `PreviousVelocity`，不再人为制造速度跳变。
- SwarmOrbit 初始化速度改为 0，由唯一 Integration 在有限加速度包络内起飞，避免“初始位置合法、首个巡航转弯却不可达”。
- Emergency 只在具体成员没有安全下一步时成立；组策略仅把受影响成员置为 Recover，健康成员继续按自身距离保持 Orbit/CatchUp/Recover。
- Relay 复用协议 v8 已有 `TrailSamples`，Active 阶段以 15Hz 保留中间轨迹；普通 5Hz/授权 10Hz Candidate 一并上传实际弧线采样，服务器逐段验证真实轨迹，而不是验证不存在的直线捷径。没有新增协议字段或版本。
- `-GuLiWingmanValidationTrace` 下增加 Integration 拒绝门诊断，默认关闭，不引入常态日志噪声。
