# 飞船 GAS 与僚机技能归属 — 开发文档

- 配对需求：[飞船 GAS 与僚机技能归属](../RequirementDocument/20260902-飞船GAS与僚机技能归属.md)
- 总体方案：[僚机体系、空中三维导航与客户端校验转发](20260902-僚机体系与空中三维导航.md)
- 协议版本：7

## 1. 模块边界

| 层 | 公共入口 | 写入权 | 禁止事项 |
|---|---|---|---|
| PlayerState Army ASC | 现有 `AGuLiBattlePlayerState` | Server PlayerState | 不承载 Ship Ability |
| Ship GAS | `UGuLiShipAbilitySystemComponent`、`UGuLiShipAbilitySet` | Server Ship；拥有客户端可预测主动请求 | 不拥有 Health/Speed/Damage 数值 |
| Ability Projection | `FGuLiGroupAbilityConfigSnapshot` | Server | 不暴露 AbilitySpecHandle |
| Ship Stats | `RecomputeStats`、CMC config barrier | Server Ship | 不由 GE/AttributeSet 改写 |
| Wingman Simulation | Mass Fragments/Processors | 当前 Lease Owner 客户端 | Server 不运行运动 Tick |
| Relay/Combat | Candidate Validator、Accepted Store、Damage Ledger | Server | 不信任客户端 Damage/Health |
| Flight Navigation | 独立 Runtime/Editor 插件 | Editor Bake；Runtime 只读 | Runtime 不依赖 GuLiStrike/GAS/Team |

依赖方向：

`Ship ASC -> GroupAbilityConfig DTO <- Relay/Wingman`  
`FlightNavigationEditor -> FlightNavigation Runtime <- Wingman Mass`  
`Ship/Wingman/Commander Adapters -> Target Registry -> Fire Validator -> Damage Ledger`

## 2. Ship ASC 生命周期

1. Ship 构造函数创建复制的 `UGuLiShipAbilitySystemComponent`，复制模式为 Mixed。
2. BeginPlay 与 NotifyControllerChanged 均调用同一个幂等 `InitializeShipAbilitySystem()`；双端执行 `InitAbilityActorInfo(Ship, Ship)`。
3. 仅 Authority 根据 PlayerState 的稳定载荷调用 `ApplyAbilitySet`。授予键为 AbilityId；已有相同 AbilityId 时更新/保留，不产生第二个 Spec。
4. 默认双环与初始武器由 Authority 自动激活；任一时刻只允许一个 Formation slot。
5. UnPossess 清除本地主动输入状态，不取消服务器被动 Ability。
6. Ship Dead/EndPlay 先失效投影、取消全部能力、结束 Group，再销毁 ASC 所在 Pawn。
7. PlayerState CopyProperties/OverrideWith 只迁移 `FGuLiShipAbilityLoadoutState` 的稳定 AbilityId；不迁移 Handle、Cooldown 或活动状态。

Ship ASC 与 Army ASC 的 Owner/Avatar 均不交叉：

- Army ASC：`Owner=PlayerState, Avatar=PlayerState`。
- Ship ASC：`Owner=Ship, Avatar=Ship`。

## 3. 数据资产与能力槽

- `UGuLiShipAbilitySet`：AbilitySetRevision、稳定 Grant 列表、默认 Formation/Basic/Missile AbilityId。
- `UGuLiWingmanFormationDefinition`：稳定 DefinitionRevision/Checksum、环参数、速度/积分/避障调参。
- `UGuLiWingmanWeaponDefinition`：稳定 DefinitionRevision、射程、速率、Sweep、伤害标识和表现标识。
- `UGuLiShipGameplayAbility`：声明 AbilityId、Slot、投影所需定义与被动/主动策略。

固定互斥槽：

- `Ship.Wingman.Formation`
- `Ship.Wingman.Weapon.Basic`
- `Ship.Wingman.Weapon.Missile`

输入 Tag：`InputTag.Ship.Wingman.Missile`。GameplayEffect 仅允许提供不修改数值的冷却 Tag；首版使用服务器明确的共享冷却时间戳。

当前持久资产：

- `/Game/GuLiStrike/Ship/Abilities/DA_ShipAbilitySet_WingmanV1`
- `/Game/GuLiStrike/Ship/Abilities/Formations/DA_WingmanFormation_DoubleRing`
- `/Game/GuLiStrike/Ship/Abilities/Weapons/DA_WingmanWeapon_BasicAuto`
- `/Game/GuLiStrike/Ship/Abilities/Weapons/DA_WingmanWeapon_MissileSalvo`

`BP_GuLiStrikeShip` CDO 持有 AbilitySet 硬引用；正式 Ship 缺失该资产时拒绝运行时瞬态回退。瞬态默认集仅供 Native Automation fixture 使用。

## 4. GroupAbilityConfig 投影

可靠快照至少包含：

1. ProtocolVersion、MatchEpoch、ShipGeneration、GroupGeneration。
2. AbilitySetRevision、SnapshotRevision、SnapshotHash。
3. FormationAbilityId、FormationDefinitionRevision、FormationDefinitionChecksum。
4. BasicWeaponAbilityId、BasicWeaponDefinitionRevision。
5. MissileAbilityId、MissileDefinitionRevision。
6. FormationCommandRevision、EffectiveClientSimTick。
7. 有效位与 Group Active Gate。

`SnapshotHash` 对显式字段按固定线序和小端数值编码执行稳定 FNV-1a 64 位；不得直接哈希结构体内存、UObject 地址、FName 比较索引或 AbilitySpecHandle。只有 Authority 可增加 SnapshotRevision；相同语义的重复投影是 no-op。

切换编队采用两阶段提交：

1. Server 产生 Pending Snapshot 和目标 EffectiveClientSimTick。
2. 当前 Lease Owner ACK 精确 Revision/Hash。
3. Server 发布 committed Snapshot。
4. Client 在指定 Tick 从旧 Guidance 原子切换到新 Guidance，不修改当前 Transform。

## 5. 协议 v7 线序

### 5.1 Bootstrap

六 Scope 固定序号：

1. Roster
2. AuthorityMap
3. Health
4. Dead
5. AcceptedSnapshot
6. GroupAbilityConfig

每个 Scope Chunk 都携带 ProtocolVersion、CutId、Scope、ScopeRevision、ScopeHash、ChunkIndex、ChunkCount；Commit 携带六项最终 Revision/Hash。任一项缺失、重复冲突或哈希不符，整组保持 Initializing。

### 5.2 Candidate

固定语义字段：ProtocolVersion、MatchEpoch、ShipGeneration、GroupGeneration、LeaseEpoch、CandidateSequence、ClientSimTick、CarrierCanonicalEpoch、CarrierMoveRevision、AbilitySetRevision、FormationCommandRevision、FormationDefinitionChecksum、量化姿态样本。

### 5.3 FireIntent

固定语义字段：ProtocolVersion、MatchEpoch、ShipGeneration、GroupGeneration、LeaseEpoch、DomainFireSequence、EmitterWingmanHandle、SourceAcceptedStateRef、ClientFireTick、TargetHandle、WeaponAbilityId、WeaponDefinitionRevision、AbilitySetRevision、客户端瞄准提示和 ClientLOSPrediction。后两者都只是客户端提示；服务器仍从 Accepted/可靠历史重建位置并重新验证目标、距离与 LOS。

线序变更必须同步修改 Golden Bytes；旧协议数据以 `ProtocolMismatch` 拒绝，不能尝试按当前结构猜测。

## 6. 拒绝原因与提交顺序

拒绝原因至少包括：`ProtocolMismatch`、`InvalidIdentity`、`WrongGeneration`、`WrongLease`、`InactiveGroup`、`MissingAbilityConfig`、`StaleAbilitySetRevision`、`StaleFormationCommand`、`FormationChecksumMismatch`、`UnknownWeaponAbility`、`WeaponDefinitionMismatch`、`EmitterDead`、`StaleSourceState`、`CarrierMovePendingTimeout`、`InvalidTarget`、`FriendlyTarget`、`OutOfRange`、`NoLineOfSight`、`CooldownActive`、`Duplicate`、`RateLimited`。

FireIntent 的服务端顺序固定为：

`结构/身份 -> Group/Lease -> AbilityConfig -> Emitter/AcceptedState -> Target/Range/LOS -> 幂等键 -> TokenBucket -> 冷却可用 -> 创建 Shot/导弹 -> 提交冷却 -> 返回 ACK`

所有失败均发生在序列推进、冷却和 Damage Ledger 提交之前；相同已接纳请求重发只返回缓存结果。

恢复链还必须满足以下不变量：

- 首个原子 Bootstrap Candidate 前，同一可靠 ActorChannel 已依次提交 AbilityConfig ACK 与 Six-Scope ACK；服务端不为启动时序放宽 ACK Gate。
- Active Roster Cut可靠携带对应切面的Accepted baseline，Owner精确ACK后才Rebase，服务器不补写姿态或序列。
- 新GroupGeneration首帧建立自己的FlightMode链；退役代次、Stale或身份未知的私有历史不能进入Resume wire。
- Retained Resume Trajectory最多4个严格递增样本，且线传样本都在Candidate端点前2秒以内；服务端3.5秒权威历史窗口保持不变。
- 全灭Flight补员仅在Active、非Transfer/Revoke且RequiredMemberMask `0 -> 非0`时获得一次不可滑动Freshness grace；首个严格Candidate清除grace，且grace不生成Accepted状态或战斗Source。

## 7. Canonical Ship Move

`UGuLiShipMovementComponent` 在 Authority 完成一次有效 CMC 模拟后追加 `FGuLiShipCanonicalMoveState`：CanonicalEpoch、MoveRevision、MovementConfigRevision、BarrierGeneration、ServerTime、Transform、Velocity。

- History 为有界环，默认 256 项。
- 新预测生命周期增加 CanonicalEpoch 并清空旧 Revision。
- 精确查询返回 Found、Pending、Expired、EpochMismatch 或 Unavailable。
- Relay 只对 Pending 等待至 0.25 秒；Expired/EpochMismatch 立即拒绝。

## 8. 逻辑导弹与 Damage Ledger

- 一次成功主动 GA 选择一个稳定 Flight，并为每个合法 Emitter 创建一条逻辑导弹记录。
- World 服务在 Authority 以 30Hz 固定步推进，使用上一位置到新位置做 Segment/Sphere Sweep。
- 逻辑记录包含 ShotId、Emitter、Target、LaunchState、速度、最大寿命和已终止位；它不是 Actor，也不复制。
- 客户端只接收 Launch、低频 Correction、Impact/Expire 事件重建表现。
- Damage Ledger 以 MatchEpoch + DamageEventId 幂等提交。目标 Adapter 是唯一生命写入口。

## 9. 测试矩阵

### 自动化/合同

- Army ASC 跨 Pawn 测试保持通过；新增 Ship ASC 独立性与 Owner/Avatar 测试。
- 重复 ActorInfo 初始化与 ApplyAbilitySet 不重复授予。
- 载荷跨 Ship 重生只保留 AbilityId，活动实例和冷却清零。
- Formation slot 恰好一个；无编队配置时 Group 不 Active。
- GroupAbilityConfig hash 与 NetSerialize Golden Bytes 确定。
- Candidate/FireIntent 的旧 Ability Revision 不推进任何状态。
- Canonical history 覆盖 Found/Pending/Expired/EpochMismatch 和容量淘汰。
- Damage Ledger 重复事件 CommitCount=1。
- 导弹齐射无合法 Emitter 不冷却；合法数量不超过 Flight 存活成员；复制 Missile Actor=0。
