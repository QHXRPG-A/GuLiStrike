### 0.2 权威分类

`EGuLiMovementAuthorityMode`固定为：

- `ServerSimulated`：Commander Soldier。
- `OwnerPredictedServerReplay`：玩家Ship CharacterMovement。
- `ClientValidatedRelay`：Wingman与玩家Ground战争机器。

`ClientValidatedRelay`的含义不是“服务器低频模拟”：

1. Lease Owner客户端产生全部运行时Position、Rotation、Velocity、Bank、FlightMode和Path结果。
2. 服务器只在Candidate到达时校验。
3. 合法Candidate经确定性量化/归一化后保存为Accepted Snapshot并转发。
4. 缺包、Rejected、Stale、换主空窗期间，服务器不生成任何替代运动值。
5. Health、Damage、Death、Replenish、Reward和比赛结果仍只由服务器写。

必须持续满足：

- `server_wingman_motion_step_count=0`
- `server_ground_machine_motion_step_count=0`
- `server_generated_runtime_transform_count=0`
- `server_wingman_state_tree_tick_count=0`
- `server_wingman_path_request_count=0`
- `server_wingman_steering_step_count=0`
- `server_wingman_flight_integration_step_count=0`
- `server_ground_machine_state_tree_tick_count=0`
- `server_ground_machine_path_request_count=0`
- `server_ground_machine_steering_step_count=0`
- `server_ground_machine_movement_integration_step_count=0`

初始出生Transform和“复制合法Candidate的已接纳值”不属于服务器生成运动；任何从上一快照积分、外推、插值后写回共享逻辑状态的行为都属于违规。

### 0.3 服务端仍然承担的工作

- 创建稳定身份、Roster、生命和SimulationLease。
- 以1Hz检查Lease、连接、Heartbeat和LastValidCandidateTime。
- 收包触发Candidate身份/时序/运动/导航/碰撞验证。
- 保存有限Accepted Snapshot历史并转发给相关客户端。
- FireIntent收包触发敌我、生命、距离、LOS、冷却和幂等验证。
- Damage Ledger、死亡、补充、奖励与可靠表现事件。
- Bootstrap、LateJoin、观战和断线清理。

服务器没有Wingman/Ground固定运动Tick；网络队列为空时，不应产生它们的Validator工作。

| 模块/目录 | 职责 | 禁止事项 |

| `Source/GuLiStrike/Gameplay/GroundMachine` | 正式Ground类接入ClientValidatedRelay | 不与Commander Soldier混用Authority |

除FlightNavigation Runtime/Editor外，上述目录仍属于单一`GuLiStrike` C++模块。依赖边界依靠Public DTO、接口、前置声明和`.cpp`注册适配器维持，不因为逻辑目录增加虚假Build.cs模块。

依赖方向：

`FlightNavigationEditor -> FlightNavigation Runtime <- Wingman -> Battle/Relay -> Battle/Contracts <- Battle/Combat <- Ship/Ground/Commander Adapters`

- Runtime导航不认识Team、PlayerGuid、Lease、Ship或Commander。
- Relay不依赖Combat实现；Combat通过`IGuLiAcceptedStateProvider`读取状态。
- Header优先前置声明，具体include放在`.cpp`。
- UCLASS/USTRUCT/UENUM只在反射、复制或资产序列化需要时使用。
- 不移动现有公开类、不更改蓝图类路径，避免资产Redirector风险。

### 1.2 计划类

- `UGuLiSimulationLeaseSubsystem : UWorldSubsystem`
  - 只在Server/Standalone拥有写入实例。
  - 使用1秒Timer运行`RunLeaseMaintenance()`，不是每帧Tickable运动系统。
- `UGuLiAcceptedRelayStateSubsystem : UWorldSubsystem`
  - 服务器保存最后Accepted Snapshot和有界历史。
  - 唯一运动写入口为`AcceptValidatedCandidate()`。

  - 只在持有Lease的游戏客户端激活30Hz客户端模拟。
- `UGuLiWingmanValidationService`
  - 由Candidate接收事件调用；无独立Tick。
- `UGuLiSimulationNetSyncComponent`
  - Battle PlayerController的独立默认组件，处理Lease/Candidate/Acceptance/Rebase。
- `UGuLiSimulationWorldReplicationComponent`
  - 发布可靠Roster/Life/Lease和不可靠Accepted Pose。
- `FGuLiCommanderBattleAdapter`、`FGuLiShipBattleAdapter`、`FGuLiWingmanBattleAdapter`
  - 通过公共接口向Combat注册目标和生命入口。

## 3. 三维Flight Navigation

### 3.1 Runtime公共类型

- `AGuLiFlightNavVolume`
  - 轴对齐飞行Bounds、Agent Profile、最小叶尺寸、最大深度、FlightNavigation碰撞通道。
  - 硬引用本地图`UGuLiFlightNavDataAsset`。
  - 首版Actor Rotation非零时Bake/Validate失败。
- `UGuLiFlightNavDataAsset : UPrimaryDataAsset`
  - Header：SchemaVersion、SourceMap、VolumeGuid、Bounds、AgentProfile、SourceSignature、SettingsHash、PayloadChecksum、节点/Portal/连通分量和烘焙统计。
  - Payload：扁平自由叶、Portal、净空、连通分量和紧凑索引；不序列化运行时指针。
- `UGuLiFlightNavWorldSubsystem`
  - Client Owner运行异步A*。
  - Server只加载相同只读资产供Candidate验证，不请求路径。
- `FGuLiFlightPathRequest`
  - Start、Goal、AgentProfileHash、VolumeGuid、NavChecksum、SettingsHash、OverlayRevision、OpaqueRequestToken、MaxVisitedNodes。
- `FGuLiFlightPathResult`
  - Status、OpaqueRequestToken、PortalCorridor、SmoothedPoints、VisitedNodes、ElapsedMicroseconds。

玩法层以`FGuLiWingmanPathEnvelope`关联MatchEpoch、Group/Generation、Flight、Lease、Roster和RequestSerial。异步结果回到游戏线程后同时核对导航版本和完整Envelope；任一不匹配即丢弃。

### 3.2 Bake与签名

Bake仅采集Volume内满足以下条件的组件：

- Static Mobility；
- 非EditorOnly；
- 在FlightNavigation通道Block；
- 具有有效碰撞几何。

签名包含稳定Actor/Component路径、组件GUID、Transform、Bounds、BodySetup/CollisionProfile和源资源标识；Volume、Agent和细分设置进入SettingsHash。输入按稳定键排序，不包含时间戳、地址和容器迭代顺序。

算法：

1. 从Volume根节点递归八分，障碍按Agent半径膨胀。
2. 完全自由保存自由叶，完全占用丢弃，混合节点继续细分。
3. 只为共享有效面的自由叶建立Portal；仅边/角接触不连通。
4. 保存Portal中心、有效矩形、最小净空和连通分量。
5. A*使用欧氏启发和稳定NodeId Tie-break。
6. 成功路径经Portal Corridor和LOS平滑，不能越出净空。

Flight共享Corridor。客户端每帧新请求预算默认4个，个人恢复路径默认2个；工作线程只读不可变Data/Overlay，不访问UObject、World、Physics或NavigationSystem。

### 3.3 Editor流程

- Details提供Bake、Validate、Clear。
- Bake成功后立即回读并校验Header/Payload checksum。
- 修改静态碰撞、Transform、BodySetup、Volume或Agent后Validate显示Stale。
- 打开地图、启动编辑器、PIE、Standalone和正式运行只加载资产，静态扫描/Build次数必须为0。
- Cook对Missing、Stale、SchemaMismatch、ChecksumMismatch直接失败。
- Runtime错误时禁止生成Wingman，不能回退到运行时构建或直线穿墙。
- 分别为`LVL_CommanderMassPrototype`、`LVL_Main`、`LVL_ShipTest`生成独立资产。

### 3.4 客户端路径与服务端验证

- A*、Corridor选择、平滑、局部避障和重新规划只在Lease Owner客户端运行。
- Candidate携带NavSchema/Checksum、CurrentLeaf、CurrentPortal、CorridorRevision和动态ObstacleRevision。
- 服务器不重跑A*，只检查：
  - 版本匹配；
  - 当前Leaf包含成员位置；
  - Portal相邻且净空足够；
  - Trail各段没有跨越不可达区域；
  - 静态/当前动态Sweep不阻挡。
- 动态障碍Overlay由障碍注册、移动超过阈值或拓扑变化时事件驱动更新，最高2Hz；不固定5Hz重建静态树。
- 小物体和Wingman间冲突由客户端本地三维哈希处理。

## 4. Wingman客户端模拟

### 4.1 身份与编制

- 一个Carrier对应一个`SimulationGroupId + GroupGeneration`、25架、5个Flight和一份Lease。
- 成员使用`WingmanId + EntityGeneration`，本局不复用。
- 每个RosterRevision冻结`RequiredActiveFlightMask`和每Flight的`RequiredActiveMemberMask`。
- 死亡先可靠移出Mask；空Flight不提交空包。补充先可靠加入新身份，再进入下一Candidate。
- 正常Active Flight Candidate独立接纳；首次Bootstrap、进入Stale后的Resume和换主后的Takeover必须原子覆盖全部Required Flight。

### 4.2 Mass Fragment与Tag

### 4.3 StateTree

客户端StateTree状态：

- JoiningEscort
- EscortOrbit
- EmergencyAvoid
- OwnerUnavailable
- Dead

信号：

- OwnerReady/OwnerLost
- PathReady/PathFailed
- CollisionThreat/ThreatCleared
- HealthZero
- LeaseGranted/LeaseRevoked
- RebaseRequired

[UE5.7 MassGameplay官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-mass-gameplay-in-unreal-engine?application_version=5.7)描述了Signal驱动Mass StateTree的运行方式，适合低频模式选择。项目必须实现带Client ExecutionFlags的专用Mass StateTree Processor，并自动化证明NM_Client Owner执行、Dedicated Server和Remote Presentation不执行。

StateTree Task只修改FlightMode、请求Guidance/Path或发信号；不逐Tick写Transform、不直接扣血。固定翼积分Processor是客户端Transform唯一写者。

### 4.4 客户端30Hz Processor顺序

1. `WingmanLeaseAndRosterConsumeProcessor`
2. `WingmanStateTreeSignalProcessor`
3. `CarrierAnchorProcessor`
4. `FormationAndPathResultProcessor`
5. `WingmanAvoidanceAndSteeringProcessor`
6. `WingmanFlightIntegrationProcessor`
7. `WingmanLocalTargetAcquireProcessor`，默认5Hz错峰
8. `WingmanFireIntentProcessor`
9. `WingmanCandidateCaptureProcessor`

`WingmanCandidateCaptureProcessor`在Cruise每6个ClientSimTick捕获一次；获得服务器短期`HighRate10Hz`授权后，在Combat/EmergencyAvoid/近障碍每3 Tick捕获一次。客户端可以申请高频档，但不能凭自报`SubmissionMode`自行取得服务器10Hz预算。模式切换记录`SUBMISSION_MODE_CHANGED`；不得用渲染帧Delta控制捕获。

### 4.5 固定翼积分

每个30Hz固定步：

1. 计算母舰预测Anchor和Flight环形Guidance。
2. 合成Corridor、槽位、邻居分离、碰撞预测和紧急拉升方向。
3. 将期望速度限制在Min/Cruise/CatchUp。
4. 按Acceleration/Deceleration限制速度变化。
5. 按MaxTurnRate限制速度方向变化。
6. `Position += Velocity * FixedDt`。
7. 前向轴对准Velocity，Pitch/Yaw来自航向，Roll根据横向加速度并限制MaxBank。
8. 更新LastSafe状态和路径摘要。

禁止直接插值Position到槽位、停速等待、逐架Chaos或由Representation反写逻辑Transform。

## 5. Candidate、Acceptance与按包验证

### 5.1 Accepted Snapshot身份

Wingman/Ground共享：

`FGuLiAcceptedClientStateRef = {MatchEpoch, SimulationGroupId, GroupGeneration, FlightOrPartitionId, AuthorityEpoch, AcceptedSnapshotSequence, RosterRevision}`

- 每Flight/Partition的AcceptedSnapshotSequence在同一GroupGeneration内单调递增，跨Roster和Lease不重置。
- AuthorityEpoch标识由哪个Lease代次产生。
- FireIntent再携带Source WingmanId/EntityGeneration。
- 不存在SourceMode、WriterEpoch、服务器补位序列或固定Canonical Slot。

### 5.2 `FGuLiWingmanFlightCandidate`

Header至少包含：

`Protocol, MatchEpoch, ConnectionGeneration, SimulationGroupId, GroupGeneration, FlightId, AuthorityEpoch, LeaseId, RosterRevision, RequiredActiveMemberMask, AbilitySetRevision, FormationCommandRevision, FormationDefinitionChecksum, RequestedSubmissionMode, ObservedGrantRevision, ClientSimTick, CaptureEstimatedServerTime, FrameSequence, BaseAcceptedSnapshotSequence, NavSchema, NavChecksum, TuningRevision, ObstacleRevision, CarrierSourceRef, TrailSampleCount`

Flight Payload：

`FlightMode, Ring, Phase, CorridorRevision, CurrentLeaf, CurrentPortal, Anchor, AnchorVelocity, StateHash`

Member：

`WingmanId, EntityGeneration, SlotIndex, MemberSequence, PositionDelta, Velocity, Quaternion, Bank, MemberStateHash`

当`ClientSimTick - PreviousSubmittedClientSimTick`大于当前模式正常间隔时，附带最多4个压缩TrailSample。Trail必须按ClientSimTick严格递增，并覆盖从Base Accepted样本之后到本次端点的关键转折；Retained Resume选择还必须把所有线传样本限制在Candidate端点前2秒以内。服务器继续以3.5秒权威历史和逐段运动学校验，超容量或过龄直接Reject并要求客户端Rebase/提高发送率，客户端窗口不得放宽服务端窗口。

新`GroupGeneration`的首个有效帧从该代次本地状态初始化FlightMode链，不能沿用已退役身份的上一模式；Stale或无法证明身份/代次的私有历史不能进入Resume wire。

### 5.3 原子Bootstrap/Resume/Takeover Batch

三类非Active恢复包共用`FGuLiAtomicSimulationCandidateBatchHeader`：

公共合同中的Flight字段对Ground实现映射为Partition字段，原子性、Roster和Baseline规则完全相同。

`Protocol, BatchId, BatchKind, SimulationGroupId, GroupGeneration, AuthorityEpoch, LeaseId, FrozenRosterRevision, FrozenRequiredFlightMask, FrozenRequiredMemberMaskHash, BaselineKind, BaselineRevision, BaselineHash, IncludedFlightMask, ClientBatchStartTick, BatchPayloadBytes, FragmentCount, BatchPayloadHash, bAtomicCommit`

其中：

- Bootstrap绑定SpawnBaselineRevision/Hash。
- Resume绑定服务器为当前Stale/Unavailable组冻结的ResumeBaselineRevision/Hash。
- Takeover绑定TransferCommit或其后Roster修订产生的TransferBaselineRevision/Hash。
- IncludedFlightMask必须精确等于FrozenRequiredFlightMask，每个Flight内部仍精确覆盖Frozen RequiredMemberMask。
- `bAtomicCommit`必须为true；BatchKind、Lease、Roster、Mask或Baseline任一不匹配都整批拒绝。

Bootstrap/Resume/Takeover需要的AbilityConfig与Six-Scope ACK必须先经同一可靠ActorChannel提交，再允许客户端发送首个原子Candidate；服务器Gate保持不变，正确性依赖可靠有序发送而不是提前放宽ACK条件。

逻辑Batch可由UE NetSerializer分片，但服务器只允许每Group/AuthorityEpoch暂存一个BatchId，最多8片/64KiB，0.5秒AssemblyDeadline。分片阶段只做大小、身份、索引、重复和Hash Gate，不写Accepted Store、不Relay、不刷新LastValidCandidateTime。全部到齐后在同一冻结Roster/Baseline切面运行普通Validator；所有Flight通过才在一个游戏线程事务中推进各自AcceptedSequence、把全部FrozenRequired Flight的LastValidCandidateTime设为同一AcceptedServerTime并发布，任一Flight失败或Deadline到期则整批释放且所有Flight保持原值。Deadline Timer只做Reject/释放，不运行运动逻辑。

### 5.4 事件驱动Validator

Candidate网络入口按以下顺序处理：

1. 包大小和连接/Group Token Bucket，按服务器持有的AllowedUploadRateClass限流，超频在完整解码前拒绝。
2. Protocol、MatchEpoch、ConnectionGeneration。
3. Group/Generation、Active AuthorityEpoch/LeaseId、Owner。
4. RosterRevision、FlightId、RequiredActiveMemberMask和成员身份。
5. FrameSequence、BaseAcceptedSnapshotSequence、ClientSimTick、CaptureTime/FutureSkew/HistoryWindow。
6. Nav/Tuning/Obstacle版本。
7. CarrierSourceRef。
8. Trail和端点运动学：速度、加速度、转向、位移、Bank、朝向。
9. Leaf/Portal/净空、静态和动态Sweep。
10. Alive、FlightMode转换和Resume/Takeover规则。

`RequestedSubmissionMode`只是一项请求。服务器根据已接纳的Fire/Target战斗事件，或经验证的EmergencyAvoid、Leaf净空和动态障碍证据，授予有时限的`HighRate10Hz`；其余时间固定`Cruise5Hz`。绝对上限始终为10Hz，客户端自报不能提升AllowedUploadRateClass。

Validator仅由`CANDIDATE_RECEIVED`、收包凑齐产生的`ATOMIC_BATCH_ASSEMBLED`或Pending Carrier Ref解析事件触发。网络队列按游戏线程预算排空可以每帧检查队列，但没有包时不得遍历实体或运行运动逻辑。

CarrierSourceRef若尚未进入Ship CMC历史：

- 每Flight最多保留1个Pending Candidate；
- 插入时注册一次性0.25秒Deadline Timer；Ship状态到达或被新包淘汰时取消；
- Ship状态到达时事件驱动重试；
- 新Candidate到达时淘汰更旧Pending；
- Deadline回调只执行Reject/释放/计数，不重跑完整Validator、不Sweep、不遍历实体、不生成运动；
- 1Hz Lease维护只做已经过期对象的最终泄漏清理，不能代替0.25秒Deadline；
- 任何路径都不得生成运动或补写旧快照。

### 5.5 接纳与拒绝

合法普通Active Flight Candidate：

1. 对Quaternion归一化、浮点做协议规定量化并生成`ValidatedPayloadHash`。
2. 原子写入该Flight新的Accepted Snapshot。
3. AcceptedSnapshotSequence加1。
4. 更新LastValidCandidateTime。
5. 返回`FGuLiSimulationAcceptance`。
6. 按相关性转发相同`ValidatedPayloadHash`的Accepted Pose。

`FGuLiSimulationAcceptance`至少包含：

`Protocol, Group/Generation, FlightId, AuthorityEpoch, LeaseId, RosterRevision, FrameSequence, Accepted/Rejected, RejectReason, AcceptedSnapshotSequence, AcceptedServerTime, ValidatedPayloadHash, NormalizationFlags, AvailabilityAfter, AllowedUploadRateClass, GrantRevision, GrantExpiryServerTime, RebaseBaseline`

高频授权另使用可靠的`FGuLiUploadRateGrant = {Group/Generation, AuthorityEpoch, LeaseId, RateClass, GrantRevision, EffectiveClientSimTick, ExpiryServerTime, Reason}`。客户端只应用当前Lease且Revision更新的Grant，到期无需等待新包即退回Cruise5Hz；服务器收包时也按自己的Expiry即时计算AllowedUploadRateClass。

原子Batch返回`FGuLiAtomicBatchAcceptance = {BatchId, BatchKind, Group/Generation, AuthorityEpoch, LeaseId, FrozenRosterRevision, BaselineRevision, BaselineHash, Accepted/Rejected, RejectReason, CommittedFlightMask, AcceptedSnapshotSequence[Flight], BatchValidatedPayloadHash, AvailabilityAfter}`。只有Accepted时CommittedFlightMask才可等于完整FrozenRequiredFlightMask；Rejected时必须为0，不能返回成员级部分成功。

Rejected Candidate：

- AcceptedSnapshotSequence不变；
- Accepted Store Count不变；
- Relay Count不变；
- LastValidCandidateTime不变；
- 返回明确RejectReason和最后Accepted Snapshot Baseline；
- 只允许Owner在本地重放或软/硬Rebase，服务器不提供替代轨迹。

核心等式：

`AcceptedSnapshotTransform == Canonicalize(ValidatedCandidateTransform)`

`AcceptedRelayPayloadHash == Acceptance.ValidatedPayloadHash == ObserverAppliedPayloadHash`

### 5.6 Owner Rebase

- Owner保留至少2秒30Hz本地历史。
- 小误差以0.15～0.30秒临界阻尼修正Representation与Guidance。
- 大误差、错误路径、Roster/Lease变化或Resume失败时从服务器最后Accepted Baseline Hard Rebase。
- Rebase后客户端自行重算StateTree/路径/运动；服务器不演算恢复过程。
- Listen Host必须走序列化等价入口，不能因为共享内存跳过Candidate Gate。
- Active Roster Cut可靠携带对应切面的Accepted baseline；Owner只有在精确Revision/Hash ACK后才按该baseline重建本地链，不能凭本地旧姿态或服务器补算姿态推进Sequence。

## 6. 1Hz Lease、Stale与换主

### 6.1 Lease数据

`FGuLiLeaseTuple`至少包含：

`MatchEpoch, SimulationGroupId, GroupGeneration, AuthorityEpoch, LeaseId, OwnerPlayerGuid, OwnerConnectionId, LeaseState, TransferToken, IssuedServerTime, RosterRevision, NavChecksum, TuningRevision, BaselineAcceptedSnapshotSequence[Flight], TransferBaselineRevision, TransferBaselineHash, AbilityConfigRevision, AbilityConfigHash`

服务器Group Record：

- ActiveLeaseTuple
- PendingLeaseTuple
- AvailabilityState
- InitialCandidateDeadline和BootstrapAccepted标志
- ActiveLeaseState/Availability与PendingLeaseTransactionState（None/AwaitingOfferReady）
- Commit后的ActiveLeaseTransactionState（AwaitingBaselineAck/AwaitingTakeoverBatch/NoOwner）
- OfferReadyDeadline、TakeoverAckDeadline、RevisedBaselineAckDeadline、TakeoverCandidateDeadline和TakeoverOverallDeadline
- TransferBaselineRevision/Hash及冻结Roster/Required Masks
- LastValidCandidateTime[Flight]
- LastHeartbeatTime
- LastMaintenanceTime
- LastAcceptedSnapshot[Flight]
- LastConsumedDomainFireSequence[Source]
- AllowedUploadRateClass和HighRateGrantExpiry

没有运动时钟、运动源模式或服务端飞行状态。

### 6.2 1Hz Maintenance

`RunLeaseMaintenance()`由1秒Timer调用。允许调度误差为一个Server Frame；禁止在Server Tick中逐实体检查失联。

初次Grant把Availability设为Initializing，并设置`InitialCandidateDeadline=IssuedServerTime+3s`。Owner从Spawn Baseline运行私有30Hz模拟；首个`FGuLiBootstrapCandidateBatch`必须原子覆盖全部Required Flight，全部验证通过才一次性写入各Flight首个Accepted Snapshot、初始化LastValidCandidateTime并切到Active。此前Target/Fire/普通单Flight Store/Relay均关闭；首个Maintenance Tick发现Deadline已过仍未完成Bootstrap时直接Revoke。

PendingLease自身不继承旧Lease的LastValidCandidateAge，但Offer绝不暂停当前ActiveLease的Freshness：TransferCommit前仍按下方1/2/3秒规则推进旧Lease的Active/Stale/Unavailable/Revoke和Fire Gate。旧Lease若在Offer期间Revoke，Pending Offer可在自己的Ready/Overall窗口内继续；Commit仍冻结当刻最后Accepted静态切面。新Lease Takeover才使用独立保护期：

1. Offer设置`AwaitingOfferReady`、`OfferReadyDeadline=OfferTime+3s`和`TakeoverOverallDeadline=OfferTime+10s`。
2. TransferCommit继承该OverallDeadline，设置`AwaitingBaselineAck`和`TakeoverAckDeadline=min(CommitTime+3s, OverallDeadline)`。
3. 精确Baseline Revision/Hash ACK后进入`AwaitingTakeoverBatch`，设置`TakeoverCandidateDeadline=min(AckTime+3s, OverallDeadline)`。
4. Ready、Baseline ACK和Takeover Batch各自到达时先用服务器Now即时检查对应Deadline及OverallDeadline；已过期消息立即Reject，不等待下一Maintenance，也不改变事务或快照。
5. 首个全批Takeover接纳时才以接纳时间初始化新Lease的各Flight LastValidCandidateTime，并切到Active。
6. 任一Deadline在1Hz Maintenance到期，撤销Pending/当前新Lease并选择下一Backup重新Offer；若旧Lease仍Active则不影响旧Lease，没有可用Backup时进入NoOwner/Unavailable，仅在连接变化或1Hz维护时重试选择。
7. Awaiting/NoOwner期间Snapshot/AcceptedSequence/Transform保持不变，不Target/Fire，不因保护期执行任何运动。

Active后固定计算`GroupFreshnessAge = max(Now - LastValidCandidateTime[f])`，其中`f`只遍历RequiredActiveFlightMask且排除零成员Flight：

- `age < 1s`：Active。
- 首个Maintenance Tick发现`age >= 1s`：Stale，关闭新Target/Fire。
- 首个Maintenance Tick发现`age >= 2s`：Unavailable，维持最后快照并可靠通知隐藏。
- 首个Maintenance Tick发现`age >= 3s`：Revoke旧Lease。

如果某Flight曾因全灭而从Required mask中移除，之后15秒补员使其RequiredMemberMask从0变为非0，则服务器仅在Active、非Transfer、未Revoke状态记录一次该Flight grace起点。后续同批/后续成员加入不能滑动该起点；首个严格Candidate提交后立即清除。Freshness计算只在本次重新纳入required时临时取`max(真实LastValidCandidateTime, grace起点)`，不写Accepted Store，也不改变上述1/2/3秒阈值。

由于1Hz扫描和Timer调度，状态事件可以比理论Deadline晚`0～1000ms+1 ServerFrame`；报告必须同时记录Deadline和DetectionLag。状态转换只改Availability/Lease，不改Position、Rotation、Velocity、Bank、AcceptedSequence或SnapshotHash。

Heartbeat默认1Hz不可靠有序；合法Candidate也证明连接活跃，但只有合法Candidate刷新运动Freshness。Heartbeat不能把没有合法Candidate的组保持Active Combat。

### 6.3 Resume

Stale/Unavailable但尚未Revoke时，原Owner可提交`FGuLiResumeCandidateBatch`：

- Owner先请求Resume；服务器以当前Roster/Required Masks和每Flight最后Accepted Snapshot冻结ResumeBaselineRevision/Hash并可靠发送，Owner精确ACK后才提交；
- 引用每Flight最后Accepted Snapshot Sequence/Hash；
- 原子覆盖全部RequiredActiveFlightMask；
- 每Flight提供从Baseline后的客户端Trail；
- 通过普通运动/Nav/Sweep Validator；
- 所有Flight通过才原子恢复Active，并在同一事务把全部Required Flight的LastValidCandidateTime刷新为该Batch的AcceptedServerTime；
- 任一失败都不恢复Active，保持提交前的Stale或Unavailable并返回Rebase；只有1Hz Maintenance可按Freshness阈值继续推进Availability。

Resume接纳前，单Flight普通Candidate不得使Group部分恢复战斗。

### 6.4 优雅换主

顺序：

1. 服务器创建PendingLease并发送`LEASE_TRANSFER_OFFER`，携带Roster/Nav/Tuning和仅供预加载的Preview Baseline，同时启动3秒OfferReadyDeadline和从OfferTime起10秒OverallDeadline。
2. 新Owner校验资产并ACK Ready；Offer Baseline不得作为最终恢复切面。
3. 服务器原子`LEASE_TRANSFER_COMMIT`：冻结Commit瞬间RosterRevision、Required Masks、每Flight最后Accepted Snapshot、FireSequence高水位、AbilityConfig Revision/Hash和新的TransferBaselineRevision/Hash，旧Lease立即失效，新Lease成为当前Lease但Availability=Unavailable。
4. 服务器可靠发送Commit Baseline；新Owner ACK精确Revision/Hash后，从该静态切面启动本地30Hz模拟。
5. 新Owner提交全Required Flight Takeover Candidate Batch。
6. 全批通过后记录`FIRST_TAKEOVER_CANDIDATE_ACCEPTED`并恢复Active。

TransferCommit到首个Takeover接纳之间：

- Snapshot Sequence/Hash/Transform不变；
- Relay不得伪造新Pose；
- 新旧Owner FireIntent均按Lease/Availability Gate处理；
- 远端隐藏；
- 不存在服务端运动桥。

### 6.5 等待Batch期间的Roster变化

Damage/Death/Lifecycle权威不能因Bootstrap/Resume/Takeover等待而暂停：

1. 已接纳Shot导致Death时，服务器照常一次性提交Ledger/Dead并可靠递增RosterRevision、更新Required Masks。
2. 立即以`RosterRevisionChanged`取消尚未原子提交的暂存Batch；任何旧RosterRevision Fragment/Batch继续到达都整批拒绝。
3. 对Bootstrap重新生成SpawnBaselineRevision；对Resume/Takeover使用当前存活Mask和各Flight最后Accepted Pose重冻结新的BaselineRevision/Hash。死亡成员只从Mask移除，服务器不为幸存者生成新Pose。
4. 按BaselineKind分支可靠发送`SIM_BASELINE_REVISED`：
   - Bootstrap保持Initializing，原InitialCandidateDeadline不重置；ACK/新Batch必须在剩余窗口内完成。
   - Resume保持提交前Stale/Unavailable并继续使用原LastValidCandidateTime与1Hz Revoke；不创建Takeover Deadline，原Lease一旦Revoke就取消事务并永久拒绝迟到ACK/Batch。
   - Takeover重新进入AwaitingBaselineAck，设置`RevisedBaselineAckDeadline=min(Now+3s, TakeoverOverallDeadline)`；旧AckDeadline取消。
5. Takeover Owner ACK精确Revision/Hash后重新进入AwaitingTakeoverBatch，并设置`TakeoverCandidateDeadline=min(AckTime+3s, OverallDeadline)`；Bootstrap/Resume ACK不改变各自原Deadline语义。
6. 每类ACK/Batch到达入口都先检查当前Lease、BaselineKind、Revision及各自适用Deadline；不得把Takeover保护期套到Bootstrap/Resume。
7. Initializing/Stale/Unavailable期间Replenish只进入可靠Schedule，不实际Spawn；恢复Active后才按每Carrier队列生成，避免接管窗口不断改变Roster。

### 6.6 真实断线

本需求的CoreWingman和GroundMachineIntegration正式Profile固定为：保留Group，选择Backup Owner，并走Offer→Ready→TransferCommit→Commit Baseline ACK→Takeover Candidate Batch。销毁旧Group并重建只属于母舰真实销毁或另一套GameMode生命周期策略，不能让本需求的真实断线换主Gate通过。

## 7. 战斗、死亡与表现

### 7.1 本地索敌

- Client Owner使用已复制Commander Pose、Accepted Wingman/Ground Pose和Ship状态建立本地三维空间哈希。
- Acquire默认5Hz错峰；目标失效时立即运行。
- 排序：Enemy/Alive/Available/球形Range/本地LOS，然后DistanceSquared、TargetKind、StableId、Generation。
- 不运行服务器周期性TargetObservation生成器。
- 客户端候选只决定“想打谁”，不决定命中和伤害。

### 7.2 状态引用

`FGuLiSourceStateRef`为类型化Variant：

- Ship：`SourceGeneration + ShipCanonicalEpoch + ServerMoveRevision`
- Wingman/Ground：`GroupGeneration + FlightOrPartitionId + AuthorityEpoch + AcceptedSnapshotSequence`
- Commander：`SourceGeneration + ServerSimTick`

`FGuLiFireIntent`至少包含：

`SourceHandle, TargetHandle, SourceStateRef, OptionalClientSeenTargetRef, ClientFireTick, DomainFireSequence, WeaponAbilityId, WeaponDefinitionRevision, AbilitySetRevision, Aim, HitCandidate, ClientLOSPrediction`

`DomainFireSequence`在同一Source EntityGeneration内严格单调，跨Roster/Lease/重连不重置。Bootstrap/Transfer Baseline冻结LastConsumed高水位。

### 7.3 服务器事件驱动Fire验证

FireIntent到达时：

1. 以`MatchEpoch + SourceKind + StableId + EntityGeneration + DomainFireSequence`只读Find；若已有Reservation/终态，直接返回既有结果，不重复执行Gate或Damage。
2. 未命中时先做廉价Source身份、Generation和类型化状态存在检查；Wingman/Ground还必须匹配当前AuthorityEpoch/Lease且Availability=Active、Alive。旧Lease在此以StaleLease拒绝，不创建Reservation、不推进LastConsumed高水位。
3. 只有当前合法权威才原子FindOrReserve新的DomainFireSequence；并发重复只能共享同一Reservation。
4. 验证Source/Target类型化Ref和历史存在。
5. Source或Target属于ClientValidatedRelay时，其Accepted Snapshot Age均不超过Profile的CombatStateAge；Ship/Commander按各自类型化服务器状态Ref窗口校验。年龄在请求到达时即时计算，不等待下一次Watchdog。
6. Target必须Alive、Enemy、Available；Stale/Unavailable或状态过旧时不作为新目标。
7. 使用服务器持有的Ship/Commander/Accepted历史，在共同可验证时间附近检查球形距离和LOS；禁止向未来外推客户端状态。
8. 验证服务器冷却、武器配置、弹药和射速。
9. 通过后创建ShotId；Damage只由Damage Ledger提交一次。

同Lease历史窗口内较旧AcceptedSnapshot Ref可以合法，只要当前组仍Active且Ref未过期。旧Lease、Stale、Unavailable、Dead或历史过期全部拒绝。已接纳Shot/Projectile可以在Source随后Stale/换主后完成一次结算。

### 7.4 Damage Ledger

- 客户端不能提交Damage、HealthAfter、Death、Reward或Replenish。
- Ledger记录Source/Target、类型化StateRef、ShotId、DamageEventId、HealthBefore/After、CommitTime、幂等键和结果。
- 同一DamageEventId/DeathEventId/RewardEventId CommitCount必须为1。
- 致死DamageEvent稳定派生DeathEventId和RewardEventId，并分别进入有界幂等记录；`BeginServerEpoch`清理旧Epoch的Damage/Death/Reward域。
- Reward只通过可选窄Policy/Sink授予；未配置时明确记录`NotGranted/PolicyUnavailable`，不得回调旧ScoreUpdate或在Ledger中硬编码经济数值。
- Health<=0后服务器可靠提交Dead并更新Roster；迟到Candidate/Fire不得复活或继续伤害。
- Commander B↔B保持现有30HzCombat Phase。

### 7.5 Ship与Projectile

- `UGuLiCombatHealthComponent`为Ship提供服务器生命和OnRep。
- Ship移动继续CMC重演，不进入ClientValidatedRelay。
- `AGuLiStrikeProjectile`携带SourceHandle、SourceStateRef、Team、Damage、SweepRadius和ShotId。
- 服务器对已接纳Shot执行Segment/Sphere Sweep，命中Mass Wingman后进入统一Ledger；保留旧NPC分支。

### 7.6 权威表现

- Owner可立即播放可撤销Muzzle预测。
- Hit/Death/Reward只由服务器事件表现。
- 按连接维护有界、ACK/重试的Combat Presentation FastArray；EventId幂等，客户端只渲染一次。
- 预测被拒绝时淡出，不能残留命中或死亡表现。

## 8. 网络复制与远端重建

### 8.1 可靠流

`AGuLiWingmanStateReplicator` FastArray只承载：

- Group/Generation、RosterRevision和Required Masks；
- Member身份、Flight/Slot、Team；
- Health/MaxHealth、LifeState、StateRevision；
- Active/Pending Lease、AuthorityEpoch、Availability；
- ActiveLeaseState/Availability、PendingLeaseTransactionState、接管各Deadline和当前BaselineRevision/Hash；
- Bootstrap/Resume Baseline Revision和FireSequence高水位。
- TransferCommit冻结的Baseline Revision/Hash和FireSequence高水位。
- UploadRateGrant的RateClass、GrantRevision、EffectiveClientSimTick和ExpiryServerTime。
- GroupAbilityConfig的Ship/Group代次、AbilitySet/Definition/FormationCommand Revision、稳定AbilityId、Checksum和EffectiveClientSimTick。

Accepted Transform、Velocity、Quaternion、AcceptedSequence和FrameSequence不进入常规可靠FastArray，避免可靠队列承载连续运动。

### 8.2 不可靠流

- Client→Server：普通Flight Candidate、Atomic Batch Fragment、Heartbeat、FireIntent。
- Server→Owner：不可靠Acceptance/Reject/Rebase，以及可靠UploadRateGrant、Baseline/RevisedBaseline和Lease Transaction状态。
- Server→Observers：Accepted Pose Chunk。

`FGuLiAcceptedPoseChunk`按`GroupGeneration + FlightId + AuthorityEpoch + RosterRevision`同质分块，包含AcceptedSnapshotSequence、AcceptedServerTime、ClientSimTick、ValidatedPayloadHash、Anchor和成员样本。客户端只应用更新Sequence、已知Roster和当前GroupGeneration数据。

### 8.3 频率

| 对象/流 | 本地模拟 | 上行 | 服务端处理 | 下行 |
|---|---:|---:|---:|---:|
| Ship | 渲染/物理帧率 | SavedMove 20～30Hz | CMC重演15～30Hz | 沿用现有CMC |
| Wingman Cruise | Owner 30Hz | 每Flight 5Hz | 收包触发Validator/Store/Relay | 可见3D近5Hz、中/远≥2.5Hz；隐藏/图标1Hz |
| Wingman Combat/Hazard | Owner 30Hz | 每Flight 10Hz | 收包触发Validator/Store/Relay | 可见3D近10Hz、中5Hz、远≥2.5Hz；隐藏/图标1Hz |
| GroundMachine | Owner 30Hz | 5Hz/战斗10Hz | 收包触发 | 5～10Hz相关性 |
| Commander | 无客户端逻辑模拟 | 无 | 服务器30Hz | 现有10Hz Pose |
| Heartbeat | — | 1Hz | 1Hz Maintenance读取 | Lease离散事件可靠 |
| FireIntent | 客户端事件 | 按武器事件 | 收包触发Combat | Shot/Damage结果事件 |

### 8.4 远端表现

- Cruise使用约250ms插值缓冲，Combat/Hazard约150ms。
- 没有新Accepted Pose时，按最后Velocity/Rotation做最多500ms视觉外推。
- 外推只写Presentation Transform，不能进入目标、碰撞、FireIntent、Candidate或服务器状态。
- 500ms后记录`REMOTE_EXTRAPOLATION_ENDED`、停止外推并立即淡出；150ms内记录`REMOTE_HIDDEN_AFTER_EXTRAPOLATION`并完成隐藏。不得只冻结后继续显示；收到Stale/Unavailable可靠状态时立即隐藏。
- 只要三维模型仍可见，相关性调度的目标下行必须≥2.5Hz；1Hz仅用于已隐藏组或聚合图标。
- Resume后用首个新Accepted Pose重新建立缓冲，不从隐藏位置长期插值穿图。

### 8.5 Bootstrap与LateJoin

每个连接由服务器冻结同一`BootstrapRevision + BootstrapCutServerTime`：

1. Roster
2. AuthorityMap（Active/Pending Lease、AuthorityEpoch、Availability、Active/Pending TransactionState、Deadline和当前BaselineRevision/Hash）
3. Health
4. Dead
5. AcceptedSnapshot
6. GroupAbilityConfig

六Scope分别使用确定性序列化和Hash，共享同一Cut/Revision。客户端全部应用并ACK后才Ready，再消费更新Pose。不存在服务器生成的中间运动历史补播。

### 8.6 带宽目标

首版目标：

- 每个Air Owner Candidate平均上行≤0.12Mbps，Combat 1秒滚动峰值≤0.25Mbps。
- 每个相关观察者Accepted Pose平均下行≤0.25Mbps。
- Combat事件与可靠状态另计，但单客户端新增双向总平均≤0.50Mbps。
- GroundMachineIntegration必须提供独立实测预算。

Network Insights按connection/direction/stream_tag读取压缩/加密后的UE Packet/Bunch字节，包含UE头和重传，不包含IP/UDP/Ethernet；不能用应用Payload估算代替。

### 10.4 S0～S9阶段

#### S0 Bootstrap

- 地图加载后30秒内完成Nav/Tuning、Roster、Health、Lease和初始Baseline ACK。

- 3秒InitialCandidateDeadline前未完成时在下一1Hz Maintenance Revoke，不能部分Active。
- Commander Lease/Candidate数为0。
- 服务端Wingman运动、StateTree和路径调用数从开局即为0。

#### S1 悬停盘旋与非法Candidate

- 两艘Ship悬停60秒。
- Client Trace必须30Hz；Cruise Capture间隔严格为6个ClientSimTick，模式边界除外。
- 从Client Trace和Accepted Snapshot分别统计最低速度、机头夹角、Bank、间距和环形误差。
- 依次注入非Owner、旧Epoch、错误Lease、重复/倒退FrameSequence、旧/未来CaptureTime、无Grant的5Hz以上Burst、超10Hz Burst、超速、转向跃迁、错误NavChecksum、穿障Candidate、缺片超时Atomic Batch、错误Baseline Hash、旧RosterRevision和不完整IncludedFlightMask。
- 每条非法包恰好Reject一次，AcceptedSequence/Hash、StoreCount、RelayCount和LastValidCandidateTime均不变。
- S1-Control不注入非法包，比较Commander 1800个30Hz FixedStep，DroppedStep=0。

#### S2 侵入、转向与绕障

- Blue Ship通过正式输入沿航点进入Red区域。
- Red Ship通过正式输入执行一段防御转向/拦截路线后悬停；Blue/Red Wingman必须分别产生非零位移与有效Heading变化样本。
- Blue/Red Commander各至少20个单位走正式地面导航并完成一次转向；GroundMachineIntegration中双方Ground Owner各走至少2个航点并完成一次转向。
- 路径至少经过3个Portal，且相对直线偏移至少2×AgentRadius。
- 固定动态障碍横穿目标Flight Corridor，客户端收到ObstacleRevision后进入EmergencyAvoid或重规划。
- 服务器只在Candidate到达时验证Portal/Sweep，不产生路径。
- 首次满足敌对Range/LOS并产生已接纳战斗证据后，服务器授予`HighRate10Hz`，客户端切换Cruise→Combat，Capture间隔从6 Tick变为3 Tick；伪造自报模式不得获得授权。

#### S3 自动交战

Core必须完成：

- Blue/Red Wingman→Enemy Commander Soldier。
- Ship→Commander Soldier。
- Wingman↔Wingman。
- Wingman→Enemy Ship。
- Commander↔Commander。
- Blue与Red Commander Soldier各至少1个通过真实Damage Ledger死亡。

每个方向先生成`TARGET_ELIGIBLE`证据，随后只允许生产客户端本地Acquire和正式FireIntent。服务器不得指定目标或直接注入Damage。

至少一条合法FireIntent引用当前Lease/AuthorityEpoch下、历史窗口内且落后最新值至少2个AcceptedSnapshotSequence的Source Ref并接纳；旧Lease、Stale和过期Ref各拒绝一次。

命名用例`CombatStateTooOld`必须在Availability仍为Active、下一次1Hz Watchdog尚未执行的窗口内，分别制造Source State Age和Target State Age超过CombatStateAge；预期`SourceStateTooOld`和`TargetStateTooOld`各拒绝一次，证明战斗入口即时计算年龄。

GroundMachineIntegration另完成Ground与Commander/Wingman/Ship六个双向方向。

`S3C-AB`和`S3C-BA`使用同一对满血Wingman、同一把致死武器和同一捕获Barrier：AB先释放Blue(A) FireIntent，预期Red死亡、随后Red(B)以`SourceDead`拒绝；BA反向释放并镜像结果。两角色各只允许一次Damage/Death Commit，最终Ledger除胜负Team镜像外一致。

#### S4 死亡与幂等

- Red侧通过真实Fire/Damage链击毁Blue同一Group中3架Wingman；Blue侧另击毁至少1架Red Wingman。
- 目标选择、Range、LOS、冷却、Shot、Damage、HealthZero和Death全部走生产链。

- GroundMachineIntegration中Blue/Red Ground各至少1台通过敌方正式Fire/Damage链死亡。
- 三个独立幂等run分别重复Fire、Overlap和并发输入；每个目标Damage/Death/Reward/Replenish Schedule CommitCount均为1。
- Dead后迟到Candidate Store/Relay/Fire/Damage应用数为0。

#### S5 撤离、归队与补充

- Blue Ship正式输入撤离。
- 幸存Wingman从Client Trace和Accepted Snapshot证明保持最低速度、正确Bank并归队。
- 每个Carrier独立按Death时间排序、每15秒补1架：Blue 22→23→24→25，Red 24→25。
- 新成员先可靠进入Roster，之后随合法Flight Candidate首次进入Accepted Snapshot；服务器不生成过渡轨迹。

#### S6 弱网、重复与乱序

- 只对Blue Owner施加RTT约500ms、上下行Loss=5%。
- Capture节奏仍是Cruise 6 Tick、Combat 3 Tick；网络只改变到达，不改变客户端模拟。
- 单调新包可接纳，乱序旧包、重复包、旧Lease和旧Group包不Store、不Relay。
- 持续合法5Hz/10Hz输入不得误入Stale；若Loss形成真实超过阈值的空窗，则按1Hz状态规则进入并留下证据。
- 四个脚本必须真实捕获2条消息、释放2条、应用1条、丢弃1条；零捕获不能Pass。
- `S6-CorrectionReverse`：先释放较新的Acceptance/Rebase，再释放较旧Baseline；应用新值，旧值以`BaselineSequenceRegression`丢弃。
- `S6-DeathBeforePose`：先释放可靠Death，再释放更早的Accepted Pose；应用Death，Pose以`EntityDead`丢弃。
- `S6-LeaseBeforeOldProposal`：先释放新Epoch TransferCommit，再释放旧Owner Candidate；应用Commit，Candidate以`LeaseOrAuthorityEpochMismatch`拒绝。
- `S6-RespawnBeforeOldPose`：先释放新GroupGeneration Roster，再释放旧Generation Pose；应用Roster，Pose以`GroupGenerationMismatch`丢弃。

#### S7 Lease Loss、换主与断线

`S7-LeaseLoss`：

1. 丢弃当前Owner的Candidate和Heartbeat。
2. 1Hz Watchdog依次产生Stale、Unavailable、Revoke；DetectionLag在`0～1000ms+1 ServerFrame`。
3. Revoke后服务器选择Backup，并严格执行`Offer → Ready → TransferCommit(new AuthorityEpoch) → Commit Baseline ACK`；Commit冻结的仍是最后Accepted静态快照和Fire高水位。
4. 新Lease在Awaiting状态只走3秒ACK、ACK后3秒Candidate和10秒Overall Deadline；旧Snapshot Age不得使它在下一Maintenance立即Revoke。
5. Backup从Commit Baseline运行私有模拟并提交全组Takeover Candidate Batch；通过后才恢复Active。
6. 从最后Accepted到Backup首个Takeover接纳之间，Snapshot Sequence/Hash/Transform、StoreCount和RelayCount不增加。
7. Stale/Unavailable新Target/Fire/Shot接受数为0；Revoke后旧Owner Candidate/Fire永久接纳数为0。

`S7-Graceful-FireBeforeCommit`：

- 在一次Watchdog Tick刚结束后发送Offer，并在Offer与TransferCommit之间额外接纳一个旧Owner Candidate；该Candidate接纳后、旧Lease仍为Active时，捕获一条已提交但由网络代理暂扣的旧Owner FireIntent。Commit Baseline必须等于更新后的最后Accepted Snapshot，且不得等于更早Preview Baseline。
- 此后暂停旧Owner Candidate，并让Pending Owner延迟Ready；在`Now >= LastValidCandidateTime + 1s`的首个1Hz Watchdog Tick上，旧ActiveLease必须进入Stale并记录`ACTIVE_LEASE_STALE_DURING_PENDING_OFFER`，PendingLease仍保持`AwaitingOfferReady`。测试时钟必须保证Ready仍早于OfferReadyDeadline。
- 旧Lease进入Stale后，Snapshot Sequence/Hash/Transform、StoreCount和RelayCount均不得推进，新Target/Fire接纳数为0；不得因Pending Offer存在而延后Stale/Unavailable/Revoke。随后允许Ready/TransferCommit继续，并只冻结该最后Accepted静态Baseline。
- 顺序为FireSubmitted < TransferCommit < FireReceived < ShotRejected(StaleLease)。
- 该旧Lease Fire不得创建Reservation或推进LastConsumed高水位；Takeover接纳后，新Owner使用Commit冻结高水位+1的首个FireIntent必须能够正常Reserve并接纳。

`S7-Graceful-DamageAckRace`：

- Shot已经服务器接纳，在TransferCommit后、Takeover Batch接纳前让该Shot造成一名成员Death。
- Death/Ledger只提交一次并递增RosterRevision；已暂存Takeover Batch以`RosterRevisionChanged`整批取消，Store/Relay均为0。
- 服务器以存活Mask重冻结`SIM_BASELINE_REVISED`，新Owner ACK后重交全组Batch；旧死亡成员不复活，幸存者Pose Hash不被服务器改写。
- Revised Baseline发送时新的ACK Deadline为`Now+3s`且受原Overall Deadline约束；ACK后Candidate Deadline再次从ACK时起算3秒且同样受Overall约束，旧Deadline不得触发误撤销。
- 本角色仅在Non-Shipping Manifest把ReplenishSeconds覆写为1秒并延迟Revised Baseline ACK约1.5秒，强制产生`deferred_replenish_due_count>=1`；Unavailable期间Spawn=0，Takeover恢复Active后该Schedule恰好Spawn一次。S5仍以正式15秒值验收平衡节奏。
- 延迟Damage ACK/同DedupeKey重放只能返回既有终态，不能再次扣血。

`S7-ActualDisconnect`：

- 真实断开当前Active Owner。
- 正式Profile保留Group；BlueBackupA故意错过OfferReadyDeadline，下一次1Hz维护取消Pending A并选择BlueBackupB。
- BlueBackupB执行Offer/Ready/TransferCommit/Commit Baseline ACK/Takeover全链；无Backup阶段保持NoOwner/Unavailable。
- 新Epoch首个全组Takeover接纳前保持Unavailable，旧Owner消息永久拒绝，服务器运动写入为0。

#### S8 Spectator/LateJoin

- Spectator/LateJoin没有Lease，Candidate/Fire接受数为0。
- S8A在首次交战前连接。
- S8B夹在一次非致死Damage和最终致死Shot之间。
- S8C夹在Lease Offer与TransferCommit之间。
- Bootstrap六Scope在同一Cut逐项Hash一致，2秒内收敛，无幽灵、双Owner或死亡复活。

#### S9 正式规模与压力

- 4个独立Air Owner、4舰、100 Wingman、500 Commander运行10分钟。
- S9-Control同硬件/地图/seed保留4舰和500 Commander但关闭Wingman。
- S9-Feature开启100 Wingman。
- 客户端统计30Hz StateTree/Path/Steering/Integration。
- 服务器统计Packet Gate、Validator、Accepted Store、Relay、Combat Ledger和1Hz Watchdog。
- 服务器运动/StateTree/A*计数必须为0。
- H4000-OwnerSimulation运行4000无渲染客户端实体。
- H4000-ServerValidator播放5Hz Cruise/10Hz Combat录制包，只测试Validate/Store/Relay，不报告成服务器模拟4000架。

### 11.3 频率与Lease

- Client Simulation固定30Hz；Cruise Capture间隔6 Tick，服务器授予HighRate10Hz后的Combat/Hazard为3 Tick，模式切换边界单独标记。
- AllowedUploadRateClass只能由服务器写；无HighRate Grant时超过Cruise5Hz、任何时候超过10Hz的包都必须在昂贵Nav/Sweep前限流。
- 每次HighRate切换必须有当前Lease的可靠GrantRevision、EffectiveClientSimTick和Expiry证据；客户端自报、旧Grant、过期Grant带来的10Hz接纳数为0。
- 服务器Validator Trigger必须是PacketReceived、AtomicBatchAssembled或PendingCarrierResolved，其他触发数为0；AtomicBatchAssembled只能由收包凑齐触发。
- Watchdog间隔`1000ms ± 1 ServerFrame`，每帧逐实体扫描次数为0。
- Initializing超时以及Stale/Unavailable/Revoke事件分别在理论Deadline后的`0～1000ms+1 ServerFrame`发生。
- Stale/Unavailable期间Snapshot Sequence/Hash/Transform不变，新Target/Fire/Shot接受数为0。
- Resume Baseline Sequence/Hash必须等于Transfer/最后Accepted冻结值；首个全组Resume接纳前Availability不得Active。
- Offer→Commit间若有新Accepted Snapshot，Transfer Baseline必须等于Commit瞬间的新值而不等于Preview；精确Revision/Hash ACK后才允许Takeover。
- Revoke/TransferCommit后旧Owner Candidate和FireIntent接纳数永久为0。
- Pending/New Lease Awaiting阶段不使用旧LastValidCandidateAge：Offer后3秒Ready、Commit后3秒ACK、ACK后3秒Candidate和从Offer起10秒Overall Deadline均有事件证据；超时撤销并选择下一Backup，无Backup时NoOwner/Unavailable且运动写入为0。
- Pending Offer不得为旧ActiveLease续鲜或暂停Watchdog：`AwaitingOfferReady`期间旧Owner停包后，首个满足Age>=1秒的1Hz检查必须产生Stale和`ACTIVE_LEASE_STALE_DURING_PENDING_OFFER`；`PENDING_OFFER_PAUSED_ACTIVE_FRESHNESS=0`，其间战斗接纳和快照推进均为0，Pending Owner仍只能按自身Ready/Overall Deadline继续。
- 迟到Ready/ACK/Takeover Batch在消息入口以DeadlineExpired拒绝，接纳数为0；1Hz Maintenance只负责没有消息时的撤销/重选。
- Takeover等待期Death必须取消旧Roster Batch、重冻结Baseline并重ACK；幸存者Accepted Pose Hash不变。实际Replenish Spawn在Active前为0。
- Takeover中的每次SIM_BASELINE_REVISED都必须生成新的RevisedBaselineAckDeadline；精确ACK后才生成新的CandidateDeadline，两者均受原OverallDeadline封顶，旧Deadline导致的撤销数为0。
- Bootstrap Revision变化不得重置InitialCandidateDeadline；Resume Revision变化不得创建Takeover Deadline或延后原Revoke，原Lease Revoke后的ACK/Batch接纳数为0。
- S7-Graceful-DamageAckRace必须满足`deferred_replenish_due_count>=1`、`pre_active_spawn_count=0`、`post_active_spawn_count=1`，并按ScheduleId证明只释放一次；空样本不得Pass。
- Initializing期间只有首个全Required Flight Bootstrap Batch可原子激活；部分Flight接纳、Target/Fire或普通Pose Relay数为0。
- Stale/Unavailable期间当前Lease Owner必须能够进入私有BootstrapOrResume模拟并生成恢复Batch；该私有运动不得写入共享状态，服务器运动计数仍为0。

### 11.5 战斗

## 14. 风险与备忘

- 5Hz巡航快照会增加远端插值延迟；应先调表现缓冲，不把服务器运动模拟重新加回来。
- 500ms RTT时Fire引用的Accepted Snapshot更旧；通过LagLoss专用CombatStateAge和服务器历史验证处理，不允许未来外推。
- 长间隔Candidate的弯曲轨迹需要TrailSample；容量不足时Reject/Rebase，而不是服务器猜测路径。
- 客户端主运动降低服务器成本，也降低了运动反作弊强度。服务器仍必须校验速度、转向、Nav和Sweep；不能退化成只检查格式。
- 1Hz Watchdog意味着状态检测最多晚1秒，这是明确接受的性能换取；战斗入口仍按Snapshot Age即时拒绝过旧Source。
- Stale/Unavailable期间逻辑快照冻结但远端会隐藏；录像和测试必须区分客户端视觉外推与共享逻辑状态。
- 玩家Ship仍保留CMC重演。若未来连Ship也改成纯Relay，必须另开需求并评估作弊、碰撞和纠正影响。
- Ground正式类、导航和武器尚未由本文证明存在，合同Harness不能冒充玩法完成。
- 服务器按包Sweep仍可能成为热点；先做批量解码、Flight聚合、碰撞查询预算和空间索引，不恢复持续飞行Tick。
- 当前工作区可能有用户其他修改。实施时只改明确范围，不恢复、删除、格式化或覆盖无关文件。
