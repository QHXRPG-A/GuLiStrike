# PIE性能基线与快照多线程优化 — 技术方案

## 技术选型与执行边界

使用源码UE5.7已有`UE::Tasks`、`ParallelFor`和工作线程池，不修改引擎、不新增Runtime模块。协程能暂停与恢复，但不自动并行；蓝图Delay/定时器不作为CPU多核优化。项目表现合同继续由[guli-client-presentation](../../.agents/skills/guli-client-presentation/SKILL.md)维护。

通用数据流：游戏线程准备不可变快照 → 工作线程按批独立计算 → 所属线程校验版本并顺序提交。Snapshot存纯值、数组、矩阵和稳定身份，不允许工作线程解引用裸Actor/组件/Widget或临时UObject指针。资产引用仍由反射对象持有，资源解析不进入工作线程热路径。

每个World拥有独立输入/输出缓冲和任务生命周期；UI再按LocalPlayer区分视图、阵营、选择和投影修订。销毁、席位切换、Widget重挂载与Epoch切换使旧结果失效。任务退出前快照与输出内存必须存活，不能捕获即将返回的栈引用。

## 已测基线

采用[需求中的完整事实与限制](../RequirementDocument/20261010-PIE性能基线与快照多线程优化.md)。重点：200单位37.89→29.43 ms/26.39→33.98 FPS；压力78.63→77.44 ms/12.72→12.91 FPS未证实收益。压力GT约77.43 ms、GPU约28.08 ms；SceneUI Paint7.93 ms、服务端避障候选5.53 ms、Projectile Movement自身4.23 ms、事件复制自身3.08 ms（单次尖峰28.91 ms）。这些耗时不能按线程数直接相除或相互重复累计。

压力镜头大部分单位可见：三轮每客户端约592/576/578可见，呈现跳过约4/14/12单位每帧。该基线适合分析大量可见负载，不能替代大规模屏外收益对照；服务器逻辑仍运行。

## 涉及入口与实施顺序

| 顺序 | 入口 | 纯计算候选 | 保留在所属线程的工作 |
|---|---|---|---|
| P0 | 场景UI `GuLiSceneUIWidget`、HUD及注册表 | 投影、完整图元裁剪、固定模板变换、顶点/索引准备 | 来源读取、MID/纹理引用、Widget生命周期、Slate绘制命令提交 |
| P1 | 专服 `GuLiCommanderPredictiveAvoidanceProcessor` / `GuLiCommanderAvoidancePolicy` | 基于共享只读连续快照与网格的各单位候选查询和排序 | Mass执行合同、按既有遍历次序消费结果和更新单位状态 |
| P2 | `GuLiCommanderPresentationActor`、`GuLiClientFlightPool` | 历史样本姿态、纯轨迹/显示位置及完整范围计算 | 样本/可靠状态接纳、目标解析、组件/ISM/Niagara上传和生命周期结算 |
| 独立问题 | `GuLiFlightReplication` | 可评估纯事件编码与有序分段准备 | 连接状态、可靠RPC、发送顺序和预算检查；先诊断队列增长与包数上限 |

P0/P1优先评估，不能因Scope较大就假定全量可并行。P2只有拆分测量证明纯计算足够大才实施；Ship物理移动和世界碰撞不直接移到通用工作线程，沿用引擎已有异步接口或另行设计。网络积压不是本方案自动附带的协议修改。

## 场景UI候选

1. 在最终单位插值/机械姿态修订发布后，从注册来源和LocalPlayer读取本帧输入。复制投影矩阵、完整图元范围、形状模板编号、颜色、层次、资源索引和稳定排序号。
2. 按图元批而不是每个单位创建任务；每批预先分配独立输出，禁止多个任务同时向共享TArray追加或改变同一缓存条目。
3. 屏幕边缘和近裁剪面保持完整裁剪路径；内部快速路径必须与串行路径结果一致。保留既有Slate层次、图元次序、16位索引上限与分段规则。
4. 合并只按原稳定顺序处理，不以任务完成次序改变绘制层次。UI内容/投影/几何修订双缓冲；结果过期时明确丢弃，视图变化立即使用当前输入或串行回退。
5. 首个候选保持当前帧结果合同，不擅自改成F+1 UI。HUD继续`EndHUDFrame()`双缓冲、空提交清空和F到F+1有效/F+2过期。若未来考虑一帧延迟，需要单独记录并验证。
6. 单独测准备、计算、合并、Paint提交、等待和分配量。原7.93 ms中对象处理与Slate提交部分不会因几何并行自动消失。

## 避障候选

1. 本域本次执行只读连续单位快照及环境快照，先完成网格构建并冻结。确认Mass处理器调度和外部访问声明，不直接从工作线程读取正在变化的Fragment/UObject。
2. 按单位索引批执行候选查询。单位前12、环境前2、最终消费12、威胁排序和环境优先槽位维持；每批拥有独立工作数组与环境代次标记，不能共享原可变Scratch或计数器。
3. 结果按原单位遍历顺序提交；30 Hz三相调度、改令强制更新、预测/软避障职责不变。不能为了异步跨帧而让服务器使用上一帧候选。
4. 汇总批内计数后一次归并，避免逐候选原子操作抵消收益。发现输入版本变化或任务失败时本次执行串行回退。
5. 并行前后比较保留前缀、候选顺序、停止/交叉/改令/环境边缘行为和实际移动量。该项属于服务端CPU优化，整进程PIE与客户端独立成本分开报告。

## 单位与弹丸纯计算候选

保持网络时钟、可靠结束和屏外预测持续处理。普通单位屏外呈现约5 Hz，实际经过时间与身份错峰不变，回屏立即求当前姿态；当前/历史枪口解析仍复用完整键缓存，不能由多个任务同时填充同一缓存。

弹丸先冻结当前目标姿态与时间，再按稳定槽位计算纯预测结果、最终显示位置和完整Bounds；各渲染消费者复用一次结果。Slot/Generation/Epoch/输入修订核对后提交，旧结果不能写入已复用槽位。混合批次逐槽位裁剪，离屏退出清理粒子与灯光；僚机离屏停止尾迹生成、回屏从当前位置增长，不补画屏外历史。

这部分不是暂停服务器碰撞、减少玩法更新或只隐藏组件。首次候选保持本帧逻辑和表现时钟合同；数据所有权清楚后才考虑与独立任务重叠执行。

## 调度、版本和回退

- 使用引擎线程池，不按600单位创建600条OS线程。依据实测选择批大小，小负载继续串行；避免逐粒子微任务、嵌套长任务和工作线程阻塞等待。
- 每类独立运行开关，拟名`gs.SceneUI.ParallelGeometry`、`gs.Avoidance.ParallelCandidates`、`gs.Presentation.ParallelPose`；当前尚未创建这些CVar。串行与并行使用相同输入、规则和资源。
- 前置任务用依赖表达，提交在必要消费点进行；同帧必须等待的部分显式计时，不能把等待隐藏成“计算下降”。不承诺无同步。
- 世界/LocalPlayer、Epoch、Generation、来源与视图修订、帧号进入结果有效性检查。对象失效、模式切换和关卡结束必须安全排空或取消；取消不等于工作线程已停止访问内存。
- 同进程专服和双客户端共享CPU与线程池，记录Worker占用、关键路径、锁等待和总CPU时间；避免把GT减少却整帧变慢的候选作为收益。

## 后续验证矩阵与采用条件

采用同版本串行→单项并行→全部有效候选。固定视口、镜头、质量、人口、任务和资源；两负载保持真实移动、避障、交火，每个有效候选三轮配对，10秒热身、30秒记录，交替顺序。

| 镜头 | 要核对的证据 |
|---|---|
| 全部/大部分可见 | 可见数、实际反馈、几何/上传量以及当前最大可见负载 |
| 混合可见 | 可见/更新/跳过、混合LOD、尾迹中段可见及独立槽位退出 |
| 主要屏外 | 5 Hz错峰、表现提交减少、瞬时回收，服务器仍移动/交火 |
| Client1屏外、Client2屏内 | 两World独立裁剪，不能用另一客户端视图唤醒本World |
| 快速转镜头/总览返回 | 当前姿态立即恢复、无旧反馈重播或屏外尾迹补画 |

报告整帧/FPS、GT/RT/GPU平均及P95、内存、准备/计算/提交/等待、任务数量、实际活跃量、移动量、接纳/出生、组件/上传以及GPU Ribbon。零反馈或积压样本可用于整帧诊断，不能用于真实反馈承载收益；压力问题解除前不宣称500枚均展示或相关收益通过。

仅在功能/排序合同通过且三轮改善超过重复波动时采用默认并行；否则保留串行并记录原因。不预设30 FPS或按四线程推算四倍提升。
