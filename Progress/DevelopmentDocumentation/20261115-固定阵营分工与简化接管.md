# 固定阵营分工与简化接管 — 技术方案

## 技术边界

GuLiNetCore 承担纯数据权威、事务和恢复；GuLiStrike 连接玩法、UDP/EOS 和本地输入；GuLiStrikeEditor 管理本地启动。玩家席位、模拟职责、当前操作模式独立。保留对象标识、可靠传输和已有状态适配器；协议版本递增。

## 任务清单

- [x] 固定阵营权威及单席回退，移除负载调度。
- [x] 移除独立 Coordinator 依赖，接通客户端房间及本地／EOS 入房。
- [x] 红蓝资源分区、矿车账本与本体分离、生产和伤害路由。
- [x] 据点转交与同队粗粒度状态备份／接管。
- [x] 单席 F1/F2/F3 操作切换、HUD 与权限。
- [x] 双端／四端 PIE 启动入口。
- [x] 完成静态检查、玩法说明与增量归档。

## 玩家验收场景

地图：`/Game/Maps/LVL_CommanderMassPrototype`。

1. 默认双端：两端各算本队，F1/F2/F3 操作切换，Tab 空地切换。
2. 四端：指挥官只算本队 Mass 完整行为，无双算公共系统和操控单位。
3. Mass 攻击敌方建筑、Mass 攻击敌方 Mass、巡天攻击 Mass，均由目标模拟者扣血。
4. 建造、生产 Mass、采矿、交矿、加工、选卡和阵营技能均走正确权威。
5. 据点换阵营后矿区与设施转交，新旧请求不重入。
6. 任一席位失联后队友接管并能操作全队；旧连接不能继续提交。
7. 整队离线与无法一致确认的网络分裂分别结束。

## 已接入的执行路径

- `GuLiNetTeamAuthority` 统一选择阵营的 Mass 与公共系统模拟者；常规对象使用固定阵营组，弹丸、效果和持续工作保留来源链。缺席席位自动回退到同队唯一在线成员。
- 出生事务直接引用 Mass 阵营组：无双生产完成后，新兵的初始模拟者就是指挥官；伤害继续按目标所有者结算。指挥官兵种选择不再迁移模拟权。
- 采矿车货仓仍以车辆标识查询，权威片段改存本队账户；矿位与矿量属于矿区组。资源、建造、生产、肉鸽和阵营技能通过已有事务链到对应模拟者。
- 据点被占领后，其矿区和设施组转给占领方无双，备份也改到新阵营队友。既有加工 FIFO 的收益归属保留。
- `GuLiNetPeerRoom` 在客户端维护成员和授权元数据。普通事务、状态和备份直接走 P2P；房主按变更发布目录，不执行兵种／资源逻辑，不接收负载上报，也不按帧扫描所有单位做调度。
- 独立服务源文件、SQLite／WebSocket 服务构建入口已删除，原服务产物未操作。旧服务验收启动器明确退出，不作为新版入口；原验收源未新增或运行。当前试玩入口为 Local PIE。
- UDP 使用本局共享的 `peers.json`；EOS 使用 Lobby 发布房间、席位与 PUID，随后走既有 EOS P2P。开局后不接受新成员、重连或权威返还。
- 玩家席位保留；另由在线阵营成员数决定可操作权限，`ActiveControlRole` 决定当前视角／输入／卡牌界面。F1 指挥官、F2 游骑兵、F3 巡天；双席在线时权限不会因按键越过席位。

## 粗粒度接管与边界

- 每个权威组每 2 秒尝试生成当前态备份，队友保留最近 2 份完整版本。备份与网络排队可能使实际最新完成版本更旧；队友不因保存备份而重复模拟。
- 3 秒没有有效包暂停；10 秒后由存活成员交换的失联报告确认，重选房主（需要时），封闭旧请求版本并恢复队友持有的完整快照。恢复窗口 15 秒。
- 恢复采用现有对象／系统当前态适配器，不回放历史事务。掉线端的未完成弹丸／临时效果清理，新于快照且无法恢复的对象丢弃。矿车账本允许回退，失效任务由恢复适配器清理／重建。
- 已明确离开的成员可立即进入同一恢复流程；有同队存活者时接管，无同队存活者时判负。
- 普通断线需要存活多数与报告一致。4 人局掉 1 人可以确认；2 人局断掉 1 人无法区分对端掉线与链路分裂，因此无结果结束。2 人局主动离队则可明确判负。
- 开局后尚无完整备份、恢复中再次失联、快照不完整或恢复超时，都无结果结束。第一版不做工业级多数派恢复、重连或状态对账。
- 正式 200／600 兵运行清单已在 2026-11-16 使用当前原生导出器刷新为 v45。v44 封装兼容不代表旧玩法目录结构仍兼容；内容契约变更时必须重新导出。网络不接受 v44 对端。

## 启动与玩家验收步骤

1. 打开 `/Game/Maps/LVL_CommanderMassPrototype`，正常点击播放。默认红方为所选角色、蓝方为无渲染指挥官，各自承担本阵营全部职责。按 F1/F2/F3 检查相机、输入、建造和卡牌入口。
2. 项目设置 **GuLi Local PIE → 四客户端 2v2** 开启后再开局：编辑器红方所选席位 + 同队另一席位 + 蓝方双席，共 1 个渲染端、3 个逻辑端。进程列表可由 `GetSessionStatus` 的 `logic_processes` 查询。
3. 四端下检查本队兵种、工程车、矿车在指挥官端；建筑、账户、肉鸽、阵营技能、游骑兵／巡天和非 Mass 召唤物在无双端。红蓝账户分别结算，造出的新兵直接属于指挥官。
4. 分别用兵种打敌方建筑、兵种打敌方兵种、巡天打敌方兵种，确认目标模拟端扣血和销毁。采矿、交矿后核对本队货仓／账户变化。
5. 占领据点，检查矿区和附属设施的模拟者、备份阵营变化；已交矿收益按原 FIFO 规则保留。
6. 四端开局并等待至少一轮完整备份后关闭红方逻辑队友。约 3 秒暂停、10 秒确认，再等待恢复；编辑器端应接管全队，F1/F2/F3 均可用。分别以指挥官、无双作为编辑器起始席位各验证一次。
7. 网络无法一致确认或恢复失败时，应结束为无结果，而非长期停在暂停或由两边同时模拟。关闭 PIE 后检查所有自有子进程退出，再重新开局。

EOS 无新增大厅界面：已配置 EOS 产品参数和客户端凭据时，房主用 `-GuLiTransport=EOS -GuLiHost -GuLiPlayers=4 -GuLiRoom=<本局GUID>`；其他三端用 `-GuLiTransport=EOS -GuLiLobby=<房主的Lobby ID>`，各自指定 `-GuLiTeam` 和 `-GuLiRole`，使用同一地图／清单。Lobby ID 在启动日志 `[GuLiPeerRoom]` 中输出；本轮未连接真实 EOS 服务验证。

## 指挥官掉线修复与复测（2026-11-16）

- 恢复阶段的Mass模拟者暂时为空，网格绑定延至新授权提交后进行，并恢复出生占位；避免Link因空模拟者失败。
