旧版“移动卡顿”的直接原因是 5Hz 摘要被客户端无插值地直接套用，不是服务端 Mass 只以 5Hz 模拟。现已迁移为 10Hz 逐兵帧与逐渲染帧插值；服务端位置仍是唯一权威，客户端平滑和预测只改变显示。

### 0.2 必须保留的已验证修复

- **频闪修复已验证**：表现层已经移除每 0.1 秒 `ClearInstances()` 全量重建，并把动态单位/脚环从会异步重建层级树的 HISM 切换为 ISM；当前采用稳定实例池、状态缓存、批量 Transform 原位更新，数量变化只补/删尾部，选择变化只更新脚环 CustomData。v0.3 不得回退这些措施。
- **场景可读性修复已验证**：原型图太阳强度 `10 → 80`、SkyLight `1.5 → 2.0`、固定曝光 EV100 `1 → 2`、补偿 `1.0 → 1.25`；全局雾密度 `0.036666 → 0.0025`、最大不透明度 `1.0 → 0.2`。PIE 前后截图已确认 Landscape 明暗纹理恢复，同时保留红蓝单位、脚环和 HUD 可读性。

### 0.3 迁移红线

- `GroupId + SlotIndex + AliveMask` 不再是玩家控制合同；不得只改名称后继续维持永久 25 人组。
- `SoldierId` 是唯一跨选择、指令和网络帧稳定的成员身份；Mass EntityHandle 只在本机使用。
- ControlCohort、OrderFormation 和 ReplicationCluster 必须彼此解耦。
- 新架构只有在对应测试或运行证据产生后才能勾选；历史 v0.2 smoke 不算 v0.3 验收。
- 客户端/服务器性能、复杂导航与 500 人同时移动、真正 seamless travel 和流场默认开启压力 Gate 未完成前，不得把阶段归档解释为全部需求最终验收。2026-08-27 用户明确要求先归档已验证基线，因此 Archive 只记录当前事实，未完成项继续保持“专项验收中”。

## 1. 技术选型与模块边界

### 1.1 技术路线

| 领域 | 采用方案 | 不采用方案及原因 |
|---|---|---|
| 权威 | Dedicated Server 30Hz 逐兵 Mass 权威 | 不做客户端权威或 Lockstep；导航、避障和浮点执行不能保证跨端确定。 |
| 选择 | 服务端空间哈希 + 确定性动态 Cohort | 不信任客户端成员列表；不再按固定组锚点选择。 |
| 导航 | 每个 OrderFormation 一条基于命名 `CommanderSoldier` 750cm NavData 的共享非 Partial 路径 | 不做 25 次独立寻路；不回退 Default NavData，也不继续使用直线穿越 Landscape。 |
| 个体移动 | 途中动态 1–5 列、终点完整 5×5 + Mass Avoidance | 不为 500 个 Soldier 创建独立 Chaos 刚体。 |
| 平滑 | 10Hz 不可靠成员帧 + 100ms 客户端插值 + 250ms 表现预测 | 不依赖 5Hz GroupState 直接驱动显示；预测不写权威状态。 |
| 流场 | 第一阶段通过后接走廊局部流场 | 不在 8km Landscape 上生成全局密集流场。 |
| 网络 | Legacy Replication、FastArray 当前状态、Owner Fast RPC + Reliable fallback/ACK、动态 PoseChunk | 首版不引入 Iris、Replication Graph 或 Epic MassReplication 主链路。 |

现有 `GuLiStrike` Runtime 模块继续承载首版。Build.cs 已有 NavigationSystem、MassMovement、MassNavigation、MassNavMeshNavigation、MassZoneGraphNavigation、MassCrowd 和 ZoneGraph 依赖，不拆新模块。

### 1.2 系统所有权

| 类/子系统 | 运行端 | v0.3 职责 |
|---|---|---|
| `UGuLiBattleAuthoritySubsystem` | Server/Standalone | 固定步长模拟、Soldier 注册表、空间索引、动态选择、指令、路径和成员帧捕获。 |
| `UGuLiCommanderAvoidanceCaptureProcessor` | Server/Standalone | 在引擎 Avoidance 后复制 `FMassForceFragment` 到项目输出 Fragment 并清空源 Force，供 30Hz 权威固定步读取，避免渲染帧率相关累积。 |

| `UGuLiCommanderNetSyncComponent` | 每连接 Owner Client + Server | OwnerOnly 选择、Fast+Reliable fallback 命令/ACK、`CommandKind + ClientCommandId` 去重 FIFO、10Hz Unreliable PoseChunk，以及 Protocol/MatchEpoch/名册快照 PoseReady 门控。 |

客户端镜像不得注册会写 Transform 的 Movement、Force、Navigation 或 Avoidance 处理器；只有客户端插值/表现处理器拥有镜像 Transform 写权限。

## 2. 公共数据合同

协议版本递增到 v0.3；v0.2 固定组协议不做混合会话兼容，版本不一致的连接在 Bootstrap 前拒绝进入可操作状态。

### 2.1 ID 与常量

```cpp
constexpr uint8 GULI_CONTROL_COHORT_CAPACITY = 25;
constexpr float GULI_COHORT_FILL_MAX_DISTANCE_CM = 30000.0f;
constexpr float GULI_SELECTION_SPATIAL_CELL_CM = 10000.0f;

USTRUCT()
struct FGuLiSoldierId
{
    GENERATED_BODY()
    uint32 Value = 0; // 0 invalid；MatchEpoch 内单调分配且不复用
};

USTRUCT()
struct FGuLiControlCohortId
{
    GENERATED_BODY()
    uint32 Value = 0; // 0 invalid；仅标识一次选择中的临时组
};
```

- `OrderId`、`SelectionRevision`、`StateRevision` 和 `FrameSequence` 使用各自独立的单调序列空间。
- SoldierId 不编码队伍、Cohort、Slot 或复制块；禁止根据整数位段反推出玩家编制。
- OrderFormation 内部可以维护 `FormationSlotIndex 0..24`，但该索引只属于当前指令，不能作为生命或网络身份。

### 2.2 OwnerOnly 选择状态

`FGuLiControlCohortDescriptor` 至少包含：

```text
CohortId
Members[1..25] : SoldierId
AliveCount
SelectionStateRevision
CurrentOrderId
CohortStatus : Ready | Pending | Moving | Rejected | Depleted
```

`FGuLiCommanderSelectionState` 改为：

```text
SelectionRevision
Cohorts[] : FGuLiControlCohortDescriptor
LastProcessedClientRequestId
```

- Cohort 描述只复制给拥有者，并只在选择或其 UI 状态变化时发送；不能作为 10Hz 运动载荷。
- Members 由服务端生成。客户端选择 RPC 中不存在 SoldierId 数组。
- Cohort 成员在其 SelectionRevision 内冻结；死亡只更新 AliveCount/状态，不自动补员。

### 2.3 Soldier 可靠当前状态

`FGuLiSoldierStateItem : FFastArraySerializerItem` 至少包含：

```text
SoldierId
Team
LifeState / Health
StateRevision
ActiveOrderId
AuthorityFlags
```

- FastArray 表示可最终收敛的当前状态，不是运动流或永久事件日志。
- 初次加入/重连必须先建立 SoldierId 名册和可靠状态，并应用不早于 Bootstrap Marker 的 `SnapshotMatchEpoch + SnapshotRevision`，随后才能消费对应 PoseChunk。
- 死亡、队伍、指令归属等事实不得仅存在于不可靠运动样本中。

### 2.4 不可靠成员帧

`FGuLiSoldierPoseChunk` 目标结构：

```text
ProtocolVersion / MatchEpoch
FrameSequence / ServerSimTick / ServerTime
ChunkIndex / ChunkCount
SpatialAnchor
Samples[1..32]

Sample:
  SoldierId
  RelativePositionXYZ : 10cm quantization
  VelocityXYZ : fixed-point quantization
  FacingYaw : uint16
  ActiveOrderId
  Flags : Teleport | Moving | DeadPose
```

- 单块序列化载荷目标不超过约 1000B；先按 Team、空间单元和 SoldierId 排序，再根据动态锚点检查 signed-int16/10cm 相对位置可编码范围。候选加入后若自身或块内既有成员将饱和，则在该 Soldier 前拆出新块；与 Cohort 和 OrderFormation 无关。
- FrameSequence 以完整捕获帧为单位递增；ChunkIndex/Count 仅用于该帧的独立分块，不要求全部到齐后才应用已收到的 Soldier 样本。
- 每个 Soldier 独立维护最近样本序列；旧帧、重复块或未知 SoldierId 样本直接丢弃。
- 协议 `GULI_MAX_POSE_CHUNKS_PER_FRAME=512` 与客户端 PendingPoseChunks 上限保持一致；Automation 使用满 32 样本的最坏值块验证 SoldierId、XYZ 位置/速度、Yaw、ActiveOrderId、State、Flags 全字段往返和≤1000B 预算。

### 2.5 RPC 保持意图级接口

```cpp
ServerRequestSelectionFast(FGuLiSelectionRequest Request); // Unreliable
ServerRequestSelection(FGuLiSelectionRequest Request);     // Reliable fallback
ServerIssueMoveFast(FGuLiMoveRequest Request);              // Unreliable
ServerIssueMove(FGuLiMoveRequest Request);                  // Reliable fallback
ClientReceiveCommandAck(FGuLiCommandAck Ack); // Reliable
ClientReceiveCommandAckFast(FGuLiCommandAck Ack); // Unreliable fast path
ClientReceivePoseChunk(FGuLiSoldierPoseChunk Chunk); // Unreliable
```

- `FGuLiSelectionRequest` 保留世界圆心、80/200/450m 半径档、Replace/Shift、ClientRequestId 和 Revision，不增加成员列表。
- `FGuLiMoveRequest` 保留世界目标、SelectionRevision 和 ClientCommandId。
- 命令 ACK 以 `CommandKind + ClientCommandId` 区分 Selection/Move 序号空间，并按 CohortId 返回 Accepted/Rejected、OrderId 和拒绝原因；允许部分成功。当前结构不携带“修正后的 Nav 目标”。
- 每个意图在 `t0` 发送一次 Fast RPC，`15ms` 未 ACK 时以同 ID/同 payload 再发一次 Fast，`150ms` 仍未 ACK 时发 Reliable fallback；每 ID 最多 2 次 Fast，Reliable ACK 回放不受 Fast replay cap 限制。
- 服务端以 `CommandKind + ClientCommandId` 定位 canonical 请求并比较完整 payload：同 ID/同 payload 只执行一次并回放缓存 ACK；同 ID/不同 payload 返回 InvalidRequest。Fast 重复缓存 ACK 最多回放 2 次，避免无限 Fast 放大。
- Selection 只允许一个 in-flight，后续请求进入最多 64 条 FIFO；Move 在 Selection 待确认时延后，并以 ACK 返回的 ServerSelectionRevision 重写 Revision。多个延后 Move 只保留最新目标（latest-wins）。
- Reliable/Fast ACK 经同一去重入口进入最多 64 条的客户端 FIFO，由 PlayerController 成批排空；`LastCommandAck` 只供最近状态/UI 查询，不作为逐命令消费源。表现预测只处理 `CommandKind == Move` 且 ID 匹配的 ACK。
- 服务端在 GameThread 完成权限、队伍、Revision、canonical 幂等和频率校验并提交选择/指令；30Hz 固定步负责推进 Soldier Transform。

## 3. 服务端选择与指令流程

### 3.1 Soldier 注册表和空间索引

- 出生时为 500 名 Soldier 分配稳定 SoldierId，默认红蓝各 250；Mass EntityHandle 存在服务器私有映射中。
- 权威固定步完成移动后，按 XY 所在 10000cm 单元更新空间哈希；死亡或不可控成员不进入可选索引。
- 查询补员候选时只遍历圆覆盖单元及 30000cm 补员半径需要的相邻单元，最终结果仍按精确二维距离校验。
- 为确保确定性，所有距离相同的比较以 SoldierId 升序打破平局。

### 3.2 确定性分组算法

1. 服务端从权威快照取得圆内存活、同队、可控 Soldier，并排序为种子列表。
2. Replace 清空旧 Cohort；Shift 先找出圆内命中的既有 Cohort，整组标记移除，并将其全部成员排除于本次新建列表。
3. 保留的 Shift Cohort 成员也排除于新建列表，避免重复选择。
4. 从最近未分配种子新建 Cohort；优先按动态质心吸纳其他圆内种子，最多 25 人。
5. Cohort 欠编时从圆外未分配友军补入；每次加入后更新质心，下一候选距离质心大于 30000cm 时停止。
6. 对剩余圆内种子重复；没有圆内种子时不执行圆外补员。
7. 分配新的 CohortId，更新 OwnerOnly SelectionState 和 SelectionRevision；成员顺序保持确定，供槽位分配初值和测试使用。

选中后成员不因移动或死亡而替换。全员死亡时 Cohort 从选择移除并递增 SelectionRevision，残骸表现按独立生命周期保留。

### 3.3 OrderFormation 生命周期

- Move Request 以 SelectionRevision 原子解析当前 Cohorts；旧 Revision 整体拒绝，不从客户端重建成员。
- 每个 Cohort 创建一份 OrderFormation，并复制下令时存活可控成员；一个批次共享 ClientCommandId，但各 Cohort 独立返回结果。
- 目标先投射到 NavMesh；不可达组返回 Rejected，其他组仍可 Accepted。
- Accepted 后为 Soldier 写入最新 ActiveOrderId。若其属于旧 Formation，则从旧 Formation 的 ActiveMembers 移除并触发旧槽位重排。
- 只选择不下令不会改 ActiveOrderId；Esc 和 Replace 也不会停止已存在指令。
- 全部 ActiveMembers 死亡、被新指令接管、到达并完成停稳或指令被服务器取消时，OrderFormation 结束。

## 4. 服务端 Mass 移动

### 4.1 Entity 配置

`ServerAuthority500` Archetype 至少包括：

- 项目 Fragment：SoldierIdentity、Team、Health/LifeState、ActiveOrder、FormationAssignment、`FGuLiMassAvoidanceOutputFragment`。
- 引擎 Fragment：Transform、Velocity、`FMassMoveTargetFragment`、`FMassForceFragment`、`FAgentRadiusFragment=750cm`，以及 NavMesh/Avoidance Traits 所需 Fragment。
- 仅服务端/Standalone 运行的 CommandDrain、Path、Formation、Movement/Avoidance、GroundFacing、Death 和 SnapshotCapture 流程。

`ClientSnapshotMirror` Mass Archetype 仅包含 SoldierIdentity、Health、Transform 和 MirrorTag；插值缓冲保存在表现层，不满足引擎 Movement/Avoidance 查询。

### 4.2 第一阶段处理顺序

| 阶段 | 处理器/能力 | 执行要求 |
|---|---|---|
| 固定步开始 | CommandDrain | Server/Standalone；消费已验证请求并创建 OrderFormation。 |
| 路径 | SharedPath | 每个 Formation 只向 `CommanderSoldier` NavData 请求一条有效且非 Partial 的 NavMesh 路径；访问 NavigationSystem 的操作在 GameThread。 |
| 槽位 | FormationAssignment | 目标组块和最多 25×25 槽位采用最小代价分配；成员或途中列数改变时重算当前指令槽位。 |
| 引导 | ElasticSlotTarget | 沿共享路径推进 MoveTarget；途中依据局部可走宽度压缩为 1–5 列，槽位修正向量不超过总转向需求 30%。 |
| 个体移动 | Mass steering/movement/avoidance | 由引擎 Fragment/Trait 完成静态导航约束和 Soldier 软分离。 |
| 收尾 | FacingGround | 根据速度更新 Yaw，完成 Landscape/NavMesh 地面贴合。 |
| 固定步末尾 | Death/SpatialIndex/SnapshotCapture | 先提交生命与索引，再按每 3 Tick 捕获 10Hz 成员帧。 |

- 默认到达阵形为 5×5、槽位中心距 1800cm；接受指令前验证完整终点足迹，途中按走廊宽度压缩为 1–5 列；欠编时保留中心对称分布，不虚构缺失成员。
- 槽位最小代价分配实现使用 25×25 Hungarian 或等价确定性最小匹配；代价相同时按 SoldierId/FormationSlotIndex 打破平局。

## 5. 网络发送、客户端插值与预测

### 5.1 服务端发送

- Authority 继续 30Hz 固定步；`ServerSimTick % 3 == 0` 时捕获 500 人精确帧。
- 捕获结果按 Team、空间单元、SoldierId 排序；动态锚点在 signed-int16/10cm 相对位置将饱和前拆块，再按最多 32 人和约 1000B 预算编码。当前 500 人形成 16 块，按 `ceil(16/3)` 错峰到后续 3 个模拟 Tick，并按 FrameSequence 轮换起始块。
- 为每个已完成 Bootstrap 的连接使用 Unreliable Client RPC 发送；即使当前没有 Ready 客户端，也会推进 PendingPoseChunkOffset 并让该快照到期，避免空服时残留旧帧喂给下一次登录。
- Soldier FastArray 与 SelectionState 使用可靠当前状态复制；命令 ACK 的 Fast/最终 Reliable 两条 Client RPC 经统一入口去重后进入有界 FIFO，并以 `CommandKind + ClientCommandId` 区分 Selection/Move 序号空间。`LastCommandAck` 只是客户端最近值快照，不再走第二条属性复制路径。
- PoseChunk 的 AuthorityEpoch 必须等于当前 MatchEpoch；PoseChunk 丢失不得改变生命、指令或命令结果事实。
- 服务端为每 Soldier 记录连续捕获位置，并在>1000cm 非预期差值时输出 authority discontinuity；编码后本地重建误差>100cm 时输出 compression error。FinalReliable 服务端两次连接均为 `compression errors=0`、`discontinuities=0`。
- 迁移完成后，5Hz `FGuLiCommandGroupStateData` 不再驱动单位 Transform；若保留，仅用于调试统计且不能成为客户端回退权威源。

### 5.2 客户端样本缓冲

- 每个 SoldierId 保存至少前后两个已排序样本和最近可靠 StateRevision。
- 估算服务器时间后，以 `ServerNow - 100ms` 为默认 RenderTime。
- 有前后样本时：位置做带速度的三次 Hermite，Yaw 做最短弧插值。
- 只有前样本时：按速度最多外推 100ms，之后保持最后位置。
- Teleport 标记或权威误差大于 1000cm 时立即重置缓冲；普通纠偏使用阻尼混合，不能在每包到达时跳变。
- PresentationActor 改为每渲染帧批量更新 ISM Transform；状态颜色只在 Selection/LifeState 事件变化时更新。
- 表现时钟使用 NetConnection AvgLag/RawPing 计算 RTT/2；连接统计未就绪时回退 PlayerState Ping。每 Soldier 保存呈现步长、累计行程、Pose 间隔、锚点/相对坐标、速度、帧/块/样本索引及未标记硬跳计数；未标记硬跳>0 时网络平滑 Gate 必须失败，不能被较低 step p95 掩盖。

### 5.3 纯表现预测与回滚

- 发出 Move Request 的同一帧记录 PendingPrediction：ClientCommandId、SelectionRevision、受影响 SoldierId、目标和开始时间。
- 已确认选择中的 Soldier 沿目标方向产生视觉偏移，持续最多 250ms、累计最多 450cm；预测位移不回写 Mass Authority Mirror 的网络样本或任何 RPC。
- 目标脉冲和命令线在点击当帧显示；命令线现已按本地命令生命周期显示 Pending/Accepted/Rejected 三种状态，并以分段高亮相位形成流水效果。该表现不改变命令权威，也不把客户端请求目标解释为服务端修正目标。
- Rejected Cohort 在 150ms 内融回普通插值轨迹；Accepted Cohort 等到成员样本出现匹配 ActiveOrderId 后，用阻尼消除剩余预测差并结束 Pending。
- 超时未收到 ACK 时停止继续外推并保持可回滚偏移；可靠 ACK 到达后按结果处理。

### 5.4 Bootstrap 顺序

1. 服务端发送包含 ProtocolVersion、MatchEpoch、SyncGeneration、ExpectedRosterCount 和 SnapshotRevision 的 Bootstrap Marker；客户端先应用本地 SyncGeneration 并关闭 PoseReady。
2. 接收带相同 SnapshotMatchEpoch/SnapshotRevision 的 Soldier FastArray 名册及当前生命、指令状态。
3. 客户端确认已应用预期数量的唯一有效 SoldierId，建立 SoldierId 到镜像 Entity/ISM Instance 的稳定映射，再 ACK 同一组版本字段。
4. 服务端复核协议、纪元、Generation、名册数和 SnapshotRevision 后才置 SyncReady 并允许 PoseChunk；成功后的客户端重试不会开启新一代 Bootstrap。
5. 客户端只消费 `AuthorityEpoch == MatchEpoch` 的新 PoseChunk；门控前或未知 SoldierId 的样本丢弃而不是生成 Soldier。
6. SelectionState 完成后开放指挥输入。

SnapshotRevision/MatchEpoch 高水位门控已落地；FinalReliable 重连 smoke 已确认服务器空服至少 5 秒后，第二个 Controller 完成 Join 与 Bootstrap Ready，并在新连接收到 34 个 fresh pose frame。该证据是断开重连 Bootstrap，不等同真正 seamless travel；跨世界无缝迁移仍是未完成 Gate。

## 9. 风险与备忘

- 固定 GroupRuntime、GroupState Replicator 和 GroupId/SlotIndex 主链路已经移除；后续变更不得把临时 Cohort、指令槽位或复制分块重新解释为永久玩家编制。
- 10Hz×500 人的带宽目标必须以实际 NetSerialize/Actor Channel 开销测量，不能只按裸结构大小估算。
- PoseChunk 不能按固定人数盲切后再让 signed-int16 相对位置饱和；Team/空间排序、动态锚点可编码检查、512 块上下限一致和无 Ready 客户端快照过期均是必须保留的协议保护。
- Fast+Reliable 命令路径必须保留 canonical payload 幂等：同 ID 冲突 payload 必须拒绝，Reliable fallback/ACK 回放不得被 Fast replay cap 截断；Selection 单 in-flight/FIFO 和 Move 等 Revision/latest-wins 不得退回无序并发。
- 当前客户端通用 HUD ACK 去重只保留最后一个 `(CommandKind, CommandId)`；交错迟到 ACK 理论上可能重复刷新一次 `LastCommandAck`，但 pending/expected ID 过滤保证其不会推进错误队列、改变预测或污染 NetworkGate。此项记为非阻断 P2，后续可改成带 SyncGeneration 的小型已交付键窗口。
- Commander 导航使用独立 750cm SupportedAgent，项目默认 34cm Agent 保持不变；后续不得为了 Commander 净空再次覆盖全局默认 NavMesh 参数。动态 1–5 列只解决途中宽度，终点仍要求完整 5×5 足迹。
- Mass Avoidance 的软分离不能替代所有战斗命中代理；本轮只解决单位移动碰撞。
- 异步流场计算不得捕获 UObject 指针；导航更新和指令改写必须通过版本检查使旧结果失效。
- Launcher UE 5.7.4 无法产出正式 Dedicated Server Target 是外部前置；`UnrealEditor-Cmd -server` 双进程可用于本轮同步 smoke，但不能冒充正式打包验收。
- 现有 `Content/GuLiStrike/Blueprints/BP_GuLiStrikeGameMode.uasset` 是受版本控制的 130B 文件，AssetRegistry 报 Invalid package tag，形态符合未还原的 Git LFS 指针。原型地图显式使用 C++ `GuLiCommanderGameMode`，本轮验证不受阻；项目级默认地图/打包前需另行恢复该资产，未经授权不执行 LFS 拉取或覆盖。
- 空服后第二 Controller Join/Bootstrap 证明断线重连 Bootstrap 可恢复，但不能冒充真正 seamless travel；跨 World 的 PlayerState/NetSync/Pose 时序仍需独立 Gate。
- 万人动态聚合 Backend、Iris/Replication Graph 和同队多 Commander 控制权均不在本轮范围；未来设计必须继续以 SoldierId 为事实身份，不得恢复永久 25 人编制。
