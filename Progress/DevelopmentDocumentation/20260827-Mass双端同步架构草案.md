# GuLiStrike：Mass 双端同步架构草案 — 技术方案

- 对应需求：[Mass 双端同步架构草案](../RequirementDocument/20260827-Mass双端同步架构草案.md)
- 日期：2026-08-27
- 状态：设计中
- 目标版本：UE 5.7.4、Win64 Client + Dedicated Server

## 0. 已锁定的不变量

> **CommandGroup（基本指挥单位）是唯一可被玩家选择、下令和持续追踪的单位；每组固定拥有 25 个成员槽。Soldier 只是组内的战斗/表现成员，任何玩家 RPC 都不得直接控制成员。**

- 当前 500 人原型：红蓝各 10 个 CommandGroup，共 20 组、500 名 Soldier。
- 最终 10000 人目标：总计 400 个 CommandGroup；具体队伍配额由玩法配置决定。
- CommandGroup 在全灭、补员和权威精度切换时保持同一个 GroupId；GroupId 在一局内不复用。
- v1 禁止拆分或合并 CommandGroup。多个组可以用 ParentFormationId 做上层编组，但不能产生少于 25 个成员槽的可控对象。
- 单兵脚环、残骸和命中反馈不改变控制边界；选择任一组后，该组所有存活成员统一进入选中表现。

## 1. 技术选型

### 1.1 候选路线与结论

| 路线 | 结论 | 原因 |
|---|---|---|
| Lockstep 全确定模拟 | 不采用 | Mass 避障、异步导航、帧率和浮点顺序无法保证跨端位级确定；不利于 FPS 交互、反作弊和晚加入。 |
| 服务端逐兵权威 + 逐兵全量复制 | 仅作为 500 人正确性基线 | 500 人可测且权威闭环完整；10000 人全局 10Hz Transform 复制预计达到约 192～307Mbps/局服务端上行，不能直接扩展。 |
| 服务端仅记账 + 各客户端完全自治 | 不采用为正式架构 | 服务端无法生成可信密度、验证圆选/射程/占点；多个客户端会成为重复裁判。 |
| **服务端分层权威 + 客户端 Mass 表现** | **目标方案** | 服务端始终模拟 20～400 个 CommandGroup；当前 500 人或热区整组展开成员级权威，远区只同步组锚点、存活和军令。 |

### 1.2 UE 网络栈选择

- 首版沿用 Legacy Replication；不启用 Iris，不启用 Replication Graph。
- 使用 `NetCore`、属性复制、`FFastArraySerializer` 和 PlayerController 所有者 RPC。
- `FastArray` 只复制“当前状态”或有明确 ACK 生命周期的事实批次，不把 ReplicationID 当业务事件号。
- 不采用 Epic `MassReplication` 作为 v1 主链路。它适合服务端逐实体 Client Bubble，但本项目需要 25 人组压缩帧、远区聚合、快照高水位和热区整体升降级；使用项目自有协议能让 500 与 10000 两种 Backend 共用同一接口。
- 现有 `GuLiStrike` Runtime 模块承载首版，不拆新模块；新增网络类型保持在 Commander 子目录，头文件只公开跨层合同。

## 2. 服务端总体架构

| 层 | 服务端职责 | 客户端职责 | 同步粒度 |
|---|---|---|---|
| Tier-0 权威 Actor | 操作者载具、建筑、据点、投射物、边界判定 | 标准 Actor 镜像与预测表现 | UE Actor 复制 |
| Tier-1 权威事实 | 比分、占领、出生/补员、AliveMask、订单结果、胜负 | 消费当前状态与事实并刷新 UI/FX | FastArray 状态 + 有序事实批次 |
| Tier-1.5 CommandGroup | 锚点、包络、路径、25 槽名册、生命、军令、热区精度 | 围绕权威锚点展开阵形 | 全局 2～5Hz、变化时立即 |
| Tier-2 Soldier 表现 | 500 模式或热区内维护成员级权威；远区不维护逐兵 Transform | Mass 移动、避障、插值、LOD、实例化表现 | 热区 5～10Hz，远区本地重建 |

核心纪律：服务端可以不知道远区每名 Soldier 的精确脚步，但必须始终知道每个 CommandGroup 的位置包络、剩余成员、订单、交战和占点贡献。客户端永远不是生命、伤害、占点或胜负的裁判。

### 2.1 Gameplay Framework 所有权

| 类/接口 | 运行端 | 职责 |
|---|---|---|
| `AGuLiCommanderGameMode : AGameMode` | Server | 5v5 登录与角色槽、比赛初始化、重连 Token、SeamlessTravel、创建复制 Actor。 |
| `AGuLiCommanderGameState : AGameState` | Server + Clients | MatchId、协议版本、服务器时间、比分、据点和十个角色槽的当前状态。 |
| `AGuLiCommanderPlayerState` | Server + Clients | PlayerGuid、队伍、角色、槽位、SyncReady；实现重连所需的 `CopyProperties/OverrideWith`。 |
| `AGuLiCommanderPlayerController` | Owner Client + Server | 选择/移动等 RPC 入口；持有同步组件；只把已确认结果通知 HUD。 |
| `UGuLiCommanderNetSyncComponent` | Owner Client + Server | 每连接事实流、精确组帧、快照分块、选择结果、命令回执和 ACK/补洞。 |
| `UGuLiBattleAuthoritySubsystem : UTickableWorldSubsystem` | Authority | 持有 Backend、权威组表、成员名册、事实号、快照队列和伤害入口。 |
| `AGuLiCommandGroupStateReplicator : AInfo` | Server + Clients | AlwaysRelevant 的 CommandGroup 摘要 FastArray；不承载客户端 RPC。 |
| `UGuLiCommanderPresentationSubsystem` | Client | GroupId/MemberLifeRef 到本地 Mass Entity 的映射、插值、表现重建和 UI 事件。 |

`UGuLiCommanderNetSyncComponent` 必须作为 PlayerController 默认子对象创建并调用 `SetIsReplicatedByDefault(true)`。GameState 没有客户端所有权，ACK、补洞、Bootstrap 和指挥请求不得挂在 GameState 上。

### 2.2 可替换 Authority Backend

`UGuLiBattleAuthoritySubsystem` 通过仅在模块 Private 范围可见的 `IGuLiUnitAuthorityBackend` 调用以下稳定能力：

```cpp
Initialize(UWorld&)
TickAuthority(float FixedDeltaSeconds)
ResolveSelection(const FSelectionRequest&)
IssueMove(const FMoveRequest&)
ApplyDamage(const FMemberLifeRef&, uint8 Amount, const FDamageContext&)
BuildSnapshot(FGuLiAuthoritySnapshot&) const
```

- `FGuLiMass500AuthorityBackend`：服务端创建完整 500 个 Mass Entity，精确处理 Transform、旋转、NavMesh、Avoidance、选择、生命和死亡。
- `FGuLiCommandGroupHybridAuthorityBackend`：服务端固定模拟最多 400 个 CommandGroup；热区整组展开 25 个成员权威代理，冷区由组级移动/战斗解析器结算。
- RPC、UI、ID、AliveMask、订单和快照格式不依赖具体 Backend，扩容时不重写上层协议。

## 3. 数据合同

### 3.1 ID 与成员生命引用

```cpp
constexpr uint32 GULI_COMMAND_GROUP_SIZE = 25;
constexpr uint32 GULI_VALID_MEMBER_MASK = (1u << 25) - 1u;

MemberSlotId = (GroupId << 5) | SlotIndex; // SlotIndex 0..24；25..31 永久非法
```

- `FCommandGroupId`：`uint32 Value`，0 为 Invalid，在 MatchEpoch 内唯一且不复用。
- `FMemberLifeRef`：`{GroupId, SlotIndex, Generation}`。Generation 在该槽每次补员/复活时递增；延迟到达的旧世代伤害或死亡不得影响新成员。
- `FMassEntityHandle` 只在本机映射中使用，永远不上网。
- `AliveMask` 仅低 25 位有效，`PopCount(AliveMask) <= 25` 必须始终成立。

### 3.2 CommandGroup 当前状态

`FGuLiCommandGroupStateItem : FFastArraySerializerItem` 至少包含：

```text
GroupId / Team / ParentFormationId
StateRevision / RosterRevision / OrderRevision / AuthorityEpoch
Anchor / FacingYaw / Velocity / SelectionRadius / FormationRadius
AliveMask / CommandGroupState
ActiveOrderId / PathRevision / HotBubbleId
```

- Anchor 与命令目标初版使用整厘米精度的 `FVector_NetQuantize`；Yaw 压为 `uint16`，速度和半径使用定点/量化字段。
- AliveCount 从 AliveMask 推导，不复制第二份可冲突数据。
- 500 模式的成员精确帧按组打包：成员相对 Anchor 的 XYZ 使用 10cm 精度 `int16`，Yaw 使用 `uint16`，状态使用 `uint8`；每组约 225～260B。
- 万人模式全局摘要不携带 25 个成员 Transform；只有当前连接相关的热区组通过 OwnerOnly 同步组件接收精确成员帧。

### 3.3 选择与订单

`FCommanderSelectionState` 为 OwnerOnly 当前状态：

```text
TArray<FCommandGroupId> SelectedGroups
uint32 SelectionRevision
uint32 AcceptedClientRequestId
```

`FCommandGroupOrder`：

```text
BatchOrderId / GroupId / OrderRevision / OrderType
Target / FinalFacing / IssuedServerTick / PathRevision
```

- 订单永远引用 GroupId，不引用 SlotIndex、MemberSlotId 或成员 Mask。
- 一次玩家操作生成一个 BatchOrderId；服务器为每个合法组生成独立 OrderRevision。
- 成员阵亡不取消组订单；AliveMask 归零时清除订单并将组置为 `Depleted`。
- 多组命令按组返回 Accepted/Rejected；某组路径失败不阻断其他合法组。
- 玩家掉线不取消已经生效的订单。

### 3.4 事实流与快照

所有不可丢事实包含：

```text
ProtocolVersion / MatchEpoch / GlobalFactId / FactType / ServerSimTick
```

- 每个连接另有连续 `StreamSeq`，用于相关性过滤后的缺口检测；未订阅的 GlobalFactId 不产生假缺口。
- 单个事实批次最多 64 条且序列化后不超过 8KiB；发布后不可修改。
- 客户端每 0.5 秒或累计 32 条发送最高连续 StreamSeq ACK。
- 每连接最多保留 4096 条事实或 30 秒；超出窗口时放弃补事件并重新生成快照。
- 快照块不超过 8KiB，包含 ChunkIndex、ChunkCount、SnapshotGeneration、BaseGlobalFactId、CRC；完整快照另做 Hash。

比赛状态均为 replicated-only；本阶段不写入 SaveGame。断线恢复只相信服务器快照，不接收客户端本地存档作为权威输入。

## 4. 权威流程

### 4.1 出生与编制

- 500 原型在服务器生成 20 个 GroupId，每组创建 25 个 MemberLifeRef 和 Mass Entity；红蓝各 10 组。
- 新编制只能一次创建完整 25 槽 CommandGroup；不足 25 的新增兵力进入服务器补员池，不能形成独立可控单位。
- SpawnTicket 必须包含 TicketId、GroupId、队伍、成员 Generation、出生点、ApplyServerTick 和 ExpectedRosterRevision，并保证幂等。
- 当前 500 原型不启用自动补员；只保留接口和测试数据。

### 4.2 圆形选择

- 三档圆半径默认 8000/20000/45000cm；客户端预测只负责即时高亮。
- 每个 CommandGroup 有固定权威 `CommandSelectionRadius`，来自 5×5 编队模板，不跟随成员局部避障变化。
- 服务端判定：`Distance2D(SelectionCenter, GroupAnchor) <= SelectionRadius + CommandSelectionRadius`。
- 未按 Shift 时替换组集合；Shift 时按 GroupId 整组切换；Esc 清空。
- 服务端只接受己方、AliveMask 非零且可控制的组。任何情况下都不能形成部分成员选择。
- AliveMask 变为 0 时自动从所有 SelectionState 移除并递增 SelectionRevision。

RPC：

```cpp
ServerRequestSelection(Center, RadiusPreset, Modifier, ClientRequestId)
ServerIssueMove(Target, SelectionRevision, ClientCommandId)
```

客户端不得提交可直接生效的成员列表。服务端对 ClientRequestId/ClientCommandId 做幂等缓存和每指挥官最多 10 次/秒限流。

### 4.3 编队移动与软碰撞

- 每个 CommandGroup 一条共享 NavMesh 路径，组内 25 人使用稳定 5×5 槽位；禁止 25 次独立寻路。
- 多组选中时先为各组分配目的地区域锚点，再生成组内槽位；命令线只连接服务器已接受的组。
- 目标先在水平 3000cm、垂直 2000cm 范围内投射到合法 NavMesh；不复制 NavMesh PolyRef，网络只发送简化后的世界坐标路径，最多 32 个 waypoint。
- 纯静态障碍由 NavMesh 阻挡；成员间使用 Mass Avoidance 软分离，不创建 500 个 Capsule/刚体。
- 默认速度 1800cm/s、Yaw 90°/s；无动画，但服务器权威更新位置与旋转。
- 同一帧最多安排 16～20 个新路径任务，超出排队，避免 400 组同时寻路造成 GameThread 峰值。

### 4.4 伤害、死亡与补员

- 通用伤害只开放服务器 C++：`ApplyDamage(MemberLifeRef, Amount, DamageContext)`；客户端不得调用“直接扣血”RPC。
- 当前原型每个成员默认 100 生命；生命归零时清除 AliveMask 位、RosterRevision++、停止运动/避障，并发布 5 秒红圈残骸表现。
- Development 构建提供 `gs.DamageSelected 100` 调试入口，经服务器伤害接口作用于当前整组选择；Shipping 不暴露该命令。
- 死亡 FX 丢失不影响事实；下一份 AliveMask 必须能自动修复客户端。
- 全组归零进入 `Depleted`，取消旧订单但保留 GroupId 和底部卡片。
- 后续补员事务在服务器认可的基地/集结点执行；重复 Ticket 不得重复补员，新成员 Generation 必须递增，且不会自动恢复全灭前订单。

### 4.5 热区权威

- 热区只改变服务端模拟精度，不转移权威；一个 CommandGroup 必须整体进入或退出精细模式。
- 建议初值：距操作者 300m、距交战据点 200m 时进入；分别超过 400m/300m 且持续 3 秒后退出。
- 当前 500 人模式中全部 20 组常驻精细模式。
- 万人模式建议 Match 级精细上限 80 组（2000 名成员），按据点交战、射击交互、距离排序；数值未验证，必须由压力测试调整。
- 每次精度转换递增 AuthorityEpoch。进入时由 GroupState 展开 25 槽权威代理；退出时先回写生命、AliveMask、Anchor 和订单，再销毁代理。
- 多个热区重叠只保留一套成员代理。预算不足时退化为服务器组包络/区域伤害，由服务器选择受伤槽，禁止退化为信任客户端 Claim。
- 操作者攻击发送 FireIntent；只有服务器依据 Tier-0 武器状态与成员代理/组包络判定命中和受伤槽。
- Soldier 对 Soldier 的远区互殴由服务器以 2～5Hz 聚合结算，客户端只播放结果。

### 4.6 Bootstrap、晚加入与重连

1. 服务端在 GlobalFactId=S 捕获一致快照。
2. 快照包含 MatchEpoch、协议版本、20/400 个 GroupState、AliveMask、每槽 Generation/生命、订单、热区 Epoch、据点、比分和角色槽。
3. 快照分块发送；期间产生的 S+1 事实继续进入该连接缓冲。
4. 客户端收齐并校验 CRC/Hash 后一次性应用，再消费 S+1 之后的 StreamSeq。
5. Bootstrap ACK 前 PlayerState 的 SyncReady=false，世界输入保持关闭。
6. Hash 错误、超时或事实窗口溢出时废弃旧 SyncGeneration 并重新快照。

- 首次登录由服务器生成 OwnerOnly 的随机 ReconnectToken；客户端 GameInstance 只在内存保存。
- Token 默认保留 300 秒；有效 Token 恢复 PlayerGuid、队伍、角色和槽位，并始终建立新的 SyncGeneration。
- 同一玩家重连可恢复过滤后的组选择；替补玩家接管指挥官槽时选择为空。有效订单属于组状态，不依赖原玩家在线。

## 5. Mass 处理器与执行域

### 5.1 500 服务端权威 EntityConfig

- `ServerAuthority500`：Identity、Health、Order、Transform、Velocity、MoveTarget、AgentRadius、Navigation、Avoidance。
- `ClientSnapshotMirror`：Identity、Transform、Interpolation、Representation；不包含 Movement/Force Fragment，防止 AllNetModes 移动处理器误改镜像。
- `ClientAutonomousHybrid`：Identity、Transform、本地 Movement/Avoidance、GroupConstraint、Representation；仅万人远区客户端使用。

| 处理器 | 顺序 | ExecutionFlags | 说明 |
|---|---|---|---|
| `UCommanderCommandDrainProcessor` | PrePhysics 最前 | Server\|Standalone | 从子系统取已验证请求；RPC 不直接改 Mass。 |
| `UCommanderGroupPathProcessor` | CommandDrain 后 | Server\|Standalone | 每组一次路径；涉及 NavigationSystem，强制 GameThread。 |
| `UCommanderSlotTargetProcessor` | Path 后 | Server\|Standalone | 生成 5×5 槽位目标和 MoveTarget。 |
| 引擎 Avoidance/Movement | 内置顺序 | AllNetModes | 只有 ServerAuthority 配置满足查询。 |
| `UCommanderFacingGroundProcessor` | Movement 后 | Server\|Standalone | 更新 Yaw 和地面贴合。 |
| `UCommanderHealthDeathProcessor` | PostPhysics | Server\|Standalone | 死亡、AliveMask 和残骸到期。 |
| `UCommanderSnapshotCaptureProcessor` | PostPhysics 最后 | Server | 10Hz 按组捕获精确成员帧。 |
| `UCommanderClientSnapshotApplyProcessor` | Client PrePhysics 最前 | Client | 用 Deferred Commands 创建/销毁镜像。 |
| `UCommanderClientInterpolationProcessor` | Representation 前 | Client | 约 100ms 插值，写 Transform/Yaw。 |

FastArray 回调只写入游戏线程队列，不直接遍历或修改 Mass EntityManager。

## 6. 500 人指挥原型整合方案

### 6.1 地图、单位和碰撞

- 从 `/Game/Maps/LVL_Main` 复制 `/Game/Maps/LVL_CommanderMassPrototype`，仅保留原 Landscape 及材质依赖；原地图不修改。
- 新地图添加最简光照、中央约 7.2km 导航区、战场边界、红蓝出生区、Mass Bootstrap 和 Commander GameMode；使用 World Settings 覆盖，不替换项目现有默认地图。
- 导航代理建议初值：半径 750cm、高度 1200cm、最大坡度 25°、最大台阶 150cm、CellSize 100cm、CellHeight 50cm、TileSize 20000cm；火山口陡壁保持不可达。
- 使用 `/Game/Assets/Arma/FourFRobot/cannon_war_machine/SkeletalMeshes/cannon_war_machine` 生成项目自有静态表现代理；保留 16 个材质映射并生成 LOD，原资源不改、无动画、无逐兵 PhysicsAsset。
- 蓝队默认中心 `(221397,-130463)`，红队镜像 `(-221397,130463)`，Z 投射到 Landscape/NavMesh；各队 10 个 5×5 CommandGroup。

### 6.2 指挥与 UI

- 1/2/3 或 HUD 按钮切换三档半透明圆；LMB 整组选择，Shift 整组切换，Esc 清空，RMB 对已确认组下达移动。
- 透视 RTS 摄像机：WASD/边缘平移、Q/E 旋转、滚轮分段缩放、地形跟随、战场边界回弹和小地图跳转；建议近/中/远缩放锚点为 25000/80000/250000cm，移动速度随缩放变化。
- 右上角使用预生成的 512×512 静态 Landscape 战术底图，并绘制镜头视野框；500 模式可单次绘制成员点，但权威交互目标始终是 CommandGroup。万人模式默认一组一个图标。
- 底部每队 10 张卡，一张对应一个 CommandGroup，显示 `Alive/25`、移动、全灭和订单状态；万人模式必须改为虚拟化/分层列表。
- 组被选中后所有存活成员显示亮黄色脚环；未选中显示队伍色；5 秒残骸显示深红色。选中脚环为 OwnerOnly，成员移动和生命对全部客户端可见。
- 流水命令线绑定 BatchOrderId，仅绘制服务器 Accepted 的组，对己方可见并在 2.5 秒内淡出。
- HUD 使用 GameAndUI 输入模式；鼠标命中 UI 时必须阻断地面选择和移动命令。

### 6.3 5v5 与 Dedicated Server

- 大厅 `/Game/Maps/LVL_CommanderLobby` 提供红蓝各 5 个唯一槽：Commander、Ground×2、Air×2；首版仅两名 Commander 可下令，其余八人使用观察 Pawn。

## 7. 更新频率与性能预算

### 7.1 建议初值

| 数据 | 500 人/20 组 | 10000 人/400 组 |
|---|---:|---:|
| CommandGroup 摘要 | 全部 5Hz | 全局 2Hz；刚接令/交战/镜头附近提升至 5Hz |
| 精确成员 Transform | 全部组 10Hz | 仅当前连接相关热区组 5～10Hz |
| AliveMask/订单 | 变化立即；热点最多 10Hz | 变化立即；热点最多 10Hz |
| 全量恢复关键帧 | 5 秒 | 5 秒 |
| 远区聚合战斗 | 不启用 | 2～5Hz |
| 客户端插值缓冲 | 约 100ms | 100～200ms，按网络实测 |

- 20 组控制摘要 5Hz 目标：单客户端不高于 100kbps、整局不高于 1Mbps。
- 500 个精确成员 10Hz 目标：单客户端平均不高于 1.5Mbps、p95 不高于 2Mbps。
- 400 组常态（全局 2Hz + 20% 补到 5Hz）目标：单客户端不高于 0.75Mbps、整局不高于 7.5Mbps。
- 400 组全部热点 5Hz 压测上限：单客户端 1.5Mbps、整局 15Mbps；不得同时向所有连接复制 10000 个精确 Transform。
- 自定义状态批次的序列化载荷目标控制在约 1000～1100B，由 UE Actor Channel 传输；快照使用独立 8KiB 应用层块，避免把大型数组塞入单个 Reliable RPC。

## 10. 风险与备忘

- 当前项目 C++ 尚无现成复制宏、服务器 RPC 或多人 GameMode；Tier-0 飞船也必须单独网络化，不能按“已权威”直接复用。
- `MassGameplay` 已启用，但网络层 `NetCore` 尚未成为直接依赖；所有新网络 API 必须先编译验证。
- 当前 Launcher UE 5.7.4 不含可打包 Server 的完整源码目标；源码引擎准备耗时、磁盘和 Epic GitHub 权限均是外部前置。
- 16 材质 FourFRobot 的 500/10000 表现成本、8.16km Landscape NavMesh 成本、80 组热区上限和全部带宽数字均为建议初值，未经过项目实测。
- 需求文档仍为草案；但 25 人最小控制粒度和客户端不得直接改变玩法事实已经确认，不得在实现中静默放宽。
