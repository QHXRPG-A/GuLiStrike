# 游骑兵初始弹与三张肉鸽卡 — 实施与交付

## 当前实现

依据[当前需求](../RequirementDocument/20261108-游骑兵初始弹与三张肉鸽卡.md)，开火入口已改为单一左右循环动画。原“申请接纳→回执→单发Montage→再次等待Fire”的游骑兵专用流程已删除；以下内容替代此前版本。

| 环节 | 实现 |
|---|---|
| 动画资源 | `Anim_GroundFire_AlternatingLoop` 为1秒，右Fire=0、左Fire=0.5；单一 `AM_GroundFire_AlternatingLoop` 循环，倍率R/2 |
| 发射入口 | 真正的 `AnimNotify_GuLiGroundFire` Branching Point明确携带枪口侧；原生逻辑步推进动画，骨骼刷新后读取枪口并调用公共池Launch |
| 持续/点按 | 按住不重启Montage；松开停止新增发射，保存下一枪侧和剩余冷却；重按及变更攻速保留相位比例 |
| 表现 | 通知触发火光、后坐；保留移动、瞄准、上下身分层。显示端刷新不再次触发玩法，离屏仍推进逻辑动画 |
| 权威 | 与Mass共用弹丸登记、碰撞、伤害及回执；无游骑兵专用预测或扣血。反馈不等待回执，公共权威激活耗时另行实测 |
| 身份/恢复 | Source生命代次+FireSerial派生ShotId，通知侧别校验；保存循环相位、下一侧、序号。重复公共Launch不能替换仍有附弹或回执的记录 |

原单发Notify异常导致整场Suspend的路径已移除。PIE管理器在成功就绪后结束启动超时计时，后续错误保留实际原因，不再伪装为120秒开局超时。此变更不取消其他系统已有的真实一致性错误报告。

动画蓝图更新还修复了默认对象与新建实例引用不同步：更新FireLoopMontage后重编译生成类，保存后同时检查CDO和新建实例。源 `Anim_Mecha_Shoot` 保持不变。

## 直接命中与逐发证据

初始伤害6/9/12，强化10/15/20。两者共用完整直接命中链路，没有强化卡前置校验。此前精确碰撞使用Mass脚底锚点，而空间网格与瞄准使用模型受击中心；现统一为 `GetHitCenter()`，包括历史采样和移动目标相交。接纳标记与攻击快照冻结标记分离，恢复记录也会读取冻结攻击。

编辑器只读入口 `GuLiGroundRogueDebugLibrary.read_state` 提供 `flight_settlement.shots`：ShotId、fire_ordinal、Fire时刻、枪口侧/位置/方向、接纳事件与状态、冻结伤害/版本、碰撞目标、结算事件、回执、applied/absorbed/remaining_health及当前目标生命/护盾。最近512条游骑兵记录和16条Mass命中记录仅用于诊断，不参与玩法。

最新构建的实际敌方Mass靶回执已覆盖六个伤害值，并补验接纳、连续节奏及独立爆炸弹。较早“左右各4发”的8发样本实际顺序包含连续同侧，它只能证明总数与伤害，不能证明严格交替。旧归档保留，最终增量归档记录勘误。

## 长时间运行暴露的公共链路问题

本轮保存了失败样本，而非把正常退出等同于验证通过：

- 早期运行在公共输入队列堆满后暂停；部分运行虽然未退出，逻辑时间已显著落后。
- `run6_logic.utrace` 的耗时导出显示资源备份维护占事务线程约八成；它在等待备份期间反复遍历所有历史对象。现在由StoreRecord维护非销毁资源候选集合，查询仍实时核对父链与私有所有权。run7持续约370秒，结束时两端逻辑时间接近且输入队列为0。
- 零冷却公共接纳规则仍拒绝晚处理的较早发射。冷却为0时允许独立冻结事实按异步处理顺序完成，稳定事件、生命周期、权限校验保留；非零冷却仍校验顺序和间隔。
- 继续实测发现出生数量校验反复扫描全部存活对象，造成接纳积压。普通源改查既有LiveChildren和增量阵营/种类计数；BusinessWork特殊亲缘语义保留。恢复和阵营变化更新同一索引，限制值不变。

- 每发写远端团队构筑计数仍把高射速限制在跨进程两阶段确认吞吐。现把 `ground_shots` 计数作为 Ground 权威载体的公共能力，按 PlayerGuid 保存等级与进度。原始普攻成功出生与计数推进在同一事务；团队构筑只提供卡牌目录和当前效果。新爆破等级按等级标记即时从零起算，其他卡牌保留进度。恢复仍由现有能力状态传输承载，不建立预测或客户端扣血。
- 公共出生请求按来源及原始时刻排队，前一事务完成后唤醒下一笔，避免GUID排序改变激活次序，以及固定重试周期引入额外等待。其他来源可以独立推进；重试仍有原有预算。

| 层 | 所有权与状态 |
|---|---|
| GuLiNetCore | 卡牌目录/冻结攻击/ground_shots计数合同；UE和Coordinator共用，协议40、Manifest26、Ground6 |
| GuLiStrike | 真实动画通知→公共池；读取已提交计数和伤害，不决定权威数值 |
| GuLiStrikeEditor | 定向资产制作、只读证据及既有PIE诊断入口；`gs.LocalPIE.LogicDiagnostics=2`仅为本地子进程启用已有网络故障工具 |

`ground_shots` 以PlayerGuid为键，随Ground载体休眠、所有权转移及现有能力快照保存；新局空表。旧协议/能力快照明确拒绝，必须新局。当前正式角色没有自动复活入口，不能将静态恢复字段核对描述为已经完成“实际死亡后复活”运行验收。

这些修改不增加开火定时器，不放宽队列上限，不通过丢弃旧请求掩盖积压。公共核心原有验收程序覆盖重试顺序、资源恢复、异步确认及捕获屏障；本轮没有新增自动化测试。各次构建和PIE证据集中在 [GroundAlternatingLoop_20261108](../../Artifacts/GroundAlternatingLoop_20261108/)。
