## 2. UE 5.7 中 Mass 的形态（先纠正三个过时认知）

1. **MassEntity 插件已废弃**。其 `.uplugin` 原文注明（DeprecatedEngineVersion 5.5）：*"All of MassEntity code has been moved to the engine and there's no need to enable this plugin anymore."* 核心代码现在位于引擎本体 `Engine/Source/Runtime/MassEntity/`，永远可用，无需启用任何插件。
2. **网上教程的类位置大多过时**。Fragment 基类（`FMassFragment` 等）原在 `MassEntityTypes.h`，5.7 已移到 `MassEntityElementTypes.h`；`UMassSimulationSubsystem`、Spawner、Representation 等集中在 **MassGameplay 插件**（5.6 新增的整合插件）。
3. **组合方式已 Trait 化**。5.7 的推荐工作流是 `UMassEntityConfigAsset`（配置资产）+ `UMassEntityTraitBase`（Trait，即"Fragment+Processor+参数"的预制积木），而不是手写 Builder 拼 Fragment。City Sample 仍是最佳参考实现，但注意其代码基于旧版，类名/位置有差异。

## 3. 核心心智模型（对照源码）

### 3.1 五个核心概念

| 概念 | 类型 | 定义处 |
|---|---|---|
| 实体 | `FMassEntityHandle`（Index+SerialNumber，非 UObject 非指针） | `MassEntity/MassEntityHandle.h` |
| 数据 | `FMassFragment`（每实体）、`FMassSharedFragment`/`FMassConstSharedFragment`（跨实体共享，省内存）、`FMassChunkFragment`（每 Chunk 一份）、`FMassTag`（零大小标记） | `MassEntity/MassEntityElementTypes.h` |
| 存储 | `FMassArchetypeData`：Fragment 组合相同的实体连续存放在 Chunk 里 | `MassEntity/MassArchetypeTypes.h`、`MassEntityManager.h` |
| 查询 | `FMassEntityQuery`：声明"需要哪些 Fragment/Tag、读还是写"，批量迭代 Chunk | `MassEntity/MassEntityQuery.h` |
| 逻辑 | `UMassProcessor`（UObject，CDO 自动注册）：`ConfigureQueries()` + `Execute()` | `MassEntity/MassProcessor.h` |

入口子系统是 `UMassEntitySubsystem`（`MassEntitySubsystem.h:18`），内部包一个 `FMassEntityManager` 持有全部 Archetype/Chunk。取用：`World.GetSubsystem<UMassEntitySubsystem>()`。

### 3.2 一帧如何跑

`UMassSimulationSubsystem`（MassGameplay/MassSimulation）持 `FMassProcessingPhaseManager`，把 Processor 挂到引擎 Tick 的 6 个阶段（`EMassProcessingPhase`，`MassProcessingTypes.h:170`，已核实枚举值）：

```
PrePhysics → StartPhysics → DuringPhysics → EndPhysics → PostPhysics → FrameEnd
```

每个阶段内由依赖声明（`ExecuteBefore/After`、`FMassProcessorExecutionOrder`）拓扑排序，Chunk 级并行。移动类 Processor 挂 PrePhysics（默认值），表现/LOD 类挂 FrameEnd 附近。

**两条铁律的出处**：
- 迭代中不能直接改实体结构（加删 Fragment），必须走 `FMassCommandBuffer`（`MassCommandBuffer.h`）延迟到安全点执行——这就是"迭代中销毁实体要 `Context.Defer().DestroyEntity()`"的原因。
- 跨 Processor 事件用 `UMassSignalSubsystem`（MassSignals/`MassSignalSubsystem.h`）发信号（如 `UE::Mass::Signals::MoveCommand`），由 `UMassSignalProcessorBase` 子类在后续帧消费——避免 Processor 间直接调用。

### 3.3 执行域

`UMassProcessor::ExecutionFlags`（`EProcessorExecutionFlags`，已核实）控制处理器在哪种世界运行：`Standalone | Server | Client | Editor | EditorWorld`。**默认不含 Editor**——想让部队在编辑器视口里也跑（摆关卡时预览），要在构造函数里设置。这是"为什么我 PIE 里正常、编辑器里没反应"的头号原因。

## 5. 最小可用示例（签名按 5.7 核实）

一个"给所有带移动组件的实体施加漂移减速"的 Processor 骨架：

```cpp
// Fragment：纯数据，USTRUCT 供反射（查询按类型找 Chunk 里的数组）
USTRUCT()
struct FGSWingmanMoveStateFragment : public FMassFragment
{
    GENERATED_BODY()
    FVector Velocity = FVector::ZeroVector;
};

USTRUCT()
struct FGSWingmanTag : public FMassTag { GENERATED_BODY() };

UCLASS()
class UGSWingmanMoveProcessor : public UMassProcessor
{
    GENERATED_BODY()
public:
    UGSWingmanMoveProcessor()
    {
        // 挂到物理前阶段；编辑器视口也想跑就放开下一行
        // ExecutionFlags = (int32)EProcessorExecutionFlags::EditorWorld;
        bAutoRegisterWithProcessingPhases = true;
    }

    virtual void ConfigureQueries(const TSharedRef<FMassEntityManager>& EntityManager) override
    {
        EntityQuery.AddRequirement<FGSWingmanMoveStateFragment>(EMassFragmentAccess::ReadWrite, EMassFragmentPresence::All);
        EntityQuery.AddTagRequirement<FGSWingmanTag>(EMassFragmentPresence::All);
        EntityQuery.RegisterWithProcessor(*this);
    }

    virtual void Execute(FMassEntityManager& EntityManager, FMassExecutionContext& Context) override
    {
        // Chunk 级并行：不同 Chunk 可跑在不同线程（Fragment 视图本身按 Chunk 切好）
        EntityQuery.ParallelForEachEntityChunk(Context, [](FMassExecutionContext& Context)
        {
            const TArrayView<FGSWingmanMoveStateFragment> States =
                Context.GetMutableFragmentView<FGSWingmanMoveStateFragment>();
            for (int32 i = 0; i < Context.GetNumEntities(); ++i)
            {
                // ... 移动/转向/编队逻辑
            }
            // 迭代中要销毁实体：Context.Defer().DestroyEntity(EntityHandle);
        });
    }

    FMassEntityQuery EntityQuery;
};
```

**单位类型组合走配置而非代码**：编辑器里新建 `MassEntityConfigAsset`，往里堆 Trait（`MassVisualizationTrait` 给渲染、`MassDistanceLODCollectorTrait` 给 LOD、`MassSteeringTrait`/`MassAvoidanceTrait` 给转向避让、`MassStateTreeTrait` 给决策），再用关卡里放的 `MassSpawner`（配 EQS/圆形/ZoneGraph 生成点）批量生成。自研系统（僚机编队、流场寻路）也做成自定义 Trait + Processor，保持同一套组合方式。

## 6. 接入 GuLiStrike 的架构规划（要点）

1. **两个世界分层**：部队在 Mass 世界（数据+Processor）；玩家/精英/Boss 留在现有 Actor/GAS 体系。互通用 `MassAgentComponent`（让 Actor 被表示为 Mass 实体，供索敌查询）+ 自定义 Subsystem 桥（GAS AoE → 查空间网格 → 对 Mass 实体结算伤害）。
2. **地面部队**：`MassNavMeshNavigation`（NavMesh 寻路）或 ZoneGraph（车道）；万级规模自研流场寻路 Processor 替代逐实体寻路；动画走 Representation LOD（近处骨骼、远处 ISM/停动画）。
3. **空中僚机**：不用 NavMesh——自定义飞行 Processor（编队跟随 + steering + ORCA 式分离）挂 PrePhysics；编队/伤害全用 Fragment 存数据。
4. **决策**：`MassStateTreeTrait` 挂 StateTree（与现有 StateTree 经验直接复用），决策结果写 Fragment，移动 Processor 消费——读写分离，避免锁。
5. **性能预算习惯**：所有 Processor 用 `ParallelForEachEntityChunk`；决策时间片轮转；索敌/伤害走空间哈希网格（自研，别用引擎遍历）。

## 8. 已知坑（提前避）

1. Processor 在编辑器默认不执行（见 3.3），预览要开 `EditorWorld` flag。
2. **Blueprint 不能直接读写 Fragment/调用 Processor**——Mass 是 C++ 域；蓝图侧只接触 Config/Trait 资产和少量 UFUNCTION 桥。设计工具链时按此假设。
3. 运行时频繁 Add/Remove Fragment 会引发实体在 Archetype 间搬迁（Chunk 重排）——兵力状态尽量用 Fragment 内部枚举表达，而不是动态拆装 Fragment。
4. `SpawnActor` 式表示每帧大量升降级会卡——LOD 距离要拉开档次，`MassRepresentationProcessor` 的切换阈值在 Settings 里调。
5. City Sample / 旧博客中的 `FMassEntityManager::ForEachEntityChunk(EntityManager, Context, ...)` 等三参签名已变为两参（`MassEntityQuery.h:89`），照抄旧代码会编译错。
6. 万级单位**联机**没有现成方案（MassReplication 覆盖有限），若未来要多人需提前单独立项评估。
