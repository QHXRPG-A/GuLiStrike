# 僚机世界空间近距编队与租约恢复 — 技术方案

- 对应需求：[僚机世界空间近距编队与租约恢复](../RequirementDocument/20260904-僚机世界空间近距编队与租约恢复.md)

## 技术选型

### 编队坐标

采用“`Carrier.Location + WorldOffset`”作为双环槽位位置，切线也直接使用世界空间相位切线。建组前 FlightNav 端点校验、初始实体位置/朝向和每帧 Guidance 必须使用同一规则。

- 不采用完整 Carrier Transform：它把 Q/E 偏航叠加到槽位相位速度，是本次异常的直接耦合点。
- 不采用仅 Yaw 对齐：需求已明确“编队不需要跟着船头转”，保留任一舰体旋转分量都会产生同类耦合。
- 不做位置吸附：Transform 仍只由固定翼积分处理，Guidance 只发布目标。

### 距离

保持双环比例不变并等比缩小 50%，同时把 CatchUp/Recovery 从 1200/2500 米收紧到 600/900 米。当前 Dreadnought 约 450 米长，300 米内环仍位于舰体纵向半长之外，并保留 15 米 Agent 半径余量。

### 运行期租约恢复

保留现有状态划分：

- `Lifecycle::Revoked`：显式拆组、Ship 销毁或初始化失败的终局墓碑；继续不可恢复。
- `Unavailable + bActiveLeaseRevoked + NoOwner`：运行期 Candidate 断流后的保留态；Roster、Health、AbilityConfig 和 Accepted Snapshot 不清空。

原 Owner 在没有 Pending Backup Offer、也没有已提交接管事务时，可以从保留态调用同一 `BeginResume`；这也覆盖“撤销时存在 Offer、但 Offer 随后过期”的空闲事务状态。客户端在 Stale/Unavailable 期间每 1 秒至多发送一次 `ServerRequestResume`；服务端仍核验当前 Group/Owner/LeaseEpoch，随后走现有可靠 Bootstrap、六 Scope ACK 与全 Flight 原子 Resume Candidate。没有放宽世界门，也没有新增服务器运动写入。

## 公共 API、生命周期与网络边界

- 公共 Blueprint API 不新增：复用 `UGuLiWingmanRelayComponent::RequestResume()`。
- 新增状态仅为组件私有的 `NextClientResumeRequestTimeSeconds`，不复制、不持久化，EndPlay/拆组时清零。
- 运行时 Formation 仍由 Ship ASC 从 DataAsset 投影给 Lease Owner；服务器拥有接纳与生命周期写权限。
- 客户端只发送恢复意图与候选样本；`OnRep_RelayState` 负责本地重建/触发，不写服务器状态。
- Backup Offer 与原 Owner 恢复互斥：已有 Pending Offer 时同 Owner reclaim 被拒绝，避免双 Owner 竞争。

## 风险与备忘

- 300/450 米是“调近一些”未给精确数值时采用的 50% 假设；若主观画面仍远或过近，应只改 Formation DataAsset 并递增 Revision。
- 当前打开的 Development Editor 仍占用旧模块 DLL；本轮已用独立 DebugGame 配置完成编译，但已加载进程不会热获得新 C++ 行为，PIE 前仍需重启编辑器。
- DebugGame 全套中 `GuLiStrike.Wingman.Performance.H4000.ServerValidator` 测得 P95 3.48ms、吞吐 38.5k Candidate/s，未过 2.5ms / 40k 门槛；单项复跑为 4.04ms / 34.8k。该门验证的是候选校验热路径，本轮未修改该热路径，需在 Development 优化配置复验，不改阈值。
- 未经用户许可不新增“旋转不影响槽位”和“watchdog reclaim”自动化用例，因此这两项需以既有测试加 PIE 证据收口。
