# 非 Mass 大规模弹道与特效架构 — 技术方案

- 对应需求：[非 Mass 大规模弹道与特效架构](../RequirementDocument/20260906-非Mass大规模弹道与特效架构.md)

## 技术选型

### 结论

保持单一 `GuLiStrike` 运行模块，以现有 `UGuLiCombatEffectRuntimeSubsystem` 作为服务器权威调度层、`UGuLiCombatEffectReplicationComponent` 作为语义事件传输层、`UGuLiCombatEffectPresentationSubsystem` 作为客户端重建与预算层。逻辑采用普通 C++ 紧凑容器和固定步长批处理；表现采用 Niagara Data Channel 与有限组件池的混合方案，不新增 Mass 依赖，也不创建逐发复制 Actor。

```text
武器/技能/Actor/现有单位域
          │  FGuLiCombatAttackRequest / 稳定目标句柄
          ▼
UGuLiCombatEffectRuntimeSubsystem（服务器，固定步长）
          ├── Trace / 空间格 / Damage Ledger ──► 权威伤害与终态
          └── 紧凑语义事件
                    ▼
UGuLiCombatEffectReplicationComponent（GameState）
          ├── 不可靠批次：枪火、曳光、小爆炸、校正
          └── 可靠状态：创建、终止、活动快照
                    ▼
UGuLiCombatEffectPresentationSubsystem（仅渲染客户端）
          ├── Burst Lane：共享 NDC System
          ├── Stream Lane：共享 NDC System + 客户端插值
          └── Hero Lane：有上限的 Niagara Component Pool
```

### 候选方案对比

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 每发 Actor/Component | 开发直观，独立生命周期简单 | Spawn/Destroy、Tick、组件注册、复制和 GC 随数量线性放大 | 只允许低频、确有独立交互的特殊物体 |
| Mass Entity | 大量同构逻辑适配良好 | 对纯表现过重；会把特效协议绑到单位实现；Niagara 仍需单独渲染层 | 本方案不采用 |
| 自定义批处理子系统 + NDC + 池 | 与现有代码一致；控制权、网络与降级边界清晰 | 需要维护句柄、生命周期和过载策略 | 采用 |

不用 Mass 的关键不是复制一个“小型 ECS”，而是只为当前效果需要实现最小数据布局。现有 `TMap<FGuid, FGuLiRuntimeCombatEffect>` 在已验证规模可继续使用；只有 Unreal Insights 证明查找、遍历或分配成为热点后，才迁移为“稠密数组 + Free List + Guid→Index”，不预先进行高风险重写。

## 总体分层

### 1. 权威逻辑层

所有伤害、命中、冷却、目标有效性和效果终止由服务器处理：

- Hitscan/短激光：每次攻击只做一次权威查询，生成完整 Start/End Cue。
- 持续激光：按技能规定的伤害频率 Trace，不按渲染帧或 Beam 分段结算；网络只传端点和状态。
- 普通弹道：优先解析轨迹或固定步长批处理，使用统一空间格做目标宽相位，再做线段/球体窄相位。
- 制导导弹：保留现有 30 Hz 非 Actor 推进、客户端预测和低频校正。
- 爆炸：只创建一个权威法术场/范围事件，使用 Damage Ledger 空间索引查询；粒子碰撞不参与伤害。

运行层需要设置最大补帧次数，积压时丢弃多余视觉校正但不能重复伤害，避免低帧率下固定步长“死亡螺旋”。所有本帧终止项先记录再批量移除，避免遍历中回调导致容器失效。

### 2. 三条客户端表现通道

| 通道 | 对象 | 生命周期与实现 | 过载行为 |
|---|---|---|---|
| Burst Lane | 枪口、曳光、命中火花、小/中型爆炸装饰层 | 每客户端一个或少量常驻 Niagara System，从 NDC 读取一帧事件并生成短粒子 | 合并同类远景装饰；减少烟、碎屑、灯光，保留核心闪光/命中点 |
| Stream Lane | 持续激光、批量弹体、长弹道端点 | 以 `EffectId` 为键维护紧凑客户端状态；每帧或降频写 NDC，由 Niagara 渲染 Beam/Mesh/Ribbon | 降低端点刷新率、Ribbon 细分和次级辉光；超距用单线/单 Sprite |
| Hero Lane | 当前 WM01 导弹、Boss 导弹、大爆炸、持续场 | 使用现有 `SpawnPooled`/`Retire` 模式，组件数量设硬上限；允许独立停止、校正和尾迹消散 | 按重要度淘汰最远低优先级组件，或切换到 Burst/Stream 的廉价替代 |

现有 `NS_CommanderGunfireBatch` 和三个 WM01 爆炸变体保持原路径，不为架构统一而强制重做。高频新增小爆炸才进入共享 Burst Lane；复杂英雄爆炸继续池化，避免把异构、多阶段系统硬塞进一个通道。

### 3. 各特效类型的数据与行为

#### 爆炸

- 服务器事件只包含 `EffectId`、位置、半径、服务器时间、随机种子、变体和终止原因。
- Damage Ledger 完成一次范围结算后发布表现；同一 DamageId 重放必须幂等。
- 客户端将核心闪光、冲击环和命中位置标记视为关键层；烟、碎片、折射、贴花和灯光视为装饰层。
- 远景聚合只允许合并装饰层，不能改变真实爆炸次数、伤害或关键危险提示。
- 贴花和后处理必须有空间范围与最大寿命；爆炸池复用前重置所有 User 参数。

#### 激光

- 瞬发激光复用完整两端 `FGuLiCombatShotCue` 思路，客户端首帧就得到完整线段，不模拟一颗慢速“激光子弹”。
- 持续激光新增有状态 Beam Cue：可靠创建/结束，不可靠端点更新；客户端按服务器时间插值，短时丢包保持上一条有效线段后自动超时。
- 服务器伤害 Tick 与客户端视觉更新频率解耦；不为每个分段建立 Actor、Spline Component 或碰撞体。
- Beam 长度决定 Bounds，必须覆盖最大端点；远距离关闭噪声、分叉、体积雾和附加灯光。

#### 弹道

- 普通机枪继续 Hitscan + 短寿命 Tracer；不开启逐粒子 CPU 碰撞。
- 可见慢弹体由服务器批量状态管理；客户端根据起点、初速、时间和种子预测，只接收合并后的最新校正。
- 当并发逻辑弹丸经测量成为热点时，将运行时存储迁移为稠密 Slot：`Index + Generation` 作为本地句柄，`Guid→Index` 只服务网络/查询；空槽通过 Free List 复用。
- 环境阻挡只对真实逻辑弹丸做场景查询；装饰性曳光、火花和碎片不做权威 Sweep。

## 预算与降级策略

预算配置放入现有 Combat Effect Settings/Catalog，不散落硬编码。每个客户端按相机和质量级独立决策，不改变服务器结果。

建议配置维度：

- 每帧 Burst NDC 行数和每类保底行数。
- Stream 活动项上限、更新频率和最大视觉距离。
- Hero Pool 按系统/类别的硬上限。
- 同屏灯光、折射、贴花、Ribbon 点数和透明粒子预算。
- 网络 Cue 的最大年龄、每 Tick 字节/批次数和积压丢弃阈值。

统一重要度顺序：

1. 本地玩家直接相关、敌方危险提示、Boss 技能。
2. 镜头内近距离攻击主体。
3. 镜头内远距离或友方重复攻击。
4. 离屏、遮挡或仅有环境装饰价值的效果。

过载时严格按以下顺序降级：动态灯光 → 折射/热浪 → 次级碎屑与火花 → 烟雾数量/寿命 → Ribbon 细分与更新频率 → 远景替代。来源、方向、命中点、阵营颜色和关键时序不因画质降低而丢失。

## 网络方案

- 瞬时枪火、曳光、小爆炸：不可靠批量 RPC，携带服务器时间和 TTL；到达时已过期则直接丢弃。
- 导弹、持续激光、持续场：可靠创建和终止；中间位置/端点使用不可靠“只保留最新值”校正。
- 后加入：只发送仍活动的长生命周期状态；不重播已结束爆炸、枪火和旧命中。
- 每批继续限制条目数并增加序列化字节预算，防止再次触发单包 64 KiB 问题。
- 网络拥塞只能丢弃表现 Cue，伤害结算和状态终止不共用可丢弃队列。
- 第一阶段保留当前公共 GameState 通道。若独立进程网络采样证明全图广播成为瓶颈，再设计每连接的距离相关队列；不在没有数据时引入 ReplicationGraph 或新插件。

## 生命周期与资源加载

- 在 `BeginEpoch`/子系统初始化阶段异步或预先加载 Catalog 和本局需要的核心 System，禁止在 Tick、每发射击或首次命中热路径调用 `LoadSynchronous`。
- NDC Reader 常驻但粒子短命；系统常驻不等于枪口、激光或爆炸常亮。
- Pooled Component 在获取时重设 Transform、全部 User 参数、激活状态和 Bounds；终止时区分立即清除与允许尾迹消散。
- 所有循环 System 必须有外部最大寿命兜底；换局、世界销毁和所有者退出时清空状态、墓碑、Pending Cue 与池租约。
- Dedicated Server 在 `ShouldCreateSubsystem` 阶段拒绝 Presentation 子系统，不加载纯表现资产。

## 分阶段实施

### 阶段 1：在现有链路上补齐预算和激光

- 保持当前 `TMap` 运行时和 WM01 池化路径。
- 抽出统一重要度、距离和质量档策略。
- 增加 Burst Lane 的小爆炸/命中数据协议，以及 Stream Lane 的瞬发与持续激光协议。
- 把同步资产加载移出 Tick/事件热路径。
- 补充队列 TTL、丢弃/降级计数器和调试显示。

### 阶段 2：只在测量证明需要时扩大批处理

- 将大量慢弹体接入共享 Stream NDC。
- 若服务器容器/分配成为热点，迁移稠密 Slot + Free List；否则保留现状。
- 若复杂小爆炸组件数量成为热点，为同类爆炸制作专用 NDC Burst System；英雄爆炸保持池化。

### 阶段 3：网络和平台专项

- 在独立进程客户端/专服上测量带宽、队列年龄和丢包表现。
- 仅当全局广播成为瓶颈时增加每连接相关性过滤。
- 按目标平台建立 Effect Quality 档和打包 Development/Shipping 预算门禁。

## 性能与验收计划

已有归档给出当前 500 单位、多 PIE 同进程参考：开启现有指挥官武器表现后，Frame p50 增加约 3.07/3.18 ms，GPU p50 增加约 1.08/1.17 ms。该数据只能作为回归参考，不是打包游戏预算。

正式验收必须固定：目标硬件、Development/Shipping 配置、地图、相机路径、单位/射击规模、分辨率、Screen Percentage、Effects Quality、网络模式、预热和采样时长。对比至少包含：

- 表现关闭、完整质量、最低质量三组。
- Frame/Game/Render/GPU p50 与 p95。
- Runtime/Presentation 每步耗时、NDC 提交/丢弃/降级行数。
- Registered/Active Niagara Component、峰值粒子和池命中率。
- GPU Niagara、Translucency、灯光和材质 Overdraw。
- 每秒可靠/不可靠字节、最大队列年龄、快照完成时间。
- Dedicated Server 纯表现组件与资产加载为零。

目标数值在用户确定平台和整帧预算后填写；在此之前只能报告“设计评审”或“基线对照”，不宣称达到最终性能目标。

## 风险与备忘

- UE5.7 NDC Reader 需要编译期访问元数据；继续使用项目已有作者工具/已验证接线方式，不能把运行时 User DI 当成等价替代。
- 大范围动态 Bounds 会削弱裁剪，过小 Bounds 会截断 Beam、Ribbon 和高速弹体；必须按最大速度、长度和尾迹时间验证。
- 池化只减少生成/销毁与注册成本，不能解决透明 Overdraw、昂贵材质或过量 GPU 模拟。
- 现有公共 GameState Multicast 尚未声明完成 Iris/ReplicationGraph 或大地图相关性验证。
- 当前 CombatEffects 中存在热路径软引用加载的可能，实施前应以 Insights 和代码审计确认并优先移出 Tick。
- `UGuLiLogicalMissileSubsystem`、旧 `AGuLiStrikeProjectile` 与新 CombatEffects 同时存在；本轮不盲目合并，后续按调用方和性能证据制定迁移表，防止破坏僚机/飞船路径。
- 任何新 Niagara/材质资产必须位于项目自有目录，商城内容只读复制；保存、编译、回读和视觉三阶段检查均按 VFX 完成门禁执行。
