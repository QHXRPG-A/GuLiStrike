### 四个候选模型

| 模型 | 一次核心决策及循环 | 战果与反制 | 主要代价 |
|---|---|---|---|
| A：断气围杀 | 识别敌方唯一通路 → 侧翼夺点 → 维持封锁 → 地面攻占失去持续增援的据点群 | 攻击者把少量节点战果放大为战区压力；守方可以夺回连接点、内外夹击或撤离 | 补给关系必须清晰；惩罚过快会造成连锁崩盘 |
| B：围地经营 | 争取若干边界据点 → 闭合控制区 → 投资区内资源与设施 → 保护边界 | 较少据点保护更多资源；对手可切开边界或进入内部建立争夺区 | 自由形状的归属和空地价值难读，可能出现贴边大圈和滚雪球 |
| C：飞地做活 | 深入敌后夺点 → 护送工程 → 建立本地维持能力 → 形成新战线 | 敌后桥头堡可以在外部连接中断后保留有限功能；防守方攻击内部补给设施或阻止施工 | 要平衡远征成本、空运能力和本地供给上限，避免无成本偷家或永久堡垒 |
| D：节拍落子 | 双方指挥官同时提交一项战略建设/争夺目标 → 全员即时战斗推进施工或占领 → 战略节拍结算 → 选择下一步 | 强化“一手棋改变局面”，让操作者决定战略意图能否兑现；对手可佯攻、破坏工程或迫使改令 | 属于替代模式；每拍行动限制可能削弱当前大战场的自由调度，不能默认叠加 |

### 优先展开 A：据点网络中的气、打吃与提子

1. **棋盘**：连续大战场上标注固定战略据点和真实可理解的地面连接。首轮讨论采用固定位置；控制区内部的炮塔、维修站等自由摆放仍属于设施层。视觉上距离近、直线相交或画成闭环，不自动代表连接、运输或包围。
2. **落子**：地面部队完成占领并稳定据点，改变节点归属。飞船通过对地压制、护航和拦截促成落子，沿用不能直接占领的角色方向。
3. **连接与断开**：己方据点通过有效连接到达大本营或有效本地供给源时获得补给。相连据点可以共享来源；缺乏供给源的孤立圈即使有多条空路，也不能凭空获得补给。首轮只由已完成的节点占领改变战略通路，普通敌兵经过不立即断路。
4. **气**：对选定前线显示可用的独立补给通路及关键连接点；两条路线共用一个可被夺取的咽喉时，不显示为两份可靠保障。完整玩法还需区分供给容量与部队需求，路线数本身不按倍数加伤害或产兵。
5. **打吃**：仅余一条关键通路时，指挥官地图标出失去哪个点会隔离哪些据点；地面和飞船玩家收到具体攻守目标。
6. **断气**：所有外部路径切断，且本地供给不足时，先消耗当地储备；持续断供后停止额外增援和维修，暴露据点核心。普通兵和玩家载具仍按战斗规则行动、受伤和撤退。
7. **提子**：攻击者仍须派地面单位完成据点占领。包围创造突破条件，不直接将区域内所有权、士兵或玩家一并清除；占领冲击波如沿用，仍受各据点自己的预警与占领规则约束。
8. **解围**：夺回连接点后恢复供给流入，但储备按速率补回，已损失的兵力和护盾不瞬间恢复。避免反复短暂接通即可清空全部包围惩罚。

示例：A、B、C 三个前线据点互相连接，经北路 X 和南路 Y 连到大本营。X 失守后仍能通过 Y 维持；Y 也失守后 A、B、C 一起消耗储备。守方可从内部反攻 X，主力从外部接应，飞船压制 X 的防御。夺回 X 的战略收益是恢复整片前线，不必逐个重占 A、B、C。

### C 的“眼”如何避免变成无敌规则

- 将“做眼”改编为在飞地内部建立有效的本地供给能力。一个维持设施只能延长坚守；两个分离、互补的设施，例如能源站和维修/重构站，可以支撑限定规模的驻军和少量本地补充。
- 两个设施的价值来自功能与容量，不是“数量达到二就无敌”。过多驻军仍会挤占供给；设施仍可被轰炸、突入和摧毁，其自身能源条件必须成立。
- 修建这些设施会占用蓝资源和当地建造容量，挤占炮塔或进攻设施，因此“做活”有明确机会成本。
- 飞船的临时空运或护送补给是后续候选能力，应有运量、耗时、拦截和着陆/投送条件。不能凭飞越战线就让全部据点长期恢复满额补给。

### B 的围地与原有资源如何衔接

- 蓝资源承担建筑、军备和战略支援投入；绿色资源沿用团队经验/成长方向，具体获取规则仍待决定。
- “气”优先作为地图上的连接与供给状态，而非第三种全局库存货币：已有资金不能自动跨越被切断的战线。
- 围地候选规则采用预先划定的区域与边界连接，而非任意几何凸包。只有真实封闭、内部敌方据点处理完毕的区域才算稳定控制；边界破口或内部敌方据点建立会使相关区域进入争夺。
- 收益来自圈内实际资源和设施，不按圈的几何面积无限产钱；山体和地图边界哪些位置可参与封闭需要显式标注。
- 后方设施失去稳定控制后先停止增益，避免切一个边点就瞬间炸毁整片经济。主基地保底收入与进攻者的封锁投入仍需保留。

### 可自然产生的战术

- **弃子取势**：主动撤出一个难守据点，以撤退所得兵力拿下另一侧连接点；收益来自实际位置和时间，不另发“弃子奖励”。
- **声东击西与劫争启发**：围攻关键连接点迫使敌人投入支援，随后在其他战区制造更大的威胁。即时玩法通过占领进度、维修成本和兵力调动形成反复争夺，不照搬围棋的禁立即回提规则。
- **围而不打**：少量部队维持断供，主力争夺别处；被围方仍可突围、空地配合和有限经营，攻击者必须为封锁支付兵力机会成本。
- **切断棋串**：夺取连接两个战区的节点，使它们分别依赖自己的供给来源；有本地维持能力的一侧可坚守，另一侧可能需要撤退。

### 最大风险与最低成本的下一步

首要假设是：玩家能理解并乐于争夺连接关系，而且救援比继续正面堆兵更有吸引力。候选组合以 A 为主，C 为后续恢复手段，B 作为可选经济扩展；D 作为独立玩法方向比较，避免一次叠加全部规则。

下一步建议做一张双大本营、约 10～12 个战略点的纸面地图，只推演通路、储备、占领与解围。点数仅为方便讨论的假设；尚未运行纸面试玩，未新增自动化测试。首先观察：操作者是否能说清应攻守哪个节点，落后方是否有时间救援，优势方是否只靠一次切断就能无代价滚完。若连通关系解释成本过高，改用明确区域的少量补给入口；若围杀没有吸引力，再比较 B 的围地收益。

### 2026-09-08 继续讨论：工程车、50 倍快速通道与据点维护

**用户本轮提出的方向，尚未要求实施：**

- 指挥官放置建筑蓝图预制体，工程车寻路到工地旁施工；施工速度与参建工程车数量成正比。
- 据点之间生成工程车专用快速通道，通道速度为普通行进速度的 50 倍，支持跨地图快速联动。
- 用户随后明确：“当该据点范围周围被敌方据点范围包围时，断气，快速通道消失。”本轮据此采用空间包围触发通道失效，不以夺取某个中间节点直接替代包围判定。
- 占点提供巨大优势：扩大快速建设范围，据点持续产生基础攻击单位，玩家建造远程导弹等设施，对相邻敌方据点形成包夹与交叉火力。
- 据点消耗阵营某种战略资源，该资源同时限制特定兵种与科技产出；用户暂定将其作为未能快速结束比赛的惩罚。

本轮以以上方向作为分析前提。上一轮提出的自动断供、储备和“眼”仍为候选，不能默认叠加为用户已接受规则。以下机制判断均为推演，未试玩。

**工程车与通道的共同作用。** 线性施工可写为 `施工速率 = 单车速率 × 实际在场施工车数`，首轮保留用户的正比关系。快速调动会使工程车接近全队共享的建设力量。假设资金已备齐、转场时间可忽略、无施工风险，两座相同建筑各需 80 车秒，8 辆车集中施工会在第 10/20 秒分别完成；分成两组各 4 辆则均在第 20 秒完成。因此集中逐个完工可能优于分散施工，分队的价值需要来自同时存在的战机、离开通道后的路程、工地暴露和损失风险。这是规则推导，不是实测工期，也不要求把线性施工改为递减。

50 倍作用于通道段。普通需要 200 秒的该路段变为 4 秒，但总响应仍包含进入通道、出口到工地和施工。保留出口后的普通移动与在场施工，能为地面操作者和飞船提供护送、袭击和阻止阵地成型的机会。未完成蓝图不提供完整火力与防御收益；工程车总量和建筑资金共同限制建设爆发。

**以敌方控制范围的空间包围触发断气。** 用户澄清后，本轮不再把“必须沿相邻己方节点中转”作为推荐前提。即使正常状态允许己方据点直达，被敌方控制范围完全包围的据点也会丧失通道资格。默认理解为该据点相关的进出快速通道全部失效，不能从另一个据点继续快速传入；普通移动与工程车以外单位的能力不据此自动改变。

| 状态 | 快速通道与玩家行为 |
|---|---|
| 尚有包围缺口 | 工程车可快速到达，据点有机会抢建防御或攻击设施；双方争夺封口与保留缺口 |
| 敌方据点控制范围形成完整包围 | 该点快速通道消失；已经在当地的工程车仍可施工，后续增援需走普通路径并承担穿越敌控区的风险 |
| 攻破包围圈 | 建议恢复快速通道，形成内外夹击与解围的奖励；恢复条件尚未单独确认 |

包围应由有效据点控制范围的封闭关系决定，不能简单替换成“邻近敌点达到某个数量”。需明确哪些控制范围可衔接、地图边界与山体是否参与封闭，以及狭小缝隙是否算有效缺口。未完成建筑蓝图不应提前提供能封圈的控制范围。圈将闭合时提前显示缺口和占领进度，闭合后按用户规则断开通道；在途工程车如何落地属于后续规则边界。

这使“最后一个缺口”具有巨大价值：包围前可集中全队工程车建设，包围后必须依靠本地已有工程力量、基础单位和玩家操作争取解围。断气本轮只明确移除快速通道，不额外自动关闭基础出兵、清除工程车或摧毁玩家建筑。

**正反馈会叠加。** `占领据点 → 工程通达范围扩大 → 快速建成攻击设施 → 基础兵与多方向火力增加 → 更易占领下一据点`。通道虽然只运输工程车，仍可通过前线制造攻击建筑间接转化为军事增援。需要让新据点从占领到阵地成型存在可反制过程，保持指挥官选择兵力投向、地面压制工地、飞船袭击高价值设施的作用。多个相邻点的部队若仍挤在同一个入口，地图邻接不自动产生真实交叉火力。

**维护费能否形成负反馈，取决于净收入。** 设战略资源库存为 S，每分钟来源为 I(N)，据点数为 N，每点每分钟维护为 c，当分钟高级单位与科技支出为 Q，则 `库存变化 = I(N) - cN - Q`。当新增据点同时增加的该资源收入不小于维护，不能仅凭存在扣费就宣称成功限制扩张。若净收入长期非负，固定维护也不会自然形成倒计时；若净收入为负，耗尽时间还取决于已有库存。

仅作逻辑示例：收入固定 10/分钟，每点维护 2/分钟，未计高级单位和科技购买时，2/4/6 个据点的净收入分别为 +6/+2/-2。前两种主要减少可投资预算，第三种才消耗已有储备；这些数值不是建议平衡初值。

**目前更明确的价值是领土广度与军备质量的取舍。** 多据点获得基础兵、施工范围和交叉火力，少据点一方可能保留更多高级单位与科技预算。这只是反制条件，不保证少据点一方一定有足够时间或兵力兑现。固定维护并不识别玩家是否故意拖延，也会扣除正在积极进攻但尚未获胜一方的资源。

特别需要避免：扩张消耗战略资源 → 买不起唯一能攻破大本营的兵种/科技 → 更难结束游戏 → 继续支付维护。若高级军备是唯一终结工具，维护机制可能反过来延长对局。永久科技先完成再扩张、大量囤积后扩张、停在低维护据点数只炮击不占领，也可能使预期惩罚失效或改变最优玩法。

空间断气又与维护产生一项交互：若被围据点仍归守方、继续付高额维护，却无法有效向外投射战力，攻方可能选择围而不取，让守方承担负担，自己避免新增维护。需要比较这种战术的短期价值与长期最优性；应让完成占领提供足以推进最终胜利的收益，例如与大本营攻城条件关联，而不是只留下持续围困的收益。

**建议优先收敛为以下取舍，尚未定稿：**

1. 让维护承担控制范围与高级军备之间的预算选择；大本营攻城窗口承担推动终局的作用。现有大战场草案已有关键据点开启攻城窗口的候选方向，可继续讨论，不能称为已实现。
2. 明确该战略资源的基础收入、与据点收入的关系、储存和支付优先级。避免拥有更多点直接同比获得更多维护资源，使限制被自身收益完全抵消。
3. 资源不足优先影响受其约束的新高级单位生产与新研究投入，保留基础作战和工程车恢复路径，避免维护一空就丢失全部反击能力。完成的科技和已有单位不因余额波动反复失效。
4. 如后续加入据点停机、弃点或军事化等级，应让减免的成本与被撤掉的收益对应，防止免维护仍保留完整快速通道、自动出兵和进攻设施。
5. 阵营共享维护若挤占其他角色的军备配额，需要让全队看到新增据点的收入、维护与可支配预算变化，避免指挥官扩张让队友无从理解地失去成长机会。

下一步最低成本推演：沿用据点纸面图并标出控制范围，固定同一批工程车与资源，分别观察扩张方封闭包围圈、先科技后扩张、被围方打破包围缺口的选择；先看是否出现有效施工阻击窗口、全工程车集中是否长期占优，以及维护是否让领先者长期围而不取。以上为待讨论验证方向，本轮只进行公式与示例算术核对，未开展试玩、修改玩法代码或新增测试。

2. **借用经营成本，把新控制区变成可用火力的过程留给工程车。** 继续以用户提出的 50 倍通行、在场线性施工和完整包围后通道消失为前提。新点的高级攻防价值由真实工程投入兑现，扩张过快会分配更多施工与保护任务。若已有施工窗口足够，不再叠加独立忠诚条或额外等待计时器。
3. **维护优先约束可主动选择的高阶军事规模。** 对用户原“每点维护”提案，可比较轻量基础维护加高级导弹设施、特殊兵种等额外运行投入的方案。总费用与功能对应，玩家能预览下一项建设如何影响高级科技预算；不能用关闭维护却保留全部产出规避成本。基础兵持续自动生成时，按所有基础兵存量征收陡峭维护会造成难以控制的支出，也与万人战争的目标存在冲突。
4. **限制重复获利，保留正常战斗价值。** 同一据点短期反复易手不重复发放完整反攻赏金；赏金随差距缩小退出，单次收益设上限。若后续确认存在刷受困战区经验的问题，再单独讨论对应额外收益的递减，避免大规模普通战斗普遍没有回报。

判断领先不能只看瞬时据点数或当前库存；应共同考虑可发挥作用的据点产出、已投入军备与科技，以及持续一段时间的差距，避免故意花空库存触发补偿。具体口径、权重、阈值与时间均未确定，不能声称已有可靠判定模型。故意丢点后收回不应通过补偿获得稳定净收益。

**设计取舍。** 反攻奖励针对成功行动，经营与维护针对规模选择；两者都应保留领先者的胜利路径。优势方持续正确行动仍能结束比赛；错误扩张、丢失关键点或重要军备后，劣势方有机会将战果转化为可用反击资源。包围和通道失效对双方对称，本身是位置战术；它也可能被优势方用于滚雪球，不单独构成可靠追赶机制。

首轮建议只展开据点反攻赏金，并利用已有工程施工成本限制瞬间扩张；维护作为第二层预算选择单独比较。下一步最低成本的纸面推演是让落后方在真实战损下夺回一个据点，观察奖励是否足够支持一次可选反击，同时比较优势方继续攻城与保守不占点的收益。应检验是否出现故意送点获利、一笔奖励完全抹平前期成果，或优势方持续正确决策却始终无法收尾。本轮仅完成官方资料核对与方案分析，未开展试玩或新增测试。

### 来源与已确认事实

2026-09-08 用户最初要求分析匈牙利算法与其他分配方案，随后明确简化为：“对空对地都用匈牙利算法分配所有僚机<->所有可攻击目标（包括空和地），ship手动索敌不走这套逻辑，分析。”算法和空地统一方向按该修正收敛。以下事实记录的是提升当时的旧实现，已由正式开发结果取代。

当前默认 25 架僚机。服务器选敌优先指定目标，否则保留当前目标，再按到 Ship 的距离选敌；可靠攻击状态只有一个共享 Target。客户端虽已逐架维护攻击状态，但尚未进入冻结地面攻击轮的成员都从共享 Target 取目标。见[选敌实现](../../Source/GuLiStrike/Battle/Combat/GuLiWingmanAttackCombat.cpp)、[攻击状态协议](../../Source/GuLiStrike/Battle/Contracts/GuLiWingmanProtocolTypes.h)和[逐架攻击执行](../../Source/GuLiStrike/Gameplay/Wingman/Combat/GuLiWingmanAttackSimulation.cpp)。

对空机枪是单目标攻击；对地是 120 米固定条带、多个落点的纯 AOE，俯冲开始后冻结条带。不同士兵作为瞄准目标不意味着其轰炸覆盖区域不同。数值和既有行为见[飞船玩法](../Gameplay/飞船.md)。已有 Damage Ledger 负责权威伤害提交、去重与死亡结算，未实现面向选敌的在途伤害预算。

### 简化后的分配规则

1. **每艘 Ship 建立一个自动分配池**：收集其范围内所有存活、可攻击的敌人，空中与地面单位放进同一列表；所有存活可用僚机按成员身份参与分配。匹配结果只决定每架攻击谁，目标类型决定沿用机枪缠斗还是俯冲轰炸。
2. **统一代价**：建议以僚机到目标的距离为主，加一个换目标惩罚以减少抖动。所有候选都进入同一模型，不再加入血量预算、目标威胁、轰炸区域聚类或第二种求解算法。
3. **配对合法性**：沿用 Ship 获取/释放范围与目标合法性检查；每架必须有对应目标类型的可用武器。分配允许正常接近和转向，实际开火继续检查自身射程、射界、LOS 与冷却，不能把当前机头没有朝向敌人直接当成永远不可分配。
4. **数量不相等**：矩形匹配允许留下未分配项；目标多时，一轮为每架选择不同目标。目标少时，建议对剩余僚机重复运行匈牙利，每轮每个目标最多分到一架，直到全部分完或没有任何合法配对。各轮先保证最大合法匹配数量，再优化总代价；禁止为了填满矩阵强配不合法目标。
5. **手动索敌单独走原流程**：有效手动目标存在时，完全跳过自动求解，继续现有指定目标攻击。取消或失效后按既有归队条件恢复自动分配；自动结果不能覆盖有效手动目标。已开始的地面俯冲仍按原冻结规则结束后响应目标变化。
6. **更新节奏**：建议沿用当前 0.2 秒扫描节奏，刷新逐架目标位置；匹配改变的目标增加分配版本。换目标惩罚用于维持稳定，冻结攻击段继续按既有执行边界切换，避免扫描频率变成实际强制转向频率。

以下示例假定全部配对合法、僚机均可参与新任务；多轮规则是本次建议，用户尚未单独确认：

| 僚机与目标 | 建议分配结果 |
|---|---|
| 25 架、25 个空地混合目标 | 一对一，25 个目标各一架 |
| 25 架、8 个空地混合目标 | 三轮各分配 8 架，末轮分配 1 架；7 个目标各 3 架、1 个目标 4 架 |
| 25 架、100 个空地混合目标 | 从全部候选中为 25 架选择 25 个不同目标；其余本轮未分配 |
| 25 架、1 个目标 | 25 架最终都分到该目标 |
| 没有合法目标 | 保持/恢复原待命与跟随行为 |

“所有目标参与候选”不等于“每个目标同一时刻都被攻击”。一对一匹配的直接覆盖受可用僚机数量及合法配对限制，目标较多时也不额外承诺定时轮换或无饥饿保证。多轮匹配优化各轮代价，不宣称所有轮次合起来具有全局最小总代价。AOE 仍可能重叠，自动分散选敌也不等于伤害零溢出；这些是简化方案接受的边界。

25 架对 100 个目标是 2500 个配对。算法规模预计可控，但尚无性能测量；目标候选构建和地面点合法性检查同样需要计入耗时。

算法模型参考：[线性指派](https://developers.google.com/optimization/assignment)。多轮分配、换敌惩罚和手动分支边界是本项目的方案建议；不要求引入外部求解库。

### 改造边界与下一步

算法逻辑简单，工程接入仍为中等改造，主要有三处：

- **服务器自动分配**：在现有 Battle/Combat 内形成统一候选列表、配对代价与匈牙利分配结果；保留独立手动分支。求解器使用纯数据，不依赖 Commander 的部队内部类型。
- **逐架执行**：自动目标从一个共享 Target 扩展为成员到目标的表；客户端每架读取自己的目标，按空地类型沿用现有攻击执行器、冻结阶段和飞行安全规则。服务器仍不接管运动模拟。
- **同步与授权**：逐架分配进入可靠状态、稳定哈希及租约交接；开火历史按具体成员和分配版本核验，兼容正在执行的冻结轮与合法迟到记录。

上述讨论形成了正式开发边界。当前实现已通过27项原定向自动化与300秒同图PIE长测；后续又修正对地圆弧净空并增加本地Ship索敌范围显示，同图确认25/25成员均进入攻击轮。玩法现状、接口和验证结果以[完成开发案](../DevelopmentDocumentation/20260908-Ship僚机空地统一匈牙利自动选敌.md)及[全员参战修正归档](../Archive/20260909-Ship僚机全员参战与索敌范围显示.md)为准。

## IDEA-202609-003 指挥官同一起点下的局内打法分化

- 状态：inbox
- 模块：commander、economy、building、combat
- 价值：指挥官通过本局资源投入、据点经营、生产与选牌，逐步形成可识别的战争风格，使相同开局产生不同的战略过程。
- 待确认：定向强化与现有军备的协同、各体系的实际成型成本和时间、有限矿藏下的投入回报，以及主路线专精与必要反制之间的平衡。
- 正式需求：无；本轮为用户新点子的分析记录。

### 当前方向修正：有限资源与体系协同促成持续专精

用户最新否定显式关闭路线的方案，希望借助不可再生资源，让玩家在游玩中意识到持续走一条路线通常最有利于赢下对局。本条目不再采用三路缩为两路再缩为一路、互斥路线核心、按已选路线移除其他路线候选等方案，也不将这些限制隐藏到后台。当前改为讨论已有军备、定向成长、配套设施与剩余资源怎样提高继续专精的实际回报，具体机制仍为候选，见末尾“有限矿藏下的持续专精”。此前分析保留为过程记录。

用户进一步用《金铲铲》明确目标：“中途改路线不是不行，而是越到游戏后面，成本越大。”当前讨论按阵容逐渐成型、专用投入增多和重新配套所需时间理解这种成本增长，不采用随对局分钟增加的转型收费或路线资格锁定。

### 2026-09-09 来源与边界

用户提出：参考《星际争霸》人族重火力稳步推进、虫族单位群战术与快速铺开、神族高端战略的作战风格。本游戏所有指挥官从相同起点出发，后续形成哪种风格，由其本局操作路线决定；高端战略包括神级卡和神级战略支援。

以上记录用户的体验目标。下文的路线机制、卡牌例子、取舍与验证方式均为候选建议，尚未定稿或实施。沿用[蓝矿、红矿、据点维护与三线成长需求](../RequirementDocument/20260908-蓝矿红矿与据点维护及三线Roguelike成长.md)：两种矿藏不可再生，采矿车与加工厂共同入库，据点维护同时消耗双矿，任一种不足触发已确认的四项停用后果；经验是唯一选牌触发源，部分强力牌另付红矿。本点子只讨论指挥官成长线。

三种种族名称在本点子中作为用户概括的风格参照，不代表《星际争霸》每个种族只能采用一种战术，也不预设固定种族克制环。暴雪的[人族组合指南](https://news.blizzard.com/en-us/article/5740272/game-guide-terran-unit-combos)明确讨论不同单位组合，并强调根据地形、资源和敌军调整；本项目下述玩法模型是本轮改编建议。

### 核心模型：由投入和行动逐渐形成打法

建议体验主张为：**同样的开局能力，通过本局经营、作战和选牌，逐渐打出不同的战争体系。** 初始共用基础单位、建设能力和资源规则；后续差异来自保有什么阵地、部署什么部队、为哪些行动储备资源，以及选择了哪些强化。

建议闭环：`侦察矿藏与敌方部署 → 选择争夺的据点和资源投入 → 工程建设与兵工厂生产 → 以对应方式作战、获得经验 → 选牌强化已有能力或为转向作准备 → 改变下一轮目标与投资`。

当前部队、建筑和矿藏状况决定一张牌能否有效兑现；指挥官主动选取的牌反过来改变下一轮决策。建设数量、占点数量或隐藏的路线分数不另行触发选牌，也不需要把玩家自动判成一个固定种族。

### 三条候选路线

下表名称只用于讨论，具体比例、费用与强度均未确定。

| 路线与参照 | 主要投入和操作 | 候选强化方向 | 作战收益 | 必须面对的代价与反制 |
|---|---|---|---|---|
| 火力阵地，参照人族风格 | 将较多蓝矿投入重火力军备、工程车和关键点设施；护送施工，阵地成型后向下一目标推进；双矿维持据点 | 部署后炮击、交叉火力、工地保护、阵地内协同 | 用稳定的局部火力把突破变成可守住的前线 | 固定投资与部署占用时间；调动和阵地未成型时有破绽，对手可绕行夺矿或袭击施工力量 |
| 群体扩张，参照虫族风格 | 将蓝矿投入量产兵工厂、基础部队补充和多线工程展开；依靠持续出兵与分兵占点形成压力；为更多据点负担双矿维护 | 基础波次组织、轻型单位量产、行军与分兵能力、轻型设施建设 | 用多个进攻方向争夺有限矿藏，形成包围并迫使敌方分散 | 单点火力和防守投入较薄；群体怕范围火力，采矿加工易被袭击，快速占点可能使维护先于新收入增长 |
| 战略决战，参照神族风格 | 蓝矿仍用于部队、工厂和必要防御；经营能支持红矿入库的区域，积攒维护以外的红矿，用于强力牌和战略支援 | 改变支援使用方式的关键牌、目标引导、集中突破和战略护盾 | 在准备充分的关键窗口，以高额投入改变局部战况，再由部队兑现战果 | 备战期间会让出部分即时兵力与扩张机会；高额支援失误会损失有限储备，准备与目标暴露给对手反应空间 |

火力阵地与群体扩张路线同样可以使用战略支援；战略路线同样需要基础军队。主路线由投入重心和能力组合体现，不把基本能力完全隔离成三套菜单。所有兵工厂兵种仍按已确认规则使用蓝矿，本轮不为战略路线追加未经确认的红矿造兵费。

### 让 Roguelike 支持主动选择与混合打法

建议每条路线都能依靠共同基础能力开始经营，后续选牌改变作战方式与投入回报。关键随机牌不应是某条路线能否开始玩的唯一条件。候选牌可以照顾当前已有单位与设施，并保留转向机会；具体发牌方式尚未指定，不承诺固定候选数或额外刷新次数。

以同一类四足机器人为例，可讨论三种不同的改装方向：部署后提供重火力、减少单体防护换取更易量产、承担战略支援目标引导。这里强调行动方式与代价的变化，不只是同一单位加不同颜色的伤害数值；这些效果当前都未确认或实现。

允许“群体扩张为主，配合一次战略打击”或“火力阵地为主，用轻型部队包围”的混合打法。先用有限矿藏、生产建设时间和经验带来的有限选牌机会形成取舍；必要时再比较同一武器槽位中的互斥改装，不默认加入额外阵营值、转职费或独立科技货币。

转向通过后续投入和新选牌逐渐完成，既有军队和工事保留其实际作用；之前用于固定火力、量产能力或强力牌的投入不能在转向时无代价变成另一条路线的完整能力。既有卡牌的生命周期和改装覆盖规则仍以相关成长草案及后续确认为准。

### 与双棋盘、维护和团队角色的关系

- 据点棋盘提供不同争夺目标：阵地路线重视能覆盖关键区域的火力位置；扩张路线重视同时施压、形成包围和阻断工程快速增援；战略路线重视有效矿藏、目标情报与可兑现支援战果的突破位置。
- 50 倍快速通道仍只明确用于工程车，施工速度继续与实际参建车数成正比；群体路线不能据此让全部战斗单位自动获得快速通行。各种路线都要把施工与普通地面作战衔接起来。
- 资源棋盘使争夺目标随矿藏耗尽而改变。新占据点能否及时提供可用入库量，取决于矿藏、采矿车和加工厂；多一块地并不立即等于多一份可支配红矿。枯竭据点仍可能有战术价值，也继续承担维护成本。
- WM 和 Ship 沿用各自独立经验与选牌。指挥官路线可以给队友创造护送工程、掩护分兵、侦察或引导打击的协作目标，具体引导机制尚属候选；不直接替队友选牌或复制指挥官全部成长效果。
- 强力支援建议有可识别的目标、准备或生效过程，使对手可以分散、撤离或干扰。它应帮助现有部队完成进攻，避免长期只靠不可干预的跨图技能决定胜负；具体条件、冷却与反制规则未定。

### 首要风险与最低成本的下一步

**首要风险是三条路线在最优打法下重新汇合。** 若扩张同时提供最多兵力、最高双矿收入和最快经验成长，扩张方也可能最先支付所有强力牌与支援；若神级卡对全部单位和所有场景都更好，战略路线就会变成所有人的必经终点。因此三条路线应在相近对局阶段具有可兑现的胜利路径，“高端战略”主要意味着高投入、强场景作用与使用窗口，不自动代表所有其他路线的上位升级。

另需观察双矿维护是否过度压制群体扩张，以及大量轻型单位是否因击杀经验结算而过度加速敌方成长。经验仍来自已确认的击杀与占点，单位价值权重和占点奖励细则待讨论，不在本轮擅自改定。

最低成本的下一步建议是用同一张双棋盘地图、相同起始库存与同等早期选牌机会，纸面比较三种投资方案及一次中途转向。先只为每条路线准备少量机制不同的候选牌，观察它们争夺的目标、战机和失误代价是否确实不同，并检查扩张路线能否无代价兼得全部战略优势。该推演尚未执行；本轮仅完成分析和 Backlog 记录，未新增测试或修改正式需求与玩法实现。

### 2026-09-09 不可逆战略选择与路线收窄

**本节方案已被用户否定。** 用户后续明确不要显式关闭路线，希望由有限资源与实际投入促成专精。本节的路线互斥、关键节点强制收窄、其他路线牌池归零等建议不作为当前方向，也不改为隐藏限制。

**当时的讨论前提。** 用户要求：“因此需要让玩家的每个策略都尽量不可逆，三条路线不允许回退和重选，最终系统会推着玩家走向其中一条路，怎么做合适。”当时按本局指挥官战略成长的单向选择展开，形成了以下已被否定的候选机制，未实施。

#### 1. 用关键选择将三条路线逐步收窄

| 阶段 | 候选规则 | 选择后的结果 |
|---|---|---|
| 共同起点 | 基础单位、工程建设和资源规则相同；先侦察、经营、作战获取经验 | 三条专精路线均开放 |
| 第一项体系选择 | 在预设的经验成长节点，提供能支持两种后续路线的体系改装；选取时展示永久放弃的路线 | 三条缩为两条；已有选择不可退还或撤销 |
| 核心专精选择 | 在后续经验节点，从仍开放的两条路线中选择一个核心；该次选择只提供有效的专精选项 | 两条缩为一条，另外两条路线的专属成长与终局能力永久关闭 |

节点以经验进度安排，不额外用建造次数、占点次数、红矿余额或时间直接触发选牌；具体等级和节点间隔待定。可暂缓处理关键选择，但建议后续成长不能绕过它继续领取，也不因超时随机替玩家决定路线。只有对局推进到相应经验阶段并完成专精选择后，才承诺路线收敛为一条。

结构约束为：`新开放路线 = 原开放路线与本次所选改装兼容路线的交集`。只提供交集非空的候选。第一项体系改装的效果应在它所支持的两条路线中都能继续发挥作用；进一步选择不删除已经合法取得的成长。

#### 2. 示例：从重型平台走向火力阵地

以下名称和效果仅用于说明分支结构：

1. 指挥官选取“重型平台”体系改装，获得支持重型军备的能力；保留火力阵地和战略决战两种后续，永久关闭群体扩张的专属量产体系。
2. 之后可以在火力方向的“炮击协同”和战略方向的“战略引导”之间决定核心发展。若选择炮击协同，战略专精随即永久关闭。
3. 后续可以继续发展阵地防御、移动推进或不同炮种的配合，但不能再领取战略路线的神级专属成长或群体路线的终局量产能力。

基础兵、普通防空反装甲能力及通用战略支援是否共享，按共同基础能力范围明确；使用一个通用导弹支援不等于获得战略决战专精。每个关闭动作应由改装真实的兼容边界与发展代价解释，并在选取前展示，不能由普通造厂、临时调兵或被迫防守暗中替玩家判定路线。

#### 3. 资源投入提供持续推力，前置互斥保证不可跨线

火力路线的蓝矿、工程时间和后续牌继续改善重军备与阵地；群体路线继续改善量产与多线行动，并承担更多据点的双矿维护；战略路线将维护以外的红矿投入专属强力牌及支援。这些已经兑现的投入提高继续深入本路线的价值。

单靠昂贵的转型费、已经花掉的资源或提高同路线发牌概率，不能保证玩家最终只拥有一条专精。领先者可能有钱承担全部费用，所以专属核心与终局能力还应具有明确、互斥的路线前置；关闭的路线候选概率为零。富裕可以支持已选路线继续发展，不能购买重新开放另一路线的资格。

已结算的战略选择不洗点、不重选，也不以退还其费用来撤销。建筑和生产取消是否退费仍待另行确认，但任何回收都不能恢复被关闭的路线资格。所有新建兵工厂和重建设施继承本局已经选择的体系，不能通过另建一座工厂重新选择其他路线核心。

#### 4. 随机性放在路线内部，关键承诺由玩家决定

建议关键节点保证展示每个仍开放方向的可选核心，后续普通强化再随机提供兼容变体。不得仅因一次随机缺牌，替玩家关闭最后想走的方向。为使路线选择不被暂时红矿余额代替，建议关键入口使用不收红矿的常规战略卡，昂贵神级牌放在其后。

神级牌继续遵守经验触发及红矿支付规则：先由经验取得选牌机会，再满足已选路线、前置与红矿费用后选取。普通选牌应有至少一个当前可选的兼容选项，不能出现全部候选均属于已关闭路线或全部因红矿不足而不可选的情况。具体候选数、牌池比例与费用未定。

界面至少同时表达本次得到的能力、永久关闭的后续能力，以及仍可继续发展的方向。所谓“系统推动”来自玩家已接受的前置与候选收窄，不通过隐藏行为分数或随机自动选核完成。

#### 5. 不可逆记录与战斗损失分开保存

建议路线与已选成长归属于本阵营的本局指挥官体系，普通单位死亡、部队全灭、设施拆毁、指挥官换任或重连均不能使路线重置。重建只恢复符合当前路线的设施能力。新的对局才重新获得共同起点；具体存储与接管实现不在本轮展开。

本轮范围限于指挥官战略专精，不将不可回退要求扩展为 WM、Ship 全部武器不得换装。既有动态武器更换方向保留，但指挥官只能从本局仍合法拥有和兼容的候选中使用能力，不能以换装绕过专属路线资格。

#### 6. 风险与最低成本的下一步

主要风险从“最终兼得三路”转为“早期选择后整局失去有效应对”。因此各路线需要保留共同基础反制，并在路线内提供应对空军、装甲、范围火力或资源争夺的可执行办法；这些办法可以效率不同，不应要求先取得已经永久关闭路线的核心。战略路线在红矿紧张时仍需依靠其现有部队、普通卡和队友创造重新争夺采集区的机会，不用免费补发矿产来撤销有限资源约束。

最低成本的下一步建议是画出三条路线共享的起点、第一项体系改装和核心专精节点，用一条实际选择序列说明每一步保留与关闭的能力，再推演一次被敌方针对后的路线内调整。重点检查已选能力是否仍有用、关键节点是否由玩家主动决定，以及是否存在新建工厂、拆毁设施或花更多资源即可绕过互斥的漏洞。本轮仅完成结构分析和文档记录；纸面试玩、数值验证及新增测试均未执行。

### 2026-09-09 有限矿藏下的持续专精

**用户最新修正。** 用户表示：“这个点子不行，不想显示地关闭某些线路，因为目前资源是不可再生的，最好让玩家游玩中意识到只有把一条路走到黑才最有可能赢下对局。”据此保留其他体系的可选性，以实际军备和有限投入的回报推动玩家持续发展主路线。下面均为新的候选机制，不改变已批准的双矿用途、双矿维护、采集加工或经验唯一触发选牌规则。

**建议体验目标。** 已有军队、设施和成长能让下一笔资源更快、更充分地转为战果；另起一套体系需要重新建设、生产与获得适用强化，可能错过当前战机。玩家根据这些可见事实决定继续专精，无需路线身份、永久关门或强制专精节点。

#### 1. 定向成长同时作用于已有与后续的适用军备

候选强化明确作用对象，例如火炮、某类基础单位、某一种战略支援。它可以改善该类现有军备，并继续作用于后续补充；换造另一类单位不会把原有专属强化复制过去。通用成长仍可存在，但不应让少量全军通用神级牌在所有场景都压过体系内配合。

示例：玩家已有一批火炮和射程、部署相关强化，再选炮击协同即可改善当前能投入战斗的炮群；选取另一类军备强化依然合法，但要等对应军备建成后才能兑现。决定其价值的是现在仍能使用的资产和未来机会，而非仅因过去花过钱就要求继续投入。若火炮已被克制或无法发挥作用，历史投入本身不能证明继续造炮合理。

以上仅讨论新增卡牌的效果范围，不把既有全部槽位通用奖励擅自改成武器专属，也不改变 WM、Ship 的独立成长与动态换装方向。

#### 2. 让成型成本来自实际功能配套

| 体系 | 既有投入怎样帮助继续深入 | 另起一套体系需要补什么 |
|---|---|---|
| 火力阵地 | 现成炮兵、工程力量、适合射击的位置和相关强化，使追加火力或阵地协同更快生效 | 能实际参战的新兵种或设施、对应火力位置与适用成长；原工事不能自动搬成完整的新体系 |
| 群体扩张 | 现有兵工厂、持续生产、采矿加工与多线据点经营，让基础部队和量产类强化影响更多适用对象 | 新体系所需的军备与成长，同时仍需支付原有据点的双矿维护并维持战线 |
| 战略决战 | 已有特定支援强化、适用军备及目标获取与协作条件，使下一次红矿支援更容易形成有效突破 | 对应数量的常规军队、生产建设时间和适用成长；已经消耗的支援红矿不能同时支付这些投入 |

具体专用设施、兵工厂模块与引导能力仅在确有功能需要时讨论，不为阻止转型另加一座纯粹收费的路线建筑。普通支援仍按已确认规则消费红矿，不能要求玩家先取得某个互斥的战略身份才能调用。

#### 3. 有限矿藏使重复起步更难回本

判断下一次投入，应共同看现有可用库存、已知且可能取得的剩余矿藏、采集加工速度、预计维护开支，以及新军备能否赶上下一次进攻或防守。地图总矿藏有限，本身并不保证一条路线最优；必须与各体系的配合、实际成型时间和对局压力共同起作用。

建议已经结算的专属成长不转成另一类成长或退回选牌机会，成品军备也不能瞬间等额兑换为另一套完整军备。具体建筑回收和生产取消退费仍待确定；普通回收可以降低损失，但不能制造超过实际投入的矿产。资源减少体现真实消耗，不另设系统识别路线后追加的转型税。

经验仍只通过原有成长来源触发选牌。单局可利用的选牌机会受经验获取和战局时长影响，当前未确定固定总次数上限，不能把“矿藏不可再生”直接等同于“经验不可再生”。

#### 4. 用配合收益支持专精，避免无限数值叠乘

优先让相关能力补齐彼此的使用条件，例如射程、部署和炮击配合，或量产、行军与基础单位生存。强化的收益依赖适用对象、位置和操作，并有明确强度边界；不通过每多选一张同色牌就无限提高所有属性来硬推路线。

不同路线内容仍可按正常前置与资源条件被选择；不因已选其他方向而将它们从候选池移除，也不通过隐藏路线分数决定资格。正常前置应表达真实能力依赖，不能把此前否定的互斥核心换个名字重新加入。选牌随机性与可选性保障的具体方式仍待定。

#### 5. 让玩家看得出投入能作用在哪里

候选界面可以显示某张牌当前影响哪些、多少适用单位或设施，以及后续生产是否受益。建设与强力牌消费可以同时展示成本、完成时间和对可用维护预算的影响。地图只依据已知信息展示剩余矿藏与采集机会，不自动泄露未侦察资源。

玩家应能看到“这张牌现在就能强化我的主力”“这笔红矿还能支持一次配合好的进攻”，从而主动继续主路线；不需要显示系统判定的人族、虫族或神族路线等级。

#### 6. 主路线专精与局势判断

目标是让多数局势下的大部分后续投入继续服务主体系。补充少量防空、反装甲或一次战略支援可以帮助主体系发挥作用，不等同于重新建立另一套完整路线。受到明确克制、丢失关键矿区或获得新战机时，改变投入仍可能合理；保留这些情况与用户要求的自然选择一致。

主要风险仍是扩张同时提供最高可支配双矿、最多兵力与最快经验，让它能顺手取得全部战略优势；也可能出现某张通用神级牌让所有打法趋同。应比较扣除维护后的实际投入能力和下一场战斗能兑现的收益，不能把不可再生视为已经解决这些问题。

最低成本的下一步建议：固定一个已有军备、已选卡与剩余矿藏的中局局面，比较继续主体系、少量补充反制、全面改建另一体系三种后续投入，在同一时间窗口内能形成什么军力、支付多少维护并争夺什么目标。先验证继续专精是否通常更有效，再加入敌方针对的情境检查是否仍有理性调整空间。本轮只完成分析与记录，未执行试玩、数值验证或新增测试。

| 《杀戮尖塔》初代 | 制作方将动态组牌及卡牌、遗物之间的配合作为核心特点。见[制作方商店说明](https://store.steampowered.com/app/646570/Slay_the_Spire/) | 新牌的价值由已有构筑和眼前需求改变，可借鉴配合形成的吸引力；不把它理解成必须坚持一个标签或不得补充应对手段 |

**转型成本的具体含义。** 本项目可将其分为重新建设生产所需的蓝矿与时间、尚未取得的新体系适用成长、调整期间不能充分发挥作用的旧专用资产，以及过渡战力不足带来的丢点和维护压力。它们不是可以直接相加的同一种数值，应通过同一局面和时间窗口比较其战果与风险。

工程车、采矿车、加工厂、剩余库存和仍适用的通用能力可以继续利用；只有确实不适用于新军备的定向成长与专用投入会成为转型负担。大规模改换主力通常比补充少量防空或一次支援需要更多重新配套，不能将局部反制也一律收取整套转型成本。

候选阶段体验为：早期投入少时可以试探，中期已有军队与卡牌形成配合，后期通常优先完善主体系和局部补强。后期转型成本增长与实际成型程度有关，不要求所有局面严格随时间递增；原主力严重受损、遇到明确克制或获得新战机时，转型仍可能值得。

以上参考支持采用实际配合与过渡成本促进专精，也提示不要把成本调到无法合理应对局势。下一步仍先比较一个中局的继续专精、局部补强和全面转型，观察新体系成型前能否承担战线与维护压力。本轮完成官方资料核对与记录，未实施玩法或新增测试。

### 建议的体验循环

`安装核心组件 → 选择适合本舰的交战位置 → 以移动和朝向组织自动火力 → 参战获得经验 → 选牌强化或改变已装组件 → 用新能力争夺更重要的战场机会`

基础攻击可以自动执行。玩家持续处理接近方向、射界、危险距离、撤离路线和目标选择；主动主炮只是可选组件行为，不要求所有流派都手动瞄准。指挥官负责全局军队与经营，Ship 负责驾驶自己的构筑进入具体交战区。双方可以拥有不同的操作密度，但 Ship 的站位和选牌必须持续影响结果。

沿用[当前资源与成长规则](../RequirementDocument/20260908-蓝矿红矿与据点维护及三线Roguelike成长.md)：经验独立触发 Ship 选牌；部分强力牌可另付红矿。蓝矿、红矿不可再生，组件和卡牌不能凭空补发矿产。参战贡献如何分配经验、组件如何获得仍待定；不擅自添加独立经验球拾取、掉落直接选牌或空中专属经济。

### 让组件改变驾驶方式

以下是候选例子，均不是现有能力承诺。

| 核心组件 | 自动火力与玩家决策 | 可能的卡牌分化 |
|---|---|---|
| 侧舷火炮 | 在有效射界内自动射击；玩家用朝向、距离和掩体把优势火力面对敌人，同时避免过度暴露 | 贯穿重炮、连续弹幕、范围爆破；相应改变射击节拍、目标偏好或暴露时间 |
| 僚机仓 | 安装后才有基础僚机与可用攻击；母舰距离影响机群周转和脱离，玩家按威胁调整站位，可再讨论简洁的指定打击/回护操作 | 数量型机群、少量精锐、对地轰炸专精；数量、补充和单机能力应有真实取舍 |
| 对地投弹舱 | 对下方有效区域投弹；玩家选择穿过敌阵的航向和进入、退出窗口 | 集束覆盖、沿航迹连续投弹、持续燃烧带；不同升级改变进场路线与打击对象 |

原型候选先使用火炮与僚机仓两类核心组件；投弹舱和其他功能组件用于后续扩展。未装僚机仓的炮舰应能独立成立，安装机库后也应立即获得基本召唤玩法，不需要再碰运气抽到“允许出击”才可用。

建议卡牌包含数值强化、行为改变和少量跨组件联动。例如炮弹从单发改为贯穿，机库从大量普通机转向少量精锐，或炮击标记使僚机更容易集中攻击高价值目标。联动是实际同时拥有两个组件的回报，不预设每局必须装齐火炮和机库。不能用连续的微小伤害加成代替可见的成型时刻。

相关强化候选应有已装组件作为实际依赖；没有机库时不给无法使用的纯机库强化。取得并安装新组件后可以接入其强化，配套通用成长仍可存在，不设置炮舰/航母的永久职业锁。槽位或真实装配能力承担取舍；具体数量及是否需要额外功率上限未定。

同型号装多件时一张卡强化单件还是全体、飞行中拆换后的升级保留、卸下机库后已召出的僚机如何收束，都需要后续细化。既有热切换方向保留；应避免拆仓仍永久保留机群或反复装拆绕过召唤代价。

### 放进大战场后必须成立的条件

**位置需要有收益与风险。** 如果高空悬停就能安全自动攻击全部目标，自动战斗仍会变薄。应让射界、遮挡、防空、追击空军和大范围攻击预警改变航线。巨舰需要与惯性相称的可读威胁和响应时间；不能照搬小角色钻密集弹缝的要求。

**成长需要服务战果。** 优先让摧毁关键火力、保护推进、拦截敌方 Ship 等行为既对团队有用，也能在经验分配中获得合理回报；具体分配待讨论。避免安全刷低威胁小兵长期成为唯一最优选择。Ship 继续不能直接占领据点，其火力优势通过地面单位兑现。

**构筑成型仍需给对手留下操作空间。** 清理成群小兵的爽感可以很强，但对操作者、大型建筑和防空反制要分别检查，不能把单人生存游戏的无限叠乘直接搬成无法接近、无法躲避的 PvP 自动秒杀。机群和连锁效果也需要可控的规模，不以无限增加僚机或弹道数量作为唯一成长。

**选牌不能让对战暂停。** 可积攒待选机会，在安全位置展开，或提供不中断驾驶的简洁入口；不能靠打开选牌获得无敌。具体交互待定。

### 下一轮最小讨论与验证方向

先纸面推演同一处战场的两种完整配置：火炮舰与僚机舰，各给几次明确的组件强化，写出它们的接近路线、危险来源、打击对象和撤退条件。检查在没有继续升级的一小段交战中，玩家是否仍有需要主动改变位置的理由；这是自动战斗能否成立的关键风险。

方向确认后再讨论最小可玩切片，不扩成完整牌库、经济、部件破坏或独立刷怪模式。当前空战成员无法持续形成第二轮有效射界是[已知遗留](../Gameplay/飞船.md)，不能把其故障造成的停火当成召唤流的平衡结果。本轮只完成参考核对与候选记录，未改动玩法、未执行试玩或新增测试。

### 2026-09-09 Ship 与指挥官的双向玩法联动讨论

用户继续询问幸存者式 Ship 如何与指挥官产生“化学反应”。本轮沿用组件决定能力、卡牌强化已选组件、机库开启召唤流的方向，以下均为候选机制，没有批准实施。

**建议核心关系：指挥官改变 Ship 的作战条件，Ship 的构筑改变指挥官能采用的战术。** 需要同时考虑己方协作和敌方应对。敌方指挥官通过真实兵力、阵型、防空部署和推进路线塑造 Ship 的压力与打击机会；这些部队仍服务于占点、攻防与资源争夺，不因 Ship 需要升级而强制送入射程。己方指挥官则用自己的部队和建设，为 Ship 提供有价值的目标、进场窗口和撤退掩护。

#### 1. 用交战位置与火力结构产生协作

| Ship 构筑 | 己方指挥官能创造的条件 | Ship 带来的战术机会 | 敌方可采取的应对 |
|---|---|---|---|
| 范围炮舰或轰炸舰 | 争夺狭窄通道、向据点施压，让守军需要在集中防守和分散避火之间取舍 | 清除密集防线，或逼敌军分散，使地面部队获得局部兵力优势 | 分散、撤离打击区、调整防空位置；不预设其必定进入伏击 |
| 僚机舰 | 地面火力威胁防空位置，己方防空阵地为母舰提供撤退掩护 | 机群打击阻挡地面推进的炮兵或工事，为地面部队和 WM 创造进攻窗口 | 截击机群、追击母舰、重新布置防空和护卫 |
| 单点重炮舰 | 正面牵制护卫、争夺侧翼射界 | 优先摧毁高价值火力单位，改变指挥官下一批部队的投入位置 | 隐蔽关键单位、轮换护卫、压缩飞船可用射界 |

以上描述的是拟议的完整玩法条件。当前建筑文档仍将功能性防空、经济与占领列为后续；不能把已有建筑放置和模型当作上述联动已经可玩。协作提高效率和安全性，各角色仍应保留独立作战与调整办法，避免必须等待队友完成唯一前置才能开始行动。

#### 2. 让敌方指挥官与 Ship 相互改变选择

范围火力出现后，敌方指挥官可以分散兵团降低损失，但需要承担局部兵力密度下降、护卫覆盖更难或机动协调的代价；己方指挥官有机会集中攻击其中一部。敌方集中防空压制僚机时，也需要考虑这些兵力的投入、位置以及其他战线的防守。不能假设“造防空必然削弱所有对地能力”，这种取舍必须由实际兵种能力和资源成本成立。

Ship 玩家据此决定留在原战区、更换进入方向或支援其他目标。敌方可以主动避开其强项；飞船需要追求战果，不能把无限追逐安全小兵视为唯一成长路径。两艘友方 Ship 可以采取不同构筑，扩大队伍的选择，也可以集中一项优势，但都要承担其他区域的机会成本。

#### 3. 让局内成长成为战术信息

Ship 取得改变组件行为的强化后，应能向队友清楚表达当前新能力，例如“现在适合覆盖密集防线”“机群可以承担更强的对地突击”。指挥官可以据此修改进攻目标、兵种配比或投入时机。反向也成立：己方炮兵、屏障或侧翼控制逐步成型后，Ship 可以更有理由强化远程火力、机群周转或借掩护深入交战。

双方各自决定自己的构筑，基础能力可独立使用。信息表达可以通过简洁的构筑摘要和进攻/撤退意图实现，避免要求指挥官逐张审阅或批准 Ship 卡牌。红矿库存与强力牌支付权限尚未确定，本轮不将其授予指挥官，也不让指挥官成为 Ship 基础成长的唯一许可者。

可进一步讨论少量共同战场状态，例如地面火力产生可读的压制效果，Ship 的某张火炮卡加强对受压制目标的打击；或 Ship 的攻击削弱一个目标，地面部队利用机会推进。双方卡牌仍只修改自己的组件或军队，通过目标状态和战场条件发生配合。具体压制、破甲和触发条件均未定，不能提前宣称这些状态已经存在，也不把某一对指定卡设为协作的必要门槛。

#### 4. 一次候选攻坚过程

敌方据点附近有阻挡地面推进的反装甲火力和保护它的防空。己方指挥官让地面远程火力威胁防空位置，并保留推进部队；敌方必须决定留守承压、转移，或主动进攻地面火力。僚机舰观察其选择，利用出现的窗口打击反装甲阵地。突破出现后，指挥官与 WM 推进地面占领。敌方若调空军追击母舰，Ship 可向己方防空掩护撤退，地面继续利用对方兵力调整产生的机会。

这一过程不保证每一步成功，也不要求固定由指挥官先手。换成重炮舰时，Ship 可以先通过侧方火力迫使敌方转移护卫，再由指挥官利用新的薄弱处。双方都能发起机会、识别失败并改变目标。

#### 5. 成长回报与下一轮推演

有效参战、协助击杀及协助占领的经验分配值得继续讨论，避免指挥官感觉地面部队帮助击杀后经验全被 Ship 最后一击拿走。具体资格、奖励预算和归属尚未定；三条成长线仍独立，经验仍是唯一选牌触发条件，不能因互相标记、重复施加状态或制造友方损失而无限产生奖励。

最优先的下一步是用同一个有防空和地面守军的据点局面，分别纸面推演炮舰与僚机舰，给敌方保留集中防守、分散和转移三种真实选择。观察双方指挥官是否会因 Ship 的组件与成长改变部署，Ship 是否也会因这些部署改变航线和目标。单看配合后总伤害上升不足以证明化学反应成立；需要出现双方相互引发的新选择。本轮仅更新讨论记录，未实施规则、未进行实机试玩或新增测试。

### 2026-09-09 《无畏战舰》拆解与 Ship 借鉴候选

用户要求拆解《无畏战舰》，判断哪些玩法和元素能够用于 Ship。本轮按 YAGER / Six Foot 的《Dreadnought》理解，沿用本条已记录的“组件决定能力、卡牌强化已装组件、安装僚机仓才获得机群”方向。以下迁移规则均为设计建议，条目保持 `inbox`。

**建议借鉴巨舰的交战决策：站位与朝向、火力窗口、有限能源的攻防取舍。** 它们可以补充幸存者式自动火力和局内构筑，让玩家在两次选牌之间也有事情可做。舰种分工适合变成组件组合后的战术倾向；保持玩家通过装配和卡牌形成自己的打法。

#### 1. 参考作品的机制与体验

本轮核对了制作方商店说明与制作人员发布的介绍，没有进行原作实机试玩。不同平台、时期的模式和规模存在差异，因此不把早期介绍或商店路线图中的未来计划当作统一的最终版本事实。

| 可核对的原作机制 | 设计解读 |
|---|---|
| 巨舰战斗采用相对从容的节奏，可在三维战场中改变高度和位置，见[制作方 Steam 说明](https://store.steampowered.com/app/835860/Dreadnought/) | 玩家要提前决定接近、暴露和撤离；大舰的承诺成本让位置判断有分量 |
| 舰船拥有用于护盾、引擎和武器强化的能源管理，见[制作方能源说明](https://store.steampowered.com/app/835860/Dreadnought/) | 同一资源连接输出、生存和机动，攻击机会与撤退余地会相互影响 |
| 舰船分成重型、突击、狙击、支援、侦察五类；制作人员举出侦察舰报告敌情、重舰在治疗舰支援下作战的例子，见[产品总监介绍](https://blog.playstation.com/2016/12/03/command-your-ship-in-dreadnought-coming-to-ps4-in-2017/) | 不同舰船改变队友可采用的战术，也产生优先攻击支援者或改变接近方向的理由 |

| PS4 的 Havoc 提供三人合作抵抗渐强波次、阶段选择预配置舰船并升级的玩法，见[游戏总监的 Havoc 介绍](https://blog.playstation.com/2017/06/06/dreadnought-out-today-new-details-on-havoc-mode/) | 可参考压力变化与阶段适应，但这不等于本项目的肉鸽卡牌规则，也不构成新增独立 PvE 模式的决定 |

对其交战过程可作如下设计归纳：`选择配装与职责 → 进入有利交战位置 → 识别集火机会 → 投入能源与能力 → 承受反击或脱离 → 恢复并重新组织进攻`。这是机制解读，不是声称原作所有玩家均按同一套步骤行动。

#### 2. 将五种舰种职责转成组件路线

下表中的组件和卡牌均是本项目候选，不是原作逐项照录，也不表示当前已经实现。中文舰种名称可能随译法不同，以英文与职责为准。

| 原作职责 / 常用舰种名 | Ship 可形成的组件路线 | 候选成长 | 应保留的代价 |
|---|---|---|---|
| 重型 / Dreadnought | 侧舷重炮＋防护组件，近中距离承担火力并压制通道 | 齐射改为贯穿重弹；防护结束后获得一次有上限的炮击强化 | 需要进入危险距离，不能全向同时输出最大火力 |
| 突击 / Destroyer | 多用途火炮＋导弹舱，寻找敌方转移或防守薄弱时的突破机会 | 连续导弹改为集中一轮的打击；牺牲覆盖换对大型目标效果 | 强化某一方向后失去部分通用性，爆发后留恢复窗口 |
| 狙击 / Artillery Cruiser | 舰首长程重炮，利用远距离射线打击关键火力 | 蓄能贯穿、缩窄射界换单点威力 | 开火前显著蓄能，暴露位置，近身防御较弱 |
| 支援 / Tactical Cruiser | 维修无人机、局部屏障或电子支援组件，仍能携带自卫武器 | 有限维修改为短时护盾；保护一个明确目标换更高单体效率 | 有距离、持续时间和能源限制；避免两艘船互修形成长期僵局 |
| 侦察骚扰 / Corvette | 侦察机库、干扰组件或机动组件，服务侧翼切入与目标发现 | 有机库后强化侦察僚机；干扰缩短但更集中 | 将侦察职责交给小机群或组件能力；大舰仍保持其尺度和惯性 |

每队只有两名 Ship 玩家，完整复制五职业配队会使必要职责难以覆盖。更合适的是让“炮舰、航母、支援炮舰”等从组件组合中出现；纯炮舰不需要机库也能成立。航母路线是结合本项目已有僚机体系的拓展，不把它描述成原作五类中的独立航母职业。

#### 3. 最有价值的迁移机制

**A. 用射界与距离让自动攻击需要驾驶。**

侧舷炮需要玩家把有效炮位转向目标，舰首重炮需要对准目标方向，投弹舱需要形成合适的通过航线。不同组件可以自动寻找合法目标，但应遵守自己的射界、距离和遮挡。这样同一张增幅卡会改变玩家愿意承担的暴露和接近方式。

侧舷设计是本项目建议，不引入“所有舰船转成侧面就统一增加伤害”的规则，也不默认原作存在完整的分区装甲或逐部件破坏系统。侧身的收益来自实际有多少炮位能开火，代价来自敌方获得的射线、暴露面积或航向承诺。

现有船体尺度约长 450m，空装配有效基础极速约 27m/s，见[当前飞船记录](../Gameplay/飞船.md)。地图掩体、通道和危险区域必须按巨舰转向、加速、制动所需空间设计。不能只缩小反应时间来提高难度，也不能让舰首已经入掩体而暴露的舰尾被视为完全安全。

**B. 让自动火力出现可以主动利用的爆发窗口。**

自动攻击维持基础输出，玩家在关键时刻投入一项与已装组件绑定的舰长指令。炮舰可以选择火力过载，机库舰可以选择一轮集中打击。主炮的蓄能、齐射和冷却要改变玩家的行动时机，而非只让每秒伤害更高。

建议第一轮只讨论一种简单指令，不同时叠加全手动瞄准、全机群微操和多个必按技能。集中打击也不要求机群同一帧射击；保留各机合法进场、射界和攻击状态，通过目标或下一轮攻击意图形成可读的打击窗口。

当前源码已有[整组手动目标入口](../../Source/GuLiStrike/Gameplay/Ship/GuLiStrikeShip.cpp)，解除后恢复自动分配。它不是“主动召回”，也不是“整组同步齐射”。按兵种优先级选敌、主动回护与同步爆发都需要单独设计，不能从现有入口推断已经具备。

**C. 用简化能源分配连接进攻、生存和撤退。**

候选规则为一条可恢复的舰载能源，以及默认巡航和三种互斥强化状态：

| 状态 | 候选作用 | 玩家牺牲了什么 |
|---|---|---|
| 巡航 | 基础移动和基础自动攻击照常运作；能源按恢复规则回补 | 暂时没有额外强化 |
| 武器强化 | 短时强化一个明确的武器或挂载组 | 消耗之后可用于防护和撤离的储备 |
| 防御强化 | 有对应组件时启动短时护盾或加强其效果 | 无法同时获得武器和机动强化 |
| 引擎强化 | 短时改善转移或撤退能力 | 可留给下一轮攻击和防护的能源减少 |

这套互斥和恢复规则是适配提案，不照抄原作具体消耗数字。耗尽时回到基础状态，避免新手因为一次错误分配而无法移动、完全停火。护盾、维修等能力仍受实际组件依赖约束，不应绕过“组件赋予能力”的方向。

先验证“打完这一轮后还剩多少保命余地”是否能产生选择，再决定是否需要完整三态。若最佳操作始终是全程武器强化，说明威胁、收益或恢复关系没有成立。切换不能刷新冷却、清空应承担的代价或反复领取开启奖励。

舰载能源是秒级作战资源的候选；既有蓝矿、红矿和经验用途不变。静态装配功率限制属于另一项可选规则，不能因提出能源分配就默认新增。武器强化默认不自动乘到 25 架僚机和所有伤害来源；机库是否受益、按哪一项参数生效，必须写进对应组件。

**D. 让高度、遮挡和撤离路线产生战术。**

高处能获得更广射界，但会被更多敌人看见和攻击；低处借山体遮挡，可能牺牲目标视线和转向余地。轰炸舰、侧舷炮舰和狙击炮舰因此应倾向不同航线。持续缩在同一安全位置不能同时覆盖全部重要目标。

这需要战场目标与威胁配合，不能只靠增加高低差。现有建筑放置与模型不等于功能性防空已经实现；作为候选的防空射线、射程和可转移能力需另行定义。威胁应让玩家能提前发现并调整，巨舰不承担小型幸存者角色钻密集弹缝的操作要求。

**E. 将支援与干扰做成制造机会的组件。**

局部维修或临时屏障可以帮助己方 WM 穿过危险通道；电子干扰可以短时削弱某一明确敌方系统，为炮击或机群创造进场窗口。先从目标明确、范围有限的单一作用开始，避免一次技能让对手所有武器、移动和整支机群长期失效。

这些效果应通过射程、视线、持续时间、能源或相应的资源成本形成取舍。舰载局部能力与既有红矿外层战略支援分别定义，不直接把全图核打击或大范围无敌变成 Ship 免费循环技能。核鱼雷式大威力武器可转译成可预警、有进场和发射限制的局部舰载爆发；具体拦截能力是额外候选。

**F. 把巨舰感落实到动作和信息。**

候选表现包括炮塔依次转向、炮口沿舰身错峰齐射、蓄能到释放的声音变化、命中护盾的局部波纹、引擎强化的尾焰变化，以及可关闭的简短舰员播报。它们要帮助玩家读懂“哪些武器已就绪、威胁从哪里来、当前有没有撤退余地”。

选牌后的行为变化应可见：连射变为少量重弹、弹道出现贯穿、机群从普通数量型转为少量精锐。真实倾斜、后坐与镜头震动保持可读并可调；先用表现建立重量，不给输入增加无意义迟滞。逐部件破坏、舰内船员模拟和细分装甲不是这些表现的前置条件。

#### 4. 与现有组件肉鸽的结合例子

| 已装组件 | 候选卡牌改变 | 新的驾驶或战场选择 |
|---|---|---|
| 侧舷火炮 | 连续小弹改为间隔更长的重型齐射 | 从持续暴露换成抢射击窗口，开完这一轮及时利用遮挡 |
| 舰首重炮 | 蓄能后穿透一条目标线，准备阶段更明显 | 寻找敌军纵列和合适射线；敌人能分散、转移或压迫炮舰 |
| 僚机仓 | 少量精锐轰炸机替代更多普通成员 | 选择值得集中投入的高价值目标，并重视单机损失与进场风险 |
| 防护组件 | 成功防御后储存一份有限的下一轮武器强化 | 判断是否冒险留在前线兑现反击，避免无限受击叠伤 |
| 火炮＋机库 | 炮击给一个目标短时标记，机群对它获得明确限定的配合效果 | 让两组件共同改变打击顺序；无机库时不发放无法兑现的纯机群联动牌 |

组件升级是否覆盖同型号全部挂载、拆换后的效果保留、僚机补充成本与死亡后的构筑保留均沿用此前待定项。经验仍是 Ship 选牌的触发条件，部分强力牌可另付红矿；不增加原作式舰船科技树或新的空中专属矿产。

#### 5. 用一次据点交战检查它能否帮助大战场

候选场景：敌军在据点方向集结，侧方有高地遮挡；己方 WM 和指挥官部队准备推进。一艘侧舷炮舰与一艘僚机舰协作，敌方有可转移的防空和一艘能威胁母舰的 Ship。防空与战场能力是推演前提，不描述成现有可玩事实。

1. 炮舰利用侧方射线迫使敌人选择集中承受炮击或分散；僚机舰判断能否从另一方向进入。
2. 敌军集中时，范围齐射可以形成明确的突破收益；敌军分散时，己方地面部队可以集中攻击其中一部，而 Ship 必须重新选择打击对象。
3. 玩家决定用能源强化本轮输出，还是预留防御和撤离。敌方 Ship 出现时，过度投入应形成可理解的风险；保留能源可以减少损失，但先前突破可能没有那么彻底。
4. 突破成功由地面单位兑现为占领；失败时调整航线、目标或投入，保留正常撤退路径。Ship 的收益通过有效参战与贡献体现，经验资格和分配仍待细化。

这组候选可以形成“位置决定能打谁，能源决定敢投入多少，组件和卡牌决定用什么方式改变战线”的连续选择。是否好玩仍需证据，不能由纸面连招直接判定。

#### 6. 优先级、成本与应后置的内容

下列成本为相对新增工作量判断，不是排期估算。

| 候选 | 建议顺序 | 主要成本或风险 |
|---|---|---|
| 火炮 / 机库组件成立，并用射界、距离和遮挡区分打法 | 最先验证 | 当前无畏舰缺自身挂载；机库授权需从默认直接授予迁移。基础能力与地图空间都要成立 |
| 一种清晰的爆发窗口与对应提示 | 接着验证 | 自动攻击到主动决策的衔接；不能将准星表现等同于主炮能力 |
| 简化舰载能源，再评估完整三态 | 高价值候选 | 新增资源生命周期、护盾或机动效果、HUD 与网络状态；若没有机会成本会退化成常驻增伤 |
| 支援、干扰和两舰互补 | 后续扩展 | 状态、目标规则、反制与贡献回报；纯治疗可能占去稀缺的 Ship 席位 |
| 多种舰体、制造商路线、长期科技树 | 后置 | 内容和平衡维护量大，可能稀释局内组件成长 |
| 完整部件破坏、舰内船员和复杂装甲 | 后置 | 命中、损伤、维修、复制与表现成本高；不是证明当前循环的必要条件 |
| 独立波次生存模式 | 后置 | 改变模式范围；可参考 Havoc 的压力起伏，但本项目仍服务现有大战场目标 |

最关键的风险是“仍可安全悬停并自动赢下所有交战”，其次是“能源操作频繁却总有固定最优答案”。下一步先在上述同一据点局面中比较炮舰与机库舰，在不继续获得新卡的交战段检查是否需要改变位置和投入。能成立后再讨论最小可玩切片，避免先扩充牌库。

当前僚机空战难以持续形成第二轮有效射界仍是[已知遗留](../Gameplay/飞船.md)，其停火不能作为航母输出平衡的证据。本轮仅追加参考核对与候选设计；未修改代码、数值表、资产或玩法状态，未执行实机试玩，未新增测试。

### 2026-09-09 《无畏战舰》后期冷清、失败因素与本项目风险

用户进一步指出原作后期“鬼服”，要求同时分析失败原因及本项目可吸取的教训。本节补充前述正向拆解，并调整候选优先级：**先证明首局价值、低人数可玩性和可理解的对抗，再扩充舰种、技能与长期内容。**

#### 1. 证据边界与已知事实

“玩家少”“排队困难”“经营无法持续”“最终停服”是不同层面的结果，不能把其中一个当成全部原因。本轮没有获得内部留存、收入、获客和全平台活跃数据，不能给各原因分配贡献百分比，也不能把一篇评价代表为所有玩家意见。

#### 2. 较可信的失败机制

以下为结合公开事实的分析，因果权重尚无内部数据验证。

**成长负担让尚未熟练的玩家承担更多劣势。** 原作的分级舰船和模块成长，使学习战术与取得配装能力相互交织。当玩家不知道失败来自操作、配合还是装备差距时，更难产生“再试一次就能改善”的动力。成长加速付费会让这种感受更敏感，但不应把所有历史版本一概定性为付费必胜。

**人数下降会恶化产品本身。** 固定规模团队战在不同模式、等级、网络条件和组队配置下分配玩家，剩余匹配余地变小。选择缩紧条件会等更久；放宽条件可能增加实力和配合差距；用机器人补位则要求 AI 真能承担职责。组队上限先收紧再恢复的历史，正好展示了这些解法之间的矛盾。

**战术深度可能收敛成少数固定打法。** 治疗舰抱团使正面消耗难有结果，理解配装和反制的老玩家又更容易协同。当最佳做法长期收敛为抱团互修、固定爆发组合或少数必选模块，庞大舰船目录不等于丰富的实际选择。原作持续调整减疗，说明这个风险不能因“有支援职业”就视为已解决。

**巨舰节奏会放大无效时间的感受。** 从容的位移与开火可以服务预判，但如果排队、加载、赶路和长时间无结果的对射连在一起，实际回报会来得很晚。这是本轮从机制推导出的体验风险，不能声称所有玩家都因“太慢”离开。已有评测也说明慢节奏本身对部分玩家具有吸引力。

**修复与内容承诺需要持续投入。** 2018 年裁员和 2020 年官方对团队规模、方向的反思，说明更新能力不能只看计划中有多少功能。人数与收入压力会缩小改进空间；改进不足又可能影响回流。这里是可能相互强化的经营过程，不把后来的每次延期都追溯为同一个单因。

可用如下因果假设理解后期冷清：`新人体验和成长摩擦 → 玩家流失 → 匹配选择变少 → 等待、碾压或低质量补位增加 → 更多人离开`。经营压力和更新能力下降可能进一步放大它。“宣传少”“题材小众”“付费毁掉游戏”都不足以单独替代这条具体分析，也没有证据证明增加宣传即可修复留存。

#### 3. GuLiStrike 最需要防的五个问题

**A. 固定角色使我们对人数结构更敏感。**

按当前 5v5 方向，一场完整对局需要两名指挥官、四名地面操作者、四名 Ship 玩家。十人在线不等于恰好能组成这套阵容，在线玩家也不全处于等待开局状态。大量自动小兵与僚机可以维持战场表现，但不能自动代替指挥官经营、WM 占领和 Ship 支援这些席位职责。

建议尽早推演同一大战场中“少量真人＋能完成缺席职责的 AI / 默认策略”的方案，并明确真人离开后的接管与重连。特别是缺指挥官时，基础生产与推进是否仍可持续。AI 指挥官并非低成本现成功能；若做不出足够好的接管，应提前调整初期开放方式与允许阵容，而非等正式公开后才发现必须凑齐十名特定角色。以上不改动已确认的完整 5v5 目标。

早期尽量集中到一个核心公开匹配入口；训练或自定义复用核心战局，不默认新增必须依赖独立人口池的多个常驻模式。

**B. 新玩家要尽早玩到宣传中的东西。**

进入首局即可使用完整的基础组件玩法：选火炮能开火，安装机库能出击；不要求先肝长期等级或再随机抽出一个必要使能能力。通过经验取得的早期升级应能让玩家看出行为或战术变化，并提供与已装组件相关的选项。第一次变化出现太晚，应调整经验与选牌节奏，仍保留经验触发规则。

没有机库时不发纯机群强化，缺红矿时不能让整次选牌只剩无法支付的候选。基础防空或对抗方法不应全部锁在某张稀有卡背后。卡牌的首次获得、组件获取和死亡保留规则尚需明确；这不是自动批准初始组件数量或免费发放额外选牌。

**C. 局内肉鸽也可能重现装备碾压。**

当前存在资源、据点防御、兵力和三线成长的关联。若先赢一仗的一方获得更多经验与资源，再取得更高伤害、更强防护和更多兵力，随后又更容易赢，局内重置本身不会阻止一局中的滚雪球。对缺乏经验的新玩家来说，被“本局已经成型的人”反复击毁，与被长期满级装备压制可能产生类似感受。

建议将基础操作和反制放在可稳定获得的能力中，让卡牌更多改变攻坚、覆盖、精确打击、机动与召唤风格，并保留强度增长的上限和代价。失败方应仍有能判断并尝试的侧翼、转移、针对性目标或局部反击；这些是需要地图和规则兑现的机会，不是无条件补发资源或自动平衡胜率。

**D. 治疗与据点防御可能叠出更牢固的僵局。**

将维修 Ship、舰载盾、WM、防空、据点护盾和兵种 buff 全部叠在一个位置，可能形成突破成本过高的防守集团。前文的维修、屏障组件因此降为需重点审查的扩展，而非默认必做职业。

候选约束包括维修受射程、视线、能量和在场承诺限制，明确同类效果的叠加规则，并通过多个有价值的战场目标使集中防守存在机会成本。不要只依赖随机抽到唯一减疗牌解决全部防守。也不能假设有限矿藏自然解决僵局：若落后方先缺维护资源并同时失去四项据点功能，原有优势反而可能扩大。已确认的双资源维护规则保持不变，断供恢复与地图资源布局需在后续推演中一起检查。

**E. 可操作内容要转化为可感知的结果。**

Ship 的自动火力需要持续让位置、目标和投入改变结果；指挥官的经营和指令也需要让玩家看出部队响应与战线变化。增加按钮、卡牌和特效不能替代这件事。巨舰重量可通过尺度、动作、炮击与声音表达；赶路、等待和看不懂伤害不应成为重量感的主要来源。

原作的投入压力也提醒本项目控制每次扩展的依赖：三角色、空地战斗、组件、肉鸽、资源与大规模单位已经形成较大的维护面。新增功能优先复用稳定组件规则，并检查它是否真的改变玩家选择。当前已知的僚机重复攻击问题属于基础体验，验证其行为应排在增加更多机型与特效前。

#### 4. 对前述借鉴清单的修正

| 元素 | 加入失败分析后的建议 |
|---|---|
| 射界、距离、遮挡与巨舰表现 | 继续优先，直接改善驾驶的意义和回报 |
| 自动基础火力＋少量爆发指令 | 继续候选，重点检查新手是否能理解、是否长期有固定最优操作 |
| 简化能源分配 | 保留，等基础战斗和提示成立后再扩展；避免叠成复杂资源操作 |
| 模块决定风格、卡牌改变行为 | 保留，同时检查无用候选、必选牌、基础反制和局内滚雪球 |
| 维修、护盾与干扰组件 | 后置审查，防止互修永动、集中防御和长时间剥夺操作 |
| 舰船等级树、长期战力积累和成长加速付费 | 当前不建议引入，尤其不要借长期战力门槛延后核心乐趣 |
| 多模式、多等级队列和严格角色等待 | 先论证人口承受能力与缺席接管，避免提前分散匹配人群 |

下一步最便宜的验证仍是纸面走完一名新 Ship 玩家与一次不完整阵容的进场过程：何时控制舰船、何时影响战斗、何时体验一次有效构筑变化、缺某角色时战局如何继续。然后再讨论真实试玩，并观察角色等待、有效交战间隔、首次构筑变化、落后时仍可采取的行动以及是否愿意马上再来一局。这里没有设定已经验证的秒数目标或留存达标线，也没有新建自动化测试、遥测或运行试玩。

本轮最终候选方向为：保留巨舰的战术和表现价值，同时把首局可玩、低人数可玩、落后仍能参与和稳定交付当作约束。只更新讨论记录，未提升正式需求、未改变现有玩法规则。

## IDEA-202609-006 蓝矿红矿模型与矿区逐步耗尽表现

- 状态：promoted（本轮单位矿资产制作；采集逻辑仍为后续范围）
- 模块：economy、world、art、commander
- 价值：让玩家从矿区轮廓与晶簇残缺程度看出资源消耗，支持巨型矿区逐步缩小并最终消失。
- 待确认：后续 UE 接入时的采集目标、阻挡规则、矿量和阶段阈值；本阶段24个模型范围与归零销毁已确认。
- 正式需求：[REQ-20260910-004 双矿单位矿模型与 Blender 审核](../RequirementDocument/20260910-双矿单位矿模型与Blender审核.md)；资源规则沿用 [REQ-20260908-003](../RequirementDocument/20260908-蓝矿红矿与据点维护及三线Roguelike成长.md)。

### 2026-09-10 实施确认（以本条定义为准）

用户澄清：**矿簇由多个单位矿组成**，中心大、外围小的布置与资源梯度由程序负责；一个单位矿耗尽后直接销毁。本次明确实施蓝红各四个造型家族、每家族完整/残缺/残矿三态，共24个模型，完整态约8米高、12米占地。只交 Blender 审核源工程、可重复脚本和12张预览，UE 与运行时逻辑在审核后推进。下方保留研究经过；早期“单簇”及“簇内晶体储量分配”等术语和建议不覆盖这次已确认的单位矿粒度。

### 2026-09-10：参考图、开源实现与候选方案

用户提供蓝矿、红矿两张晶簇矿区示意图，提出本次任务最终要完成矿资源模型及资源消耗对形态的影响；当前步骤先查阅网络讨论与开源项目，分析如何从巨型矿区采集到小型矿区并最终消失。本轮仅交付分析与交互示意，尚未制作正式三维资产或实施 UE 采矿逻辑。

**已确认前提与图像观察。** 两种矿藏有限且不可再生；地图矿藏经采矿车采集、加工厂加工后才成为可消费库存。蓝矿参考图以较饱满、分叉密集的蓝色晶簇和深色岩基为主，红矿以较细长的红色主晶和浅色岩基为主。图片用作造型参考，不据此假定每簇储量、碰撞尺寸、晶体透明材质或采集效率。

**推荐方向：区域分簇、单簇阶段模型、短暂碎裂过渡。** 把整片矿区作为管理和展示上的集合，将图中可辨认的一堆晶体作为独立资源单元。各簇拥有独立余量；采矿车采到哪簇，哪簇从完整变残缺、变残矿、再消失。已采空的簇不重新分布，剩余簇维持原位，大片矿区因此逐步形成缺口、收缩为小片并耗尽。区域总余量由各簇汇总，不同时维护一套可能不一致的独立扣量逻辑。

#### 研究证据及适用边界

1. **OpenRA：局部密度驱动视觉，是最贴近本任务的结构参考。** `ResourceLayer.RemoveResource` 限制扣除量，更新单元密度并发出变化事件；`ResourceRenderer.UpdateRenderedSprite` 将密度映射到序列帧，密度归零时移除显示。渲染代码还只更新可见的变化单元。它使用二维格子与精灵，适合借鉴“局部余量 → 局部外观”，不证明已经提供三维晶体破碎。源码取自 2026-09-10 查询的提交 `f3ec7f8e1593b482f85fd101652deb740c33dee6`：[扣量逻辑](https://github.com/OpenRA/OpenRA/blob/f3ec7f8e1593b482f85fd101652deb740c33dee6/OpenRA.Mods.Common/Traits/World/ResourceLayer.cs#L239)、[外观映射](https://github.com/OpenRA/OpenRA/blob/f3ec7f8e1593b482f85fd101652deb740c33dee6/OpenRA.Mods.Common/Traits/World/ResourceRenderer.cs#L244)。
2. **0 A.D.：资源数量和耗尽生命周期可以独立于美术。** `ResourceSupply.TakeResources / Change` 返回实际取得量及耗尽标志，将余量限制在合法区间，归零后销毁资源实体并通知资源变化。此文件没有提供逐阶段矿石模型切换，不能据此声称 0 A.D. 已实现本文推荐效果。源码提交 `61a3b9507d974084e6badb88a0826bd89a6d5b8b`：[ResourceSupply.js](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/binaries/data/mods/public/simulation/components/ResourceSupply.js#L214)。
3. **0 A.D. 开发者讨论直接覆盖残矿与碰撞问题。** 2019 年的矿山美术讨论中，elexis 指出大型矿山突然消失可能使场景留下不自然空洞；损伤形态可以改善过渡，但需要更多美术工作，替换为耗尽形态更简单；残留对象还需考虑阻挡。这是开发讨论，不是已验证的成品效果：[Mines (Stone and Metal)](https://wildfiregames.com/forum/topic/25612-mines-stone-and-metal/)。对本图的推论是把可消耗晶簇与地表底色分开制作；最终不保留可误认成资源的大块亮晶体。
4. **UE 社区讨论强调采空后的导航，以及实例与交互实体的分工。** 2019 年的两个帖子分别讨论了矿石销毁后导航仍挡路，以及空闲资源使用实例、交互时替换成 Actor 的方式。这些是社区实现建议，不能视为 UE5.7 的性能实测结论：[导航与生命周期](https://forums.unrealengine.com/t/best-way-to-implement-resource-gathering/451815)、[实例与 Actor 转换](https://forums.unrealengine.com/t/resource-gathering-help/456568)。本项目不因此自动采用频繁 Actor 转换。
5. **Zylann/voxelgame：需要自由挖洞时的另一类实现。** 平滑地形示例通过 `VoxelTool.MODE_REMOVE` 和 `do_sphere` 从体素数据中移除体积，是真正修改几何的路线。源码提交 `4cf747a8456375e527c8c976c50fb24446f9d18f`：[interaction.gd](https://github.com/Zylann/voxelgame/blob/4cf747a8456375e527c8c976c50fb24446f9d18f/project/smooth_terrain/interaction.gd#L73)。该项目是 Godot 演示并依赖体素模块；作者文档也提醒精确模型破坏可考虑预制破坏，体素不能自然表达所有精细形状：[适用边界](https://voxel-tools.readthedocs.io/en/latest/quick_start/)、[性能与更新成本](https://voxel-tools.readthedocs.io/en/latest/performance/)。对本项目的判断是：只有允许自由挖洞、掏空与改变通路时，这项新增复杂度才有明确收益。

#### 方案比较

以下成本与适配度为结合参考图和现有项目的工程判断，未做基准测试。

| 方案 | 能表现什么 | 主要代价或限制 | 本轮建议 |
|---|---|---|---|
| 整片模型统一缩放 | 整体越来越小 | 轮廓不变，像缩小玩具；无法表达采集位置；交互点可能随缩放移动 | 仅适合临时占位或很小幅的过渡 |
| 整片矿区切换大、中、小模型 | 能控制几个固定阶段 | 需要制作多套大区域模型，局部采集与区域突变容易不一致 | 可用于只在固定站点采集的抽象矿场 |
| 分簇＋每簇阶段模型 | 被采位置逐步变残，矿区自然形成缺口和收缩 | 需要配套阶段模型、稳定位置与实例映射 | 推荐主方案 |
| 模块晶体逐块移除 | 单簇也有更细腻的缺损 | 每块都做独立组件会增大管理成本，需要合并或实例化 | 适合作为制作阶段模型的方法，或近景增强 |
| 材质溶解或下沉 | 可平滑隐藏几何 | 本身不能代替余量、碰撞与导航变化，长时间溶解容易像融化 | 仅用于切换和消失时的短过渡 |
| Chaos 预破碎 | 冲击引起物理碎裂 | 需要预破碎资产与模拟管理，物理碎块数不能直接当作资源结算 | 可用于少量近景表现，后置 |
| 体素／运行时布尔切割 | 任意位置挖洞和掏空 | 几何重建、切面、碰撞、同步、存档与性能成本更高 | 当前图示目标不优先采用 |

Chaos 使用预破碎 Geometry Collection 与聚类约束，适合控制物理破坏，不能把它理解成无需准备资产的任意切割功能，见 [Epic UE5.7 Destruction Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/destruction-overview?application_version=5.7)。

#### 模型应怎样构建

- **构建粒度。** 一片矿区由若干晶簇组合；每簇美术源文件保留主晶、侧晶、小晶和岩基的分组。制作时可以拆分零件，运行时先把各阶段烘焙为合并的 Static Mesh，不要求每块碎石成为独立 Actor。
- **保持形态连续。** 从同一套完整晶簇派生残缺和残矿模型，优先移除侧晶、切短或折断主晶；保持存续部分的位置、岩基对齐、枢轴和材质坐标。避免用几套完全不同的随机模型表示同一簇的消耗，也不把普通小型完整晶簇直接等同于大型晶簇的残骸。
- **区分种类。** 蓝矿保持宽厚、密集分叉与深色岩基；红矿保持细长主晶、相对疏开的侧晶与浅色岩基。共享耗尽逻辑和材质框架，但造型差异不只依赖换颜色。首轮材质可先用不透明切面、可控高光和少量自发光建立晶体感；是否需要真实透光由近景效果再决定。
- **收敛首轮资产量。** 建议每种矿先做一个完整晶簇，以及由它派生的两个消耗阶段，即两种矿共六个主模型；归零是逻辑状态，不需要一个空网格。闭环成立后再增加轮廓变体；每个变体必须有自己的阶段对应关系。此数量是建议，不是已确认制作清单。
- **最终消失。** 采空簇移除晶体与会被误认为仍可采集的岩堆，可用短暂碎片／尘土衔接。低对比地面痕迹可以保留或随后淡去，但不应继续承载资源交互；是否允许长期痕迹仍待确认。

候选单簇阶段示例：`r = 本簇剩余量 / 本簇初始量`，初始量必须大于零；空簇直接标为耗尽。

| 余量比例示例 | 显示形态 |
|---|---|
| 66% < r ≤ 100% | 完整晶簇 |
| 33% < r ≤ 66% | 侧晶减少、主晶出现断面 |
| 0 < r ≤ 33% | 短晶与少量残矿 |
| r = 0 | 耗尽，资源模型和交互移除 |

阈值用于解释状态映射，尚未定稿。用户随后补充了下文的“中心到边缘尺寸与储量逐级递减”约束；后续阶段分界应根据对应晶体组的矿量预算重新确定，以上等分示例不作为实施默认值。变化节奏应结合每车采出量与正常镜头距离调整。阶段切换可伴随短暂碎片、尘土或遮罩过渡；余量每次更新不必都切模型。视觉阶段与按相机距离选择的 LOD 是不同维度。

#### 耗尽逻辑与空间变化

**资源扣量发生在成功采出时。** 候选流程为：校验采集资格、目标可达及车载空间 → 取实际可采量 → 原子更新该簇余量和车载矿量 → 发送状态变化 → 更新该簇形态 → 归零时停止接受采集并释放目标。候选实际量为 `min(本次请求量, 本簇剩余量, 车载可接收量)`；失败不扣矿，同簇多车采集由权威端串行结算，最后一批不足整车时只发实际余量。

矿区形态跟随地图矿藏减少。运输中、加工中与已入库数量分别维护；建造、维护或支援消费库存时不再改变矿区模型。不得等加工入库时才让已被采空的矿簇消失，也不由碎片数量或粒子销毁事件决定经济结算。

**“边缘向内”由选矿规则产生。** 若采矿车实际到达一簇附近开采，应从可达、允许采集且有余量的前沿矿簇中选目标，再按路径成本和可用采集位置选择；多车需要避免挤在同一点。由于矿体若阻挡通行，内部簇未必可达，不能只按直线最近距离选择。这样会从采矿车进入的一侧向深处退缩；多方向开采会留下多个缺口，未必是同心圆。

如果未来确认采矿车只停在矿区固定接口，那么也可以用总量驱动一个固定的由外向内消耗顺序，但必须让采集特效的位置与当前消耗区域匹配。不能对所有晶簇同时减相同比例，期待它自动缩成一小片；那通常只会得到覆盖范围仍很大的稀薄矿区。

布局一旦生成就保存种子、布局版本与各簇稳定 ID；仅总量加种子无法还原玩家从哪侧挖出的缺口，还需要每簇余量或等价的耗尽状态。重载、重连或进入可见范围时直接重建当前阶段，不重播历史碎裂。若后续加入战争迷雾，模型及小地图的耗尽显示还需遵守可见性规则，不能通过画面变化泄露不可见区域采矿。

#### UE5.7 的落地边界

本轮在 `Source/GuLiStrike` 以及两个自研插件的 `Source` 范围检索资源／采矿相关名称，未定位到可直接对接的矿藏扣量实现；未检查运行中的蓝图资产，不能据此断言项目完全没有相关蓝图。现有主模块已依赖 Engine、Niagara、NavigationSystem、NetCore 等，建议优先使用现有能力。

候选结构为一个矿区管理对象维护晶簇数据数组，渲染按“矿种＋轮廓变体＋阶段＋材质”分组实例化。单个 ISM 组件内实例共享网格，单簇换阶段需要从旧阶段组移入新阶段组，不能给同一 ISM 中某个实例单独设置另一种 Static Mesh。只更新发生变化的簇，稳定矿簇无需每帧轮询。

Epic 的[现行 ISM 文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/instanced-static-mesh-component-in-unreal-engine)说明实例共享网格与组件属性，Per Instance Custom Data 可以传递每实例材质参数；页面当前默认标为 UE5.8，因此本轮另外核对了本机 UE5.7 的 `Engine/Source/Runtime/Engine/Classes/Components/InstancedStaticMeshComponent.h`：存在 `SetCustomDataValue`、`UpdateInstanceTransform`、`RemoveInstance` 及按 ID 操作接口。该头文件明确提示按 ID 接口仍有适用限制，例如不能直接用于 HISM，编辑器操作也可能使 ID 跟踪失效。

据此建议业务层持久化自己的 `ClusterId`，与渲染组件／实例位置分开映射；增删、换组或重建时更新映射，不将数组下标或临时渲染 ID 当作永久矿藏 ID。优先以 ISM 做原型，再按实际变动频率、Nanite 设置和目标平台评估 HISM；不预设 HISM 必定更快。

碰撞和导航是玩法选择：若矿簇挡路或占据建造空间，采空后要同步解除对应阻挡和占位；若只是地表可穿行资源，则以独立交互查询定位矿簇。纯材质隐藏不能替代这一步，视觉渲染实例也不必承担全部采集碰撞。每次扣一点矿不应导致整片地图导航重建，更新频率与范围需随最终阻挡规则确定。

权威端保存和同步资源状态；客户端按状态派生模型与短暂表现。切换阶段不改变 ClusterId、采矿对象身份或重复发放资源。归零应先阻止新采集，再完成表现清理；重新选矿、运输与加工分别响应状态，避免采矿车继续朝已删除实例工作。

#### 2026-09-10 补充：单簇内中心到边缘的尺寸与储量梯度

用户补充：“一个矿簇，从中间到两边，矿的大小是逐级递减的，然后矿量也是逐级递减。”据此记录单个矿簇内部的形态与资源对应约束：中心主晶最大、储量最高，向两侧及外缘过渡到中型侧晶和小型边晶，对应可采矿量逐级降低。玩家希望由此改善外观和采集体验；具体体验收益尚未通过样片验证。

空间层级沿用“矿区 → 矿簇 → 簇内晶体／晶体组”。本次明确的是簇内梯度；整片矿区的中心是否也必须布置更大的矿簇，仍未指定。前文采矿车接口、碰撞规则及渲染实现等候选项不因本次补充而一并定稿。

| 簇内位置 | 形态约束 | 储量约束 |
|---|---|---|
| 中心 | 最大、最高的主晶，形成主要轮廓 | 最高 |
| 中层 | 逐级降低的侧晶，衔接中心与外缘 | 低于中心、高于外缘 |
| 外缘 | 最小、最低的边晶 | 最低 |

**建模建议。** 先确定中心、过渡层、外缘的体量等级，再在等级范围内调整朝向、倾斜和间距；局部变化应保留整体递减关系。形成有层次的隆起轮廓，具体构图可自然错落，避免机械左右镜像。蓝矿与红矿分别保留既有形态特征，共享这个梯度规则。岩基和装饰碎石的数量不直接代表可采矿量。

**数据建议。** 为各层或可移除晶体组配置相应的容量预算，簇总储量由它们汇总。可先按体量等级分配权重，再归一到已经设定的簇总储量，避免仅因增加装饰晶体或改美术变体就改变地图经济。具体等级数、容量比例和换算方式待定，用户本次没有指定数值。大晶储量较高本身不意味着采集速率更高；若沿用相同单位时间采出量，大晶只会持续更久。

**与耗尽方案的衔接建议。** 配合此前候选的由可达外缘向内部采集，可以形成“外缘小晶较快采空 → 中层逐渐减少、轮廓收窄 → 中心主晶继续提供较多资源 → 主晶逐步断裂变矮 → 最后耗尽”的过程。初始空间梯度本身不决定采集顺序；用户尚未要求核心必须等外缘清空后才能采，也未要求两侧同步、对称地消失。

后续模型阶段需要与实际扣除的矿量匹配：移除哪组晶体，就对应哪组的矿量消耗；中心主晶储量较大，应为它保留逐步变残的表现，避免长期完整后突然消失。之前按三等份余量举例的阈值仅是旧示意，后续按晶体组的容量预算安排阶段分界。剩余矿量以容量数据计算，不根据可见晶体数量推算。

簇内分组可以仅是数据和美术分组，不要求每块晶体成为独立 Actor；可继续比较预制阶段网格与分组移除的成本。此前交互示意尚未实现本次分层容量映射，不能当作该规则已完成的证据。本轮只同步设计记录，未新增或修改三维资产、UE 代码、蓝图及测试。

### 1. 三种生成方式的区别

| 方式 | 提前保存 | 游戏运行时处理 | 对本项目的判断 |
|---|---|---|---|
| Static | 支持 | 导航不随障碍变化更新 | 不能完整表达矿簇耗尽、建筑新增/摧毁 |
| Dynamic | 支持 | 更新脏瓦片，可重新处理几何并生成新表面 | 兼容现有坡道，适合作为第一阶段基线 |
| Dynamic Modifiers Only | 支持 | 在已烘焙的基础上更新区域、阻挡、代价等修改器；不生成新表面 | 适合固定地形上的动态障碍，但需先解决坡道等表面变化 |

UE 5.7 的 [官方模式说明](https://dev.epicgames.com/documentation/unreal-engine/overview-of-how-to-modify-the-navigation-mesh-in-unreal-engine?application_version=5.7)明确包含上述两种动态方式。当前项目已经使用 Dynamic，因此“提前保存一次”并不自动证明这 122 秒会消失；必须确认数据实际复用，以及开局更新从何处产生。

本机 UE 5.7 源码证据：`NavigationSystem/Private/NavMesh/PImplRecastNavMesh.cpp` 的 `Serialize` 保存有效瓦片，加载时恢复瓦片及压缩缓存层；`RecastNavMeshGenerator.cpp` 的初始化会检查已加载网格与当前瓦片布局是否兼容，`RebuildDirtyAreas` 按脏区决定是否重建几何。模式是 NavData 级别设置，不能把同一套 Recast 的个别瓦片直接配置成另一种 RuntimeGeneration 模式。

### 2. 建议的静态与动态边界

| 内容 | 提前处理 | 运行时处理 |
|---|---|---|
| Landscape、山坡、永久道路、固定不可破坏结构 | 生成两种代理需要的导航底图 | 地图本身未变时复用 |
| 240 个矿簇 | 烘焙时保留矿簇下方可恢复的地面 | 用可撤销 Modifier 表达阻挡；耗尽后更新相交瓦片 |
| 普通建造物、工厂占地、可破坏障碍 | 底图保留建筑移除后需要恢复的通路 | 按真实占地添加/撤销阻挡 |
| 6240 个矿石显示节点 | 沿用已有 24 个 HISM 的显示结构 | 维持显示组件不影响导航的设置 |
| 士兵、采矿车、工程车移动 | 使用适合其尺寸的导航 | 保留现有避障和移动系统；不把每次移动都变成地形烘焙 |
| 会贴地改变形状的坡道、运行时新桥面/平台 | 已知且固定的形状才可预生成 | 新可行走表面需要完整 Dynamic 局部几何更新或另行设计移动连接 |

矿簇耗尽后要恢复通行，烘焙产物必须保留底层地面信息。不能把可移除矿簇作为永久地形实体留下不可恢复的缺口，再指望撤销 Modifier 凭空造出地面。初始矿簇 Modifier 是否随烘焙结果保存，也要确保底层缓存与运行时注册对象能够正确对应。

已知初始资源布局可以进一步预置，但首阶段宜先保存稳定地形底图、批量应用真实初始障碍。避免为了省掉初始注册而引入第二份会与资源 DataAsset 漂移的障碍布局。

### 3. 当前代码中的具体适配点

- [矿簇障碍](../../Source/GuLiStrike/Gameplay/Resources/GuLiResourceActors.cpp)已经带有 NavArea_Null Modifier，并在初始化时调整碰撞球半径与导航边界；矿簇耗尽会关闭碰撞及 Modifier，适合改为基于已烘焙地面的局部阻挡更新。
- [普通建造物](../../Source/GuLiStrike/Gameplay/Building/GuLiPlacedBuilding.cpp)已有 NavModifier。源码同时注明 Modifier 的范围依赖有效的导航碰撞组件，因此不能简单全关 `CanEverAffectNavigation`；需要区分几何导出、物理碰撞、Modifier 占地三者。
- [资源工厂](../../Source/GuLiStrike/Gameplay/Resources/GuLiResourceFactoryActor.cpp)当前依靠碰撞盒影响导航，没有同等显式的工厂占地 NavModifier；其子蓝图几何和门也需按实际导航用途分类。
- [工厂接地坡道](../../Source/GuLiStrike/Gameplay/Building/GuLiGroundAccessRampComponent.cpp)在 BeginPlay 射线检测地面并改变坡道变换，且开启导航影响；[资产构建脚本](../../Scripts/build_resource_processing_factory_blueprints.py)确实把该组件加到了工厂蓝图。它可能引入烘焙时不存在的可行走几何，是不能直接全项目切换 Dynamic Modifiers Only 的具体原因。
- 对固定初始工厂，可将同一套坡道贴地计算前移至编辑器并生成一致的导航代理；对玩家运行时放置的工厂，需保留局部几何更新或明确它的接地移动方式。不能在分析阶段假定可删除现有坡道通行能力。
- 两套 NavMesh 分别服务不同代理。应分别保存并核对配置；不能仅因存在两套就删除其中一套。

### 4. 借鉴空中导航的烘焙流程

[空中导航编辑器代码](../../Plugins/GuLiFlightNavigation/Source/GuLiFlightNavigationEditor/Private/GuLiFlightNavigationEditorLibrary.cpp)生成数据时记录几何签名和设置哈希；[Cook 校验](../../Plugins/GuLiFlightNavigation/Source/GuLiFlightNavigationEditor/Private/GuLiFlightNavigationCookGate.cpp)检查烘焙是否过期；[运行时子系统](../../Plugins/GuLiFlightNavigation/Source/GuLiFlightNavigationRuntime/Private/GuLiFlightNavigationSubsystem.cpp)按校验值和修订复用查询图。这些流程适合地面导航借鉴。

建议职责边界如下：

| 层 | 职责 |
|---|---|
| GuLiStrikeEditor | 统一两套代理的实际参数，构建/保存 Recast 数据，记录地图、几何、布局与烘焙版本，检查过期数据 |
| UE NavigationSystem | 持久化瓦片与缓存、路径查询、执行局部脏区更新 |
| GuLiStrike 资源/建筑运行时 | 注册当前障碍、提交必要局部变化，读取有效性与启动就绪状态 |
| 空中导航插件 | 保持自己的三维图；地面导航借鉴其管理流程，不增加运行时对编辑器模块的依赖 |

“放本地”建议使用随关卡或导航数据包保存并参与 Cook 的正式产物。运行时只读取游戏自带数据；无需另存一套依赖机器绝对路径的文本导航文件，也不依赖 DDC 是否命中。

一致性至少覆盖：地图及几何版本、两种 Agent 参数、`NavMeshResolutionParams`、TileSize 与原点/范围。现有诊断发现旧 CellSize/CellHeight 字段与实际分辨率不同；调整分辨率后应重新烘焙并保存匹配的数据。引擎在加载发现瓦片尺寸不兼容时会丢弃瓦片，因此配置和烘焙产物必须一起更新。

### 5. 开局就绪与实施优先级

目标启动过程：**读入有效的预烘焙底图 → 批量注册本局初始障碍 → 处理必要局部更新 → 生成士兵并开放移动命令。** 后续采矿、建造和摧毁仅提交各自占地区域的变化。

第一阶段保留当前 Ready 的正确性约束，先减少它等待的工作。待证据证明需要后，再将界面/镜头就绪、出生与通行就绪拆开。只判断“没有任务正在构建”不足以证明导航有效，还需检查两套必要数据存在、版本匹配及出生点可用。

如果后续允许非关键区域后台更新，必须定义必要区域、相关路径和初始障碍批次完成条件；不能只把全局判断删掉，让士兵使用尚未更新的阻挡或空导航。客户端沿用服务器权威和资源同步，现有 `bAllowClientSideNavigation=False` 的语义不因预烘焙而改变。

候选顺序：

1. 记录两套 NavMesh 实际读入瓦片/缓存数量、开局脏区来源和面积，判断等待源于缓存缺失、参数不匹配还是有效的运行时几何更新。
2. 统一实际导航精度并保存匹配烘焙，先保留 Dynamic 兼容坡道；将初始障碍注册集中处理，避免相同区域重复更新。
3. 将纯占地障碍改为明确的动态 Modifier；对坡道、工厂门和其他表面变化完成分类后，决定哪些整套 NavData 能采用 Dynamic Modifiers Only。
4. 比较相同地图、双端和 500 士兵场景的开局耗时，重点确认烘焙确实复用、矿簇耗尽通路恢复、建筑阻挡和工厂接地通行保持正确。

预期收益来自省去可复用几何的重复处理，方向可行；仍有地图载入、局部更新、资产初始化和网络同步成本。本轮没有测得优化后的秒数，不能承诺将原来的 122 秒等待全部消除。

### 候选制作原则

- 模型保留舰体、炮塔、舱门、履带等主要轮廓；减少远景不可读的碎小零件，并在实际近景距离保留必要倒角与体积。
- 材质采用少量主色、辅色和功能色，收敛迷彩、污渍、混凝土微纹理及碎高光；阵营、矿物与危险预警通过形状、标记和颜色共同区分。
- 首轮对比简化常规光照与两至三级明暗分层；描边优先服务重要轮廓，线宽随距离控制，避免远景单位聚成黑块。
- 特效侧重可辨识的闪光、冲击环、烟团与弹道，控制持续遮挡；最终标准同时覆盖飞船、地面和指挥官视角。

现有[资源加工厂需求](../RequirementDocument/20260909-资源加工厂正式模型与门动画.md)包含数字迷彩与工业警示元素，[巨型据点需求](../RequirementDocument/20260905-据点混凝土巨构模型.md)包含混凝土细纹理；可先评估保留主体造型、调整材质与细节，逐件判断是否需要重建。以上依据文档，未进行本轮资产视觉审计。

UE 的材质、后处理与 Custom Depth/Stencil 提供实现样板所需的基础能力，参见 [Epic 后处理材质说明](https://dev.epicgames.com/documentation/unreal-engine/post-process-materials-in-unreal-engine)。当前项目配置启用了 Substrate、动态全局光照和 Custom Depth/Stencil；具体分层着色方案需要在现有渲染配置下验证，不把传统后处理配方直接视为已兼容。低模风格本身也不能保证整场性能，仍取决于单位数量、阴影、透明特效与后处理开销。

建议下一步先在独立小场景中制作一艘飞船、一栋工厂、一座炮塔、一组矿物及一次爆炸的风格样板，以三种实际游戏视角评审，再决定正式规范与迁移范围。本轮仅记录讨论，未改模型、材质、关卡、渲染配置或测试。
