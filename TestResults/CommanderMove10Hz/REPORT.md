# 指挥官 10Hz 与移动容量实测

日期：2026-09-15。10Hz实施和本机压测已完成。当前有效证据支持4,000档纯服务端移动，以及先加入再增兵到1,200人的双客户端30FPS场景；这些是本次条件下通过的档位，不是部署级最大人口。

同日补充：[客户端函数耗时、CPU/GPU时间线与相机勘误](client-hotspots.md)。旧部分渲染样本的相机未锁定，不能作为相同视野对照；已锁定相机重采1,200人一客／两客，分别满足60FPS／30FPS判据。原服务端与复制问题证据保留。

## 实现与验证

权威固定步由 30Hz 改为 10Hz，单兵从每三步更新一次改为每步更新一次。实际移动积分仍为 0.1 秒；姿态捕获、Tick 时间换算、0.2 秒索敌周期和 0.5 秒编队扩宽门槛同步调整。网络捕获保持10Hz，同一帧的姿态块按独立世界时间在约0/33/67ms三相发送，避免单帧RPC突发。独立 CPA 避让处理器仍维持原来的 30Hz 三相、每单位 10Hz 调度，不能据此宣称所有服务器开销降低三分之二。没有采集匹配的旧版基线，不报告优化百分比。

源码引擎为 `D:/UnrealEngine-5.7`，Win64 Development Editor 与 Game 目标均成功。最新采样工具构建记录：[Editor](editor-build-client-profile.log)、[Game](game-build-client-profile.log)。[BuildId 核对](editor-build-id-client-profile.json)为 `26d441ba-b96a-4e7b-b104-c2c6cd3e663c`。只更新了用户批准的两项旧测试断言，最终玩法代码的导航、战斗和网络共 [61 项既有用例](AutomationFinal/index.json)全部通过；之后仅修改压测停产隔离、相机锁定及性能采集入口并重建，这次剖析没有重跑61项用例，也没有新增自动化用例。

## 固定条件

- i9-14900KF，24 核 32 线程；RTX 4090；32GB RAM。[机器记录](environment.json)。
- `/Game/Maps/LVL_CommanderMassPrototype` 原地图、原始 Landscape/NavMesh、正式单位生成和移动接口。单位类型 ID=1，基础速度 3600cm/s。
- 计数为双方合计，各占一半。测量进程临时提高人口额度并冻结占领生产，项目默认人口上限不变。
- 最终采样器在等待客户端之前冻结占领进度，并关闭场景原有生产组件的Tick。原地图仍执行占优采样、维护和其他世界逻辑；纯移动场景不验证全军交火或大规模动态出兵的综合成本。
- 每批 100 人，通过真实 `BeginMovePlanning/PollMovePlanning` 规划；命令由服务端合成所有者发出，客户端真实连接并接收名册、姿态与插值表现。这不是一次鼠标点击选中全军的端到端响应测试。
- 默认先创建目标人口再加入，覆盖晚加入。`-JoinBeforePopulation`先加入基线战局，再每0.25秒生成每队50人，覆盖在线逐批增兵；准备和生成人口不计入持续测量时间。两个结果不能混称。
- 最终折返场景：每批初始中心以东 1000 米和以西 500 米为两端；每轮规划完成后 8 秒换向。预热 8 秒，服务器无客户端采样 40 秒；有客户端时服务端 50 秒、客户端 40 秒。重新规划的工作计入测量。
- 服务端50秒窗口包含客户端退出后的尾段，统计未裁剪到完全一致的共同窗口；服务端多客结果不能理解为整整50秒始终维持两客在线。
- 相机目标为 X=-150000、Y=110000，由正式相机解算地形高度，沿用默认镜头参数。早期采样器仍允许相机输入，部分客户端在定期重定位之间发生移屏；只有`locked-profile`采样已通过逐帧位置/速度核验锁定，实际视点X=-195886.1094、Y=110000、Z=59937.2383。1920×1080、Epic、100% 屏幕比例、关闭动态分辨率和 VSync、客户端不限帧、offscreen 完整渲染。保留正常单位剔除，未全选或显示全军路径线，不表示所有单位同时在屏幕内。
- `-HeadlessClients` 使用真实网络客户端和 NullRHI；用于观察复制和客户端 CPU 工作，禁用客户端 FPS 验收。所有场景顺序执行，没有并行编译或并行运行其他 UE 压测场景。
- 使用未 Cook 的源码 Editor 二进制 `-game`，不是打包 Shipping 容量，也不是跨机器实测。普通客户端的渲染帧时间包含同机资源竞争。

## 判据和统计口径

帧 CSV 丢弃首秒。P95 表示 95% 样本不超过该值；人数用 P05，检查低负载尾部。至少 95% 的请求人口确实发生位置变化，才把该档记为有效移动负载。人数每 0.5 秒采样，移动阈值为该间隔内水平位移大于 10cm。

服务端要求：测量窗口无丢步、模拟至少 9.9Hz、固定步 P95≤50ms，世界帧 P95≤100ms。50ms 是给 100ms 周期保留余量的本次工程预算，不是引擎硬极限。固定步计时不包含全部世界帧、规划、Mass 处理器和网络开销，所以同时报告整帧。若一帧出现多步，采样固定步成本为该帧步数的均值，报告中保留 `multi_step_frames`。

客户端分别按帧 P95≤16.67ms / ≤33.33ms 判断 60FPS / 30FPS 目标，不能把平均 FPS 当成稳定帧率。姿态频率计数按收到合法分块的捕获帧统计，不代表所有单位每帧分块齐全；远处单位仍有正式降频规则。没有把本机回环网络当作延迟、丢包或公网带宽验证。

## 发送突发修正的对照

[单相发送的800单位](netonly-n800-c2/analysis.json)在服务端全部移动，但两客呈现人数P05只有456/465。引擎`Engine/Source/Runtime/Engine/Private/NetDriver.cpp:2929`在连接饱和时跳过不可靠客户端RPC。恢复独立三相后，[相同800单位、两台NullRHI客户端](phased-net-n800-c2/analysis.json)三端实际移动P05均为800；服务器约9.999Hz，客户端收到约9.899捕获帧/秒。

本次三相采样记录22482次姿态块发送尝试，其中79次尝试时连接已饱和；这是发送入口观测，不是网络抓包丢包率。数据说明全局姿态帧计数接近10Hz并不能单独证明每个单位都正常更新。分时发送修正已实测改善完整性，但不等于消除了任意高负载下的带宽限制。

[2,000单位先加入再增兵](online-fixed-n2000-c2/analysis.json)能够完成名册同步，但两台无渲染客户端的实际移动P05只有1,401/1,399，服务端为2,000。两客全局捕获帧接收频率仍约10Hz，平均输入233.1/232.9KB/s；配置的每连接额度为250,000字节/秒。52,795次姿态块发送尝试中20,372次（38.6%）遇到饱和。结合引擎不可靠RPC的饱和跳过路径，当前在线负载也受到复制带宽约束；关闭渲染无法解决此限制。客户端探针在基线名册选中的旧单位可能已被清除，本轮不使用单探针距离作结论，使用全体存活单位的真实位移统计。

[补测1,200单位先加入再增兵](online-final-n1200-c2/analysis.json)：服务端和两台无渲染客户端实际移动P05均为1,200。服务器约10Hz、固定步P95=6.879ms、世界帧P95=21.539ms、无丢步；两客捕获帧接收约10Hz。因此在线网络场景已验证到1,200档，2,000档未通过；未将未测的中间档位或这一区间端点称为精确上限。

## 复现和分机方案

从项目根目录运行：

```powershell
# 纯服务端持续移动；Label 必须使用尚未存在的名字。
./Scripts/run_commander_move_stress.ps1 -Population 4000 -Clients 0 -Seconds 40 -Label reproduce
# 已验证能够晚加入的网络对照。
./Scripts/run_commander_move_stress.ps1 -Population 800 -Clients 2 -HeadlessClients -Seconds 40 -Label reproduce-net
# 完整渲染的一客/两客对照。
./Scripts/run_commander_move_stress.ps1 -Population 800 -Clients 1 -Seconds 40 -Label reproduce-one
./Scripts/run_commander_move_stress.ps1 -Population 800 -Clients 2 -Seconds 40 -Label reproduce-two
# 复现在线增兵后的带宽瓶颈；此档不是联机通过结果。
./Scripts/run_commander_move_stress.ps1 -Population 2000 -Clients 2 -HeadlessClients -JoinBeforePopulation -Seconds 40 -Label reproduce-online
python Scripts/analyze_commander_move_stress.py TestResults/CommanderMove10Hz/reproduce-n4000-c0
```

启动器保存完整命令到各运行的 `launch.json`，保存逐进程 CPU、内存、逐帧数据和引擎 CSV；结束时只停止自己启动的进程。`processes.csv` 包含准备/退出阶段，内存峰值不能理解为仅测量窗口的稳态值；CPU 一单位代表一个逻辑处理器的占用量。

[部分运行的逐进程峰值摘要](process-peak-summary.json)保留完整口径：800人双客时，各客WorkingSet峰值约6,096/6,002MiB，服务端约5,496MiB；各客Private提交量约11.6GiB。各进程峰值不一定同时发生，Private提交量也不是实际驻留物理内存。

实际部署验证应将服务端与两个客户端分到独立机器，保持地图、代码、单位类型、视野、画质和移动指令一致。服务端使用无渲染程序；客户端用同一份打包构建。可以复用 `launch.json` 中的分端命令，把客户端地址改为服务端局域网地址，服务端仍等待两个真实客户端就绪；本次启动器默认面向同机执行。临界档复测至少三轮，并延长到数分钟；另测真实网络条件和全选路径线场景。

同机两客共享 GPU/内存，不能将其 FPS 简单乘二来估算单机客户端。CPU 亲和性隔离只分开 CPU 调度，不能隔离 GPU、内存带宽和功耗；脚本提供 `-PartitionCpu`，本次未将其作为正式容量证据。也没有承诺部署级最大人口或擅自提高默认人口上限。

10Hz改动、用户授权的两项旧断言更新、源码Editor/Game构建及61项既有回归均已完成。没有新增自动化测试用例。最终纯服务端4,000档和在线增兵1,200档双客完整渲染取得有效样本；后续锁定相机的1,200档重采中，一客达到60FPS判据，同机两客达到30FPS判据。旧镜头对照缺陷、CSV元数据过滤修正及函数剖析均已留证。

当前优先瓶颈有两个：初始整份名册过大导致高人口晚加入失败；高人口持续姿态流遇到连接带宽配额，2,000在线档尚未通过。后续应处理名册分片及发送预算/公平性，再复测高人口，不以单纯抬高人数或带宽配置代替协议容量验证。
