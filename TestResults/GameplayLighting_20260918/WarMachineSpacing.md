# 战争机器挤在一起：诊断与修复建议

2026-09-18。状态：原因已确认，尚未实施间距/导航代码修改。

## 结论与复现

打开 `/Game/Maps/LVL_CommanderMassPrototype`，进入 PIE，不下达移动指令，观察初始战争机器方阵。预期独立车体不互相穿插；实际每排车体重叠。

这是兵种占地与生成/编队/避让参数不匹配，不是曝光导致的视觉错觉，也不是再次应用 0.2 缩放。当前地图没有 `GuLiCommanderDeploymentPoint`，走的是权威子系统的默认出生方阵。

| 读回项 | 扫荡者 | 战争机器 |
|---|---:|---:|
| ISM 组件缩放 | 1 | 1 |
| 实例缩放 | 0.2 | 0.2 |
| 有效包围盒长×宽×高 | 3.02×2.61×2.28 米 | 12.41×12.50×7.48 米 |
| 最近中心间距中位数 | 3.60 米 | 3.60 米 |
| 统一导航/避让半径 | 1.50 米 | 1.50 米 |

战争机器宽约12.5米，却按3.6米中心间距排列；两台模拟圆的半径之和仅3米，避让系统不认为3.6米中心距存在重叠。战争机器250个实例的最近中心距为3.60–3.606米。完整几何外包围盒包括武器与轮廓，不等同最终选定的底盘碰撞形状。

证据：[运行时读回](unit-spacing-diagnosis.json)、[实际俯视截图](commander-top.png)。快照中扫荡者还存在最近距离为0的样本，但本次未定位该样本的生命周期/实例身份；不把它自动归入本次战争机器结论。

## 最早发生错误的位置

1. `GuLiBattleAuthoritySubsystem.h` 的统一默认值为 `MemberSpacingCentimeters=360`、`MemberAgentRadiusCentimeters=150`；运行中 CDO 读回一致，组中心距为3000厘米。
2. `TrySpawnAuthorityPopulation()` 在 `GuLiBattleAuthoritySubsystem.cpp:1703` 用统一间距计算槽位，之后才按方阵索引选择兵种。此时大的战争机器已经被放进小兵的格子；导航投影通过不代表车体互不重叠。
3. 实体创建在同文件 `1885` 为全部兵种填入同一 `FAgentRadiusFragment`。目标槽位请求在 `2106/2217` 仍使用360厘米，局部避让代理在 `4817` 仍使用150厘米。
4. 因此只改初始摆位会在移动/重新集结时复发。单纯把全局间距放大，也会让小型扫荡者过度松散。

已有 `FGuLiSoldierDefinition::GetModelBoundsCentimeters()` 能返回含 `PresentationScale` 的有效模型尺寸，可复用其坐标约定。调用者不能再乘0.2。

## 建议的最小一致性修复

保留模型、已确认的0.2倍率、速度与地图出生锚点。让每个兵种有自己的占地定义，以下入口统一消费它：

| 入口 | 需要修改的行为 |
|---|---|
| 兵种定义/有效几何 | 从缩放后几何获取占地；明确底盘轮廓、武器外伸和绕原点转向的安全余量，必要时允许每兵种配置覆盖 |
| 默认出生/部署 | 先解析兵种，再计算槽位和方阵整体包围范围；大兵种方阵之间也要留空，不改红蓝绝对出生中心 |
| 移动/集结规划 | 槽位按参与兵种占地分配，混编也必须校验两者占地；不能只改出生布局 |
| 避让与通行 | Mass半径、邻居半径、障碍查询与通行净空一致；混合兵种用双方半径/形状而不是统一150厘米 |
| 生产/传送等复用入口 | 清查 `GetExternalUnitRadius()` 及生产生成、落点净空查询，避免新单位再次按小兵尺寸挤入 |

不建议直接把战争机器再缩小。即使采用同朝向矩形，中心距也至少应超过约12.5米并留余量；允许任意转向时还需要旋转后的占地保护，不能把“宽度÷2”直接当成所有方向都安全的圆半径。

- 已排除主要解释：实例重复缩放、光照错觉、仅由客户端移动插值造成。静止初始方阵本身就复现。
