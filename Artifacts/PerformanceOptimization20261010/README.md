## 已采用旧项与本轮候选的区别

## 固定方法

源码 UE 5.7，`GuLiStrikeEditor Win64 Development`；原地图 `/Game/Maps/LVL_CommanderMassPrototype`。同进程专服与双客户端，共享 CPU/线程池，两个客户端均为 1280×720。每轮新建 PIE，热身 10 秒、正式窗口 30 秒，三轮按 A/B、B/A、A/B 交替。常规为 200 单位，压力为 600 单位加四个来源各 125 个附加飞行物。生产建筑的自动增员在临时 World 停止，以保持人口；单位移动、避障、自然交火保留。压力额外飞行物通过真实服务器四类来源生成，不使用枪口预览代替真实反馈。

正式连接预算保持 250000 B/s；每个原生样本都核对实际预算。`1 KB = 1000 B`。生产配置、事件协议、可靠性、StateTree 原 0.1 秒调度门槛、即时转换与请求提交顺序均保持。压力下实际调度约 6.5 次/秒，标称 10 Hz 不代表低帧率时一定实现 10 次/秒；不在本轮修改追赶/错峰逻辑。临时 CVar 在每阶段 `finally` 恢复，并保存前后值。

使用引擎版本 `5.7.4-0+UE5`；十项 Scalability 均为 3，100% ScreenPercentage，动态分辨率关闭，Lumen 硬件光追和虚拟阴影保持开启。每次 `context-before/after.json` 记录实际值。

原生性能子系统按 World 与连接约每秒采集一次，首尾补样，内存保存后导出。30 秒窗口内只运行游戏和原生采集；Python 不枚举对象、截图或写资产。统计桥接的首尾帧与 Trace/CSV 窗口不完全一致：每种计时使用各自明确的帧数/实际时长，不把毫秒或事件年龄当作 RTT。

## 数据目录与口径

- `Paired/*/result.json`：场景、开关、相机、分辨率、真实移动量、反馈、可见比例、CSV 摘要、错误与构建标识。
- `native-capture.json`：旧性能字段和新增的 `network_samples`，按 World 区分；`net_mode=1` 是专服、`3` 是客户端，数组位置不代表角色。
- `frames.csv`、`session.utrace`、`clock.json`：原始帧表、Trace、公共 QPC 时间窗口。Windows 原生 `FPlatformTime::Seconds` 比 Python 原始 QPC 秒多 `2^24`；这不是网络时钟偏差。
- `counters-before/after.json`、`context-before/after.json`：窗口外采集的实体/相机/负载证据。
- `Sessions/*`：临时设置原值与恢复读回；`Build/*`：构建、哈希、模块 BuildId、静态审查与中断证据。
- `analysis.json`、`paired-summary.csv`、`cpu-frame-statistics.json`：最终统一汇总。`insights-windowed` 为采样结束后离线导出的 CPU 证据。

UE 连接吞吐包含所有流与传输开销；飞行/State/Pose 字节是其中的应用载荷，不能相加后再加连接吞吐，也不能把同一连接的发送端和接收端相加。两个不同客户端连接可计算服务器双连接总发送，但不等于操作系统网卡总出口。

飞行 `sent_*` 表示提交到可靠 RPC，不是已经到达客户端。`produced_record_bytes`/`enqueued_record_bytes` 在捕获开启后，对已附加枪口信息的最终事件编码计量：含记录体及 2 字节长度，排除每批 1 字节头；计量本身有独立耗时。初始化重建单独记 `bootstrap_*`，捕获前的初始化字节不回算。

`queued_bits_raw` 是 UE 的带宽信用/债务记账，可为负；`bandwidth_debt_bits` 仅保留正债务，`send_buffer_bits` 才是当前发送缓冲位数。可靠未确认 bunch 与应用可靠事件队列是两层队列。队首年龄基于事件时间，可能包括入队前等待，不冒充精确的队内停留时间。

工作线程的 `ComputeCpuMs` 是各批计时区间之和；`DispatchJoinMs` 是调用方墙钟时间；`DispatchWaitMs` 是墙钟减调用方执行本批计算的时间，含调度/帮助执行/等待开销，不等于纯阻塞等待。三者不能重复加总。最终全线程 CPU 与 GT Trace 分开报告。

采样发生在同进程本机 PIE，没有进行公网往返、丢包或乱序注入；本轮的零丢包与 RTT 记录仅代表该环境。回退前正式对照中，`GroupIndex=0` 为线性查询，但集中成员维护、稳定 ID 和重复成员保护属于两臂共用改动；它是查询策略的 A/B，不是整个文件回退到实施前版本。所有候选的拆分计时与捕获基础设施也同时存在于两臂，不能据此计算相对实施前整个项目的累计收益。

## 已确认的限制与中断

压力样本中真实枪口出生为零的记录用于 CPU/网络诊断，不能证明枪口承载优化收益。常规场景偶发的及时接收、枪口姿态解析失败，已新增独立原因计数；不混入网络排队过期。

视角先按实际可见比例校验。FOV 120/160 的“full”试采分别只覆盖约 78%/87% 移动单位，四个完整结果已标记 `view_eligible=false`，保留作诊断，不用于全屏内配对。最终全屏内相机高于目标 70000 cm、FOV 90，覆盖移动扩散的约 80000 cm 区域；它超出了普通 CameraActor 的既有枪口距离范围，因此该视角只核对单位/UI CPU 与全屏内几何，不证明真实枪口表现收益。相机设置完成后再预热 10 秒。屏外相机向上看，避免只绕竖轴旋转、仍看见俯视范围内单位。所有相机改变仅在临时 PIE World。

旧版 UI 按命令数均分批次会把昂贵的圆环集中在一个线程，常规三对 Paint 中位数反而增加约 0.288 ms；已拒绝该实现。当前 build4 按预计三角形计算量划分连续区间，保持图元顺序；旧 `ui` 与新 `ui_balanced` 数据分别保留。

追加屏外样本揭示另一个尚未调整的策略问题：`views-dense200-offscreen-ui_balanced-r2-*` 两客户端单位可见比例都为 0，但合计仍约 5200 条 UI 数值命令/引擎帧，多数在几何阶段快速裁掉。串行几何约 0.034 ms；当前候选仍为每客户端分 8 批，合计调度/等待约 0.051 ms，Paint 从约 0.290 增至 0.382 ms。命令条数无法区分昂贵可见几何与廉价拒绝，后续应评估基于裁剪后工作量或已有计算成本的分批门槛；本轮保留候选关闭，不将该策略问题混入“条件缓存＋避障”的归因。该对整帧 P95 增加 2.164 ms，远大于 UI 自身约 0.092 ms 增量，不能把整帧增量全部归因于这里。

2026-10-10 18:50 左右，在四项优化全部关闭的基线中，D3D12 报 `DXGI_ERROR_DEVICE_REMOVED / DEVICE_RESET`，活动面包屑为 `GPUScene.Update`。该未完成样本没有 `result.json`，不参与配对；日志与恢复记录保留在 `Build`。仅关闭本次启动的崩溃编辑器并重启，未更改画质、驱动、网络预算或协议，也不据此认定是哪项优化导致。

`selected-stress-onscreen-selected-r2-selected` 有完整 CSV，但包含 1.050743 s 的引擎帧；既有 Trace 导出器的“最长引擎帧不得超过 1 s”启发式将它排除出归一化 CPU 表。它的整帧/P95 失败结果仍参与采用判断，原始 Trace/CSV/网络数据均保留，不因为 CPU 导出器标记而删除该失败样本。独立逐事件导出显示，其中约 0.939427 s 在 `WinPumpMessages`；触发原因尚未确定，不能猜测为玩家操作、某个后台程序或缓存算法。详见 P95 调查和 `tail-diagnostics.json`。

正式游戏始终由源码引擎运行。该源码安装未提供 `UnrealInsights.exe`，离线解析使用同机 UE 5.7 的 Insights 工具，绝不作为 Launcher 引擎运行或构建证据。导出器核对公共 QPC 窗口、完整 EngineTick 数和 CSV 帧数；GUI/Slate、World Tick 等包含子 Scope 的计时不可直接累计。

各窗口重建 PIE，编辑器进程按阶段复用，没有每窗重启整个编辑器。内存和引擎消息处理会随长序列变化；CSV 保留 Physical/Virtual 内存及最大帧，不把相关变化直接归因于某个开关。A/A 的三对范围用于本轮保守采用门槛，不是每种视角、每个时刻的统计置信区间；若要进一步证明微小 P95 差异的因果，需要另行设计固定工作量与进程隔离的对照。

## 本轮不继续并行的纯姿态部分

在 build4 两个负载 `single-*-onscreen-ui_balanced-r1-baseline` 的离线 Trace 中，单位纯姿态采样每引擎帧分别约 0.049/0.157 ms；客户端飞行预测总 Scope 约 0.100/0.358 ms。压力预测中纯追踪计算约 0.311 ms，纯显示位置约 0.003 ms。预测父 Scope 包含子 Scope，不能相加；这些数字也不包含服务器物理移动、碰撞和整个客户端特效生命周期。

## 当前网络结构与发送逻辑

飞行物已经取消逐帧位置复制，但仍同步“出生配方＋权威结束事件”。客户端根据配方计算轨迹；枪口信息附在出生事件上，因此出生事件排队会同时拖延枪口反馈。

| 层级 | 当前结构/行为 | 本轮判断 |
|---|---|---|
| 服务器活跃飞行物 | `ActiveFlights: TMap<FGuid,FGuLiFlightEvent>`；`UpdateFlight` 仅更新服务器的重建状态 | 用于新连接初始化，不是每次更新都发网络 |
| 待广播事件 | `PendingFlights: TArray<FGuLiFlightEvent>`；每次接受出生/结束追加一次，重复出生/结束被过滤 | 客户端预测与权威生命周期分离合理，但事件产量仍与开火及结束频率相关 |
| 每连接可靠队列 | `FlightPeers` 中各有 `Queue + Cursor + ActorChannel`，同一批事件复制到每个客户端 | 当前没有按视角兴趣过滤、过期视觉事件合并或应用队列上限；“可靠”会保留已没有即时表现价值的历史 |
| 批编码 | 1 字节记录数，逐条 2 字节位长和记录体；最多 16 条、1000 字节 | 可变长度编码与明确边界合理；实际平均每批约 11 条，不能按恒定 16 条估算容量 |
| 发送节奏 | 组件间隔 0.05 秒；每连接每次最多 8 批，逐批检查 `IsNetReady` 后提交可靠 RPC | 受服务器实际帧率限制，压力时约 13 次/秒；预算和批数上限均会阻挡发送 |
| 客户端接纳 | 校验批边界/匹配 Epoch，重建飞行/结束；枪口另有事件年龄、姿态解析、接纳年龄检查 | 传输可靠不等于及时呈现；过期和无法解析姿态必须分别诊断 |
| 单位流 | State/Pose 载荷、状态发送窗口、姿态待发合并及连接预算 | 与飞行事件共享 UE 连接预算；不能只看飞行字节判断整条连接是否饱和 |

记录含 Epoch、EffectId/Sequence、类型/阶段/结束原因；出生按类型携带来源/目标、量化位置方向、时间与运动参数。枪口复用已有身份与出生信息，只附加槽位、型号、枪口编号与机械姿态等元数据；结束记录已精简为身份、终点/时间及命中特效信息。本轮没有把完整 C++ 结构体尺寸当作网络包尺寸。

另一个已确认的压缩机会：`GuLiFlightWire::EncodeRecord` 经 `FGuLiFlightEvent::Serialize` 调用 `State.NetSerialize(..., nullptr, ...)`，飞行配方中的资源引用因此走无 PackageMap 的字符串路径分支；船弹视觉类路径也逐条写字符串。长路径是否占主导需进一步按类型拆分字节，但代码路径本身已确认，可在后续协议设计中评估稳定资源 ID/字典。

队列消费到 256 条后使用 `TArray::RemoveAt` 压缩已消费前缀。积压变大时，这种移动剩余事件的成本可能反过来占用服务器帧时间；需要以 Trace 自身耗时进一步核对，当前只列为源码支持的风险，不冒充已测主因。

## 后续网络整改（本轮不实施）

1. 根据事件产量、有效期限和客户端重建需要，分开设计必须可靠的生命周期/校正与短时枪口等视觉反馈；评估合并、兴趣范围、过期处理及有界队列。不能直接删掉可靠结束或丢出生后仍假设客户端完整。
2. 发送预算应同时考虑每秒字节、事件/批次上限和实际调用频率；服务器低帧率时不能仅依赖“每次 8 批”获得稳定吞吐。提高预算必须和包数、CPU及其它状态流一起测。
3. 按飞行类型记录编码字节，评估资源字典、共享配方、批内公共身份/时间压缩；单独验证兼容、初始化与重连。
4. 将枪口姿态解析失败按来源/身份/时间区间定位。及时收到但解析失败的样本属于客户端接纳路径，不能用扩大带宽来证明解决。

### 单位 State / Pose 的边界

State 使用每连接 `FSender`，按 SoldierId 保存已发布值、待发最新值和队列 ticket，带 ConnectionGeneration、Generation、Epoch、Sequence。状态批有 1000 字节边界与最多 4 批应用确认窗口，客户整批校验后提交，累计 ACK；出生、命令变化、瞬移基线先应用，Pose 才能通过对应发布序号/命令 ID/位移帧下界的屏障。

Pose 按 SoldierId 在 `QueuedPoses` 保留最新样本，同时保留首次等待时间；按等待时间与稳定 ID 排序，匹配帧/仿真 tick/采样时间后成批编码。紧急 State、Pose、普通 State 顺序共用本连接的信用，按 UE 已观察支出与本地估算调和，避免同一支出重复记账。这种“可合并姿态＋必要状态屏障”比把每帧姿态无限排可靠历史队列更适合高单位数。

本轮记录窗口阻塞与预算阻塞、首等待时间、Pose 合并次数和采样间隔；压力代表样本 State 应用窗口没有持续阻塞，Pose 应用载荷约每连接 96 KB/s，因此仍是飞行事件争用预算时不可忽略的主要流。其它 Actor 复制、RPC 与传输开销尚未按类别拆分，不能把“连接字节减三条应用流”全部当成协议头。
